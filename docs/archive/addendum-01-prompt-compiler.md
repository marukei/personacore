# 追補1: プロンプトコンパイラ設計

> 引き渡しブリーフ（handoff-brief.md）の補足 / 2026-08-13 作成
> **本追補は主にフェーズ3（ComfyUI連携）の設計だが、型定義とデータモデルは早期に入れておくこと。**

---

## 1. 何を解決するコンポーネントか

会話文脈（日本語）から、画像生成用のプロンプト（Danbooruタグ列）を生成する。

**タグを人間が書かなくて済むようにすることが目的。** 日本語話者にとって適切な英語タグを選ぶのは負荷が高く、
かつ使用するチェックポイントごとにタグ規約が異なるため、人力での維持が現実的でない。

```
会話文脈（日本語）
    ↓ LLM（構造化出力）
中間表現（スロット）
    ↓ タグ辞書で検証・正規化
検証済みタグ
    ↓ テンプレート合成
最終プロンプト（positive / negative）
    ↓
ComfyUI
```

## 2. 最重要の設計判断：LLMに自由にタグを吐かせない

### 問題

LLMに「この会話をDanbooruタグにして」と投げると、それらしいタグ列が返る。
**そして高い確率で存在しないタグが混ざる。**

致命的なのは、**存在しないタグがエラーにならない**こと。
CLIPは未知の文字列も何らかのベクトルに変換するため、架空のタグは
「静かに無視される」か「ノイズとして混入する」。
生成結果が微妙になっても原因が特定できないという、最悪の壊れ方をする。

### 解決策：スロット方式

LLMには**構造化された中間表現を埋めさせるだけ**にし、
実際のタグへの変換とその妥当性検証はプログラム側で行う。

```rust
/// LLMが返す中間表現（この時点では未検証）
#[derive(Deserialize)]
struct RawSceneSpec {
    expression: Option<String>,
    pose: Option<String>,
    clothing_state: Option<String>,
    background: Option<String>,
    camera: Option<String>,
    lighting: Option<String>,
}

/// 検証済み。辞書経由でしか構築できない
struct ValidTag(String);

impl ValidTag {
    /// 唯一のコンストラクタ。辞書に存在しない場合は None
    fn lookup(dict: &TagDictionary, candidate: &str) -> Option<Self> { ... }
}

/// 最終的なシーン仕様
struct SceneSpec {
    expression: Option<ValidTag>,
    pose: Option<ValidTag>,
    // ...
}
```

**`ValidTag` のフィールドを private にし、`lookup` 以外の構築手段を提供しないこと。**
これにより「架空タグがプロンプトに混入する」ことが型レベルで不可能になる。

### 検証失敗時の挙動

- 未知の値は**破棄する**（そのスロットを空にする）
- 例外的に、部分一致やエイリアスで救済できる場合は救済する
- **破棄したことを必ずログに残す**（辞書の不足を検出するため）
- 破棄率が高い場合はプロンプト設計かLLM選定の見直しが必要なので、メトリクスとして集計できるようにする

## 3. タグ辞書

### 方針

- Danbooruタグ語彙がベース（Illustrious / NoobAI 系チェックポイントはこれで学習されている）
- 全体は数十万タグあるが、**実用上は数百〜千程度で足りる**
- 表情・ポーズ・服装・構図・背景・照明のカテゴリに分類して保持

### 検索方式

**ベクトル検索を使わないこと。完全一致・部分一致・エイリアス表で足りる。**

理由は記憶の想起と同じで、対象が数百〜千件の閉じた語彙であり、
かつLLMが返す値が概ねタグに近い形（英語の短い語句）であるため。
ベクトル検索を挟むと誤マッチのリスクの方が大きい。

日本語→タグの対応も、エイリアス表で持つのが確実：

```
「照れる」「赤面」  → blush
「顔を伏せる」      → looking_down
「微笑む」          → smile
```

### データ形式

TOML または JSON でリポジトリ内に持ち、コンパイル時または起動時に読み込む。
DBに入れる必要はない（更新頻度が低く、バージョン管理したいため）。

## 4. ネガティブプロンプトの扱い

### 認識の修正

**ネガティブプロンプトは静的である。シーンごとにLLMで生成しない。**

固定のベースラインを持ち、必要な場合のみ数語を追加する設計にする。

```rust
const NEGATIVE_BASE: &str =
    "worst quality, low quality, blurry, bad anatomy, bad hands, \
     extra digits, missing fingers, watermark, signature, text";
```

LLMに毎回生成させると、コストが増える上に品質が安定しない。

### 破綻（腕が増える・関節がおかしい）への対策の優先順位

**ネガティブプロンプトへの期待値を下げること。効果は限定的である。**

効果の大きい順：

| 順位 | 対策 | 実装フェーズ |
|---|---|---|
| 1 | **チェックポイント推奨の品質タグを使う** | 即時 |
| 2 | **複雑なポーズ・複数人の指示を避ける** | プロンプト設計 |
| 3 | ControlNet (OpenPose) で骨格を与える | 将来 |
| 4 | 手・顔の部分再生成（ディテーラー） | 将来 |
| 5 | ネガティブプロンプト・ネガティブ埋め込み | 即時 |

**1番目が最も費用対効果が高い。**
チェックポイントごとに固有の品質タグ規約があるため（`masterpiece, best quality` 系の書き方、
スコアタグの有無など）、モデル配布元の推奨プロンプトを流用すること。
**これは設定ファイルで差し替え可能にする**（チェックポイントを変更する可能性があるため）。

**2番目も重要。** SDXLは属性の帰属先を取り違えるため、
「複数人が相互作用している」「複雑な体勢」を指示するほど破綻率が上がる。
これはネガティブプロンプトでは治らない。
LLMへの指示側で、**シーン記述を単純化するよう誘導する**こと。

## 5. 固定部と可変部の分離

キャラクター一貫性の第一歩は、**外見に関わるタグを固定部に置く**こと。

| 区分 | 内容 | 供給元 |
|---|---|---|
| **固定部** | 髪色・髪型・目の色・基本の服装 | キャラ定義（DB） |
| **固定部** | 品質タグ | チェックポイント設定 |
| **固定部** | ネガティブベース | 設定ファイル |
| **可変部** | 表情・ポーズ・背景・照明・カメラ | 会話文脈からLLMが生成 |

**LoRAを導入する前でも、固定部をハードコードするだけで一貫性は相当改善する。**
LoRAは固定部をさらに強化する手段であり、この構造自体は変わらない。

### データモデルへの追加

```sql
-- キャラクターの外見定義（画像生成用）
character_appearance(
  character_id,
  fixed_tags,        -- 固定部のタグ列
  lora_name,         -- 将来のLoRA指定（現時点ではNULL）
  lora_strength
)

-- 生成した画像の記録
generated_image(
  id, session_id, message_id,
  positive_prompt, negative_prompt,   -- 再現性のため生のプロンプトを保持
  seed, checkpoint, file_path,
  created_at
)
```

**`positive_prompt` / `negative_prompt` / `seed` は必ず保持すること。**
良い結果が出たときに再現・微修正できることが、実験の効率を大きく左右する。

なお ComfyUI が出力するPNGにはワークフロー全体がメタデータとして埋め込まれるが、
それとは別にDB側でも持っておく（検索・集計のため）。

## 6. LLM呼び出しの設計

### 使用モデル

**サブLLM（`ministral-3-3b`）で十分。** メインモデルを使う必要はない。
スロット埋めは抽出タスクであり、小型モデルの得意領域。

### 構造化出力

LM Studio は Structured Output（JSON Schema指定）に対応している。
**自由記述させてパースするのではなく、スキーマを与えて構造を強制すること。**

### 呼び出しタイミング

**同期的に呼ばない。** 画像生成はユーザーが明示的にボタンを押したときのみ実行する。
会話のたびに毎回生成すると、レイテンシとGPU競合の両方で問題が出る。

### GPU競合への注意

**ComfyUI と LM Studio は同じGPU（RTX 4070 / 12GB）を奪い合う。**

- SDXL チェックポイントは約6.5GB、メインLLMは8.24GB → **同時常駐できない**
- 画像生成時はLLMをアンロードするか、生成をキューイングして順次実行する
- LM Studio の Idle TTL / Auto-Evict 機能で自動アンロードできるはずなので、これを利用する
- **どちらの戦略が体感として良いかは実測して決めること**

これは実装上の重要な制約なので、フェーズ3の着手時に最初に検証すること。

## 7. テスト方針

以下は純粋関数として切り出し、単体テストを厚くすること。

- **タグ辞書の検索**（完全一致・部分一致・エイリアス・未知値の破棄）
- **`ValidTag` の構築**（辞書外の値で構築できないことをテストで保証）
- **テンプレート合成**（固定部＋可変部の連結、重複タグの除去、順序）
- **LLM応答のパース**（不正JSON、スキーマ違反、欠損フィールドへの耐性）

LLM呼び出しはトレイトで抽象化し、テストでは固定の応答を返すモックを注入する。
**「LLMが架空タグを返してきた場合に、それが最終プロンプトに現れないこと」を明示的にテストすること。**

---

## 8. 実装順序の提案

1. タグ辞書のデータ構造と検索（LLM不要・単体でテスト可能）
2. `ValidTag` / `SceneSpec` の型定義
3. テンプレート合成（固定部＋可変部）
4. LLMによるスロット埋め（構造化出力）
5. ComfyUI へのワークフロー送信（`POST /prompt`）
6. GPU競合の解決（アンロード戦略の実測）

**1〜3はLLMもComfyUIも不要で完結する。** ここから着手するのが安全。

## 9. 補足：この設計が業務RAGに転用できる点

本コンポーネントは、実質的に**「自然言語 → 制約された語彙への正規化」**であり、
以下と同型の問題である。

- 自由記述の問い合わせを、社内システムの正規のカテゴリ・製品名にマッピングする
- LLMの出力を、後段システムが受け付ける形式に強制する
- **LLMの出力を無検証で下流に流さない**という原則の実装例

特に最後の点は、間接プロンプトインジェクション対策の基本形でもある。
「LLMの出力は信頼できない入力として扱い、許可リストで検証してから使う」という構造を、
ここで実装しておく価値は大きい。
