# ADR-0019: 中継中の停止は `server` が見張る。途中までは保存しない

- 状態: **採用**（**§3 は [ADR-0035](0035-the-watchdog-reports-the-human-decides.md) が置換**）
- 日付: 2026-08-20
- 関連: [ADR-0013](0013-context-budget-layers.md)（層で分ける考え方）/ 作業単位 11c-3 /
  **[ADR-0035](0035-the-watchdog-reports-the-human-decides.md)（§3 の撤回）**

## 背景

**生成が途中で止まったことを、いま検出できない。**

`llm` の読み取り予算は **180 秒**で、これは **JIT ロードを飲むための値**である
（LM Studio はモデルが載っていなければ最初のトークンまで数十秒かかる）。
**生成中の停止検出としては緩すぎる。**

`reqwest` の `read_timeout` は**クライアント単位でしか設定できない**ので、
`llm` の中では「最初のトークンを待つ予算」と「トークン間の予算」を分けられない。
その帰結として `LlmError::Timeout` は**2つの原因を兼ねている**
（[06-roadmap.md](../06-roadmap.md) の `llm` からの持ち越し）。

## 決定

### 1. 見張りは `server` の中継ループに置く。`llm` を厚くしない

`server::relay` の `unfold` は `events.next().await` を1件ずつ待っている。
ここを `tokio::time::timeout` で巻けば **per-item の予算**が得られる。

- **`LlmError` に新しいバリアントを足さない。** `server` は自分の SSE エラーを出せる。
- **「途中まで保存するか」は既に `server` の責務**（`relay` のモジュール doc）。
- `llm` は「1回の HTTP のための予算」だけを持ち、**中継の意味論を知らないまま**でいられる。

### 2. **最初の1件は見張らない**

**JIT ロードを打ち切ってしまう。** 最初のトークンまでの待ちは `llm` の 180 秒が担当する。
`server` の予算は **2件目以降の間隔**にだけ掛ける。

> **これは「最初のトークンが来ない」を検出しないという意味ではない。**
> `llm` の 180 秒がその役目を持ち続ける。**分担であって、穴ではない。**
> ただし**案内は出し分けられない**（`LlmError::Timeout` が2つの原因を兼ねているため。上記）。

### ~~3. しきい値は **30 秒**の定数。設定にはしない~~ → **撤回**（2026-08-26 / [ADR-0035](0035-the-watchdog-reports-the-human-decides.md)）

> **⚠ この節は撤回された。中継は 30 秒で打ち切らない。見張りは `warn` を出すだけになった。**
>
> **根拠だった「3桁の余裕」は、この機のトークン間隔（数十ミリ秒）から出た数**で、
> **CPU オフロード・上流の混雑・スリープ・画像生成との取り合いでは成り立たない。**
>
> **⚠ その反例は、この節自身が下の引用で書いていた**（「フェーズ3で見直す」）。
> **「超えうる」と書いた値を、打ち切りの権威として使っていた。**
>
> **設定可能にしない理由（つまみ1つに見張り番1本）だけは
> [ADR-0035](0035-the-watchdog-reports-the-human-decides.md) §5 に引き継がれている。**
> **以下は撤回前の記述。**

- 通常のトークン間隔はローカルで数十ミリ秒。**3桁の余裕がある。**
- **`[DONE]` の直前に入りうる最大5秒の空白**（保存の `await`）より十分に大きい。
  ただし**その空白は `next()` の外**にあるので、そもそも予算に掛からないはずである
  —— **実装時に測って確かめること。** 「掛からないはず」で通さない。
- **設定可能にしない。** 起動時に決めるものを増やすと、
  **本番の入口を通るテストを足さない限り配線が観測対象から外れる**（CLAUDE.md の実例）。
  調整が必要になってからにする。

> **フェーズ3で見直す。** GPU を画像生成と取り合うと、
> **トークン間が 30 秒を超える**ことがありうる（未実測）。
> 「アンロード vs キューイング」を決めるとき（[06-roadmap.md](../06-roadmap.md) の未決）に
> **この値も一緒に測り直すこと。**

### 4. 打ち切った回は**保存しない**

**途中で失敗した枝と同じ扱い**にする（`server::relay` の既存の規約）。

- 途中までの応答を履歴に混ぜると、**次のターンでモデルが「言いかけの文」を
  自分の発言として読む。**
- **クライアントは `[DONE]` を受けていない**ので、その回を失敗として扱っている。

> **⚠ ここには未解決の緊張がある。**
> **利用者の画面には途中までのテキストが出ている**のに、履歴には残らない。
> 次のターンで**画面と履歴が食い違う。**
> **これは切断時（FE が中継の途中で切る）と同じ性質**で、そちらは既にそうなっている
> （[06-roadmap.md](../06-roadmap.md) の「11c-3 へ渡す前提」）。
> **今回は既存の振る舞いに揃えるだけで、緊張そのものは解いていない。**
> 解くなら「途中までを打ち切りと分かる形で保存する」設計が要るが、
> **`message` に打ち切りを表す列が無い**ので、スキーマの変更を伴う別の判断になる。

### 5. 下流には既存のエラー形で伝える

**新しいエラー形を作らない。** 途中で壊れた枝と同じく、
error オブジェクトを1件流して終端し、**`[DONE]` は送らない**。
**内部の事情（何秒で切ったか・上流のどこで止まったか）を応答に載せない**（CLAUDE.md 絶対制約）。
**ログには残す。**

## 却下した選択肢

- **`llm` 側で per-item の予算を持つ** — `reqwest` の `read_timeout` はクライアント単位なので、
  ストリームを自前で巻き直すことになる。**`llm` が中継の意味論を持ち始める。**
- **`llm` のクライアントを2つ持つ**（初回用 180 秒 / 生成用 30 秒）— 1回のリクエストの途中で
  切り替えられないので、そもそも解にならない。
- **途中までを保存する** — 上記の緊張のとおり、**打ち切りと分かる形にできない**まま保存すると
  「言いかけの文が正規の発言になる」。**スキーマを伴う判断を、この作業単位に混ぜない。**
- **しきい値を設定可能にする** — 上記 3。

## 結果

- ~~**生成中の停止が 30 秒で検出でき、上流の接続も落ちる**~~ → **30 秒は `warn` に変わった**
  （[ADR-0035](0035-the-watchdog-reports-the-human-decides.md)）。**上流の接続が落ちるのは変わらない**
  （`ChatStream` を drop するため）が、**落ちるのは天井に当たった回と、人が止めた回。**
  ~~**ただし drop が実際に上流をキャンセルするかは別の作業単位で確かめる**（11c-3b）。~~
  → **11c-3b で測って決着。効いている。** 数字と対照は
  `tests/llm_lmstudio.rs` / `tests/server_chat_cancel.rs` の見張り番が正。**ここに写さない。**
- **`llm` は薄いまま。** 新しいエラーバリアントも設定も増えない。
- **打ち切りの回は履歴に残らない。** 画面と履歴の食い違いは残る（上記 ⚠）。
