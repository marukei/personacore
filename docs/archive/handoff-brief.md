## 1. このプロジェクトは何か

ローカルLLMを使ったキャラクター会話システムの**オーケストレーション層**を Rust で実装する。

推論そのものは LM Studio（llama.cpp）に委譲し、本プロジェクトが担うのは以下：

- キャラクター定義（ペルソナ）と性格ステータスのプロンプト組立
- 会話記憶の抽出・保持・矛盾解消・想起
- 直近会話のコンテキスト管理と要約
- 台詞と地の文の構造化出力パース
- （将来）ComfyUI 連携による挿絵生成

### 設計上の中核判断

**本サービス自体を OpenAI 互換 API サーバとして実装する。**

```
FE層（既存クライアント可）
    ↓ POST /v1/chat/completions（OpenAI互換）
本サービス（Rust）  ←→ SQLite
    ↓ POST /v1/chat/completions（OpenAI互換）
LM Studio（推論エンジン）
```

両側で同じ規格を話すことで：

- **フェーズ1ではフロントエンドを一切書かずにコア機能を検証できる**（既存の OpenAI 互換チャットクライアントをそのまま FE として利用）
- 推論バックエンドを LM Studio → vLLM 等に差し替えても中間層は無変更
- フェーズ2で自作 FE を載せる際も、本サービスは変更不要

### 最終目標（参考・スコープ外）

商用サービス（DLsite にじGAME 等）で実装されている以下の機能群を、
ローカル環境で再現・改良することが長期的な目標。

| 商用の実装 | 本プロジェクトの方針 |
|---|---|
| 直近N件スライディングウィンドウのみ | **要約チェーンで長期セッション対応** |
| メモリ20件FIFO＋ユーザー手動ロック | **自動的な重要度判定・矛盾解消** |
| 1メッセージ1推論（原価制約） | **サブLLM並列呼び出しで裏方処理** |
| プロンプト枠を課金販売 | 制約なし |

ローカル実行のため推論コストがゼロに近く、**商用が原価の都合で妥協した部分を作り込める**ことが本プロジェクトの主眼。

## 4. データモデル

SQLite 単一ファイル。将来 `sqlite-vec` でベクトル検索を同一DBに足せるため、別途ベクトルDBは立てない。

```sql
-- キャラクター定義
character(
  id, name, base_persona, output_format_instruction, created_at
)

-- 性格ステータス配分
stat_alloc(
  character_id, axis, value          -- axis は設定可能にする（固定6軸にしない）
)

-- 会話セッション
session(
  id, character_id, label, created_at, updated_at
)

-- メッセージ
message(
  id, session_id, role,              -- role: user | assistant
  dialogue, narration,               -- 構造化出力の分解結果
  raw_content,                       -- パース前の生出力（デバッグ用）
  created_at
)

-- 記憶
memory(
  id, character_id,
  subject,                           -- user | character（主語混線の防止に必須）
  content, category,
  created_at,
  superseded_by,                     -- 矛盾解消用（フェーズ2で使用・列は今作る）
  locked
)

-- 会話要約（フェーズ2）
summary(
  session_id, upto_message_id, content, created_at
)
```

### 設計上の必須要件

- **`subject` 列は省略しないこと。** 「猫が好き」がユーザーの発言かキャラの発言かを区別しないと、一人称が混線する。
- **`superseded_by` は上書き削除ではなく時系列保持のために使う。** フェーズ2で「以前はXと言っていたが、最近はYと言っている」という形で想起させる。
- **`raw_content` を必ず保持する。** パース失敗時の調査に不可欠。

### 想起戦略の判断

**メモリ件数が数百件を超えるまで、ベクトル検索は実装しない。**

50件 × 平均30トークン ≒ 1,500トークン程度であり、8k〜16kコンテキストなら全件注入で足りる。
検索を挟むと必要なものが漏れるリスクの方が大きい。
ベクトル検索の導入は「全件注入がコンテキストを圧迫し始めてから」でよい。

## 5. 技術選定と制約

### 言語・主要クレート

- **Rust**
- HTTPサーバ: `axum`（SSE ストリーミングが素直）
- HTTPクライアント: `reqwest`
- DB: `sqlx`（コンパイル時クエリ検証）または `rusqlite`
- 非同期: `tokio`
- シリアライズ: `serde` / `serde_json`

### Rust を選んだ理由

メモリの状態管理が本システムの中核であり、状態遷移を型で表現できることが決定的。

```rust
enum MemoryState {
    Active,
    Superseded { by: MemoryId, at: DateTime<Utc> },
    Locked,
}

enum Subject { User, Character }
```

「上書きされたメモリを誤って想起に含める」といったバグをコンパイル時に潰す。

### コンテキスト予算の制約

- メインモデルの実用コンテキストは **8k〜16k トークン**
- Q4_K_M で 8.24GB、12GB VRAM の残りは約3.5GB → KVキャッシュがここを食う
- **量子化を Q5 に上げるより、コンテキストを伸ばす方が体感品質に効く**（既に判断済み）
- プロンプト組立時に**トークン予算の配分を明示的に管理すること**
  - システムプロンプト（ペルソナ＋性格）
  - メモリ全件
  - 直近N件の会話
  - 生成用の余白

### 出力形式

台詞と地の文を分離する。プロンプトで形式を強制し、パーサで分解する。

形式は実装者の判断に任せるが、以下を満たすこと：

- **パース失敗時に落とさない**（生出力をそのまま地の文として扱うフォールバック）
- 小型モデルは形式を崩すため、寛容なパーサにする
- パース成功率をログに残し、後でプロンプト調整の判断材料にする

## 6. 開発方針

### 必須要件

- **テスト駆動開発。** 実装とテストをセットで提示すること。
  - パーサ、プロンプト組立、トークン予算計算は特に純粋関数として切り出し、単体テストを厚く
  - LM Studio への通信はトレイトで抽象化し、テストではモックを注入
- **セキュアコーディング。**
  - SQLインジェクション対策（プレースホルダ必須）
  - 外部入力（LLM出力を含む）のバリデーション
  - **LLM出力をそのままSQLやシステムコマンドに渡さない**
  - エラーメッセージに内部パスや接続情報を含めない
- **ドキュメントは適切な長さで分割。**
  長大になる場合は階層構造を持たせ、体系立てた構成にすること。

### 想定される落とし穴

1. **ストリーミングの中継**
   SSE を受けて SSE を返す二段構成。バッファリングで詰まると体感が死ぬ。
2. **サブLLM呼び出しのタイミング**
   本文生成のレスポンスを返した**後**に非同期でメモリ抽出を走らせる。
   同期的にやるとレイテンシが倍増する。
3. **性格値ゼロの扱い**
   「パッション: 0/5」とプロンプトに書くと、モデルが「情熱がない」を過剰演技して無感情になる。
   **値が0の軸はプロンプトに含めない**実装にすること。
4. **OpenAI互換の会話履歴と自前の永続化の二重管理**
   クライアントは毎回全履歴を送ってくる。本サービスは自前DBを正とし、
   クライアント送信分は最新メッセージのみ採用するのが素直。
   ただしセッション同定の方法を決める必要がある（後述）。

### 未決事項（実装時に相談または判断が必要）

- **セッション同定の方法。** OpenAI互換APIにはセッションIDの概念がない。
  モデル名に埋める / カスタムヘッダ / 会話履歴のハッシュ、等の選択肢がある。
- **プロジェクト名。** 未定。
- **出力形式の具体的なマークアップ。**

## 8. 最初のマイルストーン

以下が動けばフェーズ1の第一段階として成立する。

1. `cargo run` でサーバが起動する
2. OpenAI互換クライアントから接続でき、`/v1/models` が応答する
3. メッセージを送るとキャラクターとして応答が返る（ストリーミング）
4. 応答が台詞と地の文に分解されて SQLite に保存される
5. 性格ステータスを変更すると応答の傾向が変わることが確認できる

**5番目が最も重要な検証。** ここが機能しなければプロンプト組立の設計を見直す必要がある。

まずは `Cargo.toml`、データモデルのマイグレーション、LM Studio への疎通（ストリーミング中継）から着手すること。
