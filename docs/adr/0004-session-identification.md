# ADR-0004: セッション同定は `model` フィールドで行う

- 状態: **採用**
- 日付: 2026-08-13（提起） / 2026-08-13（決定）

## 背景

[ADR-0001](0001-openai-compatible-boundary.md) により、本サービスは OpenAI 互換 API を提供する。
しかし **OpenAI 互換 API にはセッションIDの概念がない。**

一方、本サービスは自前の SQLite を持ち、**自前DBを正として扱う**方針である
（クライアントが毎回送ってくる全履歴のうち、採用するのは最新メッセージのみ）。
そのためには「このリクエストはどのセッションの続きか」を同定する手段が要る。

同定を誤ると、**別キャラクター・別セッションの記憶が混ざる。**
一度混ざると DB 上は正常に見えるため、気づくのが遅れる。**確実性を最優先する。**

## 決定

**`model` フィールドにキャラクター名（および予約語）を書く方式のみを実装する。**

### 書式

| `model` の値 | 意味 |
|---|---|
| `aoi` | `aoi` の**最新セッションを継続**（後述の定義）。1つも無ければ暗黙に作成 |
| `aoi@new` | **新規セッションを作成**し、以後 `aoi` はそれを継続する |
| `aoi@<session-id>` | 指定セッションを明示的に継続（**一覧には出さない**。復旧・デバッグ用） |

### `GET /v1/models`

**キャラクターのみを並べる。** セッションは並べない。
クライアントのモデル選択 UI が、そのままキャラクター選択 UI になる。

`@new` / `@<session-id>` は一覧に出さないが、**受け付ける**
（モデル名を自由入力できるクライアントなら使える）。

### 未知の値の扱い

`model` は**クライアントから来る信頼できない入力**である。
**既知のキャラクター名の許可リストと照合し、一致しなければ処理しない。**
OpenAI 互換のエラー（404 / `model_not_found`）を返す。

**キャラクター名に `@` を含めることを禁止する**（登録時に検証）。予約語と衝突するため。

### カスタムヘッダ

`X-Personacore-Session` のようなヘッダによる上書きは**フェーズ1では実装しない。**
ただし `model` の解釈は**単一の関数に閉じ込め**、後からヘッダ優先を足せる形にしておく。

### 「最新セッション」の定義

**`session.updated_at` が最も新しいもの**とする（`created_at` ではない）。

> **⚠ 2026-08-27 に狭まった。** **いまは「中身のある（`message` を1件以上持つ）ものの中で、
> `updated_at` が最も新しいもの」。** 空セッションは順序の第1キーで降格する。
> **この節の残りは今も生きている**（押し上げの責務・単調増加）。**末尾の追記を読むこと。**

`created_at` 基準だと、`aoi@42` で過去セッションに復旧した直後に `aoi` へ戻ったとき、
**42 ではなく最新セッションへ飛ぶ。** これは本 ADR が最も避けたい
「気づきにくい記憶の混線」そのもの。

代償として、**メッセージを追加するたびに `session.updated_at` を必ず更新する責務**が
アプリ層に発生する。**更新漏れはセッションの取り違えとして表面化する**ため、
`store` 側でメッセージ追加と `updated_at` 更新を**同一トランザクションの1操作**にまとめ、
呼び出し側が片方だけ実行できない形にすること。

#### `updated_at` は同一キャラ内で単調増加させる

`updated_at` を「システム時刻をそのまま書く」実装にすると、**書き込みが速いと同値になり、
最新セッションの解決が不定になる。** そこで**書き込み側で単調増加を保証する**:

```sql
max(strftime(now),
    coalesce((SELECT strftime(max(updated_at), '+0.001 seconds')
              FROM session WHERE character_id = …), ''))
```

「そのキャラの既存最大値より真に大きい値」を必ず書くため、
**時計が進まなくても、システム時刻より未来の値が入っていても順序が壊れない。**
解決側は `ORDER BY updated_at DESC` だけで決定的になる。

**セッション作成（`INSERT`）にも同じ押し上げが要る。** これが無いと、既存セッションの
`updated_at` が実時刻より未来にある状態で `aoi@new` を打ったとき、
**新規セッションを作った直後に `aoi` が旧セッションを継続する**（実測で確認済み）。

> **⚠ この「実測で確認済み」は、旧セッションが空のときに限る**（2026-08-27 / 末尾の追記）。
> **中身のある旧セッションが相手なら、最初のメッセージが保存されるまで `aoi` は旧を返す。**
> **押し上げ自体は今も要る**（中身のあるものどうしの順序を決めているのはこれ）。

検証済みの前提（SQLite 3.51.3 で実測）:

- `strftime('%Y-%m-%dT%H:%M:%fZ', X, '+0.001 seconds')` は正確に 1ms 進む（1000回で丸め誤差なし）
- 出力は常に24文字固定なので**辞書順比較が ISO-8601 として正しく働く**
- **実時刻の先行は起きない。** WAL のファイル DB ではコミット1回に約2ms かかるため、
  500回連投しても実時刻を追い越さない（in-memory DB でのみ先行するが本番構成ではない）

> **`id DESC` で解決する代替は採れない。** `id` 順は `created_at` 順と同じなので、
> `aoi@42` で復旧した直後に `aoi` へ戻ると最新 id へ飛び、本 ADR が却下した挙動になる。

#### 書き込みの順序 — `UPDATE` を先に置く

`append_message` は `UPDATE session` → `INSERT message` の順に実行する。理由は2つ:

1. `PRAGMA foreign_keys` が無効な接続でも
   「メッセージだけ入って `updated_at` が付かない」状態を作らせない
2. **最初の文が書きなのでロック昇格が起きない。**
   読み→書きの昇格は `SQLITE_BUSY_SNAPSHOT`(517) になり、
   **`busy_timeout` が一切効かず即座に失敗する**（実測 163µs）。
   書き→書きなら待てる（実測 328ms 待って成功）

同じ理由で、**読みから始まって書きに昇格するトランザクションは `BEGIN IMMEDIATE` にする**
（`latest_or_create_session` が該当）。これを怠ると、最も多く通る `aoi` の経路で
FE が2本同時に投げただけで片方が失敗する。

## 理由

1. **`model` は OpenAI 互換の必須フィールドであり、どのクライアントでも必ず送れる。**
   フェーズ1の狙いは「既存クライアントをそのまま FE として使う」ことなので、
   クライアントを選ばない手段でなければ狙いが崩れる。
2. **フェーズ1で使うクライアントが未定でも先に進める。** 実装がクライアント選定に
   ブロックされない。ヘッダ対応は必要になってから足せばよく、今決めなくても損をしない。
3. **`@new` はクライアント内で完結する。** 別途 CLI や管理エンドポイントを用意せずに
   「新しい会話を始める」を表現できる。
4. **`/v1/models` にキャラだけ並べれば一覧が短く保たれる。**
   セッションを並べる方式は、増えるほど一覧が使い物にならなくなる。

### 却下した選択肢

- **カスタムヘッダ（`X-Personacore-Session`）を主にする** — 意味的には最もきれいだが、
  **送れるクライアントに限られる。** これを唯一の手段にするとフェーズ1の狙いが崩れる。
  後付け可能なので、今実装する理由がない。
- **OpenAI 標準の `user` フィールドを流用する** — 規格内に収まるが、
  **UI に露出しているクライアントは `model` より明確に少ない。** 確実性で劣る。
- **会話履歴のハッシュで同定する** — クライアント側の対応が不要な点は魅力だが、
  **履歴の編集・再生成・分岐でハッシュが変わり、黙って別セッション扱いになる。**
  切れたことに気づけないまま記憶が分断される。最も避けたい壊れ方そのもの。
- **`/v1/models` にキャラ×セッションを全部並べる** — 選択は明示的になるが、
  セッションが増えるほど一覧が崩壊する。
- **一定時間の無操作で自動的に新規セッション** — 操作は不要になるが、
  意図しない分断・結合が起き、しかも**気づきにくい**。

## 結果

### 得られたもの

- **クライアントを選ばない。** フェーズ1のクライアント選定を後回しにできる
- モデル選択 UI がキャラクター選択 UI として機能する
- 新規セッション開始が API 単体で完結する

### 諦めたもの / 前提

- **`model` が本来の用途（モデル選択）から外れる。** 上流の LM Studio に渡すモデル名は
  本サービスが別途決める（キャラ定義または設定から引く）ため、
  **クライアントから推論モデルを選ぶ手段は無くなる。** 個人利用では問題にならない判断。
- **キャラクター名に `@` を使えない。** 登録時に検証して弾く。
- モデル名を自由入力できないクライアントでは `@new` が使えず、
  新規セッションを開始できない。→ **その状況になったらヘッダ対応を足す**（後付け可能）。

### 実装上の注意

- **`model` の解釈は単一の関数に閉じ込める。** ヘッダ優先を後から足す差込口になる。
- **許可リスト照合を通す前の `model` を、DB クエリやログ以外の場所で使わない。**
  SQL プレースホルダや [`ValidTag`](0006-slot-based-tag-compilation.md) と同じ構造の対策。
- 解釈のテストを厚くする: `aoi` / `aoi@new` / `aoi@<id>` / 未知キャラ / `@` の多重 /
  空文字列 / セッション未作成のキャラ。

### 決定 — キャラクター名は登録時に正規化し、照合は完全一致

**登録時に前後の空白を除去（正規化）してから保存する。照合は正規化後の値で完全一致。**

背景: `"aoi"` と `" aoi "` が併存すると、**アプリ層が `model` を trim してから照合した瞬間**に
両方が一致し、`LIMIT 1` の順序次第で**どちらのキャラに書き込むかが不定**になる。
登録時に正規化しておけば `" aoi "` はそもそも保存されず、照合を完全一致に保てる。

実装は `domain::CharacterName` の newtype で強制する（[ADR-0006](0006-slot-based-tag-compilation.md)
の `ValidTag` と同じ発想）。**`parse` 以外の構築手段を提供しない**ことで、
未検証の文字列が `store` に届く経路を型で塞ぐ。除去対象はスキーマの CHECK と同じ8種
（半角 / TAB / VT / FF / CR / LF / 全角空白 / NBSP）。

**検索時に trim してはいけない。** 登録時に正規化済みなので、
照合側でも trim すると上記の「書き込み先が不定」を自ら再現することになる。

#### DB 側の担保

アプリ層の正規化だけでは、**DB を直接編集された場合**に不正な行が残る。
そこで正規化キーの UNIQUE インデックスを併設する:

```sql
CREATE UNIQUE INDEX character_name_key_idx ON character (
    trim(name, ' ' || char(9) || char(10) || char(11) || char(12) || char(13)
             || char(12288) || char(160)));
```

> # ⚠ この索引はもう無い（2026-08-16 / 0004b-2）
>
> **[ADR-0017](0017-handle-is-a-restricted-alphabet.md) が識別子の文字集合を絞り、
> `CharacterName::parse` が正規化（trim）をやめた。**
> **空白は識別子として表現できないので、この索引が防いでいた
> 「照合が両方に一致して書き込み先が不定になる」は原理的に起きない。**
>
> **索引を落としたのは、残すと害だけが残るため。** ゴースト行が1件あるだけで
> **正当な識別子の作成が塞がれ**、下の「袋小路」そのものになる。
>
> **`ConflictingUnnormalizedName` も消えた**（落ちる入力が存在しない）。
> **索引と `trim` は一組で、片方だけ残すと更新がゴースト行の id を返し、
> 削除が本物ごと消す**（実測。`migrations/0006_*.sql` を見ること）。
>
> **以下はその時点の記録として残す。**

**このインデックスが防ぐのは「衝突」であって「ゴースト行」ではない。**
`"aoi"` が既にある状態で `" aoi "` を直接 INSERT することは防げるが、
`" aoi "` 単独の行は依然として作れる。**最も危険な「両方が一致して不定になる」ケース**を
潰すのが目的であり、単独のゴースト行は `store` 側で一覧から除外し `warn` ログに残す。

#### ゴースト行が残ったときに何が起きるか

`" aoi "` の行が単独で存在する状態では、次の3つが同時に成立する。

| 操作 | 結果 |
|---|---|
| `GET /v1/models` | `aoi` は**出ない**（一覧から除外 + `warn`） |
| `model=aoi` でチャット | **404**（照合は完全一致なので引けない） |
| `aoi` を作成 | **UNIQUE 違反**（索引は trim 後で衝突と判定する） |

**API 越しには「一覧に出ない・チャットは404・しかし作ろうとすると既に存在する」という
袋小路に見え、原因に到達できない。** 手掛かりは `list_characters` の `warn` だけで、
しかもそれは一覧を呼んだときにしか出ない。

したがって **`store` は正当な重複作成とこのケースを別のエラーに分ける。**
`create_character` が UNIQUE 違反を受けたら正規化キーで引き直し、
格納名 ≠ 正規化名なら専用のバリアントに落とす（`Display` は定数文字列のまま、
id はログのみ）。**server 層が素直に `UniqueViolation → 409「既に存在します」` と
マップすると、この袋小路を利用者に押し付けることになる。**

#### `0002` は既存データに対して前方互換ではない

`"aoi"` と `" aoi "` が既に併存する DB にこの索引を張ろうとすると、
`UNIQUE constraint failed: index 'character_name_key_idx'` で**マイグレーションが失敗し、
`Store::connect` が恒久的に落ちる。** エラーメッセージから原因が索引だとは分からない。

実データが無い段階で導入したので実害はないが、**同種の索引を後から足すときは
既存データの検査を先に行うこと。**

> `lower()` を挟む案は採らない。**SQLite の `lower` は ASCII しか畳まない**ので
> 日本語名では効かず、大文字小文字の扱いが言語によって割れる方が害が大きい。

## 追記 —— **「最新」は「中身のある最新」になった**（2026-08-27 / 作業単位 B-2b）

### 何が起きていたか

**`resolve_session` はセッションの作成を、上流を開くより前に行う。**
**上流が開けない回は 200 の前に 502 で返り、`session` の行だけが残る**（`message` 0 件）。
そして上の「`updated_at` は同一キャラ内で単調増加させる」により **`INSERT` でも押し上がる**ので、
**その空セッションが「最新」になる。**

**素の `aoi` へ戻ると、それまでの会話ではなく空セッションの続きに着地する。**
**画面上は普通に見えるので、履歴が分断されたことに気付けない。**
**この ADR が「最も避けたい」と書いた記憶の混線の隣である。**

**2026-08-26 に司令塔がブラウザで実例を作った**（`session` 1行 / `message` 0件）。

### 決定 —— **解決の順序に「中身があること」を第1キーとして足す**

```sql
ORDER BY EXISTS (SELECT 1 FROM message WHERE message.session_id = session.id) DESC,
         updated_at DESC, id DESC LIMIT 1
```

**上の §「最新セッション」の定義は、この1行ぶん狭まった。**
**`updated_at` の押し上げ（`INSERT` を含む）は、いまも要る**——
**中身のあるセッションどうしの順序は、依然としてそれだけで決まる。**

### ⚠ 除外（`WHERE`）ではなく降格（`ORDER BY`）である

**理由は実測。** `WHERE ... AND EXISTS (...)` にすると、
**空セッションしか無い状態で `latest_or_create_session` が呼ばれるたびに新しい行を作る** ——
**32 本の並行呼び出しが 32 セッションを別々に作った**（10 本のテストが赤になる）。

**降格なら、中身のあるものが1つでもあれば必ずそちらが勝ち、
1つも無ければいちばん新しい空セッションを再利用する。**

### ⚠ 順序の入れ替えでは直らない

**「上流を開いてからセッションを作る」では直らない。**
[ADR-0019](0019-relay-idle-watchdog.md) §4 により
**打ち切られた回・人が中止した回は1行も保存されない**ので、
**上流が正常に開いた回でも空セッションは残る**（ブラウザで作った実例がまさにそれ）。
**空セッションは異常系だけの現象ではなく、正常系の中にも居る。**

### ⚠ 保証が1つ狭まった —— **承知のうえで受け入れる**

**`aoi@new` を打ってから、最初のメッセージが保存されるまでの窓では、
素の `aoi` は旧セッションを返す。**
`create_session_becomes_latest_even_against_a_future_timestamp` が固定していた主張は、
**いまや「旧セッションが空のときに限る」。**

**受け入れる理由:**

- **空セッションには継続すべき中身が無い。**
- **`aoi@new` を出したクライアントは応答で `aoi@<id>` を受け取って固定する**ので、
  **成功した `@new` はこの窓に依存しない。**
  **⚠ 窓の中でも `find_session` は届く**（明示した id は殺していない）。
- **窓に入るのは「その回が1行も保存されなかったとき」か「2つ目のタブ」だけ。**

> **⚠ これは「失敗したら `@new` を降ろす」とは別物である。**
> あれは **`@new` の意味を変える**話で、**利用者が明示した「新しい会話」を黙って捨てる**ため採らない。
> こちらは**「最新」の意味を変えた結果、中身の無いセッションが継続の対象から外れた**という話。
> **`@new` は今も必ず新規を作る。**

**見張り番は `a_fresh_session_loses_to_an_older_conversation_until_its_first_message_lands`。**
**散文ではなくテストで固定してある。**

### 結果 —— 諦めたもの

- **失敗した `@new` が残した空セッションは、読み出し経路から完全に外れる**
  （id が 200 前の応答に載らないので、利用者は指せない）。**掃除の経路は無い。**
- **`session_character_recent_idx` だけでは `ORDER BY` を賄えなくなった**
  （`EXPLAIN QUERY PLAN` が `USE TEMP B-TREE FOR ORDER BY`。変更前は `FOR LAST TERM OF ORDER BY`）。
  **行の絞り込みには今も索引が効く。時間は測っていない。**
  **⚠ セッション件数に上限は無い**ので、「実際には少ないから問題ない」とは書けない。
