# ADR-0007: 台詞は「」で表し、崩れたら全部を地の文にする

- 状態: 採用
- 日付: 2026-08-13
- 関連: [02-architecture.md](../02-architecture.md#出力形式) / [03-data-model.md](../03-data-model.md)

## 背景

キャラクターの応答を**台詞**と**地の文**に分離して `message.dialogue` / `message.narration` に
保存する。そのためには出力形式を決め、プロンプトで強制し、パーサで分解する必要がある。

引き渡しブリーフの時点から**未決**だった。判断を難しくしていたのは次の4点。

- **ストリーミングが必須。** 形式によっては中継や将来の逐次表示に影響する
- **小型モデル（3B / 14B）は形式を崩す前提**（CLAUDE.md）
- **パーサは panic せず、崩れたら生出力を丸ごと地の文として扱う**フォールバックに落ちる
- パース成功率をログに残し、プロンプト調整の判断材料にする

つまり「**厳密さ**」より「**崩れにくさ**」が効く。

## 決定

**`「` と `」` で囲まれた部分を台詞とし、それ以外を地の文とする。**

**パースが崩れたら、生出力を丸ごと地の文として扱う。** 部分的に拾わない。

> **⚠ 崩れの判定を1つ変更した（2026-08-15 / [ADR-0014](0014-nested-quotes-are-not-a-breakage.md)）。**
> **入れ子の `「」` は崩れではない。** 実測で、モデルは日本語として正しく書いており、
> `「」` の中で `『』` を使ったうえで1箇所だけ滑っていた（`ユーモア` が高いと逸話を語るため）。
> **1段目の区間を取り、内側は本文に残し、入れ子の発生は記録する。**
> 崩れは `Unclosed` と `StrayClose` の2つ。**この節の他の記述は有効。**

```
　ふと顔を上げて、彼女は目を細めた。「おかえりなさい」
　声には少しだけ安堵が混じっている。
```

→ `dialogue` = `おかえりなさい` / `narration` = 残り

## 理由

1. **日本語の小説・脚本の慣習そのもの。** モデルはこの形式を大量に学習しており、
   **指示しなくても自然に出す。** 小型モデルで最も崩れにくい形式である、というのが決め手。
2. **指示のトークンコストがほぼゼロ。** コンテキストが 8k〜16k と厳しい本プロジェクトでは、
   形式指示に数十トークン払う設計は割に合わない。
3. **文字単位で判別できる。** 現状のパースは
   [ストリーム終了後に走る](../02-architecture.md#ストリーミング中継)ので必須要件ではないが、
   将来 FE で台詞と地の文を別表示したくなったときに、逐次分類へ拡張できる。

### 却下した選択肢

- **行頭プレフィックス**（`台:` / `地:` 等）— 行単位で堅牢に拾えるのは利点だが、
  **モデルが指示を忘れやすく、文体も不自然になる。**
  キャラクターの一貫性が主題である以上、出力の自然さを削る形式は採らない。
- **XML タグ**（`<serifu>` 等）— 明示的だが**トークンコストが高く、小型モデルは閉じタグを忘れる。**
  さらに**タグが閉じるまで種別が確定しない**ため、逐次分類へ拡張できない。
- **LM Studio の構造化出力（JSON Schema）** — 形式が保証されパース失敗が原理的に起きない。
  しかし**ストリーミングと相性が悪く**（部分 JSON を FE へ流しにくい）、
  **創作文の品質が落ちる報告もある。**
  「パース失敗はフォールバックで受ける」と決めている以上、
  ストリーミングを犠牲にしてまで形式保証を買う理由がない。
  ただし**メモリ抽出のスロット埋めでは構造化出力を使う**
  （[ADR-0006](0006-slot-based-tag-compilation.md)）。**本文生成と裏方処理で判断が違う**ことに注意。

### フォールバックで部分的に拾わない理由

「拾えた部分だけ台詞にする」案は実用上の欠損が小さいが、
**「どこまで拾えたか」が挙動を説明しにくくする。**
`message.raw_content` に生出力が必ず残るので、
**後から調査も再パースもできる**（[03-data-model.md](../03-data-model.md) 不変条件3）。
フォールバックは単純で予測可能な方を採る。

## 結果

### 得られたもの

- 形式指示のコストがほぼゼロ
- 小型モデルでの崩れにくさ
- 逐次分類への拡張余地

### 諦めたもの / 前提

- **地の文中の引用と台詞を区別できない。**
  「彼は『行く』と言った」のような引用が台詞として拾われる。
  キャラクター会話では稀であり、フォールバックも無害なので許容する。
- **形式が保証されない。** パース成功率の監視が前提になる。

### 「崩れた」の判定基準

**括弧の対応だけを見る。** 崩れは次の3つに限る。

| 判定 | 例 | 理由 |
|---|---|---|
| 閉じられていない | `「おかえり` | 区間の右端が決まらない |
| 入れ子 | `「外「内」外」` | どちらが台詞か決まらない |
| 閉じが先に来る | `」あ「い」` | 区間の左端が決まらない |

**長さや中身では判定しない。** 「地の文が短すぎたら怪しい」のような発見的判定を入れると、
**正当な長台詞が理由不明でフォールバックし、しかも原因を追えない。**

崩れ**ではない**もの: 複数の台詞 / 台詞なし / 地の文なし / 空の `「」`。
**対応が取れている限り正常系**として扱う。

> 全数検証（全 Unicode スカラ値 × 文脈 ＋ 敵対アルファベット上の長さ≤4 全数）で、
> **この3分類以外の崩れ方が存在しないこと**を確認済み。

### 台詞を抜いた跡の空行

```
地の文1
「台詞」
地の文2
```

**これが日本語小説で最も一般的な体裁**であり、モデルが最も高い頻度で出す形。

- **台詞を抜いた結果として空になった行は落とす**（跡地を残さない）
- **元から空だった行は段落区切りとして残す**

区別しないと、台詞 n 個につき空行が n 個増える。逆に全部畳むと本来の段落構造が消える。

### 複数の台詞を1列にどう格納するか

`message.dialogue` は TEXT 1列。**改行で連結し、「1行 = 台詞1つ」を不変条件とする。**
そのために**台詞内の改行は半角スペースへ畳む。**

- `「」` を付け直す案は、台詞1つのとき本 ADR の例（`dialogue` = `おかえりなさい`）と食い違う
- 空白区切りは、境界が本文中の空白と区別できない
- **畳んだ改行は `raw_content` に残るので復元できるが、
  「何個の台詞だったか」は連結すると復元が難しい。** 取り出せない方を残す

### `「」` 以外の引用符は台詞にしない

`『』` / `""` / `“”` / `〈〉` / 半角 `｢｣`（U+FF62/63）は**すべて地の文**。

**特に `『』` を含めてはならない。** 含めると
**`「彼は『行く』と言った」` という慣習どおりの正しい出力が、入れ子としてフォールバックする。**

> 本 ADR の「諦めたもの」で想定していたのは「引用が台詞として誤って拾われる」方向だったが、
> 実際には**逆方向（拾おうとすると正しい出力が壊れる）が先に来る。**

### パーサへの要求（`parse` の作業単位）

- **いかなる入力でも panic しない。** これは絶対制約
- **寛容に書く。** 小型モデルは形式を崩す
- **`「` が閉じないまま終わる**、ネストする、複数の台詞が含まれる、といった形を扱う
- **パース成功率をログに残す**（プロンプト調整の判断材料）
- `dialogue` / `narration` は**両方 `None` になりうる**（フォールバック時は
  `narration` に生出力、`dialogue` は `None`）

### 制御トークンの無害化と衝突する形式は選べない

`prompt` は**括弧の形**で制御トークンを無害化する
（`[` … `]` / `<` … `>` で中身が ASCII の英数字・`_`・`/`・`|` だけなら閉じ括弧の手前に空白を挿入。
[04-environment.md](../04-environment.md)）。

したがって **XML 風のマークアップは採れない。**
「地の文は `<narration>` で囲む」という形式指示は `<narration >` になり、
**モデルへの指示そのものが壊れる。**

`「」` はこの規則の対象外（非 ASCII）なので衝突しない。
**本 ADR の決定は、この制約とも整合している。**

> 却下理由に「トークンコストが高い」「閉じタグを忘れる」を挙げたが、
> **そもそも無害化と衝突して成立しない**という、より強い理由が後から判明した。

### `character.output_format_instruction` との関係

形式指示は**キャラクターごとに DB へ持つ**（`character.output_format_instruction`）。
本 ADR が決めたのは**既定の形式**であり、`prompt` は DB の文字列をそのまま使う。
**`prompt` に形式を決め打ちしない。**
