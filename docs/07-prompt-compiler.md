# 07. プロンプトコンパイラ（画像生成）

会話文脈（日本語）から画像生成用プロンプト（Danbooru タグ列）を生成するコンポーネント。

**主にフェーズ3の実装対象だが、型定義とデータモデルは早期に入れる**（[06-roadmap.md](06-roadmap.md)）。
原典は [archive/addendum-01-prompt-compiler.md](archive/addendum-01-prompt-compiler.md)。

## 何を解決するのか

**タグを人間が書かなくて済むようにすること。**
日本語話者にとって適切な英語タグを選ぶのは負荷が高く、
チェックポイントごとにタグ規約が異なるため人力での維持が現実的でない。

```
会話文脈（日本語）
    ↓ サブLLM（構造化出力）
中間表現（スロット）        ← まだ未検証
    ↓ タグ辞書で検証・正規化
検証済みタグ（ValidTag）
    ↓ テンプレート合成
最終プロンプト（positive / negative）
    ↓
ComfyUI
```

## 中核の設計判断 — LLM に自由にタグを吐かせない

詳細と却下案は [ADR-0006](adr/0006-slot-based-tag-compilation.md)。要点のみ:

LLM に「この会話を Danbooru タグにして」と投げると、**高い確率で存在しないタグが混ざる。**
致命的なのは**存在しないタグがエラーにならない**こと。CLIP は未知の文字列も
何らかのベクトルに変換するため、架空タグは静かに無視されるかノイズとして混入する。
**生成結果が微妙になっても原因が特定できない、という最悪の壊れ方をする。**

対策は**スロット方式**。LLM には構造化された中間表現を埋めさせるだけにし、
実際のタグへの変換と妥当性検証はプログラム側で行う。

```rust
/// LLM が返す中間表現（この時点では未検証）
#[derive(Deserialize)]
struct RawSceneSpec {
    expression: Option<String>,
    pose: Option<String>,
    clothing_state: Option<String>,
    background: Option<String>,
    camera: Option<String>,
    lighting: Option<String>,
}

/// 検証済みタグ。辞書経由でしか構築できない
struct ValidTag(String);

impl ValidTag {
    /// 唯一のコンストラクタ。辞書に存在しない場合は None
    fn lookup(dict: &TagDictionary, candidate: &str) -> Option<Self> { ... }
}
```

> **`ValidTag` の内部フィールドは private にし、`lookup` 以外の構築手段を提供しないこと。**
> `From<String>` も `pub fn new` も生やさない。これにより
> **「架空タグがプロンプトに混入する」ことが型レベルで不可能になる。**

### 検証失敗時の挙動

- 未知の値は**破棄する**（そのスロットを空にする）。推測で補完しない。
- 部分一致・エイリアスで救済できる場合のみ救済する。
- **破棄したことを必ずログに残す。** 辞書の不足を検出する唯一の手段。
- **破棄率をメトリクスとして集計できるようにする。**
  高い場合はプロンプト設計か LLM 選定の見直しが必要というシグナル。

## タグ辞書

- Danbooru タグ語彙がベース（Illustrious / NoobAI 系チェックポイントはこれで学習されている）
- 全体は数十万タグあるが、**実用上は数百〜千程度で足りる**
- 表情・ポーズ・服装・構図・背景・照明のカテゴリに分類して保持

### 検索方式

**ベクトル検索を使わない。完全一致・部分一致・エイリアス表で足りる。**

理由は記憶の想起（[ADR-0003](adr/0003-full-memory-injection.md)）と同じ。
対象が数百〜千件の**閉じた語彙**であり、LLM が返す値も概ねタグに近い形（英語の短い語句）。
ベクトル検索を挟むと**誤マッチのリスクの方が大きい**。

日本語 → タグの対応もエイリアス表で持つのが確実:

```
「照れる」「赤面」  → blush
「顔を伏せる」      → looking_down
「微笑む」          → smile
```

### データ形式

TOML または JSON で**リポジトリ内に持つ**。**DB に入れない。**
更新頻度が低く、バージョン管理したいため。読み込みはコンパイル時または起動時。

## 固定部と可変部の分離

キャラクター一貫性の第一歩は、**外見に関わるタグを固定部に置く**こと。

| 区分 | 内容 | 供給元 |
|---|---|---|
| **固定部** | 髪色・髪型・目の色・基本の服装 | キャラ定義（DB） |
| **固定部** | 品質タグ | チェックポイント設定 |
| **固定部** | ネガティブベース | 設定ファイル |
| **可変部** | 表情・ポーズ・背景・照明・カメラ | 会話文脈から LLM が生成 |

**LoRA を導入する前でも、固定部をハードコードするだけで一貫性は相当改善する。**
LoRA は固定部をさらに強化する手段であり、**この構造自体は変わらない。**

## ネガティブプロンプト

**静的である。シーンごとに LLM で生成しない。**
固定のベースラインを持ち、必要な場合のみ数語を追加する。

```rust
const NEGATIVE_BASE: &str =
    "worst quality, low quality, blurry, bad anatomy, bad hands, \
     extra digits, missing fingers, watermark, signature, text";
```

毎回 LLM に生成させると、コストが増える上に品質が安定しない。

### 破綻（腕が増える・関節がおかしい）への対策

**ネガティブプロンプトへの期待値を下げること。効果は限定的。** 効果の大きい順:

| 順位 | 対策 | フェーズ |
|---|---|---|
| 1 | **チェックポイント推奨の品質タグを使う** | 即時 |
| 2 | **複雑なポーズ・複数人の指示を避ける** | プロンプト設計 |
| 3 | ControlNet (OpenPose) で骨格を与える | 将来 |
| 4 | 手・顔の部分再生成（ディテーラー） | 将来 |
| 5 | ネガティブプロンプト・ネガティブ埋め込み | 即時 |

**1番目が最も費用対効果が高い。** チェックポイントごとに固有の品質タグ規約があるため
（`masterpiece, best quality` 系の書き方、スコアタグの有無など）、
モデル配布元の推奨プロンプトを流用する。
**これは設定ファイルで差し替え可能にする**（チェックポイントを変える可能性があるため）。

**2番目も重要。** SDXL は属性の帰属先を取り違えるため、
「複数人が相互作用している」「複雑な体勢」を指示するほど破綻率が上がる。
**これはネガティブプロンプトでは治らない。**
LLM への指示側で、**シーン記述を単純化するよう誘導する**こと。

## LLM 呼び出し

| 項目 | 方針 |
|---|---|
| モデル | **サブLLM（`ministral-3-3b-instruct-2512`）で十分。** スロット埋めは抽出タスクで小型モデルの得意領域<br>⚠ **記憶抽出では 3B が足りなかった**（[ADR-0021](adr/0021-memory-extraction-format.md) §10 の実測。主語を間違え、形式が 41% 崩れる）。**スロット埋めは辞書引きで受理集合が閉じている**ので同じ結論とは限らないが、**「小型で十分」は測ってから言うこと** |
| 出力形式 | **LM Studio の Structured Output（JSON Schema 指定）を使う。** 自由記述させてパースしない |
| タイミング | **同期的に呼ばない。** 画像生成はユーザーが明示的に要求したときのみ |

会話のたびに毎回生成すると、レイテンシと GPU 競合の両方で問題が出る。

### GPU 競合（実装上の重要な制約）

**ComfyUI と LM Studio は同じ GPU（RTX 4070 / 12GB）を奪い合う。**

- SDXL チェックポイント約 6.5GB ＋ メインLLM 8.24GB → **同時常駐できない**
- 画像生成時は LLM をアンロードするか、生成をキューイングして順次実行する
- LM Studio の Idle TTL / Auto-Evict で自動アンロードできるはずなので、これを利用する
- **どちらの戦略が体感として良いかは実測して決める。机上で決めない。**

**フェーズ3の着手時に最初に検証すること。** ここが成立しないと他が全部無駄になる。

## ComfyUI クライアント実装時に決めること

### `seed` の型（未決・重要）

**ComfyUI の seed は符号なし64ビット。** 一方 DB の `generated_image.seed` は
SQLite の `INTEGER`（= `i64`）で、`typeof(seed) = 'integer'` の CHECK のみを課している。

- `i64` 格納だと **2^63 以上のシードを表現できない**
- 負値も現在は通るが、**そのまま ComfyUI へ投げ返せない**

「`u64` をビットパターンとして `i64` に入れる」のか「範囲を制限する」のかを決めないと、
**「保存はされているが再現できない seed」**という、
絶対制約が防ぎたかった状態そのものが成立する。**クライアント実装時に必ず決めること。**

### `character_appearance.lora_strength` の型と範囲

REAL 宣言だが `typeof` 制約がないため、`'abc'` は TEXT のまま格納され、
**`Option<f64>` としてデコードする瞬間に落ちる**（`value` / `seed` と同じ型アフィニティの穴）。
範囲制約を入れるなら `typeof` も同時に、が一貫する。書き込み経路を作るときに対処する。

## テスト方針

以下は純粋関数として切り出し、単体テストを厚くする。

- **タグ辞書の検索** — 完全一致・部分一致・エイリアス・**未知値の破棄**
- **`ValidTag` の構築** — **辞書外の値で構築できないことをテストで保証する**
- **テンプレート合成** — 固定部＋可変部の連結、重複タグの除去、順序
- **LLM 応答のパース** — 不正 JSON、スキーマ違反、欠損フィールドへの耐性

LLM 呼び出しはトレイトで抽象化し、テストでは固定応答を返すモックを注入する。

> **「LLM が架空タグを返してきた場合に、それが最終プロンプトに現れないこと」を
> 明示的にテストすること。** これがこのコンポーネントの存在意義そのもの。

## 実装順序

1. **タグ辞書のデータ構造と検索**（LLM 不要・単体でテスト可能）
2. **`ValidTag` / `SceneSpec` の型定義**
3. **テンプレート合成**（固定部＋可変部）
4. LLM によるスロット埋め（構造化出力）
5. ComfyUI へのワークフロー送信（`POST /prompt`）
6. GPU 競合の解決（アンロード戦略の実測）

**1〜3 は LLM も ComfyUI も不要で完結する。ここから着手するのが安全。**

## 補足 — 業務 RAG への転用

本コンポーネントは実質的に**「自然言語 → 制約された語彙への正規化」**であり、
以下と同型の問題である。

- 自由記述の問い合わせを、社内システムの正規のカテゴリ・製品名にマッピングする
- LLM の出力を、後段システムが受け付ける形式に強制する
- **LLM の出力を無検証で下流に流さない**という原則の実装例

**特に最後の点は、間接プロンプトインジェクション対策の基本形でもある。**
「LLM の出力は信頼できない入力として扱い、許可リストで検証してから使う」という構造は、
本プロジェクトの `CLAUDE.md` 絶対制約と同じものであり、ここがその最も明確な実装例になる。
