# ADR-0009: キャラクター設定は「属性（キー付き）」と「事実（散文）」の2テーブルに分ける

- 状態: **採用**
- 日付: 2026-08-14

## 背景

ジェンダー・年齢・種族のような「**記憶ではないが、変わりようのないキャラクター要素**」を
置く場所が無かった。現状で書けるのは `character.base_persona`（散文・最大1000文字）だけで、
次の3つが起きる。

1. **直せない。** キャラクター更新 API が未実装で、`/admin/characters` は作成のみ。
   年齢を1つ直すには作り直しになり、`ON DELETE CASCADE` でセッションも記憶も消える。
2. **画像側と二重管理になる。** 種族・性別・年齢は `character_appearance.fixed_tags`
   にも要る値だが、**散文からタグは引けない**（`ValidTag` は辞書引き以外の構築手段を
   持たない。[ADR-0006](0006-slot-based-tag-compilation.md)）。同じ事実を2回書くことになり、
   片方だけ直る事故が起きる。
3. **`memory` には置けない。** 観測の記録であり、編集・削除の API を作らないのが絶対制約
   （[03-data-model.md](../03-data-model.md) 不変条件2）。

[03-data-model.md](../03-data-model.md) には `character_fact`（人が書く事実・散文）が
**未実装の予定**として書いてあったが、散文一本では 2 が解決しない。

### 実測 — **一人称が揺れる**（2026-08-15）

マイルストーン5の測定中に、**同じキャラクターの一人称が応答ごとに変わる**ことが分かった。
ペルソナは「喫茶店で働いている。常連客とよく世間話をする。」だけで、**性別を持っていない。**
表示名 `葵` は日本語では男女どちらにも使う。

18条件（3発言 × 他軸2設定 × 性格値3種）を数えた結果:

| 一人称 | 条件数 |
|---|---|
| `私` | 7 |
| **`僕`** | **6** |
| 三人称自称（`葵は`） | 10（重複あり） |

**発言にも他軸にも性格値にも相関しない。** 毎回モデルが引き直している。

同一応答の中で混ざることもある:

> 暖かい店内でゆっくりしてくれるから、**僕**も楽ちんなんだけど
> …なんか心が洗われちゃう感じがする**わ**

**一人称が「僕」で語尾が「わ」。** これは性格ステータスでは直せない。
**属性として渡すしかない。**

> **この ADR の動機は「画像側と共有できる」だけではなくなった。**
> **本文の一貫性そのものが、属性を渡せないと保てない。**

### 実測 — **属性は効く。ただし揃いはしない**（2026-08-21 / 12b の完了後）

**同じペルソナ・同じ表示名・同じ性格値で、属性だけが違う2体**を作って測った
（`handle` と `display_name` を分けた[ADR-0011](0011-character-handle-and-display-name.md)が、
そのまま対照実験の器になっている）。発言5種 × 性格値2組 × 各3回、`temperature = 0`、
`ministral-3-14b-instruct-2512`。**判定は全文を読んで行った。**

| 一人称 | 属性なし | **`一人称: 僕` だけ足した側** |
|---|---|---|
| `僕` | 1 | **約 10** |
| `私` | 3 | **0** |
| `うち` | 約 4 | **0** |
| `俺` | 0 | **約 3** |

**動機は裏付けられた。** 属性1件で分布が大きく動く。

**ただし「指定すれば揃う」ではない。** `俺` へのドリフトが残り、
**同じ条件の2回目と3回目で `僕` → `俺` に変わった回もある**（読んで確認）。
**ユーモア・パッションが高い側**（`8` / `7`）で目立った。

> **交絡を明記する。** 抽出パイプラインが同時に動いていたため、
> **後半の条件は前半の会話から抽出された記憶を読んでいる。** 両群とも同じ形だが、
> **積んだ記憶の中身は群ごとに違う。** つまりこれは
> **「属性だけの差」ではなく「属性 ＋ それぞれが積んだ記憶」の差である。**
> 上流の 500 で**属性なし側の2条件が失われている**ことも含めて、
> **効果の大きさを数字として使わないこと。** 向きだけが読める測定。

#### ただし「揺れ＝欠陥」ではない

**一人称の揺れ自体はキャラクター表現として成立する。**
普段は `僕` だが照れると `私` になる（いわゆるボクっ娘）は、**設計された揺れ**である。

**区別は出力からは付かない。指定できるかどうかで分かれる。**

| | 今回のデータ | ボクっ娘 |
|---|---|---|
| きっかけ | **無い**（発言・他軸・性格値のどれとも無相関） | **ある**（照れる場面） |
| 指定されているか | **されていない** | **されている** |

**仕組みの役割は揺れを抑えることではなく、「どちらを望むか」を書けるようにすること。**
そして2つは形が違うので、**この ADR の2テーブルにそのまま対応する。**

| 書きたいこと | 置き場 |
|---|---|
| `一人称: 僕` | **`character_attribute`**（キー付き・値が閉じている） |
| 「照れると一人称が『私』になる」 | **`character_fact`**（散文・条件つきの振る舞い） |

**条件つきの振る舞いはキー付きでは書けない。** 分けた判断がここでも効いている。

> **日本語の一人称は情報量が大きい。** `私` / `僕` / `俺` / `わたくし` / 三人称自称の選択だけで
> 性別・年齢・場面・関係性がほぼ決まる。**属性1つの粒度としては最も費用対効果が高い部類。**

## 決定

**`character_attribute`（キー付き）と `character_fact`（散文）の2テーブルに分ける。**

| | `character_attribute` | `character_fact` |
|---|---|---|
| 形 | `key` / `value` の対 | 文 |
| 例 | `種族: 猫獣人` / `年齢: 19` | 「幼い頃に故郷を離れている」 |
| 件数 | 少ない（**上限を設ける**） | 増える |
| 画像側から引けるか | **引ける**（辞書経由） | 引けない |
| 置き換えの粒度 | **丸ごと置き換え**（`stat_alloc` と同じ） | 1件ずつ削除・更新 |

どちらも**人が管理 API から書く**。`memory` とはライフサイクルが正反対
（編集・削除が**できる必要がある**／履歴に価値が**無い**）。

> **⚠ 「履歴に価値が無い」は覆した**（2026-08-24 / [ADR-0028](0028-attributes-that-change.md) §決定5）。
> **書き手が人だけではなくなるから。** 会話から提案が来る形にすると、
> **属性が静かに変わったときに気付く手段が無くなる**（変容は本文に出ない ——[ADR-0024](0024-stat-drift.md) §9）。
> **「編集・削除ができる必要がある」の方はそのまま生きている。**

### なぜ形で分けるのか

書き手も編集頻度も同じなので、1つにまとめたくなる。分ける理由は**1点だけ**:

> **画像側（フェーズ3）から引けるかどうかが決定的に違う。**

「種族: 猫獣人」は `fixed_tags` に効く値で、「幼い頃に故郷を離れている」は効かない。
同じ形に押し込むと、**片方が必ず歪む。**
散文に統一すればタグを引けず、キー付きに統一すれば
`key: 生い立ち, value: 幼い頃に故郷を離れている` という**キーが意味を持たない行**が増える。

### 画像タグとの繋ぎ方

**`character_attribute` の `value` を `ValidTag` へ直接変換しない。**
値は日本語の表示用文字列（`猫獣人`）で、タグ（`cat ears, animal ears`）は**辞書引き**で得る。
これで [ADR-0006](0006-slot-based-tag-compilation.md) の「`lookup` 以外の構築手段を生やさない」
が保たれる。**辞書に無い属性値は、画像側では単に無視される**（架空タグが静かに混入するより良い）。

### キーの語彙は可変にする

`gender` / `age` / `species` を固定列にしない。作品ごとに要る属性が違う
（身長・出身・所属・一人称…）ため、固定するとマイグレーションが要る。

**`stat_alloc` の軸と同じ扱い**にする。`AttributeKey` の newtype を作り、`parse` を
唯一のコンストラクタにして正規化・検証・**文字数上限**を型に載せる
（[ADR-0004](0004-session-identification.md) の `CharacterName` と同じ形）。

> **`StatAxis` で「軸を可変にすると尺度が伝わらない」問題が出た**
> （[06-roadmap.md](../06-roadmap.md) マイルストーン5の検証手順）。
> 属性では同じ問題は起きない。値が**数値ではなく語**なので、
> 「猫獣人」はそれ自体で意味が閉じており、上限や刻みの概念が無いため。

### `subject` を持たせる

`memory` と同じく `user` / `character` を持つ。**絶対制約「`memory.subject` を省略しない」の
理由（一人称が混線する）は属性・事実にも同じく効く。**
「年齢: 19」がキャラのものか利用者のものかを落とすと、モデルは取り違える。

### 予算 — **件数に上限を設ける**

属性も事実も**プロンプトの「削れない枠」に載る**（不変属性を削ったらキャラが崩れる）。
絶対制約「削れない枠に載る自由文は必ず上限を持つ型にする」がそのまま効く。

**ただし今回は上限を持つ型だけでは足りない。** `stat_alloc` は1軸あたりの上限は
あるが**件数が無制限**で、「軸を1つ足したら以後のチャットが全部 `BudgetExhausted`」が
原理的に起こりうる状態になっている。テーブルが2つ増えると、この穴が3倍になる。

したがって **`character_attribute` は件数にも上限を設ける**（管理 API 側で拒否する）。
`character_fact` は散文で増えるものなので件数上限ではなく、**予算の枠として扱い、
溢れたら削る**（記憶と同じ扱い）。

**見張り番は既存の `every_field_at_its_limit_still_fits_the_default_budget` を拡張する。**
新しいテーブルをこのテストに含めないと、上限の意味が無くなる。

### 上限の数字と、その出どころ（2026-08-20 / 作業単位 12 の着手時に確定）

**着手前に予算を測った。結論から言うと、いまのままでは1バイトも入らない。**

```
allowance                        7168
現在の削れない枠（全項目が上限）  7054   ← うち Persona 1000 文字 = 3000 バイト
最新の記憶1件                     104
残り                               10 バイト
```

**属性をどれだけ絞っても入らない。** 8件・キー12文字・値20文字まで詰めても約 824 バイト要る。

#### 決定 — **`Persona::MAX_CHARS` を 1000 → 600 に下げる**

**この ADR 自身の主張が根拠。** 「**`base_persona` が本来の用途（口調・振る舞いの散文）に戻る**」——
不変属性が別の場所へ移る以上、**ペルソナが背負う役割は実際に縮む。**

| | 値 |
|---|---|
| `Persona::MAX_CHARS` | **1000 → 600 文字** |
| 属性の件数 | **8 件** |
| `AttributeKey::MAX_CHARS` | **12 文字** |
| `AttributeValue::MAX_CHARS` | **20 文字** |

> **⚠ ここに書いていた見積もり（`+1050` / `−1200` / 「Persona 1000 文字 = 3000 バイト」）は
> すべて誤りだった**（2026-08-20 / 12b の実測で判明。**符号まで逆**）。
>
> | | 足す | 削る | 差 |
> |---|---|---|---|
> | 見積もり（撤回） | ~~+1050~~ | ~~−1200~~ | ~~−150~~ |
> | **実測** | **+1260** | **−1600** | **+340** |
>
> **原因は数え方。** ここでは日本語1文字を **3 バイト**で数えたが、
> **見張り番は最悪ケースをアストラル面（1文字 4 バイト）で測る。**
> **上限が「文字数」で定義されている以上、バイト数の最悪は 4 倍である。**
>
> **残りは 10 バイト → 350 バイトに広がった。** 実測値は
> `every_field_at_its_limit_still_fits_the_default_budget` 側が正。**ここに写さない。**

**この節の役割は「どこから捻出するか」を決めることであって、金額を持つことではない。**

#### **足りなかったら、動かすのはペルソナの側**

**属性の上限は後から下げられない。** 書き込みと**読み出しの両方**の検証に使うので、
下げると保存済みの行が読めなくなる（`StatAxis::MAX_CHARS` と同じ事情）。
**調整の余地はペルソナ側にしか無い**ので、**属性の数字を先に固定する。**

> **ADR-0012 の「足りないときに上限を削る方向へ反応しないこと」に触れる判断である。**
> **違うのは、削る理由が「役割が縮んだから」であって「場所が無いから」ではない点。**
> **この区別は言い訳になりやすい。** 実際にペルソナから属性へ移せる記述
> （性別・年齢・種族・一人称）が無い運用では、**これは単なる削減である。**

#### ペルソナを下げる影響

**600 文字を超える既存行は読めなくなる**（`CharacterEntry::Unreadable`）。
**`PATCH` で直せる**（0012a 以降。それ以前は直せなかった）。

**着手時点の影響はゼロ**（実測）: `scripts/characters.sample.json` は **79 / 55 文字**、
作業 DB のキャラクターは 0 件。

> **⚠ ここに「237 / 165 文字」と書いていたのは誤り**（2026-08-20 に訂正）。**あれはバイト数だった。**
> `grep` で JSON から値を切り出して数えたが、**JSON の中では日本語が `\uXXXX` で書かれている**ので、
> 数えていたのは**エスケープ列の文字数**だった。**測り方が測定を歪めた**形で、
> **CLAUDE.md「測定は読んで判断する」を、読まずに数えて踏んだ。**

## 却下した選択肢

- **1テーブルに `kind` フラグを持たせて両方入れる** — `memory` と分ける理由
  （[03-data-model.md](../03-data-model.md)）と同じで、**例外を持つ防御は弱くなる。**
  「キー付きの行だけ画像側から引く」という条件分岐が、辞書引きの外側に増える。
- **`base_persona` に散文で書き続ける** — 背景の 1・2 がそのまま残る。
- **固定列（`gender TEXT, age INTEGER, species TEXT`）** — 型は最も強くなるが、
  属性を1つ足すたびにマイグレーションが要る。**作品ごとに要る属性が違う**ので、
  「全作品の和集合を列にする」形に崩れていく。
- **属性も散文にする（`character_fact` 一本）** — 画像側から引けない。
  背景の 2 を解決しないので、この ADR を書く意味が無くなる。
- **属性を `stat_alloc` に相乗りさせる** — 値が `u32` なので語を入れられない。
  `value` を TEXT に変えると、性格値の `typeof(value) = 'integer'` CHECK を失う。

## 結果

### 得られるもの

- **不変属性を後から直せる。** キャラクターを作り直さずに済む（記憶とセッションが残る）
- **テキスト側と画像側が同じ1つの値を見る。** 二重管理が消える
- `base_persona` が本来の用途（口調・振る舞いの散文）に戻る

### 諦めたもの / 前提

- **テーブルが2つ増える。** 管理 API も2系統になる
- **属性の件数に上限が付く。** 「とりあえず全部属性にする」使い方はできない。
  これは予算を守るための意図的な制約
- **辞書に無い属性値は画像に反映されない。** 静かに無視される。
  **無視した件数はログに残すこと**（`ValidTag` の破棄率と同じ構造）

### 実装上の注意

- **`memory` の SQL 走査テストは「テーブル名 `memory`」の許可リスト**なので、
  新テーブルは自動的に対象外になる。ただし
  **`memory` を含む名前のテーブルを作らないこと**（部分一致で誤検出・誤放免が起きる）
- **属性は「# 記憶」節に載せない。** 既存の決定
  （[03-data-model.md](../03-data-model.md)「`prompt` は両方を読んで同じ『# 記憶』節に載せる」）は
  **`character_fact`（散文）についてのもので、属性には適用しない。**
  属性は削れない枠、記憶は溢れたら削る枠であり、**同じ節に置くと予算の扱いが分岐する。**
- **`character_fact` を「# 記憶」節に混ぜる場合、節の説明文を直すこと。**
  現在の `MEMORY_NOTE` は「過去の会話から抽出した事実の記録です。」で、
  **人が書いた設定に対しては端的に偽**になる。混ぜる判断自体は既存決定のまま維持してよいが、
  説明文を放置すると「モデルから見れば区別の必要は無い」という前提が崩れる
- 空の `value` を持つ属性は**行ごと落とす**（「性格値 0 の軸を落とす」と同じ理由。
  `種族: ` と書くとモデルが欠落を演技する）

## `character_fact` は作らない（2026-08-22 / 12b の実測を受けた判断）

**この ADR の2テーブルのうち、`character_attribute` だけを実装した。**
**`character_fact` は当面作らない。** 設計の理由（画像側から引けるかで分ける）は**そのまま生きている**——
**作らないのは「まだ要らない」からであって、「分ける判断が間違っていた」からではない。**

### 根拠

1. **`base_persona` を使い切っていない。** 測定に使ったペルソナは
   **600 文字のうち 30 文字ほど**（「喫茶店で働いている。常連客とよく世間話をする。」）。
   実測で出た捏造——**店長として働いている**（実際はアルバイト）、
   **勤続が十年から十五年へドリフト**——は、
   **「アルバイトである。店長ではない。十年勤務。」と書けば済む可能性が高い。**
   **テーブルを足す前に、書ける場所が9割空いている。**
2. **固有の役目がまだ実務になっていない。** 2テーブルに分けた理由は
   **「画像側（フェーズ3）から引けるかどうか」の1点だけ**で、**フェーズ3は始まっていない。**
3. **`memory` と同じ節に並ぶ判断が、前提ごと揺らいだ。**
   [03-data-model.md](../03-data-model.md) は
   **「`prompt` は `character_fact` と `memory` を同じ『# 記憶』節に載せる。
   モデルから見れば区別の必要は無い」**と既に決めている。
   **その判断は `memory` が信頼できる前提で書かれた。**
   いま抽出は**誤った事実を書く**（[ADR-0021](0021-memory-extraction-format.md) の実測——
   店を経営している / 猫を犬と取り違える）。
   **人が書いた正しい事実を、誤った記憶と区別なく並べると、正しい方が埋もれる。**
   **区別を付けるなら、それは新しい設計判断**であり、
   **抽出の誤り率を下げる前に決めると手探りになる。**

### 再検討の引き金（**どれか1つで足りる**）

- **`base_persona` の 600 文字が実際に足りなくなったとき。**
- **事実を1件ずつ編集・削除したい**という運用要求が出たとき
  （散文の塊は部分編集ができない。これは `base_persona` に無い性質）。
- **フェーズ3に入り、属性と事実の切り分けが実務になったとき。**
- **抽出の誤りを「人が書いた正しい事実」で打ち消したくなったとき**
  —— ただしその時は**権威の区別をどう見せるか**を先に決めること。

> **⚠ 引き金を書かない「保留」は永久に続く。** だからここに書いた。
