# ADR-0040: 画面の見た目は Tailwind で組む。ただしトークンは1箇所、色は2つ

- 状態: **採用**（2026-09-08 / 利用者が「入れる方向で」と決め、`D-10` を閉じた `ab364f4` の直後に採用）
- 日付: 2026-09-08
- 関連: [ADR-0031](0031-front-end-stack.md)（**FE のスタック。「依存を最小に」と決めた回。この ADR はそれを1つ覆す**）/
  [ADR-0036](0036-the-range-of-machines-is-a-constraint.md)（**動く環境の幅** —— 書体を外から取らない理由の側）/
  作業単位 `D-10`（**トークンを1箇所に置いた回。この ADR はその成果を捨てない**）

---

## 背景 —— **手数の正体は CSS を書くことではなかった**

`D-10`（2026-09-08）で、この家に初めて CSS ファイルが置かれた。**生の 16 進 52 → 0、規則 91 → 27。**
**利用者が「Tailwind を検討したほうがよいのでは」と提起した**のは、その手数を見てである。

**⚠ 手数を分けると、CSS そのものは 276 行にすぎない。** 掛かったのは ——
**走査（生の 16 進が残っていないか）とその植えたソースの対照 31 本／変異 16 本と `_noguard`／
レビューが見つけた4件の是正。** **つまり大半は「守っているか」の検証で、これはこの家が選んだ費用である。**

**Tailwind を入れてもその費用は消えない。** テーマが唯一の源泉であること、任意値が漏れていないことを、
同じように見張る必要がある。**⚠ 「Tailwind にすれば検証が減る」と読まないこと。**

**それでも入れる理由は、次の2つの作業単位にある:**

| 作業単位 | いま | Tailwind なら |
|---|---|---|
| **`D-11`** 暗い配色・レスポンシブ・a11y | **9 部品ぶんの `@media` と `prefers-color-scheme` を手で書き分ける** | `dark:` / `md:` の変位で、書き分けが消える |
| **`D-12`** 情報設計の作り直し（**新しいマークアップを書く**） | 部品ごとに `<style>` を書き起こす | ユーティリティで組む |

**`D-10`（マークアップを触らない回）には効かなかった。** Tailwind はマークアップに書く道具なので、
あの制約と正面衝突する。**効くのは、マークアップを書く回から。**

---

## 決定

### 1. **Tailwind v4 を `@tailwindcss/vite` で入れる**

**依存は1つ**（`@tailwindcss/vite`。`tailwindcss` はその依存として入る）。**ビルド時だけ。実行時のコードは増えない。**
**Svelte 5 ＋ Vite 8 と共存する**（Svelte の scoped `<style>` はそのまま残る）。

**⚠ ADR-0031 §却下した選択肢 が「依存を最小に」と決めている。** **この ADR はそれを1つ覆す。**
**覆す理由は上の表**（`D-11` / `D-12` の手数）で、**`D-10` の手数ではない。**

### 2. **`@theme` が唯一の源泉。`D-10` の 15 個のトークンをそこへ移す**

**Tailwind v4 の `@theme` は、カスタムプロパティを持つ CSS ファイルそのもの**である。
**`D-10` が `app.css` に置いた `:root { --read: … }` は、`@theme { --color-read: … }` にそのまま移る。**

| `D-10`（`app.css`） | この ADR（`@theme`） | 生えるユーティリティ |
|---|---|---|
| `--paper` / `--paper2` / `--paper3` | `--color-paper` / `--color-paper-2` / `--color-paper-3` | `bg-paper` … |
| `--ink` / `--ink2` / `--muted` | `--color-ink` / `--color-ink-2` / `--color-muted` | `text-ink` … |
| `--rule` / `--rule2` | `--color-rule` / `--color-rule-2` | `border-rule` … |
| `--read` / `--readbg` | `--color-read` / `--color-read-bg` | `text-read` / `bg-read-bg` |
| `--warn` / `--warnbg` | `--color-warn` / `--color-warn-bg` | `text-warn` / `bg-warn-bg` |
| `--mincho` / `--sans` / `--mono` | `--font-mincho` / `--font-sans` / `--font-mono` | `font-mincho` … |

**⚠ 名前が変わる。** `D-10` の走査（`design-tokens.test.ts`）は **`TOKEN_NAMES` を直書き**している
（`16b` の是正 —— 実装から作らない）。**移す回に、その一覧を意図的に書き換える。** **黙って動かない。**

**⚠ 値は変えない。** **`D-10` の是正で、司令塔の「同じ彩度・同じ明度」という断定が偽だと分かった**
（`--read` は L 0.50、`--warn` は L 0.56。暖色は同じ彩度なら少し明るくしないと紙の上で沈む）。
**値は読めているので、そのまま。**

### 3. **既定のパレットを消す。色は2つのまま**

**Tailwind は既定で数百色を持つ**（`text-red-500` …）。**この家の決めは「accent は2つだけ。色は意味を持つときだけ」。**
**両立しない。** **`@theme { --color-*: initial; }` で既定のパレットを丸ごと消し、`@theme` に定義した色だけを生やす。**

**⚠ これは「作法」ではなく「構造」で守る形である** —— **`text-red-500` は存在しないクラスになる。**
**⚠ ただし任意値 `text-[#b00020]` / `text-[oklch(…)]` は残る。** これは次で止める。

### 4. **任意値を走査で止める。`@apply` は使わない**

- **`[#…]` / `[oklch(…)]` / `[rgb(…)]` を `web/src/**` と `web/index.html` から走査で弾く**
  （**`D-10` の走査を1行広げる**。植えたソースの対照も同じ形で足す）。
- **`@apply` は使わない。** **ユーティリティを CSS に戻す道具で、「規則が CSS に散る」という
  `D-10` が消した状態を作り直す。** v4 自身が非推奨としている。
- **Svelte の scoped `<style>` は残してよい** —— **部品固有で、ユーティリティで書けないもの**
  （`grid-template-columns` の特定の並び、疑似要素）**に限る。** **色・字・間隔は `<style>` に書かない**
  （トークンを直接 `var()` で引く形も、ユーティリティがある限りは使わない）。

### 5. **いつ入れるか —— `D-11` の入口。`D-10` は取り込まない**

**`D-10` は閉じる。** その成果（トークンが1箇所・生の 16 進ゼロ・`.dialogue` の明朝）はそのまま資産になる。
**`D-11` の最初の作業単位で、この ADR の 1〜4 を1回で入れる**（Tailwind 導入 ＋ `@theme` への移動 ＋ パレット消去 ＋ 走査の拡張）。
~~**そのうえで `dark:` / `md:` を使って `D-11` の本体へ。**~~
> **⚠ 訂正**（2026-09-08 / `D-11b` を出す前に司令塔が気づいた）。**`dark:` は使わない。**
> **暗い配色は `prefers-color-scheme` の中で `:root` の `--color-*` を上書きする形で出す** ——
> **v4 のユーティリティは `var(--color-…)` を参照するので、1箇所の上書きで `bg-paper` にも `text-warn` にも効く。**
> **`dark:` を部品ごとに書く形は、「トークンは1箇所」（決定2）の反対を作る**（暗い側の決定がマークアップの全箇所に散る）。
> **`md:` はマークアップを書く回（`D-12`）のもの。** `D-11b` はマークアップを触らないので、狭い幅は `app.css` の `@media` で書く。
> **この ADR が「変位で書き分けが消える」と書いたのは、`md:` については `D-12` で、`dark:` については成り立たない。**

## 理由

### 却下した選択肢

- **手書きの CSS を続ける** —— **`D-10` の 27 規則までは手で持てる。** しかし `D-11` で `@media` を9部品ぶん、
  `D-12` で新しいマークアップを部品ごとに書き起こすのは、**同じ判断を9回書く**形になる。
  **利用者の感覚（「細々で手数が掛かっている」）は、そこに向いている。**
- **Tailwind を入れて既定のパレットも残す** —— **「色は意味を持つときだけ」が作法でしかなくなる。**
  `text-red-500` が書けるなら、いつか書かれる。**構造で消せるものを作法に任せない**（`0012b` の教訓）。
- **`@apply` で `D-10` の規則を温存する** —— **消した「規則が CSS に散る」形を作り直す。** 却下。
- **UnoCSS / Open Props / CSS-in-JS** —— **利用者に Tailwind の経験がある**（Astro）。
  **道具の学習費用がゼロの側を採る。** 他の道具が劣るからではない。
- **`D-10` を捨てて Tailwind で書き直す** —— **`D-10` はほぼ閉じている。**
  **しかもその成果（トークン 15 個）は `@theme` にそのまま移る。** 捨てるものが無い。

### なぜ「依存を最小に」を覆せるのか

**ADR-0031 の「最小」は、実行時の依存と、FE をビルドしないと動かない形を避けるためだった。**
**Tailwind はビルド時だけで、実行時のコードを増やさない。** **`web/dist` を配る形は変わらない。**
~~**むしろ使ったユーティリティしか出さないので、CSS は縮みうる。**~~
> **⚠ 外れた**（`D-11a` の実測 / 2026-09-08）。**3.53 → 5.92 kB。** テーマ層と互換ブロックが必ず載り、
> **さらに走査がソース中の語を誤検出してユーティリティを 5 本（398 B）入れた。** 縮むのはマークアップを書き換えた後の話で、
> **導入の回では増える。** 依存を覆す根拠は「実行時のコードを増やさない」だけに戻す。

## 結果

### 得られるもの

- **`D-11` の暗い配色とレスポンシブが、書き分けではなく変位になる。**
- **`D-12` の新しいマークアップを、ユーティリティで組める。**
- ~~**「色は2つだけ」が構造になる**（既定のパレットが存在しない）。~~
  **⚠ 言い過ぎだった**（2026-09-08 / `D-11a` のレビュアーが実測）。**構造で消えたのは既定のパレット（`text-red-500`）だけ。**
  **任意値は走査でしか止まらず、その走査は決定4の綴り（`[#` / `[oklch(` / `[rgb(` / `[hsl(`）しか見ない** ——
  **色の名前も `lab()` も素通りする。** **正しくは「既定のパレットは構造で消え、任意値は作法と走査で押さえる。走査には穴がある（`B-44`）」。**
  **→ `B-44` で塞いだ**（2026-09-17）。**走査は「値の綴り」ではなく「色を運ぶ置き場所」（接頭辞の直後と `[color:…]`）で止める。**
  **⚠ それでも「構造」ではなく走査である。** 一覧は v4 の語彙に追いつく必要がある（`border-s` は書いた日から抜けていた）。

### 諦めたもの / 前提

- **⚠ 依存が1つ増える。** ADR-0031 の決めを1つ覆した記録が、この ADR である。
- **⚠ `D-10` の走査は書き換えが要る** —— `TOKEN_NAMES` の一覧、`@theme` の読み方、任意値の検出。
  **走査本体を変えるなら、植えたソースの対照も一緒に**（`15b` / `E-3`）。
- **⚠ 意味の色に「掛かり」が無い問題は、この ADR では解けない。**
  `D-10` のレビューで分かったとおり、**「上流が答えませんでした」のセルにはクラスが無い**ので色が当たらない。
  **Tailwind でも同じ** —— ユーティリティはマークアップに書くもので、**マークアップを触るのは `D-12`。**
- **⚠ `import` の1行が無防備な形も、この ADR では解けない**（`D-10` のレビュー / `main.ts` の取り込みを消しても 768 全緑）。
  **`D-10` の是正で見張り番を置く。Tailwind は関係ない。**
- **⚠ `vite.config.ts` に `plugins` が増える。** **Rust 側の走査 `the_default_web_dir_is_where_vite_actually_builds` は
  `outDir` の綴りを正規表現で読んでいる**ので、**`outDir: "dist"` の形を崩さないこと。**

## 追記: 土台の規則を層に入れ、部品の見た目を要素の既定に置く（2026-11-02 / D-12b-1・Issue origin#88）

**前半は書き換えていない。** `app.css` の層の注記が「`D-12` でユーティリティを部品に当て始めるとき、ここが地雷になる。
そのとき、この下を `@layer base` / `components` へ入れるかを決めること」と書いていた。その決定をここに置く。

### 決定

1. **`app.css` の規則を層に入れる。要素の既定は `@layer base`、クラスは `@layer components`。**
   **`@layer` の外の通常宣言は、どの層の通常宣言よりも強い**（CSS Cascading L5）。無層のままだと、
   **土台の `a { color: var(--color-read) }` が当たる帯のリンクに `text-ink-2` を書いても効かない。**
   D-12b-1 の帯はまさにその形（リンクに字の色のユーティリティを当てる）で、ここを決めないと最初の1本から効かなかった。
   **層は2つだけ使う**（`utilities` へ入れると、ユーティリティと同じ層で特異性の勝負になり、層に入れた意味が消える）。
2. **層の外に残すのは、主題（`@theme`）と暗い側の差し替え（`@media (prefers-color-scheme: dark)` の `:root`）だけ。**
   主題は Tailwind が自分で `theme` の層へ入れる。暗い側の差し替えはカスタムプロパティしか宣言しないので、
   ユーティリティと同じプロパティを取り合わない（主題の層より強ければよく、層の外はその条件を必ず満たす）。
   狭い幅の規則（`@media (max-width: 40rem)`）は、狙う選択子がどれも要素なので `base` の中に置いた。
3. **ボタン・文字の入力欄・チェックボックス・フォーカスの輪は、要素の既定（`base`）に置く。**
   **既存の画面の `<button>` / `<input>` / `<textarea>` / `<select>` は、マークアップを書き換えずに新しい見た目になる**
   （各画面の中身の書き直しは後の単位。ここで要素の既定が揃えば全画面が一度に変わる）。
   **チェックボックス・ラジオを包む `label` は `label:has(> input[type=…])` で横並びにする**
   （土台の `form label` の格子に入ると、箱が 10rem の列に置かれて文言から離れる。着手前からの崩れをレビューの是正で直した）。
   **区別が要るものだけをクラスにする** —— 主ボタン（`.primary`）とカード（`.card`）。
   部品の層は土台より必ず勝ち、ユーティリティには必ず負ける（画面ごとの余白などを上書きできる）。
   **⚠ `@apply` は使っていない**（決定4のまま）。クラスの中身は D-10 と同じくトークンを `var()` で引く素の宣言である。
4. **帯（`App.svelte`）はユーティリティで書き、`<style>` を外した**（決定4 —— 色・字・間隔は `<style>` に書かない）。
   **いまいる画面の印（太字・下の read の線）は `aria-[current=page]:` の変位で書く。**
   読み上げに告げる属性と目に見える印が、同じ1つの条件から出る。
   **タブの横並びと、狭い幅での折り返しだけは土台の `nav` に置いた**（`web/tests/colour-scheme.test.ts` の見張り番は
   「狭い幅の規則が狙う選択子は、広い幅の素の規則にも在ること」を見ている。その意味を変えずに保つため）。

### 実測で分かったこと

- **色を混ぜる関数（`color-mix`）は、配布 CSS に生の 16 進を書き足す。** 主ボタンにポインタを重ねたときの地を
  `color-mix(in oklch, var(--color-read) 85%, var(--color-ink))` で書いたら、`pnpm build` が
  `.primary:hover:not(:disabled){background:#285c8d}` を代替として前に置いた（その関数を読めない閲覧器のため。
  **値は明るい側のトークンで計算済みなので、暗い側でも明るい側の色が出る**）。
  **`web/src` に生の 16 進が無いことを守っても、配られるものには在る**形で、D-11a が `source(none)` で塞いだのと同じ向きの穴である。
  **ポインタを重ねたときは明るさだけを落とす（`filter: brightness(0.9)`）形に替え、色を混ぜる綴りを走査で止めた**
  （`web/tests/base-layers.test.ts`）。
- **着手前の構文の読み手（`web/tests/support/design-tokens.ts` の `cssRules`）は、`@media` の中の規則が宣言を
  2つ以上持つと、囲みの名前を選択子にした偽の規則を1件足していた**（実ファイルでは暗い側の `:root` が 11 個の偽の宣言を生んでいた）。
  どの帳簿もその鍵を使っていなかったので表に出なかった。直したうえで、層を `within`（囲み）とは別の欄（`layer`）で読むようにした ——
  層へ移しただけで帳簿の鍵が全部外れないように。

### 守れていないこと

- **部品の `<style>` は層の外に在る**（Svelte は層を付けない）。**部品の側の規則は、土台にもユーティリティにも勝つ。**
  決定4が「部品固有でユーティリティで書けないものに限る」とした `<style>` に、同じ要素の色・間隔を書くと、
  その要素にはユーティリティが効かない。
- **既定の打ち消し（preflight）は、この回も入れていない。** 入れると `h1` の大きさ・箇条書きの点などが、
  代わりのユーティリティを書かないまま消える。部品の見た目は閲覧器の既定を上書きする形で置いた。
- **帯の、いまいない画面のタブの線は `border-transparent` で、配布 CSS では `#0000` になる。** 色ではない（完全に透明）ので残した。
- **単体テストは Tailwind を走らせない。** 配布 CSS の中で `@layer base{…}` がユーティリティより前に並ぶこと、
  `aria-[current=page]:border-read` が生えたことは、D-12b-1 で `pnpm build` の出力を読んで確かめただけで、見張り番ではない。
