# ADR-0013: トークン予算は「上界・実測・答え合わせ・停止」の4層で守る

- 状態: **採用**
- 日付: 2026-08-14

> **2026-10-22 追記:** この ADR の「上流が前方から黙って切り捨てる」は、**LM Studio で測った壊れ方**である。**llama は、窓を超えたプロンプトを 400 `exceed_context_size_error` で断る**（エラーとして見える）。ただし、プロンプトは窓に入り「プロンプト ＋ 応答の上限」が窓を超えるときは断られず、**応答が黙って短くなる**（`finish_reason=length`）。[ADR-0052](0052-count-with-the-upstream-tokenizer.md) §測った結果 M5。

## 背景

**現在の「予算」はモデルの制限ではなく、単位も違う自前の数値である。**

```rust
TokenBudget::DEFAULT_CONTEXT_TOKENS = 8_192   // ハードコード
DEFAULT_RESPONSE_TOKENS             = 1_024
prompt_allowance                    = 7_168
estimate_tokens(text) == text.len()           // UTF-8 の「バイト数」
```

この 8192 は**上流に一度も問い合わせていない。** 実測すると:

```
GET http://127.0.0.1:1234/api/v0/models      （LM Studio 独自 API）
  "max_context_length":    262144
  "loaded_context_length":  16384   ← 実際に使える量
```

**半分しか使っていなかった。** しかも数える単位が実トークンではなくバイト数で、
校正テスト（`tests/prompt_estimate_calibration.rs`）の実測では日本語で 3.0〜3.7 倍の過大計上。
結果として `7168` は**日本語で実トークン約 2,400 相当**しかない。

「削れない枠の余白が 24 バイト」「日本語 2,400 文字で `BudgetExhausted`」
「[ADR-0003](0003-full-memory-injection.md) の警告が常時点灯」は、**すべてこの1つの原因から出ていた。**

### 設計要件 — 現在のモデルに依存しないこと

> モデル自身のバージョンアップや環境変化のたびに変なボトルネック
> （ないしオーバーフロー）が起きていたら事故。

`loaded_context_length` を起動時に1回引くだけでは、この要件を満たさない。

| 変化 | 起こること |
|---|---|
| 稼働中にモデルを別のコンテキスト長で再ロード | 想定が実際より**大きい**まま。上流が前方から黙って切り捨てる（LM Studio。llama は 400 で断る —— 2026-10-22 追記、ADR-0052 §測った結果 M5） |
| 上流を vLLM / Ollama に差し替え | `/api/v0/models` が無く既定値へ落ちる。**ボトルネックが復活** |
| チャットテンプレートの重いモデルへ変更 | `MESSAGE_OVERHEAD_TOKENS`（実測3・計上8）が**過小**になる |

**どれも「エラーも出ず応答も返る」形で壊れる。**

## 決定

**4層に分ける。上の層が破れても下の層が気付けるようにする。**

| 層 | 内容 | モデル依存 |
|---|---|---|
| 1 | **見積もりは上界を保つ**（UTF-8 バイト数） | **しない** |
| 2 | **コンテキスト長は推測せず取りに行く** | する（取得手段が） |
| 3 | **毎回の応答で答え合わせする**（`usage.prompt_tokens`） | **しない**（真値を使う） |
| 4 | **溢れたら止まる**（`BudgetExhausted`） | しない |

### 第1層 — 上界性はモデルに依存しない

`estimate_tokens(text) = text.len()`（UTF-8 バイト数）。
**どのトークナイザでも1トークンは入力の1バイト以上を覆う**ので、`バイト数 ≥ トークン数`
はモデルに依らず成立する。**この層はモデルが変わっても正しいまま。**

### 第2層 — 実コンテキスト長を取りに行く

優先順位: **明示設定 → 上流への照会 → 保守的な既定値 ＋ `warn`。**

照会先は LM Studio 独自の `/api/v0/models` の `loaded_context_length`。
~~**OpenAI 互換の `/v1/models` はコンテキスト長を返さない**（実測: `id` と `owned_by` のみ）。~~
照会できない上流では既定値へ落ちる。**遅くなるだけで壊れない。**

> ## ⚠ **上の1文は「LM Studio についての実測」だった**（2026-09-05 に訂正 / 作業単位 G-2）
>
> **`llama-server` の `/v1/models` は答える。** 実測:
>
> ```json
> "meta":{"n_vocab":131072,"n_ctx":8192,"n_ctx_train":262144,"n_params":13506073600}
> ```
>
> **`n_ctx` が実効値、`n_ctx_train` は訓練時の上限。**
> **⚠ 取り違えると本文の予算が 32 倍になる。** 綴りの権威は `src/llm/response.rs` の
> `EFFECTIVE_CONTEXT_FIELD`。**ここに写さない。**
>
> **いまの照会は2段** —— **`/api/v0/models` が 2xx 以外のときだけ `/v1/models` を投げる**
> （**無応答では投げない。起動時の待ちを倍にしないため**）。
> **LM Studio 経路の往復は1回のまま。**
>
> **⚠ 同定は「綴りが一致する行」か「一覧そのものが1件」のときだけ。**
> **`llama-server` の `id` は gguf の絶対パス**なので、設定の綴りとは一致しない。
> **2件以上あって一致が無ければ読まない**（＝落とし所へ落ちる。遅くなるだけで壊れない側）。
> **どちらで決めたかは `identified_by` がログの同じ行に出す。**

### 第3層 — 毎回の応答で答え合わせする（**この設計の核心**）

上流は毎リクエストで `usage.prompt_tokens` を返している。
**これは実際に答えたモデル自身が数えた真値。** 現在は捨てている（`Completion` に項目が無い）。

| 観測 | 意味 | 反応 |
|---|---|---|
| `見積もり < 実トークン` | **第1層の上界が破れた** | **`warn`。静かに進ませない** |
| `実トークン + max_tokens > 想定コンテキスト` | **第2層の想定が実際より大きい**。切り捨てが起きうる | **`warn`** |
| `実 / 見積もり` の比 | どれだけ無駄にしているか | 集計してログ |

**モデルを差し替えても次の1リクエストで分かる。** 起動時の推測に頼りきらない。
背景の表に挙げた3つの変化は、いずれもここで検出される。

#### 訂正（2026-08-15 / 11c-2 の実装で判明）

**上の表の2行目（`実トークン + max_tokens > 想定コンテキスト`）は、
「第2層の想定が実際より大きい」を検出できない。** 実装して初めて分かった。

理由は2つ。

1. **`plan` の不変条件の下では1行目に含まれる。** `plan` は
   `見積もり + response_tokens ≤ context` を保証し、`max_tokens ≤ response_tokens`。
   したがって `実 + max > context` が成立するのは**必ず `実 > 見積もり` のとき**で、
   1行目が先に鳴る。
2. **比べているのが「想定」コンテキストである。** 実コンテキストが 4,096 なのに
   16,384 と想定している状況で、実トークン 5,000・`max_tokens` 1,024 なら
   合計 6,024 < 16,384 で**鳴らない。** そして上流は黙って切り捨てる。
   **検出したかったケースがちょうど検出できない。**

**この行は残す**（`plan` の不変条件が将来崩れたときの二重の網になる）が、
**「稼働中の再ロードを検出できる」という主張は取り下げる。**

したがって、要件のうち検出できるものは次のとおり:

| 変化 | 検出できるか |
|---|---|
| チャットテンプレートが重いモデルへ変更 | **できる**（上界が破れて1行目が鳴る） |
| トークナイザの性質が変わった | **できる**（同上） |
| **稼働中に小さいコンテキストで再ロード** | **できない** |

**残るのは3つ目だけ。** `usage` からは原理的に取れない
（上流が切り捨てた結果の `prompt_tokens` は、こちらの過大な見積もりと区別が付かない）。

**対処は「観測」ではなく「取り直し」の側にある** — 起動時の1回だけでなく、
定期的に、あるいは疑わしい事象（`finish_reason` の異常など）を見たときに
`loaded_context_length` を引き直す。**作業単位 11c-4 として切り出す。**

### 第4層 — 溢れたら止まる

既存の `PromptError::BudgetExhausted`。
**過大見積もりで止まるのは損だが、過小見積もりで黙って切られるより桁違いにマシ。**

## 理由

### 校正比率で見積もりを膨らませない

[06-roadmap.md](../06-roadmap.md) は「校正テストで測った比率で換算する導線が要る」と書いていたが、**採らない。**

| 文字列 | 過大計上 |
|---|---|
| 日本語散文 | 3.67 倍 |
| 英文 | 4.30 倍 |
| UUID | 1.09 倍 |
| `𠮷𩸽𠀋`（アストラル面） | **1.00 倍** |

**最悪ケースが 1.00 倍**なので、比率で膨らませた瞬間に上界が壊れる。
キャラクター名に `𠮷` が1文字入るだけで破れ、**破れたときの症状は
「上流がシステムプロンプトを黙って切り捨てる」**——最も気付けない壊れ方である。

**そして膨らませる必要が無い。** 実コンテキスト長を使うだけで即座に2倍になり、
足りなければ利用者が LM Studio 側で `loaded_context_length` を上げられる
（最大 262,144 = 現状の 32 倍）。**実メモリを払うという正直な操作**に対応する。

> 振り回されていた原因は単位ではなく、**8192 という架空の数字の方**だった。

### 却下した選択肢

- **`n_ctx` を素通しせず比率で換算する** — 上記のとおり上界が壊れる。
- **実トークナイザを積む**（`tokenizers` クレート等）— 正確になるが、
  **モデルごとにトークナイザを取得・同期する必要**が生じ、
  「モデルが変わっても事故らない」要件を**むしろ悪化させる**。
  第3層があれば真値は上流から手に入るので、こちらを持つ理由が無い。
- **起動時の照会だけで済ませる** — 稼働中の再ロードを検出できない。要件を満たさない。
- **毎リクエスト照会する** — 検出はできるが、本文生成のたびに往復が1回増える。
  第3層は**既に受け取っている応答**を読むだけなので、こちらが安い。

## 結果

### 得られるもの

- 実コンテキスト長 16,384 をそのまま使える（**現状の2倍**）。利用者が上げればさらに増える
- **モデル・上流・テンプレートのどれが変わっても、次の1リクエストで気付ける**
- ADR-0003 の「記憶が取り分の半分」判定が実際の値で動くようになる

### 諦めたもの / 前提

- **日本語では依然として実トークンの 3 倍を計上する。** 安全側だが無駄はある。
  無駄の量は第3層が集計するので、**実測してから**次を考える
- 第2層の照会は **LM Studio 独自 API に依存**する。他の上流では既定値に落ちる
- **第3層は非ストリーミング経路から入る。** ストリーミングでは `usage` が
  最終チャンクにしか載らない（載せない実装もある）ので、11a-2b で別途扱う

### 作業単位

- **11c-1** — 第2層。設定と照会でコンテキスト長を取り、`TokenBudget` を作って `chat` まで通す
- **11c-2** — 第3層。`usage` を `Completion` に載せ、毎回の答え合わせと `warn`

**11c-1 だけでは要件を満たさない。** ボトルネックは消えるが、
「モデルが変わっても事故らない」を担保するのは第3層である。
**片方だけ入って忘れられることが最大のリスク**なので、この ADR に両方を書いた。
