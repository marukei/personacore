# ADR-0048: オープンソース化の方針 —— MIT・Apache-2.0・ACCRL の三択、履歴を持たない公開リポジトリ、origin は留保

- 状態: **採用**（2026-09-30 / 利用者が方針を決めた。細部は司令塔）
- 日付: 2026-09-30
- 関連: [ADR-0047](0047-the-api-is-the-product.md)（**API が本体で、他のソフトに組み込んでもらう** —— ライセンスの選択に効く）/
  AI Collective Creativity Respect License（ACCRL）v0.3-PROTOTYPE（利用者自身のライセンス。https://github.com/marukei の下）/
  オープンソース化の検討（2026-09-27〜30。市場調査・リポジトリの監査・ライセンスの比較 —— 会話の記録。結論だけをこの ADR に置く）

## 背景

利用者は「遊べるレベルになった一方、真剣に人格を構築しようとする営みは少ない」として、オープンソース化を検討した（2026-09-27）。

- **市場調査**（エージェントが Web で調べた。数字は司令塔が1件ずつ裏を取ったものではない）: 記憶の抽出・時系列保持・「値が動く」は、既存（SillyTavern の拡張群・Graphiti/Zep・商用の Nomi 等）に部品として在る。**キャラクター自身の性格の軸を、票の累積と閾値で遅く変容させ、中身が見えて測れて再現できる形で、小型のローカルモデルで壊れずに回す**組み合わせは空白に近い。人格の変容そのものへの需要は、記憶ほど明確には観測できなかった（ニッチだが実在する層）。
- **リポジトリの監査**: 全コミットの作者欄に実名と独自ドメインのメールアドレス／絶対パスが約 70 か所／利用者の私的な発言の引用が1か所／`LICENSE` が無い／秘密の値は無い／依存は全部緩いライセンス（MPL-2.0 の `lightningcss` は CSS のビルドの道具で exe には入らない）。

## 決定

### 1. ライセンスは三択: `MIT OR Apache-2.0 OR LicenseRef-ACCRL-0.3`

- 利用者は **ACCRL v0.3 の採用者として誓約する**（ACCRL 第6条）。**誓約は人間だけが行う**（ACCRL 第1条4号）—— AI（Claude）は誓約者として署名しない。採用の表明とその署名は利用者が行い、司令塔は文面を用意するだけ。
- OSI 承認のライセンスが要る使い手（企業・ディストリビューション・組み込む側）は MIT か Apache-2.0 を選べる。**3つとも緩いライセンスで衝突しない**（ACCRL 第13条「他のライセンスとの共存」とも整合）。
- **理由**:
  - ACCRL の第I部は実質的に無条件・撤回不能の緩い許諾で、MIT より緩いくらいである。
  - personacore は実装のほとんどを AI が書き、その経緯を ADR・引き継ぎ・振り分けの記録・コミットの `Co-Authored-By` で残してきた —— ACCRL の協働の透明性（第6・10条、レベル3〜4 相当）を最初から実践している。
  - AI が生成したコードに著作権が成立しない部分があっても、ACCRL は「規範として及ぶ」と正直に扱う（第4条）。MIT / Apache はその部分では空振りするが害は無い。
  - それでも ACCRL だけにしないのは、**OSI 承認が無いと、ADR-0047 の狙い（他のソフトに組み込んでもらう）が法務の確認で止まりうる**から。

### 2. 公開リポジトリは履歴を持たない1つのコミットから始める

- 手順の骨子（公開の作業単位で詳しく決める）:
  1. 今のリポジトリ `marukei/personacore` を **`marukei/personacore-origin`**（非公開）に改名する。
  2. 新しい `marukei/personacore`（公開）を作り、**origin の片付け済みの木を1つのコミットとして**置く。**作者は GitHub の noreply アドレス**（`marukei@users.noreply.github.com`）—— 実名とメールアドレスの問題が消える。ACCRL の採用者も `marukei` の名義で揃う。
  3. **origin に公開側の履歴を結ぶ**: origin で公開側を取り込み、最初の1回だけ `git merge --allow-unrelated-histories -s ours <公開側>/main` で「この木は公開側のこのコミットと同じ」と記録する。以後、公開側のコミットは origin へ普通に取り込める。
- **一部だけ消す（履歴の書き換え）を採らない理由**: 作者欄を直すとコミットの番号が全部変わり、docs のコミット番号への参照はどのみち切れる。手間の割に得るものが無い。
- **透明性との釣り合い**: 履歴を消すと `Co-Authored-By` による AI 協働の記録も公開側から消える。公開側に AI 協働の開示の文書を置き、「約 600 コミットの開発履歴（2026-08-13〜）は非公開の origin にある」と書き、ADR・引き継ぎ・振り分けの記録は公開側に残す（透明性レベル3を保つ）。

### 3. origin は凍結しない（留保）

- 公開の後、**開発は公開側で行い、origin には必要に応じて公開側から取り込む**（利用者の決定）。
- **公開側が軌道に乗ったら、origin を正式に閉じる**（そのとき、閉じることをこの ADR に追記する）。
- origin にだけ在るもの（Issue・Release・コミットの履歴）は origin に残る。公開側の Issue の番号は1から振り直される。

### 4. 公開の前に要る片付け（作業単位 O-1〜O-6 / Issue で開く）

| 単位 | 中身 | 公開と独立か |
|---|---|---|
| **O-1** | **依存の著作権表示を配布物に同梱する**（Rust は依存を exe に静的に組み込むので、MIT / Apache の依存の表示を zip に同梱する必要がある。`cargo-about` 等で `THIRD-PARTY-NOTICES` を生成し `package.ps1` が詰める） | **独立**（配布している以上、公開の有無に関わらず直す） |
| O-2 | ライセンスの文書: `LICENSE-MIT`・`LICENSE-APACHE`・ACCRL の条文と採用の表明（署名は利用者）、`Cargo.toml` / `web/package.json` の `license`、README のライセンスの節、ACCRL 付録A の AI エージェント向けの表示を `CLAUDE.md` に | — |
| O-3 | AI 協働の開示の文書（人間の判断と AI の担当の分担、履歴が origin にあること、透明性レベル） | — |
| O-4 | 個人の情報の片付け: 絶対パス（約 70 か所）・私的な発言の引用・見本のプロファイルの無検閲モデル・テストの入力データのユーザー名 | — |
| O-5 | **Issue の番号の参照を書き換える**（docs・コード・コメントの `#31` 等。公開側では Issue の番号が振り直され、将来の無関係な Issue に自動でリンクされる）。`origin#31` の形にするか番号を外す。**origin の `main` で行う**（公開側と origin の文面を揃え、取り込みを楽にするため） | — |
| O-6 | 公開の手順の実行（改名・新しいリポジトリ・1コミット・origin への結び付け・公開側の設定 —— Issue のテンプレート、説明文、トピック） | — |

## 却下した選択肢

- **ACCRL だけ** —— 思想は体現できるが、OSI 承認が無く、組み込む側が止まりうる（ADR-0047 の狙いを削る）。
- **MIT / Apache に誓約の表明だけを添える（ACCRL を採用しない）** —— 最も広く使われるが、ACCRL を実際に使ったソフトウェアの実例にならない。ACCRL 自身は「敬意の継承はどのライセンスの下でも行える」と言っているので不可能ではない。
- **AGPL-3.0** —— 改造品にソースの公開を強制できるが、**ACCRL の中核の「非強制」と正面から矛盾する**（違反すれば許諾が終わる —— 強制の部品そのもの）。2026-09-27 の検討で挙げた候補を取り下げた。
- **履歴を一部だけ消す（`git filter-repo` で作者欄とパスを書き換える）** —— §2。
- **origin を公開と同時に凍結する** —— 利用者が留保を選んだ（§3）。

## 結果

- personacore は、ACCRL を採用したソフトウェアの最初の実例になりうる。同時に、OSI 承認のライセンスで組み込める。
- **⚠ Issue の番号の参照（O-5）は件数が多い**（2026-09-30 に `#` ＋数字の綴りを粗く数えて 571 行。誤検出を含む）。機械的に置き換え、置き換えた後に `#` ＋数字が残っていないことの見張り番を置く。
- **⚠ 公開側で最初の Issue を開くと、`#1` から番号が振られる。** O-5 を終えるまで公開しない。
- 依存の著作権表示（O-1）は、公開と関係なく、配っている zip の欠けを埋める。

## 追記（2026-11-06）: O-6 の手順と、公開側の保護

O-6 に入るにあたり、利用者が次のことを決めた。手順の細部と実行の記録は origin#53 に置き、ここには決定と、その理由になった事実だけを置く。

### 前提になった事実（2026-11-06 に確かめた）

- **GitHub では、PR を作った人は自分の PR を承認できない。** 利用者もエージェントも `marukei` として push するので、承認を必須にすると、どちらの作業も承認待ちで止まる。そこで利用者（リポジトリの管理者）をバイパスの対象にする。
- **ルールセットのバイパスには「常に許可」と「PR のときだけ許可」がある。** 後者では、バイパスできる人も PR を開く必要があり、承認なしでマージできる。main への直接の push はできない。
- **§2 の手順3の後、origin の main は公開側の main の子孫になる。** そのため、origin のクローンから公開側へ main を push すると早送りで通り、非公開の履歴（作者欄は実名）が丸ごと公開される。ブランチの push なら、名前が何であれ通る。
- **改名すると、いまの `marukei/personacore` という URL は改名後の origin へ転送される。ただし、同じ名前で新しい公開側を作った時点で転送は止まり、その URL は公開側を指すようになる。** いまのチェックアウトの remote をそのままにしておくと、その後の push は公開側へ行く。
- **公開側では作者欄を `marukei` と noreply のアドレスにする。** そのため `tests/hashed_spellings.rs` の `user.name` の旗は、公開側では `marukei` を探し、`LICENSE` などに当たって赤になる。
- **キーワードによる Issue の自動クローズは、コミットが既定のブランチに入ったときに働く。** 公開側のコミットの本文に `Closes #N` があると、origin へ取り込んだ時点で、origin の同じ番号の Issue を閉じうる（O-5 のレビューからの申し送り）。

### 決定

1. **公開側の main はルールセットで守る。**
   - PR を必須にし、承認は1件とする。新しい push があったら承認を取り消し、最後の push への承認と、会話の解決を求める。
   - force push と削除を禁じる。マージの方法として、マージコミットと squash を許す（rebase は許さない）。
   - **バイパスはリポジトリの管理者（利用者）に「PR のときだけ許可」で与える。** 利用者の PR も承認なしでマージできる。ほかの人の PR は、利用者の承認が無いとマージできない。直接の push は、利用者にもできない。誤って origin の履歴を push しても、main では止まる。
   - リリースのタグ（`v*`）も削除と付け替えを禁じる。
   - 必須のチェック（CI）は、CI の作業単位（O-13）が入った後に足す。
2. **エージェントが開いた PR は、エージェントがマージしてよい**（いまの pr-cycle と同じ。マージは管理者のバイパスを使う）。
3. **公開の後の開発は公開側を新しく clone したチェックアウトで行う。** そのチェックアウトの手元の履歴は、公開側の1コミットから始まる。
   - いまのチェックアウトは origin 専用にする。remote を `personacore-origin` へ向け直し、公開側の remote には取り込み用の fetch だけを許す（push の URL を通らない値にしておく）。
   - **公開側を作る前に、remote を向け直す。** 改名と向け直しの間には、ほかの作業を挟まない。
4. **実名の検査は追加の綴りのファイルへ移す。**
   - `user.name` の旗は利用者レベルの cargo の設定から外す。
   - 実名の綴り（ローマ字と漢字）は、利用者がどの Git の作業ツリーにも入っていないファイルに書き、`PERSONACORE_PRIVATE_SPELLINGS` で指す。司令塔とエージェントはその綴りを書かない。
5. **Issue の参照の書き方を2つのリポジトリで揃える。**
   - 追跡ファイルでは、origin の Issue は `origin#N`、公開側の Issue は `marukei/personacore#N` と書く（どちらも `tests/issue_references.rs` の走査に当たらない）。
   - コミットの本文の閉じるキーワードは、`Closes marukei/personacore#N` と完全な形で書く。こう書けば、origin へ取り込んでも origin の Issue を閉じない。PR の本文では `Closes #N` と書いてよい（PR の結び付きで閉じ、マージコミットの本文には写らないように設定する）。
   - 取り込む前に、取り込むコミットの本文に、完全な形でない閉じるキーワードが無いことを確かめる。
6. **origin に開いている Issue は、着手するときに公開側で開き直す**（本文に `origin#N` を書く）。一度に全部は移さない。
7. **`NOTICE-AI-COLLABORATION.md` の数は公開の直前に数え直す。** 司令塔が新しい文面を用意し、人間創作者が再承認してから、`tests/license.rs` の指紋を付け替える。
8. **ADR に残した、第三者の製品を特定しうる描写と、決定を引いた形の引用は、このまま公開する**（O-11 で受容したもの。製品の名前そのものは無い）。
9. **公開側には次の文書と設定を置く。**
   - `SECURITY.md`: 脆弱性は GitHub の非公開の報告（Private vulnerability reporting）で受ける。ホストの検査や、起動するコマンドを保存・実行する口があるので、公開の Issue での報告を避けてもらう。
   - `CONTRIBUTING.md`: PR の流れ、AI に関与させたときの記録（ACCRL）、テストの回し方、利用者の承認が要ること。
   - Issue と PR のテンプレート。
   - CI（GitHub Actions）: 公開の後に、公開側の最初の作業単位（O-13）として入れる。公開側なら Actions の実行時間を気にせずに済み、PR の流れの最初の通し稽古にもなる。
   - 秘密の値の走査と push protection、Dependabot のアラートを有効にする。Actions は外部の人の PR から走るワークフローに毎回承認を求め、`GITHUB_TOKEN` を読み取りだけにする。Wiki と Projects は使わない。
   - アカウントの設定（メールアドレスを非公開にし、それを含む push を止める）は、利用者が行う。

## 追記（2026-11-06）: O-6 を実行した記録

O-6 を実行し、2026-11-06 に公開した。手順の細部は origin#53 にある。ここには実行してから分かったことと、そのとき利用者が決めたことを置く。

- **公開した木は origin の 96f9600 の木である。** 公開側の最初のコミット f5a33ab は、その木を親なしの1コミットにしたもので（`git commit-tree`）、木のハッシュは一致する。origin の 799e8c9 で、公開側と `-s ours` で結んだ。
- **noreply のアドレスは、`marukei@users.noreply.github.com` と、ID 付きの形のどちらでもアカウントに結び付く。** 公開の前に、origin の使い捨てのブランチで確かめた。追跡ファイルと作者は前者に揃える。
- **利用者はアカウントの「メールアドレスを非公開にする」「それを含む push を止める」を有効にした。** この設定の説明によれば、非公開のアドレスで作ったコミットは origin へも push できない（試してはいない）。そのため、origin のチェックアウトの作者も `marukei` と noreply にした。
- **ルールセットは、非公開のうちに入れることができた。** 秘密の値の走査・push protection・非公開の脆弱性報告・外部の人の PR への承認は、公開してから入れた。管理者からの `main` への直接の push が止まることは、実際に push して確かめた。
- **GitHub にマージさせたコミットの作者名は、アカウントのプロフィールの名前になる**（メールアドレスは ID 付きの noreply）。最初の PR のマージ（33f12fc）で分かった。その名前はプロフィールで公開しているので、利用者はマージコミットに載ることを受け入れた（33f12fc も書き換えない）。
- **マージコミットの題名には「(#番号)」が付く。** origin へ取り込むと、origin の同じ番号の Issue に「参照された」記録が付く（最初の取り込みで確かめた）。「(#番号)」は閉じるキーワードではないので、Issue は閉じないはずである（このとき参照された Issue はもともと閉じていたので、閉じないことは観測していない）。害が無いので、そのままにする。
- O-13（CI）は公開側の最初の Issue と PR として入れた（https://github.com/marukei/personacore/issues/1 、https://github.com/marukei/personacore/pull/2 ）。Windows のランナーで Rust は約 24 分、web は約 2 分かかる。**マージの後に、CI の2つのジョブをルールセット `main` の必須のチェックにした**（決定1）。
- **管理者のバイパスは必須のチェックも飛ばす**（GitHub の仕様による。ルールセットのバイパスはルールセット単位で効き、ルールごとには外せない。観測はしていない）。そのため、`--admin` でマージする前に、CI の緑を確かめる（`CLAUDE.md` §4「公開の後の運用」）。
