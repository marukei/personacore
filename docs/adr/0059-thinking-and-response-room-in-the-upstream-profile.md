## 背景

### 思考を切ったままでは、長い会話で返答が縮んで戻らない（2026-11-11〜12 の測定）

第三者の推論サーバ（Qwen3.8-Flash-Next を VRAM・RAM・SSD に分けて載せるもの。以下「その推論サーバ」）に IQ3_S を載せ、中継を通さずローカルで直結した。ADR-0058 の `repeat_penalty 1.0` を書いても、利用者の会話は 10 ターン前後から縮み、台詞が数文字になった。

測定は隔離した exe（A-16 入り）とその推論サーバの間に測定の中継を置き、本文の要求だけを書き換えて行った。台本は2種類ある。利用者の会話の発言 27 本をそのまま流したもの（後半の発言は、元の会話の崩れに合わせて短い）と、利用者役の LLM に毎回 100〜200 文字で返すよう指示したもの（台本の偏りを除く。実際の文字数は 64〜400、多くは 100〜230）である。

ADR-0058 の背景では、`repeat_penalty 1.0` で崩れは 0/4 だった。その測定の台本は、私たちが用意した当たり障りのない発言の 10 ターンで、崩れの引き金になる会話の中身を含んでいなかったと見ている（同じ構成の 20 ターンでも崩れなかった。利用者の会話の発言を流すと崩れた）。

| 腕（利用者役の LLM・27 ターン） | 本文の文字数 | 本文が空 | 上限で切れた | 1ターン（中央値 / 最大） |
|---|---|---|---|---|
| 思考なし（`reasoning_effort: none`、いまの personacore） | 290 → 3〜65 に崩れる（後半10ターンの平均 約 30 文字） | 0 | 0 | 7 / 15 秒 |
| 思考あり（`low`、上限 2048） | 391〜1050 | 0 | 0 | 33 / 54 秒 |
| 思考あり（2回目） | 280〜762、最後だけ 2007 | 0 | 0 | 28 / 85 秒 |

- **崩れは台本の偏りによるものではなかった。** 利用者役が後半も長く返し続けても（思考なしの腕で 66〜193 文字）、思考なしでは崩れた。
- **思考を入れると、崩れは一度も起きなかった**（利用者の発言をそのまま流した台本でも、2回とも同じ）。
- **温度の交絡は切り分けた。** 本文の要求は `temperature` を送らない。直結の構成では、`none` の腕にはその推論サーバのモデルカードの思考オフの既定（`temperature 0.7`）が、`low` の腕には思考ありの既定（`1.0`）が当たっていたと見ている（marukei/personacore#32）。そこで、思考なしのまま本文の要求に `temperature 1.0` を明示した腕を回した（ほかのサンプラは personacore が明示で送るので、思考ありの腕との違いは思考の有無と返答の上限だけ。上限はこの腕が 1024、思考ありの腕が 2048 だが、この腕の生成は最大 247 トークンで上限に届いていない）。**それでも崩れた**（本文 402 → 後半はほぼ 4〜5 文字、後半10ターンの平均 約 12 文字、50 文字未満が 27 中 12 回）。**崩れを止めていたのは温度ではなく思考である。**
- 思考の量（生成数から本文の文字数 × 0.6 を引いた粗い見積もり）は、最大で約 500〜900 トークンだった。いまの返答の上限 1024 では足りない。思考だけ・上限 2048 の2回目の腕では、生成の合計が 1332 と 1744 の回があり、上限が 1024 なら 27 ターン中 2 回切れていた。上限 1024 で強い念押しと組み合わせた腕では、27 ターン中 12 回が上限で切れた（本文が途中で切れた）。同じ腕で本文が空の回が 2 回あったが、どちらも上限に届かずに終わった回（下の「思考だけで答えを終えた」回）である。**上限で思考が切れて本文が空になった回は、記録に一度も無い。**
- 念押し（最新の発言の直前に書き方の注意を差し込む）と組み合わせると、上限に当たらなくても**思考だけで答えを終えて本文が空になる回**が出た（強い念押しで 27 中 6 回、弱い念押しで 1 回）。思考だけの腕では 108 ターンで 0 回。
- **空の本文を1回だけ引き直すと、3回とも2回目で本文が返った。** 測定の中継で、本文が空のときだけ同じ要求を送り直した（強い念押しの腕で 0 → 860 文字・0 → 822 文字、弱い念押しの腕で 0 → 461 文字）。最終的に空の回は 0 になり、1ターンの中央値はほとんど変わらなかった（弱い念押し＋引き直しで、中央値 26 秒・最大 46 秒、本文 233〜517 文字）。測定の中継は2回とも丸ごと受けてから片方を返したので、§決定3 の「同じ応答の続きとして流す」形そのものは測っていない。
- **その推論サーバは思考を別欄で返す。** 思考ありのストリーミングの応答を1本記録したところ、差分の欄は `role`・`reasoning_content`・`content` で、先頭から 35 チャンクが `reasoning_content`、36 チャンク目から `content` だった。本文の中に `<think>` は無かった（記録は測定の置き場所の `wire/thinking-stream-low.sse`）。

### いまの決定と仕組み

- ADR-0038 §決定3 は `reasoning_effort: "none"` を全経路で常に送ると決めた。理由は「personacore は `content` を読み、裏方の予算はトークン単位で小さい（抽出は 320）ので、思考させたくない」ことだった。経路で変わる値（裏方の `temperature`）は、全経路で1つの `RequestPolicy` には載せず、要求の側（`ChatRequest`）に置いた（ADR-0038 §決定2 の A-7d）。
- 返答の上限は `TokenBudget::DEFAULT_RESPONSE_TOKENS = 1024`（`src/prompt/budget.rs`）で、予算は `窓 − 余白` で組む。応答の余白を定数とする ADR の明示の決定は無い。ただし ADR-0013・0052・0054 はこの値を前提にしている。コードの doc は、据え置く理由として「余白まで設定で動かすと『応答が途中で切れる』設定が作れてしまう」（`src/server/config.rs`）と「生成用に何を残すかは上流の都合ではない」（`src/server/context.rs`）を挙げている。
- 返答が空のときの扱い: 本文から漏れた思考を剥がした（ADR-0053）あとが空なら、`ParseOutcome::Empty` として正当な往復で保存し、画面は「応答が空でした。」を出す。引き直しは無い。`raw_content` は生の出力を丸ごと保つ（ADR-0053 §決定3）ので、思考が本文に漏れて閉じないまま終わった回の `raw_content` は空ではない。思考を別欄（`reasoning_content`）で返す上流の回では空文字になる。personacore は別欄を読まない。
- ストリーミングでは、中継（`src/server/relay.rs`）が上流の本文の差分を剥がさずにその場で利用者へ流し、`finish_reason` 付きのチャンクもその場で流す。剥がすのは保存と読み手の側だけである。

## 決定

### 1. 本文の面に `reasoning_effort` を書ける。値は本文の経路が要求に載せる

`upstreams.json` の `main` 面の `sampling` に `reasoning_effort` を書ける。

```json
"main": {
  "endpoint": "http://127.0.0.1:8080",
  "model": "IQ3_S",
  "sampling": { "repeat_penalty": 1.0, "reasoning_effort": "low" },
  "response_tokens": 2048
}
```

- **書ける値はまず `"none"`（既定）と `"low"` だけ。** 測ったのはこの2つだけで、ほかの値は上流によって 500 になる（ADR-0038 §決定3 の G-6 の表で `minimal` / `high`）。測ってから追記で足す。知らない値は読み込みで名前を挙げて止める。
- **値の出どころは要求の側に置き、本文の経路だけが載せる。** 本文の経路は `ChatRequest` に `reasoning_effort` の上書き（任意）を持たせる。`wire_request` は、それがあるときだけ `RequestPolicy` の `reasoning_effort` を要求ごとに置き換えて送る。欄の位置は今と同じ（`RequestPolicy` を `flatten` で載せる位置）なので、書かない面の要求のバイト列は変わらず、重複キーにもならない。裏方の経路は上書きを持たないので、常に `"none"` を送る。
  - 値の出どころを要求の側に置く点は、裏方の `temperature`（ADR-0038 §決定2 の A-7d）と同じ。ただし `temperature` は要求の最上位の欄で、`reasoning_effort` は `RequestPolicy` の欄なので、載せ方は違う。
  - `RequestPolicy::PERSONACORE` の doc の「全経路で同じ1つ。経路ごとに変えないこと」は、「既定は全経路で同じ1つ。本文の経路だけが `reasoning_effort` を要求ごとに上書きする」と改める。
  - `sub` 面の無い構成では、裏方のクライアントは本文の設定の複製になる。それでも面の設定（`Sampling`）には載せないので、裏方へは写らない。**ADR-0058 §決定1 の `sub` 面の規則は、この欄には当てはまらない。**
- **裏方（抽出・変容・約束・軸）は常に `"none"` を送る。** ADR-0038 §決定3 の理由（裏方の予算がトークン単位で小さい）は、裏方には今もそのまま当てはまる。
- **`sub` 面に `reasoning_effort` を書いたら、読み込みで止める。** 文面は「知らない鍵」と区別して、「裏方の面には書けない」と言う（`SAMPLING_KEYS` は面で共通の一覧なので、面ごとの判定を足す）。
- **書かない面の要求のバイト列は、今と1バイトも変えない。**
- 面の上では `sampling` に置くが、ADR-0058 §決定1 が `reasoning_effort` を「サンプラではないので対象外」としていた点は改める。面の `sampling` は「要求ごとに personacore が明示で送る値」の入れ物と読み替える。内部の入れ先は上のとおり経路の側である。
- 封（ADR-0052）は本文の要求と同じ値を載せた本文で作る（チャットテンプレートの出力が変わるため）。
- 効き方は上流による。デスクトップアプリの中継越しの構成では、その推論サーバが `reasoning_effort` を思考の判定に使わなかった、という記録がある（ADR-0038 §決定2 の 2026-11-01 の訂正）。一方、直結の構成では `"low"` で思考が入ったことを測った。起動時と切り替え時の送る値のログ（ADR-0058 §決定3）に `reasoning_effort` を加える。ログが言うのは送った値で、効いたかどうかは言わない。

### 2. 本文の面に `response_tokens`（本文の返答の上限）を書ける

`main` 面に任意の欄 `response_tokens`（整数）を書ける。本文の要求の応答の余白（`TokenBudget` の `response_tokens`）と、本文の要求の `max_tokens` の天井になる。書かなければ今の 1024。

- **上限は「長さを決めるつまみ」ではなく「壊れないための天井」として選ぶ。** 低すぎると本文が途中で切れる（観測した）。思考が上限まで続けば本文が空になる（推論。観測していない）。高い側は、その回が遅くなるだけで、窓が大きければ予算もほとんど減らない。思考を入れる面では高めに置く。2026-11-12 の測定では、2048 は思考だけの腕と念押しのある腕（強い・弱い）では一度も切れなかった。ただし、強い念押しに「必ず本文を書く」を重ねた腕では 27 中 7 回切れた。長さを整えるのは文体の側（キャラクターの出力形式の指示・A-20 の念押し）の仕事で、上限ではない。
- **裏方の上限は変えない**（抽出 320 など。裏方は思考しないので足りる）。`sub` 面に `response_tokens` を書いたら、読み込みで止める（文面は §決定1 と同じく区別する）。
- **読み込みの検証:**
  - 0 は止める。
  - 明示の窓（面の `context_tokens`、無ければ `PERSONACORE_CONTEXT_TOKENS`。ADR-0054 §決定2 の順位）があり、`response_tokens` がそれ以上なら止める（予算が組めない）。面の `context_tokens` の「余白以下は止める」検証（ADR-0054 §決定1）は、その面の `response_tokens` に追従させる。
- **照会した窓（明示が無い面）が `response_tokens` 以下だったとき:** 読み込みの時点では分からないので、予算を組む時点で判定する。そのときは既定の 1024 に戻して `warn` を1本出し、止めない。窓に収まらない上限のまま本文を送れなくなるより、短い上限で送るほうを選ぶ（思考を入れた面では、本文が切れうる）。5分ごとの照会し直し（ADR-0020）で窓が変われば、同じ判定をやり直す（窓が十分なら面の値に戻る）。
- 起動時と切り替え時のログ（ADR-0058 §決定3）に、本文の面の `response_tokens`（と、既定に戻したかどうか）を加える。
- コードの doc が据え置く理由に挙げていた「応答が途中で切れる設定が作れてしまう」は、上の検証（窓以上は止める）と、上限を高めに置く指針で受ける。doc はこの決定を参照する形に直す。

### 3. 本文が空なら、1回だけ引き直す

- **何を空とみなすか:** 本文から漏れた思考を剥がした（ADR-0053）あとの文字列が、空か空白だけのとき。`ParseOutcome::Empty` には、ほかに「空の `「」` だけ」「宙に浮いた強調の印だけ」も含まれるが、それらは上流が文字を返した回なので、引き直しの対象にしない。
- **上流も面も選ばない**（思考を入れた面に限らない）。思考を切った面では空はほとんど起きないので、実害の小さい安全網になる。つまみにしない。
- **2回目も空なら、今と同じく空として保存する**（画面は「応答が空でした。」）。回数は1回で固定し、それ以上は引き直さない。
- **非ストリーミング:** 保存の前に引き直す。閉じない思考を剥がして空になった回も対象にする。
- **ストリーミング:** 上流の終わり（`finish_reason`）が届いた時点で、それまでに積み上げた本文の差分を剥がした結果が空（空白だけを含む）で、かつ**閉じない思考ではない**とき、引き直す。思考を別欄で返す上流で本文が空のまま終わった回（その推論サーバはこの形）と、本文の中で閉じた思考だけを返した回が当たる。その回は `finish_reason` 付きのチャンクと終わりの印を利用者へ流さずに保留して引き直し、2回目の本文を同じ応答の続きとして流す。すでに流れた差分（役割だけのチャンク、`content: ""` の空の差分、空白、閉じた思考）は、積み上げた本文の先頭に残るが、剥がしとパースで落ちるので2回目の本文を損なわない。
  - **本文に思考が漏れて閉じないまま終わった回は、ストリーミングでは引き直さない。** 続きとして2回目を流すと、積み上げた本文は「閉じない思考＋2回目の本文」になり、ADR-0053 §決定2 の規則で2回目の本文まで思考として捨てられる。今と同じく空として保存する。
  - 中継は引き直しのために、そのターンで使った上流のクライアントの写しと、同じ要求を持つ。途中で上流が切り替わっても、引き直しは1回目と同じ上流へ送る。
  - 中継のモジュール doc の「溜め込まない」は、`finish_reason` と終わりの印に限って保留する、と改める。2回目を待つ間の沈黙は、番人に「最初のトークンの後の沈黙」として報告される。その意味が「喋り出してから止まった」から広がるので、doc を直す。
- **2回目の要求が失敗したとき**（接続の失敗・上流のエラー）: 引き直しが無かったときと同じ結果にする。1回目の空を空として保存し、ストリーミングでは保留していた `finish_reason` と終わりの印を流す。失敗はログに出す。
- **使用量:** 答え合わせ（ADR-0013 第3層）と封の清算（ADR-0052）は、2回目の `usage` で1回だけ行う（プロンプトは同じ）。1回目の生成トークン数は分解の行の欄に出す。
- **保存:** `raw_content` には採用した回（2回目）の生の出力を保存する。捨てた1回目の生の出力は保存しない。その長さと「閉じない思考だったか」を、分解の行（`応答を分解しました`）に欄として出す。引き直した回数の欄も足す（0 の回も出す）。
  - `raw_content` はパースの失敗を調べる唯一の手段である（CLAUDE.md の絶対制約）。採用した回の生の出力は今と同じく丸ごと保つので、その目的は損なわない。捨てた回は空か閉じない思考で、パースの対象になる本文を持たない。
- **測っていないこと:** 上限で思考が切れて空になった回は、同じ `max_tokens` で送り直すと、また切れうる。引き直しを測った腕では、上限に当たった回が 0 だった。

### 4. ADR-0036 §決定3 の条件に当てはめる

| 条件 | `reasoning_effort`（本文の面） | `response_tokens`（本文の面） |
|---|---|---|
| 根拠が無い | 思考が要るかはモデルと上流で変わる（同じ推論サーバで、思考なしでは `temperature 1.0` を明示しても崩れ、思考ありでは崩れなかった。思考しない Ministral は思考なしで崩れなかった） | 必要な余白は、モデルの思考の量と言語（文字あたりのトークン数）で変わる |
| 外すと破壊的 | 切ったままでは会話が台詞数文字に縮んで戻らない | **低い側だけ**: 本文が切れる・空になる。高い側は遅くなるだけ（ADR-0036 §決定2 の「緩い天井」の性質を持つ） |
| 導出も観測もできない | 上流は「思考を入れるべきか」を答えない | 上流は「思考に何トークン使うか」を前もって答えない。A-19 の校正で候補を示せる見込みはあるが、それも「示す」までで、決めるのは利用者 |

**足すつまみは2つ**（本文の面の `reasoning_effort` と `response_tokens`）。`App::bind` を通る見張り番を、それぞれについて置く。腕の組み方は ADR-0058 §決定4 に倣い、少なくとも次を観測する。

| 腕 | 観測すること |
|---|---|
| 1 | 本文の面に書いた `reasoning_effort` が、本文の要求に載る |
| 2 | 裏方の要求は、本文の面に `"low"` を書いても `"none"` のまま（`sub` 面が無い構成で写さない。経路と値の帰属を見る） |
| 3 | 本文の面に書いた `response_tokens` が、本文の要求の `max_tokens` と予算に効き、裏方の上限は変わらない（クライアントが `max_tokens` を送らない固定データで見る） |
| 4 | 切り替えで、宛先とモデルが同じで `reasoning_effort` / `response_tokens` だけが違うプロファイルへも追従する（予算の余白も追従する） |
| 5 | 空の本文は1回だけ引き直され、2回目も空なら空として保存される。空でない回は1往復だけ。`reasoning_effort` を書いていない面でも引き直す。ストリーミングと非ストリーミングの両方。ストリーミングで閉じない思考が流れた回は引き直さず、閉じた思考だけ・空白だけの回は引き直す。2回目が失敗したら1回目の空を保存する |
| 6 | 照会した窓が `response_tokens` 以下のとき、既定に戻して `warn` を出す（実行時の分岐） |

### 5. 画面の編集は ADR-0058 §決定6 と同じ形にする

画面から保存しても、書いた `reasoning_effort` と `response_tokens` を消さない（~~依頼の型には足さない。画面の欄は marukei/personacore#36 で追いつく~~ → 依頼の型に任意の欄として足し、省けば残す。[ADR-0060](0060-sampling-and-response-room-on-the-screen.md) §決定2）。`response_tokens` は `FACE_KEYS` の 10 個目にし、~~doc の例外の節に加える（`EDITABLE_FACE_KEYS` からは除く）~~ → 画面が欄を持つので例外から外す（ADR-0060 §決定4）。画面の写し（`web/src/lib/upstreamProfiles.ts` の `FACE_KEYS`）と、仕様書の閉じた綴りも、同じ作業単位で変える。API の版は ADR-0047 に照らして決める。

### 6. この ADR で決めないこと

- **念押し**（最新の発言の直前に書き方の注意を差し込む）: marukei/personacore#38。文面の強さで、長さと空の本文の回数が大きく変わった。文面は固定の定数にせず、キャラクターの側で選べる形を検討する。強い念押し（長めの返答）も、読み物として楽しむ使い方の選択肢として除外しない。
  - **念押しに「考え終えたら、必ず本文を書くこと」を足す案は、空の本文の守りとしては当てにしない。文面の候補としては残す。** 2026-11-12 の測定（各1回）:
    - 強い念押しに足すと、空の本文は 6 回から 0 回になった。一方で思考と本文が膨らみ、27 ターン中 7 回が上限 2048 で切れ、1ターンが最大 122 秒になった。
    - 弱い念押しに足すと、空の本文は 1 回から 2 回で減らず、本文は短くなった（平均 355 → 226 文字）。
    - 効き方が組み合わせる文面で向きまで変わる。空の本文の守りは §決定3 の引き直しに任せる（弱い念押し＋引き直しで、空は 0）。
- **校正**（プロファイルを足したときに、思考の量などを測って候補を示す）: marukei/personacore#37。
- **本文の温度**: marukei/personacore#32。思考ありの腕は上流の既定（1.0 と見ている）で走った。温度は崩れの原因ではなかった（背景）が、思考ありのときの値を personacore が持つかは決めていない。
- `"low"` 以外の `reasoning_effort` の値。

### 追記（2026-11-12 / A-18a の実装とレビューで決めたこと）

- **照会した窓にも下限 1024 を残す。** 照会した窓が 1024 以下なら、面の `response_tokens` が 1024 未満でも、今までどおり予算として採らない（読み込み中の上流が小さな窓を答える回への備え）。1024 を超えて `response_tokens` 以下なら、§決定2 のとおり既定の 1024 に戻して `warn` を出す。明示の窓の検証（下限 1024 を据え置く）と揃える。
- **窓が分からないとき（照会が答えず、落とし所の窓 8192 で組むとき）は、面の `response_tokens` を使わず既定の 1024 にする。** §決定2 の「高い側は遅くなるだけ」は、窓が分かっている前提だった。窓が分からないまま大きな余白を取ると、プロンプトの予算が縮み、削れない枠が収まらずに `BudgetExhausted` になりうる（壊れる側）。照会で窓が分かれば面の値に戻る。送る値のログは、既定に戻した理由（窓の不足 / 窓が分からない）を区別して言う。
- **裏方の要求は1つの口で作る**（`ChatRequest::background`。温度は裏方の値、思考の量は上書きしない）。5つの裏方の経路が個別に `reasoning_effort` を書く形をやめ、取り違えを表現しにくくした。
- **切り替えの送る値の行は、外の上流を照会し直した後に言う。** 差し替えた直後は窓がまだ分からないので、そこで言うと常に既定の 1024 になる。起こす上流（まだ載っていない）は `window_unknown` と言う。起こす上流で起動したときの「窓がまだ分からない」は、照会の失敗ではないので `warn` ではなく `info` で言う。

### 追記（2026-11-12 / A-18b の実装とレビューで決めたこと）

- **中継で2回目を開いた後に上流が壊れた回は、途中で上流が壊れた回と同じく error で終え、何も保存しない（1回目の空も保存しない）。** §決定3 の「2回目の要求が失敗したとき」は、2回目を開けなかった回（接続の失敗・上流のエラー）に限る。2回目の差分がすでに下流へ流れた後では、引き直しが無かった形には戻せない。
- **保留した終わりのチャンクに本文の差分が載っていれば、引き直すときも捨てず、`finish_reason` を外して2回目の前に流す。** 閉じタグ（`</think>`）が終わりのチャンクに載る上流では、このチャンクを捨てると下流の本文が「閉じない思考＋2回目」になり、使い手の側で2回目まで思考として扱われる。2回目を開けなかったときは、保留したチャンクをそのまま流す（引き直しが無かったときと同じ並び）。
- **引き直すかは最初の `finish_reason` 付きのチャンクを受けた時点で決め、2回目を開くのは1回目の上流が尽きた後にする。** 終わりのチャンクの後に来る使用量だけのチャンクまで読み切り、捨てた回の生成トークン数を取るため。
- **`finish_reason` 付きのチャンクを2本以上送る上流では、後のチャンクを保留に足す**（差分は連結し、`finish_reason` は後のものを使う）。上書きすると先の差分が下流にも `raw_content` にも残らない。下流へは1件にまとめて流れるので、引き直しが無い回でもチャンクの件数は上流と一致しない。
- **保留の後に `finish_reason` の無い本文の差分が届く上流は想定しない。** 届いた差分は受けたそばに流して蓄積する（落とさない）が、保留した差分より前に並ぶ。引き直すかどうかは、最初の `finish_reason` 付きのチャンクで決めたまま変わらない。
- **`finish_reason` が来ないまま尽きた空の回は、中継では引き直さない**（§決定3 の文言どおり）。非ストリーミングは `finish_reason` を見ずに引き直すので、経路によって扱いが違う。
- **2回目を開く待ちも番人が報告する**（`after_first_token` が `true` の沈黙として）。1回目を開く待ちには、今までどおり番人を巻かない（ADR-0019 §2）。
- **分解の行の欄は次の5つ。** `empty_retries`（2回目を送った回数。2回目が失敗した回も 1）、`empty_retry_failed`（2回目を開けなかったか）、`discarded_reply_chars`（捨てた回の生の出力の文字数。思考を含む。思考を別欄で返す上流では 0 になりうるので、量は生成数の欄 `discarded_completion_tokens` で見る）、`discarded_reply_unclosed`、`discarded_completion_tokens`。`empty_retry_failed` を §決定3 の欄に足したのは、1回目が空文字で使用量も無い回では、「2回目が失敗した」と「捨てた長さが 0」を他の欄で区別できないため。
- **「途中で上流が切り替わっても、引き直しは1回目と同じ上流へ送る」（§決定3）には、まだ見張り番が無い。** 作り方の上では守られている（1回目と同じクライアントの写しを渡す）。marukei/personacore#43。

## 理由

### 却下した選択肢

- **値を面の設定（`Sampling` / `RequestPolicy`）に載せる。** `sub` 面の無い構成では、裏方のクライアントが本文の設定の複製なので、本文の思考が裏方へ写る。抽出の予算 320 を思考で使い切り、本文の出ない経路（抽出・変容）が気づかないうちに空になる（ADR-0038 §決定3 が避けた失敗）。
- **思考を入れた面だけ、固定の大きめの余白にする（つまみにしない）。** 固定値では足りない。2048 でも、強い念押しと重ねた腕では 27 中 7 回切れた。必要な余白はモデルの思考の量・言語・文体で変わる。
- **返答の上限を一律に上げる（既定を 2048 にする）。** 思考しない上流の振る舞いと予算まで変わる。書かない面のバイト列を変えない約束（ADR-0058）を破る。
- **思考の量に上限をかける上流固有の欄（例: 推論サーバの思考予算の欄）を送る。** 欄の綴りが上流ごとに違う方言で、ADR-0058 §決定5 が足さないと決めた範囲に入る。
- **空の本文を引き直さず、画面で利用者に引き直させる。** 思考を入れた面では空が一定の頻度で起き、そのたびに利用者が操作することになる。

念押しだけで直す案は却下していない。利用者の発言をそのまま流した台本では、念押しだけで崩れの勢いが止まった（後半10ターンの平均が 36 から 138 トークンへ）。ただ、その台本には偏りがあり、利用者役の LLM の台本では念押しだけの腕を測っていない。marukei/personacore#38 で扱う。

## 結果

### 得られるもの

- 思考を入れた上流で、長い会話の返答が縮まない構成を、プロファイル1つで選べる。書かない面の要求のバイト列は変わらない（空の本文の回に限り、要求が2回になる）。
- 思考に使うトークンを見込んだ上限を、上流ごとに置ける。
- 本文が空の回を、利用者に見せずに1回は取り返せる（ストリーミングでは、本文に漏れた思考が閉じないまま終わった回を除く）。

### 諦めるもの・新しく負うもの

- 「全経路で思考を切る」という単純さを、本文の経路について失う。測定を並べるときは、本文の面の `reasoning_effort` と `response_tokens` を見る（起動時のログで分かる）。
- 思考を入れた面では、1ターンが思考の分だけ遅くなりうる（測定では中央値 28〜33 秒、最大 54〜85 秒）。
- 空の本文を引き直した回は、待ちが約2倍になる。
- 中継が `finish_reason` と終わりの印を保留する分だけ、ストリーミングの作りが複雑になる。
- つまみが2つ増え、見張り番の腕が6本以上要る。
- 応答の余白を定数とする前提（ADR-0013・0052・0054）に、面ごとの値という例外が入る。

### この ADR が答えていないこと

- 各上流に合う `response_tokens` の値そのもの。2048 は、その推論サーバ＋Qwen3.8 IQ3_S＋日本語で、念押しの無い腕と念押しのある腕（強い・弱い）では切れなかった値であって、最適値ではない。
- 思考を入れたときの、長い会話での長さの伸び（思考だけの腕で、後半へ向けて伸びる傾向があった）。文体の側（marukei/personacore#38）で扱う。
- 上限で思考が切れて空になった回を引き直したときの振る舞い（§決定3）。
- 思考の別欄（`reasoning_content`）は今も読まない。本文に混じった思考は ADR-0053 が剥がす。
