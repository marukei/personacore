## 背景 —— **13d の成果が、そのまま罠になる**

[ADR-0023](0023-three-layer-recall.md) の 13d で分かったこと:

> **身元の事実を属性に書くと、捏造が止まる。**
> 名指しした事実は**ドリフトゼロ**、欠陥率 14.9% → 9.1%。**コードは1行も変えていない。**

**属性は「削れない枠」に載る**ので、モデルは毎ターン必ず読む。だから効く。
**そして同じ理由で、古くなっても毎ターン必ず読む。**

**属性を書き換える道は、いま管理 API しかない。**
会話で「引っ越しました」「転職しました」と言われても、**属性は古い事実を固定し続ける。**
**しかも固定する力は 13d が測ったとおり強い** ——
記憶に新しい事実が入っても、**削れない枠に載っている古い属性の方が勝つ形になる。**

> **これは「属性が効かない」という故障ではない。効きすぎる場所に、更新の経路が無い。**

[ADR-0009](0009-character-attributes-and-facts.md) は属性を**不変属性**と呼び、
「編集・削除が**できる必要がある**／履歴に価値が**無い**」と書いた。
**前半は正しい。後半をこの ADR が覆す**（理由は §決定5）。

## 診断 —— **性格の変容とも、記憶の修復とも違う**

| | 性格の変容（16） | 記憶の修復（[ADR-0022](0022-repairing-memories-without-deleting.md)） | **属性の変容（17）** |
|---|---|---|---|
| 何が変わるか | 数値（0〜尺度） | 壊れた行の訂正版 | **語**（`猫獣人` / `僕`） |
| 誤りの重さ | **軽い。**次のターンで戻せる | 重いが、**直す導線がこれ** | **重い。**削れない枠に毎ターン載る |
| 頻度 | 毎ターン | 事故のとき | **稀。**しかし起きる |
| 判定の難しさ | **測定器そのものが偏っている**（ADR-0027） | 判定しない（人が書く） | **偏りは未測定** |
| 直せるか | 値なので上書きできる | 訂正版を書く | **置き換え API がある。直せる** |

**3つの違いが設計を決める:**

1. **稀なので、毎ターン尋ねる必要が無い。** 性格の変容は毎ターン尋ねるが、
   属性は「引っ越した」「歳を取った」のような**出来事に紐づく。**
2. **重いので、自動では適用しない。** 削れない枠に嘘が1行入ると、
   **そのキャラクターの以後の全ターンがそれを前提に喋る。**
3. **語なので、閾値で薄めるという手が使えない。**
   数値なら「累積が費用に届くまで待つ」で誤りを吸収できるが、
   **`僕` か `私` かに中間は無い。**

## 決定（提案）

### 1. **提案の入力は「記憶」であって、生の会話ではない**

**属性の見直しは、`memory` のうち前回の見直し以降に増えた行だけを読む。**
本文も、生の LLM 出力も読まない。

**これが「抽出に直接書かせない」を、規約ではなく構造で満たす形である。**

| | |
|---|---|
| **記憶はすでに検証済み** | 主語（`subject`）が付き、上限を持つ型を通り、分類も入っている |
| **記憶は消えない** | 提案の根拠が後から必ず引ける（`memory` に削除は無い） |
| **層がひとつ増える** | 抽出が間違えた行は**記憶として残るだけ**で、属性には届かない |

> **⚠ 抽出の誤りが2段になる。** 記憶が誤っていれば提案も誤る。
> **だから §決定6 の確認が要る。** 誤りを止めるのではなく、**人の目に映るところまで運ぶ。**

### 2. **走らせるのは毎ターンではなく、溜まってから**

**新しい記憶が N 件たまったときに1回だけ走らせる。**

理由は3つ:

- **稀な出来事を毎ターン尋ねると、「何も無い」を毎ターン言わせることになる。**
  **ADR-0027 の診断がそのまま効く** ——
  **モデルは「なし」を言わない。** 328 ターン試して一度も出なかった。
  **尋ねる回数を減らすことが、そのまま偽陽性を減らす。**
- **サブ LLM の呼び出しは、いま1ターンあたり2回**（抽出・変容）。
  **3回目を毎ターン足すと裏方が本文より重くなる。**
- **利用者が最初に提案した形そのものである** ——
  「一定以上のターン数や要素数が溜まったら変動させる」。
  **性格の変容ではこれが累積の設計になった。属性では発火の間隔になる。**

> **`N` は定数にして設定で振れる形にする**（ADR-0027 §決定8 と同じ）。
> **測っていない値を既定に据えるので、動かせない形にしないこと。**

### 3. **提案できるのは、保存済みのキーの値だけ**

**新しいキーを作れるのは人だけ。** サブ LLM は
**`character_attribute` にすでにあるキーの、値の差し替えしか提案できない。**

**ADR-0024 §1 の許可リストと同じ形**である（変容は保存済みの軸名との完全一致しか受けない）。

- **件数の上限（8件）を、提案が食い潰せない。**
- **架空のキー（`好きな色`）が削れない枠に静かに増えない。**
- **「このキャラクターについて何を追跡するか」は設定の決定であって、会話の結果ではない。**

> **⚠ これは制限であって、防御ではない。**
> **キーが既存でも、値は自由文である。** 値の側は `AttributeValue::parse`（20 文字上限）だけが門番。
> **`ValidTag` のような「表現できなくする」形にはなっていない**
> ——ここでそう書かない（[CLAUDE.md](../../CLAUDE.md) の `0012b` の教訓）。

### 4. **`subject` は提案に載せさせない。元の記憶から取る**

**サブ LLM は「どのキーを、どの値に」だけを答える。「誰の属性か」は答えない。**
**主語は、根拠にした `memory` の行の `subject` をそのまま使う。**

**理由は、この基盤で最も繰り返し出ている穴だからである** ——

> **抜けるのはいつも「帰属」。**「載っているか」ではなく「どれのものか」。
> [ADR-0021](0021-memory-extraction-format.md) は**主語の取り違えを 6% 実測**している。

**`年齢: 19` がキャラクターのものか利用者のものかを取り違えると、
モデルは利用者の年齢で自分を演じる。** そして**属性は削れない枠なので、毎ターン効く。**

**モデルに主語を言わせなければ、モデルは主語を間違えられない。**

> **見張り番の形まで決めておく:** 同じ提案を、**主語だけが違う2つの記憶**に紐づけて通し、
> **`subject` が入れ替わること**を1本で固定する。
> **`assert_ne!` では防げない**（値は全部違っていて、組み合わせだけが間違っている）。

### 5. **履歴は追記だけ。`character_attribute` は導出。書き込み経路は1つ**

**新しいテーブル（`attribute_revision` 相当）を足し、変更を追記する。**
**`character_attribute` の中身は、その追記の「いま」の投影**とする。

**[ADR-0009](0009-character-attributes-and-facts.md) の「履歴に価値が無い」を、ここで覆す。**
**理由は、書き手が人だけではなくなるから:**

> **属性が静かに変わると、気付く手段が無い。**
> [ADR-0024](0024-stat-drift.md) §9 が決めたとおり**変容は本文に出ない**ので、
> **利用者から見ると「なんか前と違う」以上のことが分からない。**
> **性格の変容には票の表がある。属性にも同じものが要る。**

**書き込みは1つの関数に閉じ、`INSERT`（履歴）と置き換え（現在）を
1つのトランザクションで行う**（[ADR-0022](0022-repairing-memories-without-deleting.md) §決定3 と同じ）。

> **⚠ `BEGIN IMMEDIATE` を使うこと。** 現在の行を読んでから書くので、
> **素の `BEGIN` では `SQLITE_BUSY_SNAPSHOT` になり `busy_timeout` では救えない**
> （`0011a-2` で 315 回中 298 回失敗した実測）。

> **⚠ 2箇所に同じ事実が載る形になる。**
> [CLAUDE.md](../../CLAUDE.md)「**同じ発見を2箇所に書かない。片方を直しても、もう片方が黙って古びる。**」
> **投影を導出のままに保つ見張り番が要る** ——
> `src/**` を走査して、**この関数以外から `character_attribute` へ書く文が無いこと**を見る
> （`store::memory` の `no_statement_updates_or_deletes_a_memory` と同じ形）。
>
> **⚠ その走査の対照テストは自己成就する**（`15b` の実測）。
> **走査本体を「引数でソースを受け取る形」にして、植えたソースと実ファイルの
> 両方を同じ判定に通すこと。**

### 6. **確認の導線 —— 一覧・採用・却下。「削除」は作らない**

[ADR-0022](0022-repairing-memories-without-deleting.md) の形をそのまま借りる。

| 導線 | 何をするか |
|---|---|
| **一覧** | 未処理の提案を、**根拠の記憶ごと**並べる。**プロンプトには一切載らない** |
| **採用** | 履歴へ追記し、現在の投影を差し替える（1トランザクション） |
| **却下** | **却下したことを記録する**（§決定7） |

**「この提案を無かったことにする」だけの操作は入れない。**
**却下は「いまの値が正しい」という判断**なので、記録に値する。

> **これは [ADR-0003](0003-full-memory-injection.md) の「想起の入口はひとつ」に反しない。**
> **想起ではない。管理のための一覧である。名前と置き場所で区別すること。**

### 7. **却下も記録する**

**記録しないと、同じ提案が見直しのたびに出続ける。**

根拠になった記憶は**消えない**（絶対制約）ので、
**却下した提案は、次の見直しでも同じ入力から同じ形で再生する。**
**人が同じ提案を何度も却下することになり、導線が使われなくなる。**

> **⚠ 「一度却下したキーは二度と提案しない」にはしないこと。**
> **却下したのは「その値への変更」であって「そのキーが変わりうること」ではない。**
> `住所` の提案を1回却下したら、**引っ越しても二度と提案されない**のは違う。
> **却下は（キー, 値, 根拠）の組に対して記録する。**

### 8. **記録専用モードから始める**

**既定は `off`。** 次に**提案を記録するだけで適用しないモード**を置き、
**適用は最後**（[ADR-0026](0026-drift-by-accumulation.md) §決定1 と同じ）。

**16 の全期間で、この順序が効き続けた。**
記録専用モードで集めた提案列があったから、
**重みの形も係数も、実機を回さずに何通りでも当て直せた。**

## 危険（**すべて実測に基づく。憶測ではない**）

| # | 危険 | 出どころ | 打ち手 |
|---|---|---|---|
| 1 | **「なし」を言わない** | ADR-0027 §診断（328 ターンで 0 件） | §決定2 で**尋ねる回数そのものを減らす** |
| 2 | **主語を取り違える** | ADR-0021 §10（**6% 実測**） | §決定4 で**モデルに主語を答えさせない** |
| 3 | **依頼に載る数字を読んで答えを変える** | ADR-0027 訂正（16f の実測） | **属性でも起きるか未測定。**記録専用モードで見る |
| 4 | **軸名（＝キー）が崩れる** | 16 の実測（`陽気さ` → `阳気さ` が3腕で8件） | §決定3 の完全一致で落ちる。**落ちた件数をログに出す** |
| 5 | **記憶が誤っていれば提案も誤る** | 抽出の欠陥率（13d 時点で 9.1%） | §決定6 の確認。**止めるのではなく、人の目に映るところまで運ぶ** |

> **⚠ 危険3 が、この作業単位でいちばん読めない。**
> 性格の変容では「値が高いと下げを出す」という**天井の肩代わり**が出た。
> **属性で同じことが起きるとしたら「いまの値と違う値を言いたがる」**形になる。
> **記録専用モードの最初の問いはこれである。**

## 測る問い（**着手前に決めておく**）

1. **提案は何ターンに1回出るか。** 出過ぎるなら §決定2 の `N` が小さい。
2. **提案のうち、人が採用するのは何割か。** 低ければ、この導線は使われなくなる。
3. **同じ入力を2回通すと、同じ提案が出るか**（決定性ではなく再現性）。
4. **「変わっていない」入力で提案が出るか**（危険1・危険3 の直接の検査）。

> **⚠ 4 が本命である。** 1〜3 は「動くか」を見るが、
> **4 だけが「意味があるか」を見る**（[docs/05-development.md](../05-development.md)
> 「『出るか』と『意味があるか』は別の問い」）。

## 却下した選択肢

- **抽出のサブ LLM に属性を直接書かせる。**
  **削れない枠に、検証を1層も通っていない出力が入る。**
  ロードマップが最初から禁じている。
- **属性を毎ターン見直す。**
  裏方が本文より重くなり、**危険1（「なし」を言わない）を最大化する。**
- **提案に新しいキーを作らせる。** §決定3。件数の上限を食い潰せる。
- **人の確認を挟まずに適用する。**
  **語には中間が無い**ので、閾値で誤りを吸収できない（§診断3）。
  **性格の変容が閾値で吸収できるのは、値が連続量だから。**
- **`character_attribute` の主キーを組み替えて履歴を持たせる。**
  **適用済みのマイグレーションは編集できない**ので、テーブルの作り直しと移送が要る。
  **読み出し経路（プロンプト）を触らずに済む追記テーブルの方が、壊す面が小さい。**

## まだ決めていないこと

- **`N`（見直しの間隔）の値。** 測ってから決める。
- **提案を出すサブ LLM の依頼の形。**
  全キーを毎回並べるか（ADR-0027 の `all` と同じ）、
  変わった可能性のあるキーだけを尋ねるか。
  **`all` の形は「なし」の偏りを 94% → 69% に下げた実測がある**ので、そちらから試す。
- **危険3 の有無。** 記録専用モードの最初の測定で見る。
