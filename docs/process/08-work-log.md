### 0006 の範囲 — ログ観測テストの直列化（**実測済みのフレーキー**）

**`tracing` の callsite interest はプロセス全体で1つのキャッシュ**なので、
`with_default` を張るテストが並行すると衝突する。**2026-08-15 に無変異のツリーで再現**:

```
既定スレッド数 20回 → 1回失敗
--test-threads=32 25回 → 1回失敗      計 70回中 2回（約3%）
```

機構（tracing-core 0.1.36 のソースで確認）:

- `callsite.rs` の interest キャッシュはプロセス全体で1つ
- 生存 Dispatch が1つ以下のとき、interest は**登録した側のスレッドが見ている dispatcher** で決まる
- **subscriber を差していないスレッドが最初にその callsite を踏むと
  `Interest::never()` がグローバルに焼き付く**

**危険なのは偽陽性ではなく偽陰性である。**

> callsite が `never` に焼き付くと、**否定側のテスト（`output.is_empty()`）は
> 「何も出なかった」ので緑**になる。**見張り番が赤くならずに黙る形で壊れる。**

対象は**19件**（`body` 2 / `context` 3 / `telemetry` 8 / `usage` 5 / `response` 1）で、
ログ観測テストは今後も増える。

**採った手**（2026-08-15 / 実装済み）:

- **番人の常駐。** `Interest::sometimes()` を返すだけの subscriber を2つ常駐させる。
  `Interest::and` は意見が割れたら `sometimes` になるので、**どの callsite も `never` に
  焼き付かない。** 見張り番は `the_sentinels_are_registered_and_always_ask`
  （**既定の走らせ方で 5/5 決定的に赤**）
- **否定側テストの `trace` 先出し。** 「**先に `trace` フィルタでイベント自体が出ていることを
  確認**してから否定を主張する」形を19件全部に広げた。
  **実測で偽陰性を赤に変えた実例が出ている**（番人なしの128実行で出た失敗3件は、
  いずれも先出しのアサート自体が捕まえた）
- 捕捉ヘルパを `src/testlog.rs`（crate 直下の `#[cfg(test)]`）へ集約。5箇所の複製を解消

**却下した手 — テスト専用の `Mutex` による直列化**:

- **焼き付ける側は捕捉ヘルパを通らない。** `choose_budget(None, None)` を素で呼ぶ
  通常のテストが callsite を登録するので、ヘルパ内の錠では原理的に届かない
- **むしろ逆効果。** 錠は生存 `Dispatch` を常に1つ以下に保つので
  **`has_just_one` を true に張り付かせ**、焼き付きが起きる唯一の経路を選ばれやすくする
  （実測: 番人なしで錠あり 3/128 失敗 / 錠なし 1/128）
- **効果を測れない。** 錠を即座に解放する変異を入れても全緑だった

> **`tests/server_telemetry.rs` 方式（1バイナリ1テストへ隔離）は使えない。** 対象が private 関数。

### 統合テスト側には同じ問題が残っている（**方針だけ決めてある**）

`src/testlog.rs` は crate 直下の `#[cfg(test)]` なので、**`tests/` 配下の統合テストからは使えない。**
統合テストは `SharedBuffer` ＋ `set_global_default` を各バイナリで持つしかなく、
**同じバイナリ内の他テストのログが同じバッファに混ざる。**

2026-08-15 に `tests/server_chat_stream.rs` で実際に踏んだ:

> 新テストが `prompt_tokens=100_000` を申告すると超過の `warn` が同じバッファに出て、
> `the_usage_crosscheck_runs_on_the_streaming_path` が引く行が**そちらに化けて落ちた**
> （単独実行では緑）。申告値を `1` にして回避した。

**タイミングの問題ではない**（ログは `[DONE]` を yield する前に同じタスクで書かれる）。
**「どの行が自分のものか」の同定手段が無い**ことが原因で、
`line_containing` は「マーカーを含む最初の行」を取るので、**同じマーカーが2本出た瞬間に破れる。**

**次に「答え合わせが鳴るテスト」を足す人は、回避ではなく次のどちらかを採ること:**

1. **観測するテストを専用のテストバイナリへ分ける**（例 `tests/server_chat_stream_usage.rs`）。
   cargo は `tests/*.rs` ごとに別プロセスにするので**バッファの共有そのものが消える。**
   ヘルパの重複は既知の許容事項なので、**一番安い決定的な解**
2. **ログ行に同定子を載せる。** `usage::report` に応答 id かセッション id を足し、
   テストは SSE 本文から読んだ id で行を選ぶ。同じバイナリに何本足しても壊れず、
   **本番の運用ログでも「どの応答の答え合わせか」が分かる**という利点がある。
   ただし引数が増える設計変更なので司令塔の採否が要る

> **測り方の注意**: `--test-threads=N` の単発連続実行では**再現しない**
> （この機の既定スレッド数が 32 なので `--test-threads=32` は既定と同義）。
> **同じ exe を 8〜16 本同時に走らせる**こと。
> なお 1000 実行前後で **Windows の一時ポートが枯渇**するので、
> 高回数の計測では wiremock を使うテストを除外する。

### 11c-4 の範囲 — コンテキスト長を引き直す

**11c-2（`usage` の答え合わせ）では「稼働中に小さいコンテキストで再ロードされた」を
検出できない。** 理由は [ADR-0013](../adr/0013-context-budget-layers.md) の「訂正」節。
要するに **`usage.prompt_tokens` からは原理的に取れない**
（上流が切り捨てた結果の値は、こちらの過大な見積もりと区別が付かない）。

**対処は「観測」ではなく「取り直し」の側にある。**

- 起動時の1回だけでなく、**定期的に**、あるいは**疑わしい事象**を見たときに
  `loaded_context_length` を引き直す
- 疑わしい事象の候補: `finish_reason` の異常、上界破れの `warn`、上流エラーの連続
- **引き直しの頻度は本文生成の邪魔をしない範囲に。** 毎リクエスト引くと往復が倍になる
  （ADR-0013 が「毎リクエスト照会する」を却下した理由）
- **引き直して値が変わったら `warn`。** 黙って予算だけ変えると、
  「昨日と同じ発言が今日は 422 になる」理由が追えない

### 0005 の範囲 — 413 の応答が届かない（**実測済みの製品欠陥**）

**上限を大きく超える本文を送ると、`body_too_large` の JSON が高確率で届かない。**
届くのは「接続がリセットされた」だけ。2026-08-14 に本物のサーバへ生 TCP で実測:

| 本文 | 413 を受け取れた | 応答を失った |
|---|---|---|
| 2.86 MB | 6 | **9** |
| 2.10 MB | 15 | 0 |

機構は次のとおり。**超過量が大きいほど壊れる**サイズ依存の競合。

1. axum 既定の 2MB 制限は Content-Length ではなく**実際に読んだバイト数**で打ち切る
2. サーバは約 2MB 読んだ時点で読むのをやめ、413 を書いて接続を閉じる
3. クライアントはまだ書いている。**未読データを残して閉じると OS が RST を送る**ので、
   クライアントの write が失敗し、**受信済みの 413 も破棄される**

`ApiError::body_too_large` の doc が「400 に潰すと原因から遠い」と書いた状況が、
そもそも応答が届かないという形で成立している。

- **対処の方向**: 413 を返すと決めた後、**残りの本文を上限付きで読み捨ててから**応答・切断する
- **Content-Length で即時に弾く案は逆効果。** 未読が本文まるごとになり、悪化する
- **テストの本文を 2.1MB に下げて緑にしないこと。** 実挙動を隠すだけ。
  `tests/server_chat.rs::an_oversized_chat_body_is_rejected_as_too_large` が
  **負荷の高いときだけ落ちる**のはこの欠陥が理由であって、テストの欠陥ではない

### 0004b の受け入れ条件（`handle` への改名 ＋ 文字集合を絞る）

設計は [ADR-0017](../adr/0017-handle-is-a-restricted-alphabet.md)。
**「機能は増えない」作業単位ではなくなった。欠陥のクラスが1つ消える。**

- 使えるのは **ASCII の小文字英字・数字・`-`・`_`** だけ。**大文字も拒否する**
  （畳み込みは正規化であり、正規化がある限り「畳み込む前の行」が存在しうる）。
- **正規化を捨てる。** trim も畳み込みもしない。**比較は `=` で足りる。**
- **0004b-2 の根拠は「作れないから」ではなく「作られても照合が当たらないから」。**
  〈0004b-1 のレビューで判明〉**CHECK を入れてもゴースト行は作れる**ので、
  「入口を塞いだから機構を捨ててよい」は成り立たない。
  **実測と詳しい理由は `tests/common/mod.rs` の doc が正**（ここに書き写さないこと）。
- **役目を終えるもの**（消す／消せることを確かめる）:
  `character_name_key_idx` / `SELECT_BY_NORMALIZED_KEY` /
  `StoreError::ConflictingUnnormalizedName` / `TRIMMABLE` の写しのうち識別子に関わる分。
  > **「消せる」ことを実測で示すこと。** 消してからテストが緑なのは当然なので、
  > **消す前に「この機構が守っていた状態を、新しい規則では作れない」ことを確かめる。**
- **`character` 1表だけを再構築すること。**〈0004b-1 のレビューで確定〉
  8テーブル再構築は `DROP TABLE memory` を要求し、
  **記憶を潰さないための走査（絶対制約の見張り番）を緩めることになる。**
  実測で**記憶を全滅させる移行が3形態通った**（うち2つは作業者の申告に無かった）。
  > **緩めずに済む道がある。** `sqlx 0.9.0` は **`-- no-transaction`** に対応しており、
  > 自前で `PRAGMA foreign_keys = OFF` を立てられる。
  >
  > **絶対制約の見張り番は、代替があるのに緩めない。**
  >
  > **`ALTER TABLE ... RENAME` と子の `REFERENCES` の関係は、プラグマ2つの
  > 組み合わせで決まる**（4通りの実測表は `migrations/0005_*.sql` のコメントが正）。
  > **`foreign_keys = OFF` だけでは止まらない。**
  > 実装は**誰も参照していない新表だけを改名する**ことで、この組み合わせから独立させている。
- **マイグレーションは黙って変換せず、落ちること。**
  識別子は不変（[ADR-0016](../adr/0016-character-update-and-delete.md)）なので **API では直せない。**
  勝手に変えると、FE 側の `model` 設定が指さなくなるのと同じ壊れ方になる。
  > **落ちたときの復旧手段は `sqlite3` だけ。**〈0012b で判明〉
  > 0012 で修復の導線を作ったが、**識別子そのものが読めない行は
  > 一覧に `name: None` として出るだけで、API からは直せない。**
  > **落ちる原因になる行こそが、いちばん直せない行**という構図になっている。
  > **移行の手順書に「先に `sqlite3` で確認する」を書くこと。**
- **`ModelSelector` の検査が緩められないか確認する。** `@` が文字集合から外れるので、
  分割の曖昧さが減るはず。**減らないなら理由を報告すること。**

### 0012 の受け入れ条件（キャラクターの更新と削除）

設計は [ADR-0016](../adr/0016-character-update-and-delete.md)。**3つに割る。**

| # | 内容 |
|---|---|
| **0012a** | `store` の更新・削除。**既存の行を `parse` せずに書けること** |
| **0012b** | `list_characters` が壊れた行を指し示す（**修復の入口**。これが無いと 0012a が届かない） |
| **0012c** | `/admin/` の `PATCH` と `DELETE`（**引き当ての非対称に注意。下記**） |

- **識別子（`character.name`）は更新の対象にしない。** 型かシグネチャで**表現できなくする**
  （`Option<Handle>` を受け取る形にしない）。
- **更新は部分更新。** 「表示名だけ変える」ができること。
  **省略されたフィールドを既定値で上書きしない**（`serde` の `Option` の扱いに注意）。
- **削除はセッションが1件でもあれば拒否。** 数えてから消すのではなく、
  **`DELETE ... WHERE NOT EXISTS (SELECT 1 FROM session ...)` の1文**で判定と削除を不可分にする
  （数えてから消すと、その間に会話が始まりうる）。
- **見張り番は「会話のあるキャラクターは消せない」こと。**
  「エラーが返る」だけでなく、**`character` の行数が変化しないこと**を確かめる
  （`append_turn` の「片方だけ入る状態を作れない」と同じ形）。
- **0012c は「引き当ての非対称」を踏む。**〈0012a のレビューで判明〉
  `update_character` / `delete_character` は**正規化キー**で引く（ゴースト行を掃除するため）が、
  `find_character_by_handle` / `list_characters` は**完全一致**のまま。
  結果 **`PATCH /admin/characters/aoi` は 200 なのに、直後の `GET` とチャットは 404**
  という状態が作れる。[ADR-0016](../adr/0016-character-update-and-delete.md) の帰結として
  **挙動は正しい**が、**応答の設計を決めるときに効く**（直した相手が読み出せない）。
  > **⚠ 解消済み（2026-08-16 / 0004b-2）。** 予告どおり消えた。
  > 更新も削除も**完全一致**で引くようになったので、
  > 「更新は 200 なのに `GET` は 404」は起きない。
  > **ゴースト行は `sqlite3` でなら今も作れるが、どの経路からも当たらない**
  > （一覧に「読めない行」として出るだけ）。**以下は過渡期の記録。**
- **0012b の見張り番は「正常な行が巻き添えにならない」こと。**
  壊れた行を1件混ぜて、**他のキャラクターが一覧に出ること**を確かめる。
  **黙って読み飛ばさない**ことも同時に固定する（壊れていると分かる形で出る）。

### キャラクターに修復手段が無いこと（0009 で根が見えた）

**0009 で出た指摘は、ほぼ全部が同じ根に繋がっている。**

- 「保存はできるのに以後のチャットが必ず失敗する」（上限の穴。3回出た）
- 「呼び名の無いキャラクターを作れて、二度と直せない」（0009）
- 「不正な行が1件あると `list_characters` が丸ごと 500 になる」（同）

**どれも `character` に更新・削除の API が無いことが増幅している。**
入口を厳しくしても**既に作られた行は残る**ので、**入口だけでは閉じない。**

> **`memory` に更新・削除を作らない方針（ADR-0008）と混同しないこと。**
> あちらは「時系列を潰さない」ための意図的な制約で、
> **`character` は運用者が編集する設定**である。**性質が違う。**

**0009 で、この根に直接ぶら下がるものが3つ増えた。**

- **0009 以前に作られた行は、今度は「読めない」方向に倒れる。**
  `list_characters` は `?` なので**不正な行が1件でも 500**。正常なキャラの一覧すら見られない。
  **救済のマイグレーションは入れていない**（入口を塞いだだけ）。
- **`aoi` と `aoi\u{200B}` は別のキャラクターとして併存できる。**
  見た目が同一なのに識別子が違う。**入口の判定は「見える文字が1つでもあれば通す」**ので、
  不可視文字を混ぜた別名を止めない。[ADR-0004](../adr/0004-session-identification.md) の
  正規化の話とは**別の軸**（あちらは前後の空白）。
- **`DisplayName` と `MemoryCategory` は受理集合が完全に一致している。**
  型検査は取り違えを止めるが、**値の検査では原理的に区別できない**（実測。42組中この2組だけ）。

**決めること**: `character` の更新（と削除）をどこまで持つか。
[ADR-0009](../adr/0009-character-attributes-and-facts.md) は
`character_attribute` について「更新・削除の API を持つ」と既に書いており、
**本体だけ持たないのは一貫していない。**

### 0009 の受け入れ条件（`parse` は通るのに無害化で空になる値）

**0008 の変異検査で見つかった。** `domain::text::contains_control` は `char::is_control`（Cc）
だけを見るが、`prompt::SafeText` は `LINE_BREAKS`（**U+0085 / U+2028 / U+2029**）も畳む。
**`"\u{2028}"` だけの値は `parse` も DB の CHECK も通り、プロンプトでは空になる。**
**`/admin/characters` から到達できることを実測済み**（読み戻したバイト列が `[226,128,168]`）。

実際に組み上がるプロンプト（レビュアーの実測）:

```text
# 名前
>                      ← DisplayName
# 性格ステータス
数値が大きいほどその傾向が強く出ます。記載のない軸は考慮しません。
項目名や数値に触れない。
> - : 5                ← StatAxis。**名前の無い軸に数値だけが載る**
# 記憶
> -                    ← MemoryContent。**枠と予算を食って中身が無い**
```

**`StatAxis` が最も害が大きい。** 直前の「記載のない軸は考慮しません。」と矛盾し、
**性格値 0 の軸を落としている理由と同じ形の劣化**を起こす。
`Handle` は識別子でプロンプトに載らないので影響は小さい。
`Persona` / `OutputFormat` は「空なら節ごと落とす」分岐があるので実害なし。

- **不変条件は「`parse` を通った値は無害化後も非空」。**
  1行のラベル型（`DisplayName` / `Handle` / `StatAxis` / `MemoryCategory`）は
  `is_control` に加えて `LINE_BREAKS` も拒否する。
- **~~更新・削除 API が無いので、一度作られたキャラクターは二度と直せない。~~**
  **0012 で `PATCH` / `DELETE` ができた**（[ADR-0016](../adr/0016-character-update-and-delete.md)）。
  **0009 に着手した当時の理由としてはこのまま。** CLAUDE.md の上限の穴と同じ類。
- **同時に畳むものがある。** `the_show_dont_tell_line_is_unconditional` が通す形のうち
  **表示名が空にサニタイズされる形は構築不能になり、死んだ検査になる**
  （**形の数はここに書かない。** コード側の doc が正）。
  > **これは `0006` の `Mutex` と同型**（見張り番が、塞ぐべき欠陥の存在に寄りかかって
  > 担い手になっている）。**畳むと同時に、その分岐を別の手段で見張れるかを測り直すこと。**
- **`> ` だけの行が残る挙動を前提に置いているアサートがある**
  （`the_show_dont_tell_line_is_unconditional` の呼び名の形）。
  名前の節を空なら落とす方向に直すと落ちるので、**前提を振り替えること。**

### 11b の受け入れ条件（パース ＋ 永続化）

**マイルストーン4**（台詞と地の文に分解して保存）に届き、**多ターンの会話が成立する。**
`parse::parse_response` と `Store::append_message` は既にあるので、**本体は配線**である。

#### なぜ2つに割るか

**利用者の発言と応答を別々に書くと、後者だけ失敗したときに「返答の無い利用者ターン」が
履歴に残る。** 次のターンのプロンプトに利用者発言が2つ並び、**誰も赤にしない。**
先に往復を1トランザクションで書く口を作ってから配線する。

#### 11b-1 — `Store::append_turn`

- **利用者の発言と応答を1トランザクションで書く。** 順序は利用者 → 応答。
- **`append_message` は残す**（`memory` 側のテストなど既存の利用がある）。
  共通化するなら内部だけ。**`append_message` の公開シグネチャを変えないこと。**
- `TOUCH_SESSION` は**1回で足りる**（同一トランザクション内なので `updated_at` は
  そのキャラクターの全セッションより真に大きい値に1回進めばよい）。
  **対象0件ならその場で `UnknownSession`** にして、片方だけ入る経路を作らない。
- **見張り番は「片方だけ入る状態を作れない」ことを示すもの。**
  存在しないセッション ID を渡し、**`message` の行数が変化しないこと**を確かめる。
  「エラーが返る」だけでは足りない。
- **往復の形（`User` → `Assistant`）を検証して、違えば `StoreError` で弾く。**
  `Role` は2値なので形は一意に定まる。**検証しないと
  「利用者の発言が2つ並ぶ履歴」を不可分に書き込めてしまい**、それは
  この作業単位が防ぐと宣言した状態そのもの。**弾いたとき1行も書かないこと。**
  > **`role` を位置から決め打つのとは別の話。** 格納する値は `NewMessage::role` から取る。
  > 「握り潰さない」と「防ぐ」は両立する。
- **並行実行の見張り番を持つ。** 失敗注入だけでは足りない。
  **実運用で起きる失敗モードは並行実行**で、非不可分な実装では
  **同一往復の間に他の書き込みが割り込む**（実測で 23 件割り込んだ）。
  判定は「往復の2件の rowid が連続すること」。

#### 11b-2 — `chat` / `relay` の配線

- **応答が完全に返り切ってから保存する。** 中継が途中で失敗した回は**何も保存しない**
  （利用者の発言も。部分的な応答を履歴に混ぜると以後の文脈が汚れる）。
- **利用者の発言はパースしない。** `dialogue` / `narration` は `None`、`raw_content` に本文。
  **モデルの出力ではないものに `parse_response` を通さないこと。**
- **`raw_content` は必ず入れる**（絶対制約）。パースが崩れた回も生出力を丸ごと保持する。
  プロンプト側は `raw_content` を読む（`prompt::history_turn`）ので、
  **崩れた応答もそのまま履歴に載る。** これは意図した挙動。
- **パース成功率をログに残す**（絶対制約）。`ParseOutcome::label()` をそのまま使い、
  **生出力をログに載せない。** 非ストリーミングと中継の**両方**の経路で出すこと。
- **保存の失敗で応答を壊さない。** 中継経路では `[DONE]` を送った後なので手遅れであり、
  非ストリーミング経路でも**生成し直させる方が高くつく。** `error!` で記録して応答は返す。
  > **これは黙ったデータ欠落なので、持ち越しに積むこと**（「破棄率のメトリクス」と同じ枠）。
- **トランザクションの中で `await` しない**（絶対制約）。上流呼び出しは必ず完了させてから書く。

#### 持ち越し（11b-2 で判明）

- **`tests/server_chat.rs` と `tests/server_chat_stream.rs` のログ観測が、
  まだコメントで守られている**（「この文言を出すのはここだけなので判定は壊れない」）。
  `tests/server_chat_parse_log.rs` には `LogSection`（区間 ＋ 回転扉）を入れたが、
  この2本には無い。**subscriber を差すテストが各バイナリ1本ずつなので今は実害が無いだけで、
  2本目を足した瞬間に同じ穴になる。**

#### `turn_messages` と `append_turn` の間は無防備（0010 で判明）

**分解の結果を見張っているのは純粋関数 `turn_messages` の出力だけ**で、
そこから `Store::append_turn` へ渡るまでの間に処理を挟まれると観測できない。
**実測**: 「入れ子の回だけ台詞を落とす」処理を `persist` の中に置くと **701/701 緑**。

**いま安全なのは `persist` が分岐を1つも持たない素通しだから**であって、
見張り番が守っているからではない。**`persist` に加工が1行でも入った瞬間に実害へ変わる。**
そのときは DB まで通す結合テストが要る（現状は重複コストの方が大きいので置いていない）。

#### 11c-3 へ渡す前提（11b-2 で判明）

- **`[DONE]` の直前に最大5秒の空白が入りうる。** 保存は `[DONE]` を流す**前**に `await` される
  （成否をもう変えられない位置で書くための設計）。書き込みが `busy_timeout`（5秒）に
  近づく状況では、その分だけ `[DONE]` が遅れる。**無通信の閾値をこれより短くしないこと。**
- **FE が中継の途中で切断すると、その回は保存されない。** axum が本文ストリームを落とすので
  `[DONE]` の枝に到達しない。「途中で失敗した回は保存しない」と同じ扱い。
  > ~~**上流の生成は完走しているかもしれない**点が違う。~~
  > → **11c-3b で決着。完走しない**（drop が上流の TCP を閉じることを実測）。
  > **切断時キャンセルと一緒に決める、という前提そのものが消えた。**
  >
  > **ただし「切断した回は保存しない」に見張り番は無い。** 打ち切り側（11c-3a）は
  > 保存の側から見ているが、**切断側は測っても固定してもいない。**

#### 検証

- **多ターンが成立すること**を、**同じセッション ID を2回叩いて**確かめる
  （2回目のプロンプトに1回目の往復が載る）。**`aoi@new` を2回叩くのでは検証にならない。**
- **`recent_messages` は空を返さなくなる。** 「配線は通っているが常に空」という
  現在の状態（下記の持ち越し）が解消したことを、実際に載っていることで示す。

### 12 の受け入れ条件（`character_attribute` / `character_fact`）

設計は [ADR-0009](../adr/0009-character-attributes-and-facts.md)。**2テーブルに分ける。**

> **2026-08-15 に優先度が上がった。** マイルストーン5の測定中に
> **同じキャラクターの一人称が応答ごとに揺れる**ことが分かった。
> **発言にも他軸にも性格値にも相関しない。**
> 同一応答の中で「**僕**も楽ちんなんだけど」「心が洗われちゃう**わ**」が混ざった例もある。
>
> **同日夕の30条件では `僕` 7 / `ぼく` 5 / `俺` 3 / 三人称自称 7**（`私` は0）。
> **1つのキャラクター定義から一人称が4通り出ている。**
> ユーザ指摘のとおり「普段は僕、照れたら私」のような**意図した揺れは設定として正当**なので、
> 問題は揺れること自体ではなく**指定できないこと**。
>
> **性格ステータスでは直せない。属性として渡すしかない。**
> この ADR の動機は「画像側と共有できる」だけではなく、
> **本文の一貫性そのもの**になった。

- **`character_attribute` は件数にも上限を持つ。** 1件あたりの上限だけでは足りない。
  `stat_alloc` は件数無制限のままなので、**同じ穴を増やさないこと**
- **見張り番 `every_field_at_its_limit_still_fits_the_default_budget` を両テーブルに広げる。**
  広げなければ上限を設ける意味が無い。**これは新規テストではなく既存テストの拡張**なので、
  意味が変わる場合は司令塔の採否を仰ぐこと
- **属性は「# 記憶」節に載せない**（削れない枠と削れる枠を1つの節に混ぜない）
- **`character_fact` を「# 記憶」節に混ぜるなら `MEMORY_NOTE` を直す。**
  「過去の会話から抽出した事実の記録です。」は人が書いた設定に対しては偽
- **空の `value` を持つ属性は行ごと落とす**（性格値 0 の軸と同じ理由）
- **`memory` を含む名前のテーブルを作らない。** SQL 走査テストの許可リストは
  テーブル名の文字列で走査するため、誤検出・誤放免の両方が起こりうる
- 更新・削除の API を持つ（`memory` とは正反対）。
  **`memory` の「DELETE / UPDATE の API を作らない」防御に例外を作らないこと**が前提

### マイルストーン5 — **測定の記録は ADR-0012 に置く**

> **ここに測定結果を書き写さないこと。**
> 2026-08-15 に、この節と [ADR-0012](../adr/0012-stat-section-directive.md) の両方へ

> **同じ発見を2箇所に書くと、片方を直しても、もう片方が黙って古びる。**

**判断が要るときは [ADR-0012](../adr/0012-stat-section-directive.md) の「⚠ 先に読むこと」から入る。**

**決着済み**（詳細は追わないこと。理由と実測は ADR-0012 が正）:

- **小数は実装しない。** 刻みは軸の方向に沿わない（目隠しの順位付け＋対照で確認）
- **尺度はキャラごとの独立項目にする**（[ADR-0015](../adr/0015-stat-scale-per-character.md)）。
  **本番のプロンプトはまだ尺度を載せていない** —— 0011a / 0011b がその作業
- **定数行は2つに割った**（無条件の1本と、性格ステータス節の1本）。軸ゼロのキャラで欠陥が出たため
- **入れ子の `「」` は崩れではない**（[ADR-0014](../adr/0014-nested-quotes-are-not-a-breakage.md)）
- **一人称の揺れは性格値では直せない**（[ADR-0009](../adr/0009-character-attributes-and-facts.md)）。
  **1つのキャラ定義から `僕` / `ぼく` / `俺` / 三人称の4通りが出た**（30条件の実測）

### 小数を入れるなら何が要るか — **入口の実測記録**（実装しないと決めた）

> **判断は決着済み（実装しない）。** ここに残すのは**コードの事実**（入口が何を受けるか）だけで、
> **将来ひっくり返すときのコストの見積もり**として置いてある。

**現状は入れられない。** `1.1` は入口で拒否される。実測（2026-08-14）:

| 入力 | HTTP（`PUT /admin/characters/{handle}/stats`） | SQLite の CHECK |
|---|---|---|
| `3` | 受理 | 受理 |
| `1.1` | **拒否** `invalid type: floating point 1.1, expected u32` | 拒否（`typeof` ≠ integer） |
| `3.0` | **拒否**（同上） | **受理**（アフィニティで `3` に正規化） |
| `"3"` | **拒否** `invalid type: string "3"` | 受理（同上） |
| `-1` | **拒否** `invalid value: integer -1` | 拒否（`value >= 0`） |

**API の方が DB より厳しい。** `3.0` と `"3"` は SQLite なら通るが、
`StatAllocRequest.value: u32` が先に弾く。**この差は意図した多層防御**であって、
どちらかを緩めてよいという意味ではない。

#### 入れると決めた場合のコスト

- `StatAlloc.value: u32` の変更。`f64` にすると `Eq` / `Hash` を失う。
  負値・NaN・`inf` を**型で表現できなくする**新しい有界型が要る
- スキーマの `CHECK (typeof(value) = 'integer')` の変更 →
  **適用済みマイグレーションは編集禁止**なので新しい `000N_*.sql` を足す
- プロンプトに載る桁数が増え、**削れない枠**を圧迫する
- 上限と同じく**後から精度を下げられない**（保存済みの値が読めなくなる）

### メモリ抽出パイプラインの作業単位の受け入れ条件

- **`domain` の検証で弾いた事実を、呼び出し側で `warn` に残すこと。**
  `MemoryContent::parse` / `MemoryCategory::parse` は純粋関数なので `tracing` を持てない。
  そのため**上限や空で弾かれた記憶は、この層に痕跡がまったく残らない。**
  ログが無いと「なぜ記憶が増えないのか」が `message.raw_content` を
  突き合わせるまで分からない。
- **破棄率をメトリクスとして集計できるようにする。** 高い場合は
  プロンプト設計かモデル選定の見直しが必要というシグナル
  （[ADR-0006](../adr/0006-slot-based-tag-compilation.md) の `ValidTag` と同じ構造）。

### prompt の作業単位の受け入れ条件

- **プロンプト注入への防御は `prompt` 層で行う。** 記憶本文・ペルソナ・ユーザー入力の
  すべてに同じ整形（行頭の正規化、偽の役割行の無害化）を通すこと。
  **`store` 側で記憶の改行を弾く形にしない。** 理由:
  - 記憶本文は散文で、複数行の記憶は正当
  - **同じ防御が `base_persona` と会話履歴にも要る。** 記憶だけ `store` で弾いても
    穴は塞がらず、防御が2箇所に分散してどちらも不完全になる
  - 記憶を弾いても、攻撃者は同じ文字列を会話履歴側から注入できる
- **性格値が 0 の軸をプロンプトに含めない**（絶対制約）。
  `store` は 0 の軸も保存して返すので、落とすのは `prompt` の責務。
- **トークン予算を明示的に配分する。** 溢れたときにどの枠から削るかを実装で示す。

- ~~**FE 切断時に上流へのリクエストをキャンセルする。** `ChatStream` を drop すれば
  コネクションが閉じる形になっているが、**それが実際に効くかは確かめられない。**~~
  → **11c-3b で測って決着。効いている。** 測定の条件・数字・対照は
  `tests/server_chat_cancel.rs` と `tests/llm_lmstudio.rs` の見張り番が正。**ここに写さない。**
  > **無通信の見張り（11c-3a）と切断時キャンセル（11c-3b）は、
  > 「上流を逐次読む」という同じ1点に寄りかかっている。**
  > 上流を先読みタスクへ抱えさせる変異は**両方を同時に壊す**（実測。`src/server/relay.rs` の doc）。
  > **片方の見張り番を外すと、もう片方が弱る。**
- **`LlmError::Truncated` の扱いを決める。** 現在は「`[DONE]` を受けずに EOF」を無条件に
  `Truncated` としており、直前に `finish_reason: "stop"` を受けていても同じ。
  LM Studio は `[DONE]` を送るので今は顕在化しないが、
  **これを「不完全なので警告／再生成」に使う設計にすると、`[DONE]` を省く互換サーバ相手で
  正常完了した応答が打ち切り扱いになる。**
- `LmStudioClient::new` の失敗（TLS / リゾルバの初期化）は現在 `Transport` に相乗りしている。
  起動時の構成エラーであり上流との通信失敗とは案内が変わるので、起動フローを書くときに分ける。
- **`LlmError::Timeout` は2つの原因を兼ねている** — 「初回トークンが来ない
  （JIT ロードが 180 秒を超えた）」と「生成中に固まった」。
  `reqwest` の `read_timeout` がクライアント単位でしか設定できないため、
  読み取り予算を1つに統合した帰結。**FE への案内を出し分けたいなら区別できない。**
- **トークン間の無通信の見張りは `server` の中継ループに置く。**
  `llm` の 180 秒は JIT ロードを飲むための値で、生成中の停止検出としては緩い。
  ただし**これを `llm` 側で直そうとしないこと。** `server` は中継ループで
  `tokio::time::timeout(d, stream.next())` を巻くだけで per-item の予算を得られ、
  `LlmError` の新バリアントも要らない（自分の SSE エラーを出せるし、
  「途中まで保存するか」の判断も既に `server` の責務）。
  **`llm` を厚くする方向へ進まないこと。**
  そのとき `LmStudioConfig` にタイムアウトの getter が要る（現在は無い）。
  定数を二重に持たないため。

**`store` の作業単位から持ち越されたもの:**

- **`tracing-subscriber` を初期化する。** 既定フィルタが `warn` を落とさないこと。
  `store` は「正規化されていないキャラ名の行を一覧から除外した」等を `warn` で報告するが、
  **subscriber が無い間、その警告はどこにも出力されない。**
  黙って除外する方針は「ログで気づける」ことを前提に採用している。
- **終了時に `Store::close()` を必ず通す。** WAL のデータは `-wal` 側に残るため、
  `close()` を経ずに落ちると失われる（[04-environment.md](../04-environment.md)）。
- **エラーレスポンスに `{err:?}` を載せない。** `Debug` は `#[source]` 経由でパスを含みうる。
