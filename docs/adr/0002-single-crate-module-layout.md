# ADR-0002: 単一クレート + モジュール分割で始める

- 状態: 採用
- 日付: 2026-08-13

## 背景

`domain` / `prompt` / `parse` / `llm` / `store` / `server` という6つの関心事があり、
これを Cargo workspace で複数クレートに分けるか、単一クレートのモジュールで分けるかを決める必要があった。

## 決定

**単一クレート（`personacore`）+ モジュール分割で始める。**
ただし**モジュール境界は crate 境界のつもりで引き**、将来 workspace へ分割できる形を保つ。

```
src/
  domain/   純粋関数。ドメイン型と不変条件
  prompt/   純粋関数。プロンプト組立とトークン予算
  parse/    純粋関数。台詞 / 地の文のパース
  llm/      トレイト + LM Studio クライアント
  store/    SQLite (sqlx)
  server/   axum + SSE 中継
```

## 理由

1. **フェーズ1のスコープに対して workspace は過剰。** エンドポイント2本と
   テーブル6つの規模であり、クレート分割の管理コストが利得を上回る。
2. **境界がまだ動く。** 特に `prompt` と `domain` の責務配分は、
   実際にプロンプト組立を書いてみないと確定しない。
   クレートに固めると、境界を動かすたびに `Cargo.toml` と再ビルドのコストがかかる。
3. 単一クレートなら**あとから workspace へ分割するのは容易**。逆（統合）より安い。

### 却下した選択肢

- **最初から Cargo workspace** — 境界が未確定な段階で固めると、
  設計の試行錯誤にビルド構成の変更が付いてくる。フェーズ1では利得がない。
- **モジュール分割せず `main.rs` に詰める** — 純粋関数側（`domain`/`prompt`/`parse`）を
  I/O から隔離できず、TDD 方針が成立しない。

## 結果

### 得られたもの

- 境界を安く動かせる
- ビルド構成が単純

### 諦めたもの / 注意点

- **クレート境界による強制力がない。** `domain` から `store` を呼ぶといった
  レイヤ違反をコンパイラが止めてくれない。
  → **これはレビュアーの検出項目とする**（`domain` / `prompt` / `parse` への I/O 混入）。
- 分割の判断時期: `llm` / `store` / `server` にロジックが溜まり始めたら、
  それは分割の合図ではなく**純粋関数側へ移すべきロジックが漏れているサイン**として扱う。
