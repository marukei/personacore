# ADR-0022: 壊れた記憶・誤った記憶は、消さずに「訂正版で置き換える」

- 状態: 採用
- 日付: 2026-08-22
- 関連: [ADR-0003](0003-full-memory-injection.md)（想起の入口はひとつ）/
  [ADR-0016](0016-character-update-and-delete.md)（キャラクターの修復の導線）/
  [ADR-0021](0021-memory-extraction-format.md)（抽出）/ 作業単位 14

## 背景

**`memory` には更新も削除も無い**（絶対制約）。これは意図した設計で、
[ADR-0021](0021-memory-extraction-format.md) のほぼ全ての判断がこの制約から出ている
——遅くても正確な方を採る、捨てるなら数える、推測して埋めない。

**しかし 13c-3b で、この制約が「直せない故障」に変わった。**

`Store::recall_memories` の doc は、これを**先に予言していた**:

> **抽出の書き込み経路が入った時点で** `list_characters` の doc に書いた話が
> そのまま当てはまる（こちらは**そのキャラクターの想起が丸ごと止まる**）。

いま起きること:

- **記憶が1行でも `InvalidStoredValue` になると、そのキャラクターの `chat` が 500 になる。**
- **13c-3b で抽出も記憶を読むようになったので、抽出も止まる**（[ADR-0021](0021-memory-extraction-format.md) §13）。
- **アプリ経由で直す手段が無い。**

そして**壊れていない誤りも溜まる。** 実測で入った例:

    あなた | 店を経営している            ← ペルソナはアルバイト
    あなた | 黒い犬を「コーヒー」と名付けている  ← 猫を犬と取り違えた
    あなた | 飼育している動物の名前が犬にもつけられている（混乱がある）
                                        ← 取り違えを「事実」として書き込んだ

**キャラクターには一覧と `PATCH` の導線がある**（[ADR-0016](0016-character-update-and-delete.md)）。
**記憶には無い。**

## 決定

**「消す」道は作らない。「いま何が正しいか」を書かせ、古い行にそれを指させる。**

```
新しい行を INSERT   →   古い行の superseded_by に、その id を入れる
```

**これは絶対制約が最初から用意していた経路**である
——`superseded_by` は「上書き削除」ではなく「**時系列保持**」の列で、
`store::memory` の doc も「フェーズ2では `UPDATE memory SET superseded_by = ?` という
**正当な文**が入る」と予告している。

**想起は `superseded_by IS NULL` の行しか読まない。**
したがって**古い行を指させた瞬間、読み出し経路から外れる**
——`chat` の 500 も、抽出の停止も、これで解ける。**行は消えない。**

> **⚠ 「消えない」と「読める」は別だった**（2026-08-28 / 作業単位 D-3b で解いた）。
> **修復の一覧も `superseded_by IS NULL` で絞っていて、`MemoryView` に欄も無かった。**
> **つまりこの ADR の要である「時系列で残す」は、外からは書き込み専用に見えていた。**
> **⚠ 2026-08-27 に画面（D-3）を作って初めて分かった** ——
> 画面は**その画面が `POST` を通した行しか訂正済みとして並べられず、再読み込みで消える。**
>
> **→ `GET .../memories?include=superseded`。** **経路は増やしていない**
> （**1件を指すパスを作れば `PUT` と `DELETE` に置き場ができる**という §決定の立場は変えない）。
> **読み出しだけ。書き込みは足していない。** **各行が自分の後継を名乗るので、訂正の鎖を辿れる。**
> **上限と総数を返す**（上書き済みの行は消えないので際限なく増える）。
>
> **⚠ 画面はまだ無い**（D-3c）。**入口ができただけで、D-3 の制限はそのまま残っている。**

### 1. **後継の無い「取り消し」は作らない**

「この記憶を無かったことにする」だけの操作は**入れない。**
**直したければ、正しい方を書く。**

- 壊れた行（本文が空白のみ等）でも、**訂正版を書かせる。**
- **「消したい」は「今は何が正しいか」を言えるはず**、という立場を取る。
- これは摩擦だが、**時系列保持という設計の中心をそのまま守る形**である。

> **循環は構造的に作れない。** 後継は**必ず新しく作る行**なので、
> 後継が古い行を先に指していることはありえない。
> （複合外部キーが**別キャラクターの行を指すこと**も既に潰している。）

### 2. **修復の入口には、壊れた行が見える一覧が要る**

`recall_memories` は**1行でも壊れていると丸ごと落ちる**ので、修復には使えない。
**壊れた行を「壊れている」と示せる一覧**を別に置く
——キャラクターで同じ問題を解いた形（[ADR-0016](0016-character-update-and-delete.md) /
`CharacterEntry::Unreadable`）をそのまま使う。

> **これは [ADR-0003](0003-full-memory-injection.md) の「想起の入口はひとつ」に反しない。**
> **想起ではない。** 管理のための一覧で、プロンプトには一切載らない。
> **混同しないよう、名前と置き場所で区別すること。**

> **⚠ [ADR-0016] の教訓をそのまま持ち込むこと。**
> `enum { Readable, Unreadable }` を「呼び出し側が無視できない形」と書いたが、
> **`filter_map` で捨てる実装はそのままコンパイルが通った**（`0012b`）。
> **`ValidTag` と同じ強さに読める文言を書かないこと。** 守るのは見張り番である。

### 3. **書き込みは1つのトランザクションで**

INSERT と UPDATE は**両方入るか、どちらも入らないか**でなければならない。
片方だけ通ると、**後継のない訂正版**か、**存在しない行を指す古い行**が残る。

> **⚠ `BEGIN IMMEDIATE` を使うこと。** 古い行の存在を確かめてから書くので
> **読んでから書く形**になり、素の `BEGIN` では `SQLITE_BUSY_SNAPSHOT` になる
> ——**`busy_timeout` では救えない**（`0011a-2` で 315 回中 298 回失敗した実測がある）。

### 4. **`locked` は「読めるか」だけ見る。意味には触れない**

> **⚠ 当初この節は「読みも書きもしない」と書いていた**（2026-08-22 に訂正。14a の実測）。
> **それでは、この ADR が存在する理由そのものの故障が、修復の入口から見えなくなる。**
>
> `memory` の行が読めなくなる経路は4通りある（主語・本文・分類・`locked`）。
> **一覧が `locked` を検証しないと、`locked ∉ {0,1}` の行だけが「読めた行」として並ぶ。**
> **その行はチャットも抽出も止めているのに、修復の一覧は健全に見える。**

**したがって一覧は `locked` を「0 か 1 か」だけ見る。** それ以外は一切しない:

- **絞り込みに使わない**（`locked` の行も並べる）。
- **訂正の可否に使わない。**
- **書き込まない**（訂正版は DB の既定値 0 のまま）。

**`locked` が何を意味するかは、まだ決めていない。** 決めているのは
**「0 / 1 以外なら読めない行」**だけである。

### 5. **自動化はしない**

**人が叩く導線だけを作る。** 抽出が自分で「これは前の記憶の訂正だ」と判断して
`superseded_by` を書く道は、**別の判断**（フェーズ2）であり、
**誤って上書きすると正しい記憶が読めなくなる。**

## 理由

1. **故障が「直せない」から「直せる」に変わる。** いま記憶が1行壊れると、
   そのキャラクターは**チャットも抽出も止まり、アプリ経由で回復できない。**
2. **フェーズ2の入口がこれと同じ経路である。** 手で叩ける形を先に作れば、
   自動化するときに**書き込み側の不変条件がすでに実装され、見張られている。**
3. **抽出が誤った事実を書くことは実測済み**（[ADR-0021](0021-memory-extraction-format.md)）。
   **誤りが恒久である前提で設計を続けるより、訂正できる前提に変える方が、
   以後の判断が素直になる。**

### 却下した選択肢

- **`DELETE` を入れる** — 絶対制約違反。**「以前はXだったが今はY」が復元できなくなる**、
  という設計の中心をそのまま捨てることになる。
- **`content` を `UPDATE` して直す** — 同上。**履歴が消える。**
  しかも「どの時点で何を信じていたか」が追えなくなり、
  **抽出の品質を後から測り直せなくなる。**
- **壊れた行を想起側で読み飛ばす** — 一見親切だが、
  **壊れていることに誰も気づかなくなる。** いまの「丸ごと止まる」は
  **うるさいが正しい**（`InvalidStoredValue` として原因も残る）。
  **静かに間違うより、うるさく止まる方を選ぶ。**
- **抽出に訂正まで任せる** — 上記5。**誤った上書きは、誤った追加より悪い。**

## 結果

### 得られるもの

- **記憶が1行壊れてもキャラクターが死なない。**
- **誤った記憶を、履歴を残したまま無効化できる。**
- **フェーズ2の書き込み経路が、見張り番つきで先に立つ。**

### 諦めたもの / 前提

- **「ただ消す」ができない。** 訂正版を書く手間が必ずかかる。
- **行は増え続ける。** `superseded_by` の付いた行も残るので、
  **テーブルは単調増加**する。想起には載らないが、容量は食う。
- **一覧が増える。** 想起の入口と管理の一覧が別々に存在することになり、
  **混同されうる。** 名前と置き場所で区別する。

### テストで守ること

- **`superseded_by` を付けた行が、想起から消えること。**
- **行が消えていないこと**（`SELECT` すれば依然そこにある）。
- **INSERT と UPDATE が不可分であること**（片方だけ通る道が無い）。
- **後継の無い取り消しができないこと。**
- **別キャラクターの行を指せないこと。**
- **壊れた行が一覧に現れること**、かつ**壊れた行があっても一覧が丸ごと落ちないこと。**

## 走査で守れる範囲（2026-08-22 / 14a で測り直した）

**絶対制約「行を DELETE / UPDATE で潰さない」は SQL のテキスト走査で見張っている。**
**その射程を正確に書く。**

| | |
|---|---|
| **守れる** | 後継の印を消す文が**ソースに綴られている**形。`superseded_by` に NULL を綴る代入、および **1行を指さない更新**（`WHERE character_id = ?` 等） |
| **守れない** | 正当な文（`... WHERE id = ?`）の**プレースホルダに `None` を束ねる**形 |

> **⚠ 司令塔は当初これを「塞いだ」と書いた。過大主張だった。**
> **SQL 文そのものは正当な上書きと1バイトも違わないので、テキスト走査では原理的に見えない。**
> **正しくは「文の形は縛った。束ねる値は縛れていない」。**
>
> **いま寄りかかっているのは「その1文が1箇所しか無い」ことだけである。**
> 縛るとしたら型の側（束ねる値を `MemoryId` に限る）。

**許可形は完全一致にしてある** —— `UPDATE memory SET superseded_by = ? WHERE id = ?` だけ。
`WHERE id = ? AND …` のような**足す形も落ちる。**
**「どこまでが安全な追加か」を走査に判定させるより、新しい形が要るときに
許可形を書き換えさせる**（＝レビューが掛かる）方を選んだ。

## 拒否の優先順（14a）

**別キャラクターの・すでに上書き済みの記憶**を指したとき、**宛先違いを先に返す。**

> **`MemoryAlreadySuperseded` を返すと、「その記憶は存在し、訂正済みである」という
> 他キャラクターの状態の開示になる。** 加えて運用者の調査先が変わる。
