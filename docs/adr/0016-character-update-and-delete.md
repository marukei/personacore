# ADR-0016: キャラクターの更新と削除を持つ。識別子は不変、削除は会話が無いときだけ

- 状態: **採用**
- 日付: 2026-08-15
- 関連: [ADR-0008](0008-admin-api.md)（`/admin/` の位置づけ） /
  [ADR-0011](0011-character-handle-and-display-name.md)（識別子と呼び名の分離） /
  [ADR-0004](0004-session-identification.md)（正規化キーとゴースト行）

## 背景

**キャラクターは運用者が編集する設定である。** 呼び名を変える、ペルソナを微調整する、
実験で作った個体を捨てる——どれも普通に起こる。
フェーズ2では**会話の結果で性格値が変動する**案もあり、そのときは更新が前提になる。

にもかかわらず、いま更新できるのは**性格ステータスだけ**である。

| | 現状 |
|---|---|
| 性格ステータス | `PUT /admin/characters/{name}/stats` |
| 表示名・ペルソナ・出力形式 | **更新できない** |
| 削除 | **できない** |

**この欠落が、他の欠陥を全部増幅していた。**

- 「保存はできるのに以後のチャットが必ず失敗する」（上限の穴。**3回出た**）
- 「呼び名の無いキャラクターを作れて、二度と直せない」（[0009](../06-roadmap.md)）

**入口を厳しくしても、既に作られた行には届かない。**

> **`memory` に更新・削除を作らない方針（ADR-0008）と混同しないこと。**
> あちらは「以前は X だったが今は Y」を支えるための**時系列保持**が目的であり、
> **`character` は運用者が書いた設定**である。性質が違う。
> [ADR-0009](0009-character-attributes-and-facts.md) も
> `character_attribute` について「更新・削除の API を持つ」と既に書いている。

## 決定

### 1. 更新は「表示名・ペルソナ・出力形式」だけ

**識別子（`character.name`）は不変とする。**

`model` フィールドで指す値であり、変えると **FE 側に保存された `aoi@42` が指さなくなる。**
[ADR-0011](0011-character-handle-and-display-name.md) が識別子と呼び名を分けたのは
**まさにこのため**で、「名前を変える」の実態は**呼び名の変更で足りる。**

**識別子を不変に保つと、FE 側の設定が壊れる経路が原理的に無くなる。**

### 2. 削除は「会話が1つも無いとき」だけ

**セッションが1つでもあれば拒否する。**

- **作り損ないの掃除**には十分（実験で作った個体はまだ会話していない）。
- **会話を黙って失う事故が起きない。** カスケードで `session` / `message` / `memory` まで
  消す案は、**誤削除が取り返しつかない**うえ、フェーズ2の時系列保持と衝突する。
- 会話のあるキャラクターを消したくなったときの導線は**別途決める**（この ADR では決めない）。

### 3. 一覧は、壊れた行を握り潰さずに**指し示す**

**これが無いと、更新 API を足しても修復に届かない。**

`Store::list_characters` は行を読んで `parse` を通すので、
**不正な行が1件でもあると一覧が丸ごと失敗する。**
つまり**壊れた行の id を知る手段が無い。**

**壊れた行は、壊れていることが分かる形で一覧に出す。**
正常な行まで巻き添えにしない。**黙って読み飛ばさない**（それは別の壊れ方になる）。

### 4. 更新は、既存の行を `parse` せずに書けること

**修復が目的なので、壊れた値を読めなくても直せなければならない。**
`find_character_by_name` は全フィールドを `parse` するので、**その経路を通してはいけない。**

## 理由

### 却下: カスケードで会話ごと削除

**誤削除が取り返しつかない。** このプロジェクトは
「作った時点で直せない状態を作らない」を繰り返し優先してきた（上限の穴・0009）。
**削除でそれを裏切るのは一貫していない。**

### 却下: 論理削除（`archived` フラグ）

会話を保ったまま隠せる点は魅力だが、
**「実験で作った個体が DB に残り続ける」問題が解けない。**
「会話が無ければ物理削除」なら**掃除は完全にでき、事故は起きない。**
論理削除が要るのは「会話はあるが表に出したくない」場合で、**それはまだ必要になっていない。**

### 却下: 識別子の変更を許す

DB 上は安全（セッションは `character_id` で繋がる）だが、
**FE 側に保存された `model` 文字列が指さなくなる。**
壊れ方が「404 になる」ではなく「**別のキャラクターの最新セッションに繋がる**」形もありうる
（同じ識別子を後から別のキャラクターに付けた場合）。**不変にすればこの経路が消える。**

## 結果

- **作り損ないを掃除できるようになる。** 実験のたびに DB が汚れていく問題が解ける。
- **0009 以前に作られた壊れた行を、アプリから直せるようになる。**
  ただし**識別子そのものが壊れている行は対象外**（識別子で指せないため）。
  0009 で新規には作れなくなっているので、**残るのは既存の DB だけ。**
- **会話のあるキャラクターは消せない。** 消したくなったときの導線は未決のまま残る。
- **識別子は永久に変えられない。** 付け間違えたら、会話前なら削除して作り直す。
  **会話後は変えられない**——これは受け入れる代償。
