## 背景

### ADR-0038 §決定2 が決めたこと

サンプラ（`top_k` / `top_p` / `min_p` / `repeat_penalty` / `presence_penalty`）は personacore が持ち、要求ごとに明示で送る。
値は `RequestPolicy::PERSONACORE` の1組で、本文と裏方のすべての経路に、どの上流にも同じ値を送る（`src/llm/request.rs` の `wire_request`）。
目的は**測定が再現し、効いている値が観測できること**だった。同じ節は「**つまみにしない**（CLAUDE.md）。**環境変数を足さない。**」とも書いている。

値の根拠は C-13 で測った「当時の上流の実効の既定」である。§決定2 の代償の節はすでに次のように書いている。この機・この上流では振る舞いが変わらないが、**「別の上流」へ移ったときは違う。そちらの既定とは一致しないので、線はそこで引くこと。**

### 別の上流で、1組では会話が壊れた（2026-11-10 の実測 / marukei/personacore#30）

遊ぶ用の上流を、ADR-0054 と同じ第三者の推論サーバ（Qwen3.8-Flash-Next を VRAM・RAM・SSD に分けて載せるもの。以下「その推論サーバ」）に、中継を通さずローカルで直結して当てると、キャラクターの返答がターンごとに縮み、数ターンで台詞1つになった。

| 上流 | `repeat_penalty` 1.1（いまの固定値）で崩れた回数 | 1.0 で崩れた回数 |
|---|---|---|
| その推論サーバ ＋ IQ3_S | 2/4 | 0/4 |
| その推論サーバ ＋ IQ3_XXS | 4/4 | 1/2 |
| llama.cpp ＋ Ministral 3 14B（利用者の会話） | 30 ターン以上縮まない | （測っていない） |

- 同じ値が上流によって無害だったり会話を壊したりする。
- **同じエンジン・同じモデルでも、量子化が変わるだけで崩れ方が変わる。** 適切な値は「上流の系統（その推論サーバ / llama.cpp / …）」ではなく「エンジン・モデル・量子化の組」に付いている。その組に名前を付けているのは上流プロファイルである。
- **上流の側では直せない。** その推論サーバの文書によると、サンプリングの値は「要求 > 画面の設定 > 設定ファイル > モデルカード」の順に優先され、personacore が要求に書いた値は上流の設定で上書きできない。直せる場所は personacore だけである。

### 観測できない既定も残っている（marukei/personacore#32）

本文の要求は `temperature` を送らない（クライアントの値を通すだけで、自前の画面は送らない）。その推論サーバをローカルで直結した構成では、`reasoning_effort: "none"` が思考オフとして扱われ、モデルカードの思考オフの既定 `temperature 0.7` が知らないうちに当たっている。§決定2 が消そうとした「観測できない既定」が、本文の温度にだけ残っている。

## 決定

### 1. 面に `sampling` を足す。書ける鍵は、まず `repeat_penalty` だけ

`upstreams.json` の面（`main` / `sub`）に、任意の欄 `sampling`（オブジェクト）を足す。ADR-0042 §決定1 の「それ以外の鍵は足さない」を、ADR-0054（`context_tokens`）と ADR-0056（`api_key` / `allow_key_over_plain_http`）に続いて改める（`src/server/upstreams.rs` の `FACE_KEYS` の9つ目）。

```json
"Qwen3.8-Flash-Next IQ3_S": {
  "main": {
    "endpoint": "http://127.0.0.1:8080",
    "model": "IQ3_S",
    "sampling": { "repeat_penalty": 1.0 }
  }
}
```

- **書ける鍵は `repeat_penalty` だけ。** ADR-0036 §決定3 の3条件（§決定4）を実測で示せているのは、サンプラの5つのうちこの1つだけである（`RequestPolicy` にはほかに `reasoning_effort` があるが、サンプラではないので対象外）。ほかの4つ（`top_k` / `top_p` / `min_p` / `presence_penalty`）は、外すと壊れることを測ってから、この ADR に追記して足す。オブジェクトにしておくのは、そのときに面の鍵を増やさずに済むためである。
- **知らない鍵は名前を挙げて読み込みで止める**（ADR-0042 §決定1 の「知らない鍵は止まる」と同じ。綴りの誤りを何も知らせずに無視すると、書いたつもりの値が効かない）。まだ書けない4つも、知らない鍵として止める。範囲の検証も読み込みで行う（値の範囲は実装で決める）。
- **書いた値だけが `RequestPolicy::PERSONACORE` の値を置き換える。**
- **`sampling` を書かない面の要求のバイト列は、今と1バイトも変えない**（変わるのは §決定3 のログの1行だけ）。既定の1組（`repeat_penalty 1.1` を含む）も変えない。Ministral の構成を測り直さずに済む。
- **`sub` 面が無ければ、`main` の値を裏方の全経路（抽出・変容・約束・軸の発見と試行）にも使う。** プロファイルに `sub` 面が無いと、裏方は本文と同じ宛先（ADR-0039 §決定1）・同じモデル（`upstreams.rs` の読み込みが `main` のモデルを入れる）へ行くので、値が付く相手も同じである。`sub` 面があって `sampling` を書いていなければ、裏方には既定の1組を使い、`main` の値を写さない（ADR-0054 §決定1 と同じ規則）。
  **⚠ 裏方に値を当てることは測っていない。** marukei/personacore#30 の測定は本文の要求だけを書き換え、裏方は既定のまま走らせた。同じモデルなので裏方にも同じ値が合う、というのは推論で、抽出・変容などの振る舞いはこの決定で変わりうる。
- 値は personacore が持ち、要求ごとに明示で送る。**§決定2 の目的（再現・観測）はそのまま保たれる。** 改めるのは「つまみにしない」の部分で、改める根拠は §決定4 で ADR-0036 §決定3 の条件に当てはめる。

### 2. 走ったまま切り替えても追従する

画面から上流を切り替える（ADR-0042 §決定4）と、次の往復から切り替え先の面の値で送る（ADR-0054 §決定3 と同じ形）。

- 値あり → 値あり（値が変わる）、値あり → 値なし、値なし → 値ありの3通りすべてで、次の往復から効く。
- **切り替え先の面に `sampling` が無ければ、既定の1組に戻る。** 切り替え前の値を持ち越さない。
- **宛先とモデルが同じで `sampling` だけが違うプロファイルへの切り替えでも追従する。** 切り替えは、宛先・モデル・子の記述が同じ面を「1バイトも触らない」（`src/server/switch.rs` の「変わらない面は触らない」）。`context_tokens`・鍵・承認と同じく、`sampling` も比べる対象に足す。この切り替えは同じ量子化で値だけを変えて比べる、という使い方で現に起こる。

### 3. 送る値を言う

起動時と切り替え時に、面ごとに**実際に送るサンプラの5つの値**と、どれをプロファイルで置き換えたかを `info` で1行出す。観測できることが §決定2 の目的なので、置き換えた結果も観測できるようにする。

- これは「送った値」であって「上流で効いた値」ではない。効いた値の権威は上流の側の観測（llama.cpp なら `/slots`。ADR-0038 §決定2）である。

### 4. ADR-0036 §決定3 の条件に当てはめる（`repeat_penalty`）

| 条件 | この値 |
|---|---|
| 根拠が無い | 適切な値はエンジン・モデル・量子化の組で変わり、personacore の中に根拠は無い。上流ごとに測って決めるしかない |
| 外すと破壊的 | 遅くなるのではなく、会話が台詞1つに縮んで戻らない（IQ3_XXS で 4/4） |
| 導出も観測もできない | 上流は「この上流に合う罰の値」を答えない |

**足すつまみは2つ**（`main` 面の値と `sub` 面の値）。ADR-0036 §決定3 は「つまみ1つにつき `App::bind` を通る見張り番を1本」とする。この ADR ではつまみの数え方を ADR-0054 と同じ「面ごとに1つ」にし、次の腕を `App::bind` を通して置く。

| 腕 | 観測すること |
|---|---|
| 1 | `main` 面の値が本文の要求に載る |
| 2 | `sub` 面が無いとき、`main` 面の値が裏方の要求にも載る |
| 3 | `sub` 面に書いた値が裏方の要求に載り、本文の要求には載らない |
| 4 | `sub` 面があって `sampling` が無いとき、裏方の要求は既定の値で、`main` 面の値を写さない |
| 5 | 切り替えで、§決定2 の3通りの遷移がそれぞれ次の往復から効く。**宛先とモデルが同じで `sampling` だけが違う**プロファイルの間でも効く |

- 腕2と腕3・4は、互いを隠す実装（「`sub` は常に `main` の値を使う」「`sub` は常に既定を使う」）をそれぞれ赤にするための対である。
- 腕1〜4の固定データの値は既定の 1.1 とも、互いとも違う値にする。腕4の「写さない」は、`main` の値が既定と違わないと観測できない。
- 腕5の固定データは宛先とモデルの綴りを揃える。綴りが違うと、`sampling` を比べない実装でも切り替えが起きて緑になる。

### 5. 方言（欄の綴り・送ってよい欄・上流固有の拡張）は、この ADR では足さない

`repeat_penalty` / `repetition_penalty` の綴り、未知の欄を 400 で拒む上流のための省略、その推論サーバが受け付ける「この要求をキャッシュに残さない」欄のような拡張は、**値ではなく方言**である。足せば、ADR-0036 §決定4（上流固有の漏れは、増えたら決定の変更）を変えることになる。

- いま具体的に要るものは無い。その推論サーバは両方の綴りを受け付け、キャッシュの追い出しはその推論サーバの設定で解消できた（marukei/personacore#29）。400 で拒む上流にはまだ当たっていない。
- **⚠ 方言を足さないので、`sampling.repeat_penalty` は llama.cpp 系の綴りのまま送る。** vLLM / TGI はこの欄を `repetition_penalty` と綴る疑いがある（`request.rs` の `repeat_penalty` の doc。未確認）。その上流では、面に書いた値も今の既定と同じく効かないおそれがある。§決定3 のログは送った値しか言わないので、この食い違いはログでは見えない。
- **2つ目の具体的な必要が出たら、そのときに別の ADR で「上流の種類」を面に足すかを決める。** `src/llm/mod.rs` の `upstream_leaks` の見張り番が赤くなれば、それは決定の変更の合図である。ただし、この台帳が数えるのは `llm::lmstudio` の公開面への結合で、上流固有の綴りそのものではない（ADR-0036 の 2026-08-29 の訂正）。方言を継ぎ目の側に実装すれば緑のまま通るので、**赤くならないことは、方言を足していないことの証拠にならない。** 方言を足す変更は台帳の色にかかわらず ADR を要する。

### 6. 画面の編集では、書いた値を消さない

画面のプロファイル編集（ADR-0042 §決定8）は、面を固定の組から組み直す（`profile_editor.rs` の `FaceEdit::to_value`）。`sampling` を `FACE_KEYS` に入れただけでは、画面から保存したときに値が何も知らせずに消える。そこで ADR-0056 の `allow_key_over_plain_http`（作業単位 A-13b-2）と同じ形にする。

- **編集の依頼が `sampling` を送らなければ、保存はいまのファイルの、同じ名前・同じ面の `sampling` を残す。** 画面に欄が無いあいだも、手で書いた値は画面から別の欄を直しても消えない。~~この作業単位では依頼の型（`WrittenFaceRequest`）に `sampling` を足さない。依頼の型は知らない欄を拒む（`deny_unknown_fields`）ので、依頼が `sampling` を送ることはなく、「送らなければ残す」が常に当たる。~~ → 依頼の型に `sampling` を任意の欄として足し、省けば残す・`null` で消す・値で置き換える（[ADR-0060](0060-sampling-and-response-room-on-the-screen.md) §決定2）。「送らなければ残す」はそのまま生きている。
- `allow_key_over_plain_http` と違い、`endpoint` や `model` が変わっても落とさない。値が合わなくなる可能性はあるが、知らせずに消えるほうが、知らせずに残るより見つけにくい。残した値は §決定3 のログに出る。
- ~~**`FACE_KEYS` の doc の主規則（「画面の編集がその欄を持つまでは足さないこと」）の、3つ目の例外にする。** `api_key` と `allow_key_over_plain_http` と同じく、doc に例外の節を足す。~~ → 画面が欄を持ったので、例外から外した（[ADR-0060](0060-sampling-and-response-room-on-the-screen.md) §決定4）。`FACE_KEYS` は画面の写し（`web/src/lib/upstreamProfiles.ts`）と仕様書の閉じた綴りを兼ねるので、それらも同じ作業単位で変える。
- ~~**画面の写しでは `sampling` を「画面が欄を持つ鍵」（`EDITABLE_FACE_KEYS` / `EditableFaceKey`）から除く。** `allow_key_over_plain_http` を除いているのと同じ形にする。除かないと、画面に無い欄を持つことになり、`key: "sampling"` の 422 を存在しない欄に結びつけようとする（`isEditableFaceKey`）。~~ → 画面が欄を持つので、例外から外して `EDITABLE_FACE_KEYS` に入れる（[ADR-0060](0060-sampling-and-response-room-on-the-screen.md) §決定4）。
- 見張り番は前例に倣って2本置く。画面から別の欄を直して保存しても `sampling` が残ること（前例 `a_hand_written_approval_survives_a_save_from_the_screen`）と、`sampling` を書いていない面は保存のバイト列が変わらないこと（前例 `a_face_without_context_tokens_is_written_byte_for_byte_as_before`）。
- ~~画面で値を表示・編集できるようにする作業は、別の作業単位で後から行う。~~ → [ADR-0060](0060-sampling-and-response-room-on-the-screen.md)（作業単位 D-21）で決めた。

### 7. 本文の温度は、この ADR では決めない（未決として残す）

本文の `temperature` を面の `sampling` に入れる（クライアントが送らなかった回だけ使う）かどうかは、利用者の判断を仰ぐ。

- 入れれば、§決定2 の「観測できない既定」の最後の1つが消える。
- 入れると、クライアントが送らなかった回の値が上流の既定から personacore の値に変わる。今日の実効値は上流と思考の有無で 0.7 / 1.0 と違うので、どの上流でも振る舞いを変えない値は無い。
- **`temperature` は `RequestPolicy` の欄ではない。** 要求の本文の最上位に `ChatRequest.temperature` から別に載り、`RequestPolicy` に入れると重複キーになる（`request.rs` の `RequestPolicy` の doc と、見張り番 `the_wire_bytes_carry_each_top_level_key_exactly_once`）。`sampling` に入れるなら、§決定1 の「`RequestPolicy` の値を置き換える」とは別の規則が要る。
- 決めるまでは marukei/personacore#32 で追う。

## 理由

### 却下した選択肢

- **既定の1組を 1.0 に変える。** IQ3_S の崩れは止まるが、IQ3_XXS では 1.0 でも崩れた（1/2）ので、次に当たる上流で同じ議論が繰り返される。既存の Ministral の構成の振る舞いも変わり、測り直しが要る。
- **サンプラの5つを最初から全部書けるようにする。** 形は揃うが、ADR-0036 §決定3 の「外すと破壊的」を示せているのは `repeat_penalty` だけで、残りの4つはまだ示せていない。モデルカードが勧める値（たとえば Qwen3.8 の思考オフは `top_k 20` / `top_p 0.8`）は personacore の既定と違うが、違うことと壊れることは別である。
- **上流の系統（その推論サーバ / llama.cpp / 標準）ごとに値を持つ。** 同じ推論サーバで量子化を変えると崩れ方が変わったので、系統は値を決める単位として粗すぎる。系統は方言の単位としては正しいが、それは §決定5 の話である。
- **環境変数で上書きする。** 全プロファイルに効くので、切り替えた先の上流にも同じ値が当たる（ADR-0054 の背景の穴1と同じ）。ADR-0038 §決定2 も「環境変数を足さない」と書いている。
- **上流の側で直す。** 上流は要求に書いた値を優先するので、personacore が送る限り上流の設定は効かない。送らないことにすると、§決定2 の「観測できない既定」に戻る。
- **画面が追いつくまで、`sampling` を `FACE_KEYS` に入れず別の定数で受け付ける（ADR-0054 の A-13a-1 の形）。** その間、欄を書いたファイルは画面のプロファイルの一覧ごと扱えなくなる（ADR-0054 の追記）。§決定6 の形なら、一覧も保存も今のまま使える。

## 結果

### 得られるもの

- 上流ごとに測った値を、その上流のプロファイルに書いて使える。書かない上流の振る舞いは変わらない。
- 値は personacore が持って明示で送り、送った値をログで観測できるので、測定の再現性は保たれる。

### 諦めるもの・新しく負うもの

- 「全上流に同じ値を送る」という単純さを失う。測定を並べるときは、どのプロファイルの値で走ったかを見る必要がある（§決定3 のログで分かる）。
- つまみが2つ増え、`App::bind` を通る腕が5本要る（§決定4）。
- 画面で値を見られるようになるまでは、値はファイルとログでしか見えない。

### この ADR が答えていないこと

- 各上流に合う値そのもの。その推論サーバ ＋ IQ3_S の `repeat_penalty 1.0` は4回の比較で崩れなかったという実測であって、最適値ではない（1.05 は測っていない）。
- 裏方の要求に値を当てたときの振る舞い（§決定1 の ⚠。marukei/personacore#30 の測定は本文だけを書き換えた）。
- `repeat_penalty` 以外の4つ（§決定1）。
- 本文の温度（§決定7）。
- 方言（§決定5）。
