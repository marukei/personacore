# ADR-0032: 上流の枠は「見る」のではなく前提として宣言し、破れたら名指しで言う

- 状態: **採用**
- 日付: 2026-08-26
- 関連: [ADR-0013](0013-context-budget-layers.md)（コンテキスト予算の3層）/
  [ADR-0020](0020-context-length-requery.md)（コンテキスト長の引き直し）/
  [ADR-0019](0019-relay-idle-watchdog.md)（中継の無通信の見張り）/
  [ADR-0021](0021-memory-extraction-format.md) §6・§7（抽出は応答後に非同期・同時1件）

## 背景 —— **本文と抽出の予算の和を、誰も見ていない**

- **本文の予算**は `loaded_context_length`（16384）から決まる（[ADR-0013](0013-context-budget-layers.md) 第2層）。
- ~~**抽出の予算**は `ASSUMED_SUB_CONTEXT_TOKENS / 2`（8192）から決まる（`server::extract`）。~~
- ~~**2つは独立に、同じ 16384 から決められている。**~~
  > **⚠ 訂正**（2026-08-27 / 作業単位 B-7）。**抽出（と変容）の予算は、
  > サブモデルの窓を上流に引いた値の半分**になった（`SubContext::prompt_limit()`）。
  > **同じ 16384 から、ではない。** `PERSONACORE_SUB_MODEL` を分ければ2つは別の数になる。
  >
  > **⚠ この節の主張は弱くならない。むしろ強くなる。**
  > **和を誰も見ていないのは変わらず**、**しかも両方が実行時に動くようになった。**
  > **上流の枠（`Max Concurrent Predictions`）は、いまも API に出ない。**
- **上流は `Σ(prompt + max_tokens)` を1つの枠で捌く。**

**抽出は本文を返し切った後に非同期で走る**（[ADR-0021](0021-memory-extraction-format.md) §6 / 絶対制約）ので、
**次のターンの本文生成と重なるのは設計どおりである。**

### 実測（2026-08-26）

`Max Concurrent Predictions = 4` のとき:

| 組 | `Σ(prompt + max_tokens)` | 結果 |
|---|---|---|
| 抽出 × 3（4248+300 が3本） | 13644 | 成功 |
| 抽出 × 4 | 18192 | **0/4 成功** |
| **本文（11619+300）＋ 抽出（4248+300）** | **16467** | **2回とも両方が 500** |

    Engine protocol predict stream returned an error:
    {"code":500,"message":"Context size has been exceeded."}

**巻き添えで利用者向けの応答が落ちる。**

`Max Concurrent Predictions = 1` に変えると:

| 組 | 結果 |
|---|---|
| 本文 ＋ 抽出 同時 | **両方成功。** 本文 20.8s（**単独と同じ**）/ 抽出 35.7s |
| 抽出 × 4 同時 | **4/4 成功**（15 / 30 / 45 / 60s の**きれいな行列**） |

**加えて単発が 3.4 倍速くなった**（5.4 t/s → 16.6〜19.6 t/s）。
**枠を4つに割ることが、単発の速さそのものを削っていた。**

## 決定

### 1. **「上流の枠を見て予算を決める」は実装しない。原理的にできない**

**`Max Concurrent Predictions` は API に出ない。** 2026-08-26 に `/api/v0/models` を確認した ——
返るのは `loaded_context_length` / `max_context_length` / `state` / `quantization` だけ。

**同時に何本走っているかも、上流は教えてくれない。**
**こちらが投げた本数は分かるが、他のクライアントが投げた本数は分からない。**

### 2. **`Max Concurrent Predictions = 1` を配備の前提として宣言する**

[04-environment.md](../04-environment.md) に書く。**前提であって、こちらが強制できるものではない。**

### 3. **前提が破れたことを、名指しで言う**

**`Context size has been exceeded.` を上流エラー一般から切り出し、
「前提が破れている」と打ち手つきでログに出す。**

**いまは謎の 500 にしか見えない。**
**同じ症状の宿題が既にある**（「14B の JIT ロード中に 500 が返る」）が、
**2026-08-26 の実測で別の説明が出た。どちらだったかは分からない。**
**切り分けの手段そのものが無いのが問題である。**

> **⚠ エラー本文をそのままレスポンスに載せないこと**（絶対制約）。
> **切り出すのはログの側だけ。** `Display` は定数文字列のまま、詳細は `#[source]` へ。

## 理由

### 却下した選択肢

- **予算の和を縛る**（本文 ＋ 抽出 ≤ 16384）——
  **本文の予算を半分近くまで削ることになる。**
  **履歴と記憶が犠牲**になり、**設定で防げる事象のために製品の質を落とす。**
  しかも**上流の枠が 16384 であること自体がロード時の設定**なので、
  **縛った先が正しい保証も無い。**
- **上流のエラーを捕まえて抽出を投げ直す** ——
  **500 は本文側にも返っている。** 抽出を直しても利用者の応答は落ちたまま。
- **本文生成が走っている間は抽出を始めない** ——
  **抽出は応答を返し切った直後に始まる。** そのとき本文は走っていない。
  **衝突するのは「次のターン」**なので、**始める時点では判定できない。**
  **走り出した抽出を、次の本文のために打ち切る**手はあるが、
  **`= 1` なら行列に並ぶだけで済む**ものを、わざわざ捨てることになる。
- **`Max Concurrent Predictions` を上げて速くする** ——
  **実測で逆だった。** 単発が 3.4 倍遅くなり、そのうえ 500 が出る。

## 結果

### 得られるもの

- **謎の 500 が、打ち手のあるメッセージになる。**
- **本文の予算を削らずに済む。**

### 諦めたもの / 前提

- **⚠ これは「設定で回避している」状態である。コードは何も見ていない。**
  **`= 4` に戻した瞬間に再発する。** そのとき**名指しのログだけが手がかりになる。**
- **⚠ 行列の余裕は、これとは別の問題として残る。**
  **最悪ケースの抽出の後ろに並んだ本文は、最初の中身まで 27.1〜27.8 秒。**
  **`relay::IDLE_BUDGET` は 30 秒。**
  `QUEUE_SAFE_MAX_EXTRACTION_RESPONSE_TOKENS`(368) が上限を挟んでいるが、
  **`IDLE_BUDGET` との関係を自動で確かめている検査はどこにも無い**
  （[ADR-0021](0021-memory-extraction-format.md) §17）。
