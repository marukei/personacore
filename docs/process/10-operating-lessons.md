- <a id="l01"></a>**変異検査を「落ちるはず」で済ませない。実際に壊して落として、結果を転記させる。**
  この体制で**繰り返し見つかった問題は、ほぼ全部「テストが緑なのに守れていない」**だった。
  変異させて初めて分かる。
- <a id="l02"></a>**変異検査では、変異ごとに `Compiling personacore` が出たかを確認させる。**
  cargo は mtime で再ビルドを判断するので、`Copy-Item` のように**元の mtime を保つ手段で
  ファイルを戻す／当てると、変異版のテストバイナリがそのまま再利用される。**
  実際にレビュアーが踏んでいる（復元済みなのに `2 failed`、mtime を現在時刻にして初めて緑）。
  逆向きにも効き、**「変異を入れて赤になった」という報告が、一度もコンパイルされていない
  可能性がある。** 「Finished in 0.4s は直っていない、何もしていない」と同じ罠。
  > **`Compiling` が出ても、置換が起きたとは限らない。変異後のソースを目で見ること。**
  > `0011c` で実測: **`src/server/chat.rs` は CRLF、新規ファイルは LF** なので
  > `perl` の `\n` パターンが当たらず**一置換も起きなかった**が、
  > 直前に別ファイルを戻していたため `Compiling` は1回出て、
  > **「838 passed / 0 failed」という誤った値**になった。
  >
  > **⚠ 有効な対策が1つある —— 置換件数を数えて、1でなければ止める**
  > （`D-3c` の作業者が実装し、実際にこれで捕まえた / 2026-08-28）。
  > **多行のパターンが CRLF に当たらず一置換も起きなかったのを、道具が自分で止めた。**
  > **止めなければ「緑＝穴なし」と誤読していた形。**
  > **目視の規約は残したうえで、道具にも門を置くこと。**
  > **⚠ 門が止めたとき、まず疑うのは自分の探し方**（`D-11a` のマージ前 / 2026-09-08 / 司令塔が2回続けて踏んだ）。
  > **1回目: `s.index('}')` が `@theme` の doc コメント内の `}` を掴み、変異は何も変えずに 52 緑を出した**（門を置いていなかった）。
  > **2回目: 括弧を数えて範囲は正しくなったが、「消去の行」を探す正規表現が同じコメント内の綴りにも当たって 3 件になり、門が止めた。**
  > **行頭に錨を打って 2 件になり、1 赤。**
  > **⚠ 1回目の「52 緑」は、門が無かったから出た数である。** 信じていれば「この見張り番は位置を見ていない」と読んで、
  > **レビューの是正のほうを疑うところだった。** **このリポジトリは doc コメントが長く、綴りの言及を含むので、
  > 「その綴りが在る」だけで探す変異は、コメントに当たる。**
  > **⚠ 変異の「定義」を、結果のログの隣に必ず残すこと**（`G-2` の是正で実際に困った / 2026-09-05）。
  > **前のセッションの `m1`〜`m12` は結果のログだけが残り、適用したコマンドが消えていた。**
  > **是正後の作業者は、失敗したテスト名の署名から定義を復元して測り直し、
  > 12 のうち 7 本しか一意に決められなかった**（残り5本は「測っていない」と報告した。正しい対応）。
  > **⚠ しかも復元した1本は、赤くなったテスト名が歴史と違い、
  > 「自分の復元が元の変異と同一でない」と自分で判定している。**
  > **ログの隣に、適用したコマンドそのものを1ファイル残すこと。**
  > **⚠ そして `%TEMP%` に置いた定義は、次のセッションでは消えている**
  > （`G-5` の2周目 / 2026-09-06。**作業者が `%TEMP%` を全部見て、残っていなかった**）。
  > **世代をまたぐ回帰を当てにしないこと。** **その回で自分が定義した変異だけを権威にする。**
  > **⚠ 「前回と同じ結果でした」と書けるのは、その回に自分で定義して測ったときだけ。**
  > **⚠ そして doc だけを変える変異では `Compiling personacore` が 0 回になる**
  > （`F-3` の作業者が実測 / 2026-09-03）。**テストが実行時にファイルを読む形なら正しい振る舞い。**
  > **つまり `Compiling` は「変異が効いた」の必要条件ですらない場合がある。**
  > **権威は置換件数の門と目視。`Compiling` を合否の代わりに使わないこと。**
  > ~~**`.gitattributes` が無く、改行コードはリポジトリ内で混在している。**~~
  > **⚠ 前提を訂正**（2026-08-27 に司令塔が実測）。**「リポジトリ内で混在」は正しくない。**
  > **`core.autocrlf = true` がシステム全体に設定されていて、`.gitattributes` は無い。**
  > **コミット済み 166 ファイルを全部数えて、CR を含むものは 0 だった。**
  >
  > * **索引は例外なく LF。作業ツリーの CRLF は checkout が作っている。**
  > * **⚠ つまり作業ツリーで改行を潰しても、コミットには絶対に届かない。**
  >   **成果物が壊れる心配は無い。`cargo fmt --all` の潰しも同じで、索引には無害。**
  > * **⚠ そして `git diff` では見えない**（autocrlf が正規化するため）。
  >   **改行だけの変更は差分に一切出ない。** 差分の行数で気付ける、とは限らない。
  > * **混在の理由は「ツールが書き直したファイルだけが LF で残っている」から。**
  >   **clone した直後は全部 CRLF になる。**
  >
  > **⚠ 危険が消えたわけではない。移った。**
  > **残るのは「変異検査の道具が空振りする」だけ**（`\n` パターンが CRLF に当たらない）。
  > **しかも clone 直後は全ファイルで起きる。** 数えて確かめる規約はそのまま要る。
  > **⚠ 逆に、CRLF へ戻す手作業は要らない。** `B-7` の作業者が実際に払った（無駄になった）。
  > **Git Bash の `grep` / `sed` は CR を落とすので、CR の有無の確認には使えない**
  > （レビュアーも一度誤った）。`tr -cd '\r' < f | wc -c` で数えること。
  > **さらに `perl -0pi` は日本語コメントを含むファイルを壊す。** `13c-1` の是正で実測:
  > **ファイル全体が二重 UTF-8 エンコードになった**（`Wide character in print`）。
  > 控えから復元できたが、**変異検査の最中なので「変異が効いた」と誤読しうる形**だった。
  > ASCII だけを狙う `sed` は安全。**置換後にソースを目で見る**規約がここでも効く。
  > **PowerShell の置換スクリプトも同じ壊し方をする。** `13c-2` でレビュアーが実測:
  > **入力ファイルが欠けたときの `ReadAllText` の例外が非終端で流れ、
  > `Replace(old, $null)` が走って定数行を削除した状態で書き戻した。**
  > **控えから復元して事なきを得たが、気づけたのは目視していたからだけ。**
  > **⚠ そして `[IO.File]::ReadAllText` / `WriteAllText` は相対パスを `Set-Location` ではなく
  > プロセスの作業ディレクトリで解決する**（`A-1a` のレビューで実測 / 2026-08-27）。
  > **複製ツリーへ `Set-Location` した状態で相対パスを渡したら、`main` のツリーの古いファイルを読んでいた。**
  > **気づけたのは、探した綴りがそちらに無くて例外になったからだけ。**
  > **⚠ 両方のツリーに同じ綴りがあったら、複製したつもりで `main` を書き換えていた。**
  > **置換スクリプトには絶対パスだけを渡すこと。**
  > **⚠ `sed -i` と `awk` は、この Git Bash では CRLF のファイルを丸ごと LF に潰す。**
  > `D-0` と `B-1` のレビューで別々に実測（`src/server/config.rs` の **CR 2004本 → 0**）。
  > **1行だけ触ったつもりが全行変わる。しかもコンパイル結果は変わらないので気付かない。**
  > **`perl -0pi` を避けても `sed -i` で、`sed -i` を避けても `awk` で同じ穴に落ちる。**
  > **使うなら `tr -cd '\r' < f | wc -c` で前後に数えること。**
  > **⚠ `-i` を付けなくても同じ**（2026-08-26 に司令塔が実測）。
  > **`sed -n '1,93p' f > new` で組み直したら、`web/README.md` の CRLF 145 本が 4 本になった。**
  > **書き込みの `-i` を避けても、読み出しの `-n p` で同じ穴に落ちる。**
  > **`head` と `tail` は CR を保つ**（同じ回に測って確かめた）。**組み直しはこの2つで行うこと。**
  > ~~**差分の行数で気付ける** —— **1〜2行のつもりが全行になっていたら、それ。**~~
  > **⚠ 気付けない**（2026-08-27 に訂正）。**`git diff` は改行だけの変更を表示しない。**
  > **⚠ `cargo fmt --all`（書き込み側）も同じことをする。** `D-0-2` で実測 ——
  > ~~**改行が混在した状態で回すと**~~ **混在は関係ない**（`B-7` で実測 / 2026-08-27）——
  > **100% CRLF のファイルでも潰れる**（`context.rs` CR 2242→0 / `extract.rs` 3886→0）。
  > `D-0-2` の実測は `config.rs`（CRLF 2004行）が丸ごと LF になった、というもの。
  > **⚠ ただし索引は元から LF なので、これは作業ツリーだけの話**（上の訂正）。
  > ~~**⚠ 逆向きも出た** —— `cargo fmt --all` が CRLF へ揃えることがある。~~
  > **⚠ 撤回**（2026-09-03 / `B-39` のレビュアーが測って否定した）。
  > **司令塔が、作業者の報告を裏を取らずにここへ書き込んだ。**
  > **実測: rustfmt 1.9.0（`newline_style = Auto`）は、書き換えが実際に起きる4通り
  > （純 CRLF / 純 LF / 混在・先頭 CRLF / 混在・先頭 LF）で、4通りとも LF にした。**
  > **`cargo fmt --all` を現物に掛けると CR 1835 → 0。**
  > **⚠ 「CRLF へ揃った」ように見えたのは、整形の必要が無くて rustfmt がそのファイルを
  > 一度も書かなかったから**（CRLF は `core.autocrlf` の checkout 由来）。
  > **潰す向きは一定。書いたときは LF になる。**
  > **戻す手作業に意味は無い。** 変異検査の道具が当たるかだけ気にすればよい。
  > **⚠ `sed` はアンカーを付けること。** `24-2` で実測: アンカー無しの置換が
  > **テスト側のフィクスチャまで書き換え、両側が動いて「赤1本」という無意味な結果**になった。
  > **⚠ `sed` の置換文字列で `&` を素で書かないこと。** `&` は**マッチ全体**に展開される
  > （`E-1` の作業者が実測 / 2026-09-02）。**このリポジトリは Rust なので `&mut` / `&str` /
  > `&[T]` が至る所にあり、置換文字列にそのまま入る。**
  > **⚠ 結果は「意図と違う綴りが入るが、コンパイルは通る」形になりうる。**
  > **CLAUDE.md はここまで、`sed` の危険を「改行とエンコーディング」としか書いていなかった。**
  > **メタ文字は別の危険で、`-i` を避けても、CRLF を避けても、残る。**
  > **`&` は `\&` に逃がし、バックスラッシュ自身も逃がすこと。置換後にソースを目で見る規約がここでも効く。**
  > **⚠ Git Bash（MSYS）は引数の `//x` を `/x` へ潰す**（`B-40` の作業者が実測 / 2026-09-05）。
  > **置換文字列を `// コメント` で始めたら `/ コメント` が埋め込まれて構文エラーになった。**
  > **⚠ 赤で気づけたのは運で、潰れた結果が構文として通る綴りなら黙って通る**
  > （`D-4` の `/\s+/g` → `/s+/g` と同じ族）。
  > **⚠ `&` だけではない。`\t` / `\n` も展開される**（`B-38` の作業者が実測 / 2026-09-03）。
  > **⚠ Git Bash では `2>NUL` が「NUL という名のファイル」を作る**
  > （`G-5` の4周目の作業者が実測 / 2026-09-06。**リポジトリ本体の直下に 0 バイトの `NUL` が出来ていた**）。
  > **`cmd` の綴りをそのまま持ち込むと、捨てたつもりの出力がファイルになる。**

  黙って変えられるのが最も危険。
  > **⚠ 「見張り番の意味を変えていない」は、ハンクの位置で確かめられる**
  > （`G-5` のレビュアーが使った形 / 2026-09-06）。
  > **`git diff -U0` のハンクを読んで、名指しの見張り番の行が1バイトも触られていないことを見る。**
  > **⚠ そのうえで、その見張り番が「いまも生きている」ことは変異で別に確かめること。**
  > **触っていないことと、効いていることは別の主張である。**
