# web — personacore の画面

Svelte 5 + Vite 8 + TypeScript 7。**なぜこの組み合わせかは
[ADR-0031](../docs/adr/0031-front-end-stack.md) にある**（ここには理由を写さない）。

いまあるのは **8画面** ——**会話**（`#/chat`）、**キャラクター**（`#/characters`）、
**記憶**（`#/memories/{識別子}`）、**性格値と変容**（`#/stats/{識別子}`。作業単位 D-4）、
**上流モデル**（`#/upstream`。作業単位 D-9）、
**属性と変更の記録**（`#/attributes/{識別子}`。作業単位 D-12a）、
**約束・決まり**（`#/agreements/{識別子}`。作業単位 A-12a）、
**設定**（`#/settings`。作業単位 F-12b）。
2つ目は**一覧 ＋ 作成・編集**（作業単位 D-2。フォームは一覧の中で開く）**＋ 削除**
（作業単位 D-7。**会話があるキャラクターは、しまってからでないと消せない** / 下記）
**＋ しまう・戻す・完全に消す**（作業単位 A-10 / [ADR-0049](../docs/adr/0049-deleting-characters-and-conversations.md)。**しまった一覧は同じ画面の下** / 下記）**＋ 壊れた行の修復**
（作業単位 D-6。**「読み出せなかった行」の各行から開く** / 下記）。
3つ目は**記憶の一覧と修復**（作業単位 D-3 / [ADR-0022](../docs/adr/0022-repairing-memories-without-deleting.md)）で、
**キャラクターごと**なので**経路が識別子を運ぶ**（入口は一覧の各行の「記憶」）。
5つ目は **`GET /admin/upstream` を出すだけの画面**（作業単位 D-9。**読むだけ** / 下記）で、
**キャラクターに紐づかない**ので**ナビゲーションに並ぶ。**
6つ目は**いまの属性 ＋ 変更の記録 ＋ 置き換え**（作業単位 D-12a / 下記）で、
**キャラクターごと**なので**経路が識別子を運ぶ**（入口は一覧の各行の「属性」）。

## 開発時

**2つ動かす。**

```bash
# 1つめ: API（リポジトリのルートで）
PERSONACORE_PORT=9000 cargo run

# 2つめ: 画面（web/ で）。番号は1つめと同じ値（理由は下の ⚠）
PERSONACORE_PORT=9000 pnpm dev
```

**開くのは Vite の dev server の方**（既定 `http://127.0.0.1:5173`。
**この番号の権威はこのリポジトリに無い** —— `vite.config.ts` は `server.port` を
設定しておらず、**Vite の組み込みの既定**である。しかも `strictPort` の既定は `false` なので、
**塞がっていれば Vite は次の番号へずらす**（未実測）。
**確実なのは `pnpm dev` が表示する URL の方**）。

> **⚠ `vite.config.ts` に `server.port` を書いて「権威」を作らないこと。**
> **挙動はほぼ変わらない**（`strictPort` が `false` のままなら、明示してもずれる）**うえに、
> 写しを正当化するために権威を作るのは規則の向きが逆である。**
> **`server.port` はいま必要とされていない** ——書けば
> **「散文が写せるようにするためだけに存在する定数」が1つ増えるだけ。**
`/v1` と `/admin` は **Vite が axum へ proxy する**ので、
本番と同じ「同一オリジン」の形のまま書ける（ADR-0031 §3）。

**proxy 先のポートは `PERSONACORE_PORT`、無ければ `src/server/config.rs` の `DEFAULT_PORT` を読んで決めている**
（`vite.config.ts`。**写していない**）。

**⚠ 開発中は `PERSONACORE_PORT` を明示して、`cargo run` と `pnpm dev` の両方に同じ値を渡すこと**
（作業単位 F-12b / [ADR-0057](../docs/adr/0057-the-listening-port-shifts-when-taken-and-is-set-from-the-screen.md) §決定7）。
`cargo run` は、明示しなければ画面の「設定」で保存した番号を読む（既定の置き場所の `listening-port.txt`。
配布版の exe で保存した番号も同じファイルにある）。**proxy には保存のファイルを読ませない**
（保存のファイルを読む実装を2つ持たない）。明示しないと、保存した番号で起きた API と、既定を向いた proxy がずれる
（上のコードブロックの2行が両方に同じ値を渡しているのは、そのため）。
**明示しないと、ずらしでもずれる**（作業単位 F-11c / ADR-0057 §決定3）——保存した番号や既定の番号が使われていると、
`cargo run` は空いている次の番号へずらして起きるが、proxy はそれを知らない。**明示した番号はずらさない**
（使われていれば `cargo run` が止まるので、ずれたまま動くことはない）。

**proxy は `Host` と `Origin` を書き換える**（作業単位 B-58）。personacore は `Host` / `Origin` が
自分のもの（`127.0.0.1:<port>` / `localhost:<port>`）でない要求を 403 で断るので、
そのまま中継すると dev server の画面から叩く API が全部 403 になる。

* `Host` は宛先の綴り（`127.0.0.1:<port>`）に替える（`changeOrigin: true`）。
* `Origin` は **dev server 自身のオリジン**（`http://` ＋ dev server が受け取った `Host`）のときだけ
  宛先の綴りに替える。**外のページの `Origin` は替えない** ——替えると、`pnpm dev` の間だけ
  dev server が外のページの依頼を personacore へ通す中継になる。

処理は `dev-proxy.ts` にあり、`vite.config.ts` はそれを呼ぶだけ。見張り番は `tests/dev-proxy.test.ts`
（`vite.config.ts` が実際に組んだ proxy の設定に、偽の proxy を通す）。

## 本番（axum に配らせる）

```bash
cd web && pnpm build     # → web/dist
cd .. && cargo run       # 起動ログが出す URL で画面が出る
```

**⚠ この順番が本質**（[ADR-0041](../docs/adr/0041-one-executable-per-os.md) §決定2 / 作業単位 F-4a）。
**`web/dist` はコンパイル時に実行ファイルへ埋め込まれる**ので、
**`pnpm build` を後に回すと、実行ファイルの中の画面は古いまま**になる。
**`cargo build` し直すまで、いくら `pnpm build` しても画面は変わらない。**

> **⚠ ここにポート番号を書かないこと**（作業単位 B-30）。
> 在処は上の節と同じ `src/server/config.rs` の `DEFAULT_PORT`。
> **markdown は Rust のソースを読めない**（`vite.config.ts` は読める）ので、
> **写す代わりに書かない**——理由は根の [README.md](../README.md) が持つ。
>
> **⚠ 見張り番が見ているのは2つだけ**（`tests/readme.rs` の
> `the_documents_the_readme_links_to_point_at_the_default_port_instead_of_copying_it`）——
> **この文書が既定ポートを写していないこと**と、
> **在処として名指ししたファイルが本当にその定数を持っていること**（**全部の名指しを見る**）。
> **この段落が在ることは誰も見ていない** ——
> 消しても上の節が在処を指したままなので緑になる（**実測**）。

**`web/dist` はビルド成果物で `.gitignore` に入っている。**
つまり **clone した直後や `pnpm build` を忘れた状態では画面が出ない。**

**起動ログが必ずそれを言う:**

```text
INFO personacore::server: 待ち受けを開始しました … ui_source=embedded ui_origin=web/dist ui_files=0
WARN personacore::server: 画面が実行ファイルに1件も埋め込まれていません。… ui_origin=web/dist
```

* `ui_source` —— **`embedded`（実行ファイルの中）か `disk`（ディレクトリから）か。**
* `ui_origin` —— **埋め込み元、またはディスクの配り先の綴り。**
* `ui_files` —— **配れるファイルの件数。`0` なら警告も出る。**

**`PERSONACORE_WEB_DIR` を立てると、埋め込みではなくそのディレクトリから配る**
（[ADR-0041](../docs/adr/0041-one-executable-per-os.md) §決定2。**未設定は「既定のパス」ではなく「埋め込み」**）。
**用途は開発** —— `vite build --watch` の成果物を、実行ファイルを組み直さずに見る。

## 型検査

```bash
pnpm check
```

**`svelte-check --tsgo`。** `.svelte` も `.ts` も `vite.config.ts` も、この1本で見る。

**最初に必ずこの行が出る:**

```text
Version 7.0.2
```

**出なければ、その後の `0 ERRORS` は信用しないこと。**
`pnpm check` が**先に型検査器そのものを起動している**のはそのため——
**`svelte-check` は型検査器を起動できなくても `0 ERRORS` と言って `exit 0` を返す**
（上流の欠陥。**実測と、なぜこの一行で止まるかは
[ADR-0031](../docs/adr/0031-front-end-stack.md) §5**）。

> **⚠ `typescript` が2つ入っているのは冗長ではない。**
> **どちらか片方を消すと検査が成立しない。** 理由は同じく ADR-0031 §5。
> **`--tsgo` も外さないこと**（外すと TS 6 で検査することになる）。

**検証は「型検査 ＋ ビルド ＋ 単体テスト」まで**（ADR-0031 §5 / **決めた同じ日に改めた**）。
**⚠ Playwright は入れない** —— **CDP を使うので、この機の EDR が
クッキー窃取として検知してプロセスを kill する**（CLAUDE.md に経緯）。

### 時刻の測定は `process.env.TZ` に寄りかかっている（作業単位 F-7c）

**画面は `browserZone()` で機械に時間帯を訊く**ので、
**読み手の時間帯を作るには `process.env.TZ` を立てるしかない。**
**`TZ` はプロセスに効く**ので、**測定ファイルが別プロセスで走ること**が前提になる
（`vitest.config.ts` の `pool: "forks"`）。

> **⚠ `--pool=threads` を CLI で渡されると、その前提は崩れる。**
> **CLI は `vitest.config.ts` の固定に勝つ**（F-7b の実測）。
> **止められない。**
>
> **⚠ そして「うるさく落ちるから安全」ではなかった。**
> **崩れた状態では、機械の既定とたまたま同じ時間帯を名指しした腕が緑で残る** ——
> **赤の山に偶然の緑が混ざる。**
> **実測の内訳は `tests/timestamp-wiring.test.ts` の冒頭が持つ**（ここに写さない）。
>
> **⚠ 見張っているのは pool ではない。** pool を見張るのは pool を見張っているだけで、
> **本当の不変条件は「`TZ` が実際に効いていること」**である。
> 仕掛けは `tests/support/zone.ts` の **`enterZone`**（立てた時間帯が実際に解決されたか）と
> **`enterAsReader`**（**機械の既定とも目的とも違う時間帯を先に通す**）の2つで、
> **どちらも既定の走りで観測されている。**
> **機械に依らない権威は `tests/zone-control.test.ts`** ——
> **実行時に機械の既定を読んで、それとは違う時間帯で確かめる**
> （「東京を立てて東京が返る」では何も見ていない）。

### 名乗らないと、画面は時間帯を読めない（作業単位 F-7d）

**F-7c までは「呼び忘れ」を誰も見ていなかった** ——
`readerInZone` / `enterAsReader` を書き忘れても画面は動き、
**この機の既定（`Asia/Tokyo`）で描かれる。**
**東京の壁時計で書いた期待値が、この機でだけ緑になる。**

**いまは落ちる。** `vitest.config.ts` の `setupFiles` が
`tests/support/zone-setup.ts` を据え、
**「読み手の時間帯」を読んだ瞬間に、名乗っていなければ例外**になる
（`tests/support/ambient-zone.ts`）。名乗りを付けるのは `enterZone` だけなので、
**`readerInZone` / `enterAsReader` / `enterZone` のどれかを通るまで、画面は時間帯を読めない。**

> **⚠ 「どのファイルが対象か」の一覧を持たない。**
> 対象かどうかは**実際に読んだかどうか**で決まるので、
> **`App.svelte` 越しに `MemoryList` / `StatsPanel` へ届く形**も同じ門を通る。
> **`import` を書いただけでは名乗ったことにならない。**
>
> **⚠ 着手時に4本が無防備だった** ——
> `app-routing` / `app-routing-stats` / `stats-repair-panel` / `stat-scale-path`。
> **どれも時刻の綴りは見ていないが、時刻を読む画面を開いていた。**
>
> **⚠ 何を守っていないか** ——
> **どの時間帯を名乗るべきかは見ていない**（配線の権威は `tests/timestamp-wiring.test.ts`）。
> **⚠ 門が見ているのは `resolvedOptions().timeZone` の欄1つだけである** ——
> **`timeZone` を渡さない書式の `format` / `formatToParts` は落ちずに機械の既定を返し、**
> **`Date` のローカル読み（`getHours` 族 / `getTimezoneOffset`）も、**

（`#666` ×16 / `#b00020` ×14 / `#ccc` ×7 / …）。

### 任意値は「入れ物」で止める（作業単位 B-44）

**D-11a の走査は、角括弧の**中身の綴り**しか見ていなかった** ——
**色名も lab / lch / hwb / color-mix も素通りし、配布 CSS に生えた**
（**D-11a のレビューが実測。789 全緑**）。
**B-44 で、色を運ぶユーティリティの接頭辞の直後に角括弧が来る形を止める目を足した。**
**中身を読まない**ので、**色の書き方が増えても止まる**（変位が前に付いていても同じ）。

- **⚠ 長さも一緒に止まる。** **同じ接頭辞が色と長さの両方を運ぶ**ので、
  **長さが要るときは「長さである」と名乗り、かつ数字で始まる形で書く**
  （**`calc(…)` と `var(…)` の長さは止まる。型の綴りは Tailwind が検査しないので、
  信用できるのは値の先頭の字だけ**）。
- **⚠ 一覧に無い接頭辞は射程の外**（格子の並び・幅など）。
  **⚠ その通す側は、現に使われていない** —— **2026-09-17 に数えて、
  `web/src` ＋ `index.html` に任意値のユーティリティは 0 件**（`grid-cols` の綴りも 0 件。
  狭い幅の格子は `src/app.css` の素の宣言）。
  **かつてここには「`D-12b` が実際に使っている」と書いてあった。偽である。**
  **通す側の判断の当否は、まだ何にも測られていない。**
- **⚠ 「一覧に無い」は「色を運べない」ではない** —— **枠の論理的な辺の綴りが
  一覧から漏れていて、配布 CSS に色が載った**（B-44 のレビューが実測）。
- **⚠ 接頭辞を持たない形も止める**（任意プロパティ / 第2の腕）。
- **⚠ 中身の綴りを見る目も残してある** —— **そちらは接頭辞に依らない。**
- **⚠ 色を運ぶ接頭辞で「色でない値」を素で書く綴りは、咎められる**
  （階調の止め位置など。**型を名乗り、かつ数字で始まる形なら通る**）。
  **通しすぎない側へ倒した結果で、外れではない。**
  **要る日に、その型の綴りだけを通す形を足す。**

**⚠ 交換したのは「追いつけない一覧」を「増えにくい一覧」にしただけで、穴は残っている** ——
**色を運ぶユーティリティが増えた日、この走査は黙って素通りする。**
**守れていないことの全部は `tests/design-tokens.test.ts` の冒頭にある**（ここに写さない）。

### プロファイルの編集の鍵の欄と、保存の前の確認（作業単位 A-13b-3 / [ADR-0056](../docs/adr/0056-a-key-for-the-upstream.md)）

  欄の隣で言う。新しい鍵を書けば文字列、「鍵を消す」なら `null`、触らなければ送らない（＝残す。種類を切り替えても残す）。

- **承認は欄にしない。** 依頼の `allow_key_over_plain_http` は、承認したら `true`、承認しない・外すなら `false`、

  **`見た行` は内訳の和**なので、そう書く（「全部一致」と読ませない）。

  読み手が何を見るかの権威ではない（CLAUDE.md / `D-4` の実測）。
- **⚠ 注記は「事実か」まで見る**（レビュー是正 / 2026-09-08）。
  着手時ここには「**突き合わせは、起動時に測った相手といまの上流を照らした結果です**」と

  → 文を直し、**注記そのものを見る見張り番を置いた**

### 綴りを写さず、導線を張った理由（**実測**）

会話の画面が**自分で `GET /admin/upstream` を読んで綴りを出す**形も採れた。**採らなかった。**

| 理由 | 中身 |
|---|---|
| **写しが2つになる** | `/admin/upstream` の値を読む場所が2箇所になり、片方だけが黙って古びる |
| **既存の見張り番を書き換えることになる** | **`m21b`（会話の画面が `getUpstream()` を呼ぶだけ）で 21 赤 / 2 ファイル**（`chat-view-session` 15 本 ＋ `chat-view-notices` 6 本 / exit 1）。**綴りを画面に出すところまでやると 22 赤 / 3 ファイル**（`chat-view-outgoing` の「会話の画面は綴りを名乗らない」が加わる） |

**どれも `fetch` の身代わりが `/admin/upstream` を知らないために落ちる。**
**21 本の見張り番を書き換えるより、導線を張るほうが安い。**

## キャラクターの作成・編集で気をつけたこと

**入口は一覧の中**（`#/characters`）。「新規作成」と、各行の「編集」。

### **作成が通ったら、そのまま編集を続ける**（この作業単位で決めた）

**一覧へ戻さない。会話へも飛ばさない。**

- **`POST` が通った時点でその識別子はもう存在する。** 同じフォームがもう一度
  `POST` すると 409（`character_already_exists`）になるだけなので、
  **送り先を `PATCH` に切り替える。**
  見張り番は `tests/character-form.test.ts` の
  **「POST で作り、その後の保存は作ったキャラクターの PATCH になる」**。
- **一覧は裏で読み直す**（作った行が出ないと「作れていない」に見える）。
- **会話へ飛ばさないのは、作った直後のキャラクターに性格値も属性もまだ無いから**
  （どちらも別の入口 —— **この作業単位では入れていない**。下記）。

### **入れていないもの**

| 入れていない | なぜ |
|---|---|
| **`stats` / `attributes` の編集** | `PUT` の従属資源で、**丸ごと置き換え**の意味論。**別の作業単位** |
| **識別子の自動生成** | ADR-0017 が「FE ができてから」と書いている。**打たせて、サーバの検証エラーを見せる**形にしてある |
| **壊れた行（`unreadable`）の修復フォーム** | **`PATCH` は通る**（ADR-0016 §4）が、**差分を取る元の値が読めない**ので、いまのフォームでは表現できない。**別の作業単位** |

### 削除（`DELETE`）—— **本体は「消せなかったときの案内」**（作業単位 D-7）

**入口は各行の「削除」。** 設計は
[ADR-0016](../docs/adr/0016-character-update-and-delete.md) §2 ——**ここに理由を写さない。**
会話のあるキャラクターを消す道（しまう → 完全に消す）は下の「しまう・戻す・完全に消す」。

- **⚠ 消せるかどうかは、押してみるまで分からない。**
  **しまっておらず、会話が1件でもあれば拒否される**が、**判定は `store` が削除と同じ文で不可分に行う**
  （数えてから消すと、その間に始まった会話が黙って消えるため）。
  **したがって「消せるか調べてから押させる」画面は原理的に作れない。**
  **画面はそのことを隠さずに書く。**
- **確認は画面の中で訊く。`confirm()` は使わない**（jsdom で観測できない＝
  見張り番を置けない）。**押しただけでは1バイトも送らない。**
  > **⚠ 「確認を挟む」と「確認が警告する」は別の主張。**
  > **レビューの実測で、構造（即送信しない）は守られていたのに、
  > 文面は丸ごと無防備だった** ——
  > **「押してみるまで分かりません」を「会話が無いので確実に消せます」へ
  > 静かに置換できた**（ADR-0016 §2 の真逆の断言）。
  > **いまは文面そのものを見ている**（`確認は、取り消せないことと、
  > 押してみるまで分からないことを警告する`）。
  > **逆向き**——**「確実」と断言していないこと**も同じ1本が見ている。
- **⚠ 断り方を1つに潰さない。** 「**居るが消せない**」（409 /
  `character_has_sessions`）と「**そもそも居ない**」（404 / `character_not_found`）は
  **対処が正反対**で、前者は綴りを直しても永久に通らない。
  **見分けるのは `code`**（状態番号ではない —— **UI のフォールバックに落ちた 404 は
  素の本文で返る**ので、404 だけを見ると「経路が無い」を「キャラクターが居ない」と読む）。
- **⚠ 無い操作を案内しないこと。** **会話を1つだけ消す入口はいまも存在しない**
  （ADR-0049 §決定2）ので、**「会話を消せば削除できます」とは書かない。** 案内してよいのは、
  **この画面に実在する導線だけ** —— 409 には行の「しまう」→「しまったキャラクター」の一覧の「完全に消す」
  （会話・記憶も一緒に消えることも言う）と行の「編集」、404 には一覧の「再読み込み」
  （文言は `characterDelete.ts` の `HAS_SESSIONS_GUIDANCE` / `NOT_FOUND_GUIDANCE`）。
- **分類できなかった失敗には、次の一手を書かない**（`guidance` が `null`）。
  **サーバが言ったこと以上を推測しない**（`chat.ts` の `outcomeNotice` と同じ立場）。
- **成功したら一覧を取り直す。** 画面の側で行を落とすと、
  **「消えたように見えるが実は消えていない」形を作れてしまう。**

### しまう・戻す・完全に消す（作業単位 A-10）

設計は [ADR-0049](../docs/adr/0049-deleting-characters-and-conversations.md) §決定1 ——**ここに理由を写さない。**
画面の側の判断は `characterArchive.ts`（I/O なし）、描くのは `CharacterList.svelte` と `ChatView.svelte`。

- **しまう**: 上の一覧の各行の「しまう」。**確認を挟まない** —— 中身は1行も変わらず、下の一覧から戻せる。
  送るのは `PATCH /admin/characters/{handle}` の `{ "archived": true }`。しまった行は上の一覧から消え、下の一覧へ移る。
- **しまった一覧**: 同じ画面の下の「しまったキャラクター（N 件）」。**0件でも節ごと消さない。**
  各行から**記憶・性格値・属性**を今までどおり見られる（消す前に中を確かめられるように）。
  「戻す」は `{ "archived": false }` を送り、上の一覧へ戻す。
- **完全に消す**: **しまった一覧にしか置かない**（完全に消す前に必ず「しまう」を通る）。
  確認は**識別子を打ち込ませる** —— 打った文字列が識別子と一致するまで「完全に消す」は押せない
  （`purgeConfirmed`。**前後の空白を落とす・大文字小文字を畳むといった整えをせずに比べる**）。
  確認の文は、会話・記憶・性格値・属性もすべて消え、取り消せないことを言う。押すと `DELETE` が飛ぶ。
- **しまったかどうかは `archived_at` だけで決める**（`activeCharacters` / `archivedCharacters` の2つの関数だけ）。
  **欄が無い応答は「しまっていない」と読む**（しまう操作を知らない版のサーバには、しまったキャラクターが居ない）。
- **しまった時刻が読めない行**は、しまった一覧にも出ないので「戻す」が届かない。
  「読み出せなかった行」の表のその行に「しまった時刻を消す」を出す（`archivedAtFixOf`。消すと、しまっていない状態に戻る）。
- **しまったキャラクターしか居ない**ときは「1件もありません」と言わず、下の一覧にあることを言う。
- **会話の画面では、しまったキャラクターを相手に選べない**（`ChatView.svelte`）。仮に選べても、送れば 409 `model_archived` で断られる。
  **最初に開く相手も、しまっていない方から選ぶ。** しまったキャラクターしか居ないときは、
  キャラクターの画面の「戻す」で話せるようになることを案内する。
- 見張り番は `tests/character-archive.test.ts` / `tests/character-list-archiving.test.ts` /
  `tests/character-list-archived-at-repair.test.ts` / `tests/chat-view-archived.test.ts`（上の表）。

### **上限は画面でも数える。ただし写しである**

**削れない枠に載る自由文には上限がある**（CLAUDE.md 1節）。
**4欄すべて**（識別子・表示名・ペルソナ本文・出力形式指示）で
**入力中に画面側でも数える** —— 欄ごとに `いま / 上限` を出し、
**超えたら送らずに、どの欄かを名乗る。**

> **⚠ サーバも欄を名乗る。** `error.rs` の `code` は
> `persona_too_long` / `display_name_too_long` / `character_handle_too_long` /
> `output_format_too_long` と欄ごとに分かれていて、`message` も欄を名乗る。
> **画面側で数えるのは「欄が分からないから」ではなく「送る前に止めるため」。**
> **`code → 欄` の対応表は作っていない**（見張り番の無い写しが増えるだけなので、
> サーバの `message` をそのまま出す）。

- **数え方は符号位置**（Rust の `chars().count()` と同じ）。
  **`.length` は UTF-16 の個数**なので、絵文字を含む本文だけ数がずれる。
- **前後の空白は数えない**（サーバも正規化してから数える）。
  **`TRIMMABLE` は写していない** —— JS の `trim()` はその上位集合なので、
  **外れる向きが「こちらが少なく数える」に固定される**（＝早まって弾かない）。
- **`Handle::ALLOWED_CHARACTERS` と `StatScale` の上下限では判定しない。**
  **サーバが理由付きで返すので、それを見せる**（上記）。
  > **⚠ ただし `ALLOWED_CHARACTERS` と `StatScale::DEFAULT` は、画面の説明文に写してある**
  > （作業単位 D-14 —— 入力する前に使える文字と既定の値を言うため）。
  > **写し元を読む見張り番は `tests/character-form-examples.test.ts`。**
- **⚠ 編集では識別子を数えない。** **上限を超えた識別子で保存されている行**
  （＝上限を下げた後の DB）を、**数えると編集できなくしてしまう** ——
  識別子は不変（ADR-0016 §1）なので**直す入口が塞がる。**
  見張り番は `tests/character-edit.test.ts` の
  **「保存済みの識別子が上限を超えていても、その行を編集できる」**。
- **⚠ 識別子は画面側で直さない**（ADR-0017）。`" rin "` を `trim` せずに送り、
  **サーバに拒否させる** ——`Handle::parse` は「直さずに拒否する」設計で、
  **こちらで黙って直すと、貼り付け事故が「気付かないまま別の綴りで作られた」形**になる
  （識別子は不変なので後から直せない）。
  **表示名とペルソナは逆**——**サーバが正規化する**ので生のまま送る。

**上限の値そのものは写し**で、**写し元を読む見張り番がある**（上記「単体テスト」）。

### 壊れた行の修復 —— **第3のモード**（作業単位 D-6 / ADR-0016 §3・§4）

**入口は「読み出せなかった行」の各行の「修復」**（一覧の下の節）。

**ADR-0016 §4 の核心は「更新は、既存の行を `parse` せずに書けること」**である。
ところが **D-2 の編集は差分だけを送る**ので、**差分を取る元の値が読めない行には使えない。**
`UnreadableCharacterView` は **`id` と `handle` と読めなかった列名しか持たず、
格納値そのものは1つも返ってこない。**

**そこで「全部の欄を送る」モードを別に持つ**（`src/lib/characterRepair.ts` の `buildRepair`）。

| モード | 送るもの | どこ |
|---|---|---|
| 作成（`POST`） | 空でない欄（既定はサーバ） | `buildCreate` |
| 編集（`PATCH`） | **変えた欄だけ** | `buildUpdate` |
| **修復（`PATCH`）** | **4欄すべて。1つも落とさない** | **`buildRepair`** |

- **⚠ 壊れていない列も、書いた値で上書きされる。** **承知のうえで選んでいる** ——
  元の値は読み出す手段が無いので、**「壊れていない列だけ残す」を選んでも
  残った値を確かめる方法が無い。** 画面は代償を明記し、`invalid_columns` を出す。
- **⚠ 尺度は省略できない。** この列は NOT NULL で**保存済みの値も読めない**ので、
  キーを落とすと「変えない」になり**壊れた尺度がそのまま残る。**
- **初期値は空。推測で埋めない**（`MemoryList` の「読み出せなかった行」と同じ立場）。
- **⚠ `handle` が `null` の行には、修復の入口を出さない。**
  識別子は不変（ADR-0016 §1）なので `PATCH` でも `DELETE` でも指せない ——
  **直す手段は `sqlite3` だけ**（`domain::UnreadableCharacter` の `handle` の doc）。
  **無い操作を案内しない**（D-7 と同じ立場）ので、
  **「DB を直せ」も操作としては案内せず、状態の説明にとどめる。**
- **区別する拒否は2つだけ** —— `src/server/admin.rs` の `classify_update` が
  分けているのが `character_not_found`（404）と
  `stat_scale_below_stored_value`（409）だけで、**残りは全部 500。**
  500 に次の一手は無いので `unknown` のまま文言だけ出す。
  **400（`parse` の拒否）も素通し** ——**サーバが壊れている欄を名乗る。**
- **⚠ 409 の案内の文面は、いま見直せる。**
  ~~**性格ステータスを変える画面はまだ無い**（`PUT .../stats` に導線が無い / D-4 は未着手）。~~
  **→ D-4 は出荷済み**（`StatsPanel.svelte` / `#/stats/{識別子}`）。**この段はその前提で書かれている。**
  **いま言えるのは「もっと大きい尺度を入れて押し直す」だけではなく、
  「性格値の画面で下げてから戻る」も言える。** **文面の更新は未着手**（`characterRepair.ts` の
  `HAS_SESSIONS_GUIDANCE` の隣）。
- **⚠ 「型で表現できなくした」とは書けない。**
  `RepairableRow.handle` が `string` なので**そう読めるが、
  `handle: broken.handle ?? ""` は `pnpm run check` を 0 エラーで通る**（D-6 のレビューで実測）。
  **守っているのは `repairTargetOf` の `null` ガードと、それを見るテスト4本。**

> **⚠ 上限の門は、列ごとに1本ずつ見張ること**（D-6 のレビューの是正）。
> **実測**: `REPAIR_LIMITED_FIELDS` から `output_format_instruction` を落とす変異が
> **262 全緑**だった。**編集側の同じ変異は 2 赤**で、うち1本が
> `character-edit.test.ts` の **`出力形式指示は、作成でも更新でも止まる`** ——
> **D-2 が「この列は別に見張る」と名指しで置いた見張り番**である。
> **doc は写したのに、doc が名指ししていた見張り番だけを写していなかった**
> （CLAUDE.md の「doc を写すときは…」の6例目）。
> **是正後は 3 列とも個別に赤**（`1 / 2 / 2 赤`）。

> **⚠ 画面に書く列名を `string` で受けないこと**（同上）。
> **`broken(column: string)` だと、テンプレートの綴りが
> `REPAIR_COLUMNS`（写し元を読む見張り番つき）から独立した第2の写しになる。**
> **実測**: `broken("output_format_instruction")` → `broken("output_format")` が
> **262 全緑・`pnpm check` も 0 エラー**だった。
> **`broken(column: RepairColumn)` にしたので、いまは
> `pnpm run check` が型エラーで落ち、`pnpm test` も 1 赤になる**（両方を実測）。
> **そのうえで、4列すべてに「印が付く腕」と「付かない腕」を置いてある**
> ——`output_format_instruction` だけが正の主張を受けていなかった。

## 記憶の一覧と修復で気をつけたこと

**入口はキャラクター一覧の各行の「記憶」**（`#/memories/{識別子}`）。
**設計は [ADR-0022](../docs/adr/0022-repairing-memories-without-deleting.md)** ——
**ここに理由を写さない。**

- **消す道は画面にも無い。** できるのは**訂正版を足して、古い行にそれを指させる**こと
  だけで、**サーバにも `GET .../memories` と `POST .../memories/{id}/corrections` の
  2本しか経路が無い。** **文言も「削除」「修正」ではなく「訂正版を足す」で揃えてある。**
- **主語（`user` / `character`）を必ず出す。** どちらの記憶かが分からないと、
  **訂正版を書くときに主語ごと取り違える** ——しかも**持ち主を取り違えた記憶は、
  正しい持ち主へ移す手段が無い**（CLAUDE.md 1節の ⚠）。
- **読み出せなかった行を落とさない。** 落とすと、**チャットと抽出を止めている当の行が
  修復の入口から消える。** **壊れた行にも訂正版を書ける**が、
  **主語は既定を作らない**（元の値が読めないので推測しない）。
- **元と同じ内容では送らない。** ただし**判定に主語を含める** ——
  実測でいちばん多い誤りは**主語の取り違え**で、その訂正は**本文が1文字も変わらない。**
  本文だけで判定すると、**いちばん直したい誤りだけが送れなくなる。**

### ⚠ **「訂正済み」に出るのは、画面を開いている間に訂正した行だけ**

**サーバは上書き済みの行を返さない**（`SELECT_ACTIVE_MEMORY_ROWS` は
`superseded_by IS NULL` だけを引き、`MemoryView` に `superseded_by` も無い）。
したがって **`GET` だけでは「すでに訂正された行」を1件も見られない。**
**この画面を開く前に訂正された行は、ここには現れない**
——履歴を見たいときは DB を直接見る（ADR-0022 が意識的にそう決めている）。

**画面が「訂正済み」として並べるのは、いまこの画面が `POST` を通した行**で、
**それを「想起される側」に残さない**ことがその節の目的である。

**⚠ その節は画面と同じ寿命しか持たない** ——
**別のキャラクターへ移って戻れば消え**（`App.svelte` が `{#key}` で作り直す）、
**再読み込みでも消え**、**一覧の取得に失敗している間は節ごと出ない。**
**記録ではない。記録は DB の側にある**（行は消えていない）。

### **入れていないもの**

| 入れていない | なぜ |
|---|---|
| **文字数計** | 上限（`MemoryContent::MAX_CHARS` 等）を**写していない**ので出せない。長すぎればサーバが理由を返す |
| **絞り込み・並べ替え** | サーバの並び（作成順）をそのまま出す。**別の作業単位** |
| **`locked` の表示** | 意味が未確定なので API が返さない（ADR-0022 §4）。**壊れている場合だけ `invalid_columns` に列名として出る** |

## 属性と変更の記録で気をつけたこと（作業単位 D-12a）

**入口はキャラクター一覧の各行の「属性」**（`#/attributes/{識別子}`）。
**設計は [ADR-0009](../docs/adr/0009-character-attributes-and-facts.md) と
[ADR-0028](../docs/adr/0028-attributes-that-change.md)** ——**ここに理由を写さない。**

**画面は2つの節を持つ** ——**いまの値**（表 ＋ 置き換えのフォーム）と、
**変更の記録**（履歴の表）。

- **⚠ `PUT .../attributes` は丸ごと置き換えである。**
  **要求に含まれない属性は消える。空の配列を渡すと全属性が消える。**
  **「変えない」を表す手段が無い**ので、**画面は必ず全行を送る**
  （`attributesEdit.ts` の `buildReplaceAttributes` / `statsEdit.ts` と同じ作法）。
  **属性を消す手段は「送らないこと」しかない**ので、
  **「外す」は押した時点では何も起きず、保存したときに消える。**
- **押す前に、何が記録されるかを数えて言う**（`replaceSummary`）。
  **追加 / 変更 / 削除の3つを別々に出す** ——数え方は
  **`src/domain/attribute.rs` の `attribute_changes` の写し**で、
  **`(subject, key)` の組で突き合わせ、値まで同じなら数えない。**
  > **⚠ キーだけで突き合わせないこと。** `年齢` を利用者とキャラクターの両方が持つとき、
  > **持ち主をまたいだ差分**が出る（ADR-0021 が 6% 実測した主語の取り違えを、
  > 画面の側で作り込む形になる）。
  > 見張り番のフィクスチャは**わざと `user / 年齢` を `character / 年齢` の保存値と同じ綴り**に
  > してあるので、**キーだけで突き合わせる実装では数が減る。**
- **主語は必ず出す。そして足す行では既定を作らない。**
  属性は**削れない枠に毎ターン載る**ので、
  **主語を取り違えると、そのキャラクターの以後の全ターンが利用者の事実で喋る**
  （ADR-0028 §決定4）。**`<select>` の初期値は「主語を選んでください」**で、
  選ぶまで送れない。
- **保存済みの主語とキーは書き換えられない。**
  付け替えも改名も「消して足す」でしかない（`(subject, key)` が変われば別の属性）ので、
  **その2手を1つの欄に見せない** ——気付かずに属性を消すことになる。
  **要約は「削除 ＋ 追加」としてそれを言う。**
- **文字数は画面でも数える。ただし写しである**（上限の節と同じ立場）。
  **キー 12 / 値 20 / 件数 8** を写し、**越えたら送らずにどの欄かを名乗る。**
  数え方は `characterEdit.ts` の `countChars` を**そのまま使う**（写しを2つ持たない）。
- **総数を必ず言う。** `revisions` は上限で切られるので、
  **`total_revisions` との差が「見えていない件数」**である
  （`DriftView.total_votes` と同じ形）。**上限は応答の `revisions_limit` を出す**
  ——**写しを持たない**（写すとサーバ側の定数を変える変異が画面側で緑を通る）。
  > **⚠ 数だけを探す検査は、役の入れ替えを見ていない**（レビュー1周目の実測）。
  > `toContain("208")` は**その数が文中のどこかに在る**しか言わないので、
  > **総数と出した件数を入れ替える変異が 959 全緑を通った。**
  > **数は必ず、それを名乗る語と一緒に探すこと**（`全 208 件` / `新しい 200 件` / `残り 8 件`）。
  > **⚠ そして、切られている状態では出した件数と上限が必ず同じ数になる**ので、
  > **その2つを見分けられるのは「全部出している」腕だけ**である（3 件 / 上限 200 件）。
- **`before` / `after` の `null` を、同じ見え方にしない。**
  **`before` の `null` は「無かった」（＝追加）、`after` の `null` は「消えた」（＝削除）**で、
  **潰すと追加と削除の区別が画面から消える。**
- **保存が通ったら、記録を読み直す。**
  読み直さないと、**いま自分が起こした変更だけが表に出ない**
  ——「静かに変わったことに気付く」ための表なのに、それでは目的を果たさない。
  > **⚠ 見張り番は「保存前の応答には無かった行が現れること」を待つ。**
  > 「表に行がある」を待つと、**保存前から4行あるので即座に成立する**
  > （`vi.waitFor` は最初に成立した時点で返る / D-4 の教訓）。
- **⚠ 通った回だけ読み直す。断られた回は、打った下書きを残す。**
  **`await load()` を `finally` へ置かない**（レビュー1周目の指摘 / 変異は 959 全緑だった）——
  断られた回にサーバの値から下書きを作り直すと、
  **案内が指す行が画面から消える**（`duplicate_attribute` の案内は
  「片方を「外す」か、キーを直してください」と言うのに、その2つ目の行はもう無い）。
  **保存の失敗は打ち直させるためのものなので、打ったものを消してはならない。**
- **「再読み込み」は、打ちかけを捨てて作り直す。**
  残すと、**別の窓で変わった値の上に古い写しを書き戻す** ——
  `PUT` は丸ごと置き換えなので、それは**その属性を古い値へ戻す**ことであり、
  **属性は削れない枠に毎ターン載る**ので、以後の全ターンがその古い事実で喋る。
  > **⚠ 見張り番は「待つ前に、打った値が在ること」を見る**（同じ `D-4` の形）。
  > これが無いと、**打てていなかった回**（欄が最初からサーバの値）でも緑になる。
- **2つの読みは独立に扱う。**
  **1行でも壊れていれば履歴の一覧だけが 500 になる**（属性そのものの読みも置き換えも通る）。
  **片方の失敗で画面ごと落とすと、記録が読めないだけで置き換えの入口まで消える。**
- **記録を消す・直す操作を生やさない。** 履歴は追記のみで、
  **書くのは `PUT .../attributes` ひとつ**（ADR-0028 §決定5）。
  **サーバにも 1件を指すパスすら無い。**

### 守れていないこと

- **壊れた行の修復フォームが無い。**
  `GET .../attributes` が 500 になる状態（上限を超えた値が保存されている等）でも
  **`PUT` は既存の行を読まないので届く** ——つまり**サーバ側には修復経路がある。**
  **しかし画面は下書きを `GET` から作る**ので、その回はフォームを描けない。
  `StatsPanel` の `StatsRepairForm`（D-8）に当たるものは**作っていない。**
  **いまの手段は `curl` か `sqlite3`。**
  **⚠ 画面は「読み出せない」までしか言わない** ——`ApiError::internal()` に `code` は無いので、
  **格納値が壊れた 500 と DB 障害の 500 を FE は区別できない。**
- **修復した件数が画面から見えない。**
  **壊れた行を直しても履歴に残らない**（`docs/03-data-model.md`
  「壊れた行の修復は履歴に残らない」——履歴側の CHECK が写しなので、
  壊れた値を `before` に書くと INSERT が落ち、**唯一の修復経路が閉じる**）。
  **サーバは `warn` を残して修復を通す**ので、**その事実はログにしか無い。**
  **応答に件数を載せる案は宿題**（同 doc / 応答の形が変わると欄の突き合わせに触れる）。
- **200 件を超えた履歴は、総数でしか見えない。**
  **1件を指すパスも、続きを読む問い合わせも無い**（`revisions_limit` は 200）。
  **古い変更を読む手段は `sqlite3` だけ。** 画面はそう書く（「残り N 件はここに出ていません」）。
- **`too_many_attributes` / 空 / 長すぎの `code` を読み分けていない。**
  **画面が送る前に止める**ので、**そこへは（上限が食い違っていない限り）来ない。**
  来たときは**サーバの文言をそのまま出す**（欄を自分で名乗るので、言い換えると情報が減る）。
- **表は狭い幅で畳んでいない**（5列）。D-11b の「守れていないこと」と同じ立場 ——
  **列を畳むのは `D-12b`。**
- **「実際に読み上げられるか」は、どのテストも言えない**（jsdom は読み上げない）。
  見ているのは**属性と、その要素が持つ文字**まで。
