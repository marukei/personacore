# ADR-0015: 性格ステータスの尺度をキャラクターごとに持つ

- 状態: **採用**
- 日付: 2026-08-15
- 関連: [ADR-0012](0012-stat-section-directive.md) の未決「尺度をどこに置くか」を閉じる

## 背景

**本番のプロンプトは、性格ステータスの尺度を一切載せていない。**
`STAT_NOTE` は「数値が大きいほどその傾向が強く出ます。」とだけ言い、**範囲を言わない。**

[ADR-0012](0012-stat-section-directive.md) の実測で分かったこと:

- **尺度を伝えないと、数値は裸のまま**で意味を持たない
- **伝えると数値が意味を持つ**（合成した定数行の下では (A) の再発も起きない）
- **刻みは軸の方向に沿わない**ので、**小数は実装しない**（同 結論3）

測定で「尺度あり」を再現したのは `base_persona` に手で書いた個体である。
**つまり測って良かった構成が、本番では動いていない。**

もう1つ、`StatAlloc::value` は **`u32` で上限が無い。**
`0〜10` と宣言しても `100` を保存でき、**宣言と実データがずれる。**

## 決定

**尺度をキャラクターごとの独立した項目として持つ。**

- 値の上限を持つ列を `character` に足し、**プロンプトには事実として載せる**
  （定数行ではなく、軸の一覧と同じ引用行。**尺度は指示ではなく事実**）。
- **`StatAlloc::value` の上限をその尺度に従わせる。** 型で「尺度を超える値」を作れなくする。

  > **型が守る範囲は「尺度を超える値」までで、そこが限界**（2026-08-19 / 0011a-2 の着手時に確定）。
  > **どの尺度で検証したかは型が覚えるが、「その尺度がそのキャラクターのものか」は型では守れない。**
  > `3/100` と `3/10` は**別の性格**なのに、どちらも `3` として通ってしまうため、
  > **照合は `store` が保存済みの尺度と突き合わせる実行時の検査**になる。
  > **`ValidTag`（[ADR-0006](0006-slot-based-tag-compilation.md)）と同じ強さだと読まないこと。**

- **小数は入れない**（[ADR-0012](0012-stat-section-directive.md) 結論3）。整数だけを受ける。

**`0〜10` か `0〜100` かはこの ADR では決めない。** 既定値を決めれば足り、後から変えられる。

> **既定は `10`、上限は `100` に決めた**（2026-08-19 / 作業単位 0011a-1）。
>
> [ADR-0012](0012-stat-section-directive.md) の実測が既に2つ言っている:
>
> * **段数そのものは応答の質にほぼ効かない**（「段数の選択（0〜5 か 0〜10 か 0〜100 か）は…」）。
>   効くのは**尺度を伝えるかどうか**と**値が範囲のどこにあるか**。
> * **`0〜100` は採らない。** 尺度を伝えると**上端で形式が崩れる**
>   （理由は一度変わったが、採らない結論自体は残っている）。
>
> **効かない軸なら短い方を既定にする**（プロンプトのバイト数だけが差になる）ので `10`。
> **`100` は「表現できる範囲」であって推奨ではない。**
> キャラクターごとに変えられるので、比較実験で上端を試す道は残る。

### 尺度の下限は `1`。**値の下限は `0`。別物である**

> **⚠ この節の理由は一度間違っていた**（2026-08-20 に訂正）。
> 当初 **「`0` を許すと一行も載らないキャラクターが作れてしまう」** と書いていたが、
> **それは尺度がいくつでも作れる**（全軸に `0` を入れればよい）。
> **`MIN = 1` はそれを防いでいない。** しかも
> **「一行も載らない」こと自体が欠陥ではない** —— 軸が0本のキャラクターは正当な形で、
> `the_show_dont_tell_line_is_unconditional` が軸数 0 を通している。
> **誤った理由を残す方が、理由が無いより危ない**（CLAUDE.md）。

尺度 `0` が実際に作るのは、**値を何に設定しても性格ステータスの節が出ない**キャラクターである。
**黙ってはいない**（非ゼロの値は `stat_value_above_scale` で弾かれる）ので、
これは**失敗を防ぐ境界ではなく、得るものが無い状態を表現できなくする境界**にすぎない。
`0〜0` は幅が1点しかなく、「大きいほど強い」という方向が意味を持たない。

### 値 `0` は正当な値で、**絶対制約がそれに依存している**

**`StatValue` に下限は無い**（`u32` なので `0` が床）。`0` は「その軸は考慮しない」を意味し、
`prompt` が**軸ごと落とす**（CLAUDE.md 絶対制約。「パッション: 0/10」と書くと
モデルが情熱の欠如を過剰演技して無感情になる）。**`0` の性格は存在する。**

**「少なくとも1軸は `1` 以上」という制約は入れない。**
全軸 `0` は「軸はあるが、いまは考慮しない」という正当な状態で、
**空リストとは保存されるデータが違う**（軸名が残る）。
禁じると、**軸名を `0` で置いておく使い方が消える。**

### 尺度を下げる更新は拒否する（2026-08-19 / 作業単位 0011a-2）

**保存済みの値より小さい尺度への `PATCH` はエラーにする。**

許すと、**その `PATCH` 一回でそのキャラクターの性格ステータスが読めなくなり、
以後のチャットが必ず失敗する。** これは**この ADR が閉じると宣言した穴そのもの**を、
アプリ自身が新しい経路から開けることになる。

却下した選択肢:

- **黙って切り詰める（クランプ）** — **データが黙って変わる。** 「50 だったはずの軸が 10 になった」を
  観測する手段が無い。`memory.superseded_by` を「上書き削除」に使わないのと同じ理由。
- **超える軸を消す** — さらに強い破壊。しかも消えた軸は `prompt` が節ごと落とすだけなので
  **エラーにも警告にもならない。**
- **許して読めなくする** — 上記のとおり。復旧は `PUT .../stats` で可能だが、
  **止まるまで誰も気付かない。**

**復旧経路は順序で足りる。** 先に `PUT .../stats` で値を下げ、次に尺度を下げる。
**どちらも既にある API で、新しい入口を足さない。**

> **代償: 尺度を下げるには2回の API 呼び出しが要り、順序が決まっている。**
> GUI から見ると「先に値を下げてください」と案内する必要がある。
> **拒否の理由がエラーで区別できること**（尺度が小さすぎるのか、他の理由か）を
> 実装の条件に含める。

> **⚠ 「順序で足りる」が成り立つのは `stat_alloc` 側だけが壊れている場合**
> （2026-08-19 / 0011a-2 のレビューで実測）。
> **`character.stat_scale` 列そのものが壊れた行には `PUT .../stats` が届かない** ——
> 置き換えも保存済みの尺度を `parse` するため、同じ `InvalidStoredValue` で止まる。
> その行は**先に `PATCH` で尺度を直す**必要があり、保存値が大きいと
> **一旦尺度を上げてから下げる3手**になる。**手順は `store` 側の doc が正。**

- **GUI で明示できる。** 「この軸は 0〜10 の整数」と画面に出せる。
  **小数が無意味であることも同時に明示できる**ので、利用者が試して失望する経路が消える。
- **`base_persona` への手書きが不要になる。** 手書きは**書き漏らした個体だけ静かに劣化する。**
  これは ADR-0012 が `output_format_instruction` について挙げたのと同じ理由。
- **`value` に上限が入る。** CLAUDE.md の「削れない枠に載る自由文は必ず上限を持つ型にする」を、
  自由文ではない数値にも広げる形になる。

### 却下: `prompt` 層の定数で固定する

**宣言と実データがずれる。** `value` が `u32` のままなら `100` を保存でき、
プロンプトには「0〜10」と書かれる。**モデルは矛盾した入力を受け取り、
その矛盾はログにもエラーにも出ない。** 上限を型に入れるなら、
**その上限がどこかに保存されている必要がある**ので、結局は列が要る。

### 却下: 載せない（現状維持）

予算はゼロで済むが、**実測で得た「尺度を伝えると数値が意味を持つ」という結果を使えない。**

### 予算をどう払うか

**尺度を明示すると `STAT_NOTE` の「数値が大きいほど」が冗長になる。**
そこを削れば**足す分をおおむね相殺できる**（削れる分の方が大きい）。

> **削れない枠の余白は 2 バイトしかない**（[ADR-0012](0012-stat-section-directive.md)
> 「余白という数字の出どころ」）。**先に相殺の見積もりを取ってから実装すること。**
> **足りないときに上限（`Persona::MAX_CHARS` 等）を削る方向へ反応しないこと。**

## 結果

- **測定で良かった構成が本番でも動く。**
- **`value` の上限が型で守られる。** 「保存はできるのに以後のチャットが必ず失敗する」型の穴が
  1つ減る（性格値については）。

  > **これが成り立つのは 0011a-2 以降。** 0011a-1 は**列を往復させるだけ**で、
  > **`StatAlloc::value` は `u32` のままであり、尺度を超える値をいまも保存できる。**
  > 型側の doc（`src/domain/stat.rs` の `StatScale`）は
  > **「この型は値を縛らない」と明言している。** 食い違って読めるのはこの節だけなので、
  > **先にこの注記を読むこと。**
- **スキーマ変更が要る。** 既存行には既定値を入れる。
  **適用済みのマイグレーションは編集しない**（新しい `000N_*.sql` を足す）。
- **尺度の上限（0〜10 か 0〜100 か）は未決のまま残る。** ただし
  **後から変えられる形になる**ので、決めるまで進行が止まらない。
- **キャラクターごとに違う尺度を持てる。** 比較実験で「同じ相対関係・違う尺度」を
  1つの DB で並べられる（ADR-0012 の測定はキャラクターを分けて実現していた）。
