## 2. 次の一手

**origin#43（A-9c: 試用と判定）。** Issue に申し送りが2つある（`gh issue view 43 --comments`）:
1. 却下・不合格の名前には上限が無く、溜まると候補づくりの依頼が「長すぎる」で**永久に止まる**。A-9c で不合格を作り始めるので、ここで手当てする。
2. 試用の票の `session_id` がキャラクターに縛られていない（`stat_drift_vote` と同じ前例）。

**origin#43 の後**: 司令塔が ADR-0046 §測る問い（**合格率**と、**美徳の名前がどれだけ出るか**）を既存の台本（`<measurements>\`）で測り、利用者に見せてから第2段（提案の画面・採用・却下）へ進むかを相談する。**合格率がほぼ 0 なら作る価値が無い**と ADR に書いてある。
> **実機で1件だけ見た**（origin#42 の確認 / Ministral 14B）: 候補は **「準備神経」** —— 造語めいた名前。1件なので何も言えないが、測る価値の兆しではある。

痛みの出うるもの: **origin#39**（プロファイルの切り替えの途中で画面を移ると、差し替えが途中で落ち、死んだ子の「準備完了」が残る —— **読んだだけの推定。まず実測**）。v0.1.3 の Release の説明で「準備完了まで待つ」と案内してある。

## 3. この期間に分かった、運用の形

- **全体の `cargo test` が一時的に遅くなり、無関係な赤がまとめて出る回がある**（2026-09-26〜27 に3回。`store_session` 32 本・`upstream_launch` 1 本で 1035 秒・`store_schema` 2 本）。**Rust を変えていないマージの後でも起きた。** 手順: 赤のテスト名とメッセージを見る → そのバイナリを単独で回す → 全体を回し直す。緑なら既知の揺れの一覧（CLAUDE.md §4）へ足す。**原因は特定していない**（利用者の llama は動いていなかった）。
- **定型の A/B を初めて回した**（`docs/process/model-tiering-log.md`）: Opus low（origin#40）は報告が英語・リポジトリ固有の作法を依頼に書かないと拾わない、Sonnet high（origin#34）は手戻り 0 だが doc に1件のずれ。**単位の大きさが違うので比較はまだ言えない。** 依頼に「報告は日本語で」を書くこと（設計階層の Opus も一度英語で返した）。
- **Issue の番号の衝突**: origin#34 を B-54 と名乗ったが、B-54 は origin#26 が先に使っていた（B-57 に改めた。コミットの綴りは B-54 のまま）。**新しい番号を振る前に `gh issue list --state all --search "<番号> in:title"` で確かめる。**
- **Issue の無い作業単位を出しかけた**（origin#40。作業者を出した直後に Issue を開き、`Closes` を追って伝えた）。ADR-0043 のとおり、**出す前に開く**。
- **作業者・レビュアーは変異を作業ツリーに直接当てることがある**（D-15 の作業者・D-18 のレビュアー）。依頼に「**変異は複製ツリーで**」と毎回書く。
- **1つの画面の単位とサーバの単位が API の写しの走査（`api-fields` / `character-repair`）で結びつくときは、同じブランチで続けて作って一緒に `main` へ入れる**（origin#31+origin#32、origin#35+origin#4）。`main` に赤を置かない。
- **`taskkill //IM personacore.exe` は利用者の exe まで殺す。** 自分が起こしたものは PID で止める。
- **Bash のヒアドキュメントの中の `\\` は化けることがある**（変異の道具で踏んだ）。バックスラッシュは `chr(92)` で組む（CLAUDE.md §4 の既存の規則）。
- 前の引き継ぎ §3 の運用（MSIX の仮想化で `LOCALAPPDATA` を一時ディレクトリへ／実機の確認は別のポート＋`--no-browser`／`Remove-Item` は単独の呼び出しで／長いパスの削除は `\\?\` を付ける）は今も有効。
