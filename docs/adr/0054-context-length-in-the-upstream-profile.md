## 背景

C-21 で、第三者の推論サーバ（Qwen3.8-Flash-Next を VRAM・RAM・SSD に分けて載せるもの。以下「その推論サーバ」）を遊ぶ用の上流にすると決めた。
personacore からつなげるのは、その推論サーバの host が開く中継（ループバックの1つのポート。例 `127.0.0.1:46001`。鍵なし・ローカル限定）だけである
（この中継には鍵を作れることが、のちに分かった。利用者が鍵を作った —— [ADR-0056](0056-a-key-for-the-upstream.md) の「鍵で守られた中継」）。

- 推論サーバ本体（中継とは別のポート。例 `:46002`）は API キーが必須で、**デスクトップアプリはモデルを読み込むたびに鍵を作り直す**（作り直すので、書き写した鍵は古くなる）。
  personacore に鍵を送る設定を足しても（A-13b）、利用者がデスクトップアプリを使う限り、本体には直接つなげない
- **中継の `/v1/models` は `meta.n_ctx` を落とす。** personacore は `/api/v0/models` と `/v1/models` の両方を読む（G-2）が、どちらからもコンテキスト長が取れない
- その結果、本文の予算は既定の 8192 に、抽出の上限は落とし所（16384、上限 8192）に落ちる。実際の窓は 32768 である

いま使える逃げ道は `PERSONACORE_CONTEXT_TOKENS` だけで、これには穴が2つある。

1. **全プロファイルに効く。** 常設すると、窓が 16384 の llama-server のプロファイルに切り替えても 32768 の予算で組み、上流に拒まれる
2. **抽出の上限には明示の口が無い**（`context.rs` の `resolve_sub_context`）

## 決定

### 1. 面に `context_tokens` を足す

`upstreams.json` の面（`main` / `sub`）に、任意の欄 `context_tokens`（整数）を足す。ADR-0042 §決定1 の「それ以外の鍵は足さない」を、この1つだけ改める。

```json
"relay": {
  "main": { "endpoint": "http://127.0.0.1:46001", "model": "iq3_xxs", "context_tokens": 32768 }
}
```

- **`main` の値は本文の予算の明示**で、`PERSONACORE_CONTEXT_TOKENS` と同じ意味を持つ。検証も同じ規則（`config::parse_context_budget`：0 と、応答の余白 1024 以下は読み込みの検証で止める）を通す
- **`sub` の値は抽出の上限の明示**で、上流への照会と落とし所の代わりになる
- **`sub` 面が無ければ、`main` の値を抽出にも使う。** 抽出は本文と同じ上流へ行く（[ADR-0039](0039-two-upstreams-for-two-jobs.md) §決定1）ので、窓も同じである
- **`sub` 面があって値を書いていなければ、今までどおり照会する。** 本文と別の上流かもしれないので、`main` の値を写さない
- 書いた面は、その値について**上流への照会もしないし、定期的な引き直し（ADR-0020）もしない**。今の `PERSONACORE_CONTEXT_TOKENS` と同じ扱いである
- **書かない面の振る舞いは今と1バイトも変えない**

### 2. プロファイルが環境変数に勝つ

`PERSONACORE_CONTEXT_TOKENS` と面の値がぶつかったら、**面の値を使い、`warn` を1本出す。** エンドポイントとモデルの扱い（`upstreams::overlay_profile` / `main.rs` の `warn_on_conflicts`）と同じ規則である。面に値が無ければ、環境変数があればそれを使う。

### 3. 走ったまま切り替えても、明示の有無と値は切り替え先に追従する

画面から上流を切り替える（ADR-0042 §決定4）と、**明示の値は切り替え先のプロファイルのものになる。**

- 明示 → 明示（値が変わる）、明示 → 照会、照会 → 明示の3通りすべてで、次の往復から効く
- 今は「明示かどうか」を起動時に決め、引き直しのタスクを本文について止めている（`context.rs` の `refresh_source`）。**これを「いまの明示」を毎回読む形にする**
- 切り替え先に値が無ければ、起動時の環境変数の値に戻る（決定2 の順位を切り替え後にも当てはめる）

### 4. ADR-0036 §決定3 の条件に当てはめる

ADR-0036 は、つまみにしてよい値を「根拠が無い・外すと破壊的・導出も観測もできない」の3つが揃ったものに限っている。

| 条件 | この値 |
|---|---|
| 根拠が無い | 窓は利用者が上流の側で選ぶ（その推論サーバの画面の「会話コンテキスト」）。personacore の中に根拠は無い |
| 外すと破壊的 | 実際の窓より大きいと、上流がコンテキスト超過で拒む。小さいと履歴が縮むだけ |
| 導出も観測もできない | **中継が `meta.n_ctx` を答えない上流では、観測できない**。観測できる上流では書かなくてよい（決定1 の最後） |

**足すつまみは2つ**（`main` の値と `sub` の値）。**それぞれに `App::bind` を通る見張り番を1本ずつ置く**（ADR-0036 §決定3）。決定3 の追従にも、切り替えを通る見張り番を置く。

### 5. 画面の編集は後から追いつく

画面のプロファイル編集（ADR-0042 §決定8）は、面の欄を固定の組で組み直す（`profile_editor.rs` の `WrittenFace` / `to_value`）。

- **A-13a-1（Rust）**: ファイルの読み込み・起動・切り替えに `context_tokens` を通す。画面の編集の型にはまだ足さないので、この欄を持つプロファイルを画面から保存しようとすると、今の規則（`Unrepresentable`）で**断る**。ファイルは壊れない
- **A-13a-2（web と編集の API）**: 編集の型と画面に欄を足し、表示と編集をできるようにする

### 追記（2026-11-01 / A-13a-1 の実装とレビューで決めたこと）

- **決定1 の「照会しない」は「値を照会で決めない」の意味である。** 起動時の照会と5分ごとの引き直しはしない。ただし、走ったままの切り替えの直後の測り直しと、起こした子の番人は、`PERSONACORE_CONTEXT_TOKENS` のときと同じく観測のために照会する。照会の答えの値は採らない（値と「明示か」の印を同じ錠で持ち、照会の答えを採る側が印を見て断る）
- **`sub` の値は `main` と同じ規則で検証する**（`config::context_budget_of`：応答の余白 1024 より大）。`sub` 面が無いと `main` の値が抽出にも入るので、規則を1つにする
- ~~**欄は `FACE_KEYS` に入れず、別の定数にした。** `FACE_KEYS` は画面の写し・プロファイル編集の分解・仕様書の閉じた綴りを兼ねており、入れるとそれらが一度に変わる。画面には A-13a-2 で通す~~ → **A-13a-2 で `FACE_KEYS` に入れた**（6つ目。画面の写しと仕様書も同時に変えた）
- ~~**A-13a-2 までの間は**、この欄を書いたファイルは、画面のプロファイルの一覧（`GET`）ごと扱えなくなり、画面からは切り替えられない（保存を断るだけではない）。`--upstream` での起動と `POST /admin/upstream/profile` は使える。この状態は決定5 の「画面からの保存を断る」より広いので、A-13a-2 を続けて行う~~ → **A-13a-2 で解消した。** 画面のプロファイル編集で、面ごとにこの欄を表示・入力でき、空にもできる。そのため理由のコード `not_yet_editable` は外した
- **A-13a-2 では、編集の依頼の `context_tokens` を `u32` ではなく `u64` で受ける。** `u32` で受けると、32 ビットに収まらない値が依頼の読み取りで 400 になり、どの欄のどんな理由かが画面に届かない。`u64` で受け、範囲は読み込みの検証（`parse_profiles`）に決めさせ、範囲外は 422 `context_tokens_unusable` としてその欄に出す。画面は範囲の規則を写さず、送る前に止めるのは「半角数字だけでない」と「正確に送れない桁数（2^53 以上）」だけにする
- **次の窓は受容した。** 照会の答えを採る直前に明示へ切り替わると、値は変わらないのに「予算が変わりました」の `warn` だけが出うる。影響はログだけで、値は印の検査が守る

## 却下した選択肢

- **その推論サーバに固有の口（host の `/api/...`）からコンテキスト長を読む** —— 上流ごとの綴りを personacore に持ち込む。`llm::upstream_leaks` の台帳が増え、ADR-0036 決定4 は「増えたら決定の変更」と書いている。しかもその中継の都合に personacore が合わせることになる
- **`PERSONACORE_CONTEXT_TOKENS` を常設して使う** —— 背景の穴1。全プロファイルに効き、llama-server に切り替えると窓を超える
- **抽出用の環境変数を足す** —— 同じく全プロファイルに効く。プロファイルごとの値という問題の形に合わない
- **鍵を送って本体（例 `:46002`）に直接つなぐ（A-13 の当初の案）** —— 本体は `meta.n_ctx` を答えるので、コンテキスト長は自動で取れる。しかしデスクトップアプリは読み込みのたびに鍵を作り直すので、利用者が鍵を書き写し続けることになる。鍵の対応そのものは A-13b として残す（その推論サーバを端末から起動して鍵を固定する使い方や、他の上流のため）
- **その推論サーバに、中継でも `meta.n_ctx` を返してもらう** —— 他者の製品なので待てない。返すようになれば、書かなくても照会で取れる（決定1 の最後）

## 結果

- この中継のように「窓を答えない上流」でも、プロファイル1つで本文と抽出の両方に正しい窓を渡せる。環境変数を常設しなくてよい
- llama-server のプロファイルと行き来しても、それぞれの窓で組む
- 書き間違い（実際の窓より大きい値）は personacore からは分からない。分かるのは上流に拒まれたときである
- **この決定は、その推論サーバと llama-server の GPU の取り合いを防がない。** 覚えたプロファイルが `gguf` 付きなら、その推論サーバにモデルを載せたまま personacore を起動した瞬間に llama を起こす（ADR-0042 §決定9）。これは F-10 で扱う
