# ADR-0010: セッション ID は `AUTOINCREMENT` の整数にする（UUID は使わない）

- 状態: **採用**
- 日付: 2026-08-14

## 背景

[ADR-0004](0004-session-identification.md) により、セッションは `model` フィールドに
`aoi@42` の形で指す。この `42` は `session.id`（`INTEGER PRIMARY KEY` = rowid エイリアス）。

**SQLite は `AUTOINCREMENT` なしの `INTEGER PRIMARY KEY` で、最大 rowid の行を削除すると
id を再利用する。** 同じ問題は [03-data-model.md](../03-data-model.md) に `message.id` について
記録済みだったが、**`session.id` については書かれていなかった。**

**`session.id` の方が危険である。**

> `message.id` は DB の中で完結する。**`session.id` は `model` フィールドに載って DB の外へ出る。**

外へ出る経路は2つある。利用者がクライアントの設定に `aoi@42` を書く場合と、
本サービスが応答の `model` に `aoi@<session-id>` を返す場合（作業単位 11a-2a で実装）。
**外に出た参照は、DB 側で id が再利用されても更新されない。**

キャラクター削除（`ON DELETE CASCADE` でセッションも消える）が入った瞬間、
`aoi@42` が**別のセッションを指す**。ADR-0004 が最も避けたい「気づきにくい記憶の混線」そのもの。

現時点では削除 API が1つも無いため、実際には起きていない。

## 決定

**`session` と `message` を `AUTOINCREMENT` 付きで作り直す。UUID は採用しない。**

`AUTOINCREMENT` は「これまでに使った最大値より大きい値」を保証するため、
**行を削除しても id が再利用されない。**

## 理由

推測可能性（ID を推測して他人のデータを読む）は、この構成では問題にならない。

- `Store::find_session` が**キャラクター所有確認**をする（`aoi@<他キャラのid>` は 404）
- サーバは **`127.0.0.1` のみにバインド**（絶対制約）
- **単一利用者**で、跨ぐべきテナント境界が存在しない

したがって UUID が守るものは増えない。一方で失うものがある。

> セッション ID は `model` フィールドに `aoi@42` の形で**人が打つ可能性がある**ため短く保つ。
> （`migrations/0001_initial.sql` の冒頭）

`aoi@0192f8c1-...` は手で打てない。ADR-0004 が復旧・デバッグ用として明示的に残した性質を壊す。

**解きたい問題は再利用だけで、それは `AUTOINCREMENT` で完全に止まる。**

### 却下した選択肢

- **UUIDv7** — 再利用は止まるが `model` に手で打てなくなる。
  UUID が追加で解くのは**別マシンの DB をマージしたときの衝突**だけで、
  単一 DB 内の衝突しない内部キーは **`character.id` / `session.id` として既にある**。
  複数人利用も DB のマージも想定していないので、対価に見合わない。
  > 「UUID ＋ 手打ち用エイリアス」を分解すると、**エイリアスこそが実体**である。
  > その形は [ADR-0011](0011-character-handle-and-display-name.md) が別の理由で採るが、
  > そちらでも UUID 側は要らない。
- **ソフト削除（行を消さない）** — 再利用は止まるが、`memory` と違い
  セッションは「消したい」ことがある。消せない設計を全テーブルへ広げる理由が無い。
- **`message` だけ `ORDER BY created_at, id` に変える** — `message` の**順序**問題は解けるが、
  **`session` は「同一性」の問題なので順序の工夫では解けない。**
  2つのテーブルで必要な対処が違う。

## 結果

- `aoi@42` が別のセッションを指すことは無くなる。削除 API を後から足しても安全
- **`AUTOINCREMENT` は `ALTER TABLE` では足せない。テーブル再構築が要る。**
  **データが空の今なら安い。**後からだとデータ移行が必要になり、コストは時間とともに増える
- `sqlite_sequence` テーブルが増える。書き込みごとにその行も更新されるが、
  本サービスの書き込み頻度では無視できる
- **別マシンの DB をマージする運用は引き続きできない。** 必要になったら再検討する

### 実装上の注意

- **適用済みのマイグレーションは編集しない。** 新しい `0003_*.sql` で作り直す
- 再構築後、**`Store::create_session` の `last_insert_rowid()` は変わらず使える**
- [03-data-model.md](../03-data-model.md) の `message.id` に関する注記は、
  この ADR で解消されるので更新すること

### 実装して分かったこと（2026-08-14 追記）

**作り直すのは2テーブルではなく4テーブルになった。** `session` / `message` に加えて
`summary` / `generated_image` を巻き込む。

**選んだのではなく強制された。** SQLite には次の制約があり、
**`PRAGMA foreign_keys` はトランザクション内では無視される**ため回避できない。

> **親テーブルが存在しない状態では、子テーブルへの DML
> （`DROP TABLE` の暗黙 `DELETE FROM` を含む）がコンパイルできない。**

親を先に落としても子を先に落としても失敗するので、依存関係で繋がった4テーブルを
**子→親の順で落とし、親→子の順で戻す**以外に道が無い。

`-- no-transaction` ＋ `PRAGMA foreign_keys = OFF` で公式12ステップを踏む案は**却下した。**
sqlx は「SQL 実行」と「`_sqlx_migrations` への記録」を**別文**で行うため、
途中で落ちると**スキーマだけ移行済みで記録が無い DB** が残る。
さらに no-tx では SQL 自体が原子でなくなり、`DROP TABLE` の途中で落ちると
**テーブルが消えたままの DB** が残る。どちらも `Store::connect` が恒久的に落ちる。

詳細と、再構築で静かに落ちるもの（索引の列順・`DESC`、復元 INSERT の `created_at`）は
[05-development.md](../05-development.md) の「テーブルを作り直すときの罠」に書いた。
