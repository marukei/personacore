# ADR-0006: 画像生成タグはスロット方式で組み立て、`ValidTag` で型的に強制する

- 状態: 採用
- 日付: 2026-08-13（追補1より）
- 関連: [07-prompt-compiler.md](../07-prompt-compiler.md) / [ADR-0003](0003-full-memory-injection.md)

## 背景

会話文脈（日本語）から画像生成用の Danbooru タグ列を生成する必要がある。
日本語話者が適切な英語タグを選ぶのは負荷が高く、チェックポイントごとにタグ規約も異なるため、
人力での維持は現実的でない。

素直な実装は「この会話を Danbooru タグにして」と LLM に投げることだが、
**高い確率で存在しないタグが混ざる。**

そして致命的なのは、**存在しないタグがエラーにならない**こと。
CLIP は未知の文字列も何らかのベクトルに変換するため、架空のタグは
「静かに無視される」か「ノイズとして混入する」。
**生成結果が微妙になっても原因が特定できない**という、最悪の壊れ方をする。

## 決定

**LLM には構造化された中間表現（スロット）を埋めさせるだけにし、
実際のタグへの変換と妥当性検証はプログラム側で行う。**

さらに、検証済みタグを表す newtype `ValidTag` を定義し、
**辞書引き（`lookup`）以外の構築手段を一切提供しない。**

```rust
struct ValidTag(String);   // フィールドは private

impl ValidTag {
    /// 唯一のコンストラクタ
    fn lookup(dict: &TagDictionary, candidate: &str) -> Option<Self> { ... }
}
```

`From<String>` も `pub fn new` も生やさない。
これにより**「架空タグがプロンプトに混入する」ことが型レベルで不可能になる。**

検証に失敗した値は**破棄**し（そのスロットを空にする）、
**破棄したことを必ずログに残す。破棄率をメトリクスとして集計できるようにする。**

## 理由

1. **架空タグの混入は検出できない形で壊れる。** ランタイム検証やレビューでは防ぎきれない。
   「防ぐ」のではなく「表現できなくする」必要がある。
2. **これは本プロジェクトの既存原則の直接の帰結。**
   `CLAUDE.md` の絶対制約「LLM の出力を信頼できない入力として扱う」を、
   型で強制した形。SQL プレースホルダと同じ構造の対策。
3. **スロット方式は小型モデルで足りる。** 抽出タスクなのでサブLLM
   （`ministral-3-3b-instruct-2512`）で十分。メインモデルを占有しない。
   > **⚠ この主張は未検証**（2026-08-21 に注記）。**記憶抽出では 3B が足りなかった**
   > （[ADR-0021](0021-memory-extraction-format.md) §10。主語を間違え、形式が 41% 崩れる）。
   > **同じ結論とは限らない** —— スロット埋めは**辞書引きで受理集合が閉じており**、
   > 架空タグは `ValidTag` が構造的に止める。**それでも「足りる」は測ってから言うこと。**
4. 破棄率がそのまま**辞書の不足を検出するシグナル**になり、改善のループが回る。

### 却下した選択肢

- **LLM に直接タグ列を生成させ、事後に検証する** — 検証を通す場所が増えるほど
  漏れる。`String` のまま持ち回ると「どこかで検証済み」の保証が型に乗らない。
  レビューで「この String は検証済みか？」を毎回追う羽目になる。
- **ベクトル検索で最も近いタグにマッピングする** — 対象が数百〜千件の**閉じた語彙**であり、
  LLM の返す値も概ねタグに近い形（英語の短い語句）。
  **誤マッチのリスクの方が大きい。** 完全一致・部分一致・エイリアス表で足りる。
  （[ADR-0003](0003-full-memory-injection.md) と同じ判断構造）
- **未知タグを推測で補完する** — 破棄より悪い。誤ったタグが混入したうえ、
  破棄率メトリクスも汚染され、辞書の不足に気づけなくなる。

## 結果

### 得られたもの

- 架空タグの混入がコンパイル時に不可能
- 破棄率という形で辞書の品質が可観測になる
- **間接プロンプトインジェクション対策の基本形**を、実際に動くコードとして持てる
  （業務 RAG へ転用可能な構造）

### 諦めたもの / 前提

- **辞書に無いタグは絶対に使えない。** 表現力は辞書の網羅性に上限を持つ。
  → 破棄ログを見て辞書を育てる運用が前提になる。
- 辞書のメンテナンスコストが発生する。
  → TOML / JSON でリポジトリ内に持ち、**DB に入れない**。
  更新頻度が低くバージョン管理したいため。

### テストで守ること

- **辞書外の値で `ValidTag` を構築できないこと**を明示的にテストする。
- **「LLM が架空タグを返した場合に、それが最終プロンプトに現れないこと」を
  テストする。** これがこのコンポーネントの存在意義そのもの。
