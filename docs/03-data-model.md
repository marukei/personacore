# 03. データモデル

SQLite 単一ファイル。将来 `sqlite-vec` でベクトル検索を同一DBに足せるため、
**別途ベクトルDBは立てない。**

スキーマの正は `migrations/` 配下の SQL。このドキュメントは意図と不変条件を説明する。

## テーブル

### `character` — キャラクター定義

| 列 | 用途 |
|---|---|
| `id` | 主キー。**`AUTOINCREMENT` ではない**ので、いちばん新しいキャラクターを完全に消してすぐ作ると**同じ id が使い回される**（[ADR-0049](adr/0049-deleting-characters-and-conversations.md) の 2026-10-21 追記）。裏方の書き込みを `character_id` だけで縛らず、それを生んだ会話（`session.id` は使い回されない）に縛るのはそのため |
| `handle` | **識別子。** `model` フィールドで指す値（`aoi`）。一意。**ASCII の小文字英字・数字・`-`・`_` だけ**（[ADR-0017](adr/0017-handle-is-a-restricted-alphabet.md)）。**不変**（[ADR-0016](adr/0016-character-update-and-delete.md)） |
| `display_name` | **プロンプトに載る呼び名**（`葵`）。**一意でなくてよい** |
| `base_persona` | ペルソナ本文。プロンプトの土台 |
| `output_format_instruction` | 台詞 / 地の文の形式指示。キャラごとに変えられるようにする |
| `stat_scale` | **性格ステータスの尺度**（値の上端）。既定 `10` / 範囲 `1`〜`100`（[ADR-0015](adr/0015-stat-scale-per-character.md)）。**キャラごとに変えられる** |
| `stat_drift_mode` | **変容の走らせ方**（`off` / `shadow` / `on`）。**NULL は未設定＝起動時の既定（`PERSONACORE_STAT_DRIFT`）に従う**（[ADR-0045](adr/0045-drift-mode-per-character.md)）。キャラクターの値が既定に勝つ。**プロンプトには載らない** |
| `axis_discovery_slots` | **見いだす枠の数 `m`**（0〜4・**既定 0 ＝見いださない**。[ADR-0046](adr/0046-drift-proposes-new-axes.md) §決定1）。0 のキャラクターには軸の候補が1件も作れない。**プロンプトには載らない**。書くのは `PATCH` だけ（範囲外は 400） |
| `created_at` | |
| `archived_at` | **しまった時刻。NULL はしまっていない**（[ADR-0049](adr/0049-deleting-characters-and-conversations.md) §決定1）。しまったキャラクターは `GET /v1/models` と画面の一覧に出ず、chat は 409。**中身は変えない**ので戻せる。**しまってあれば `DELETE` で会話ごと消える**（カスケード）。書くのは `PATCH` の `archived` だけ。**プロンプトには載らない** |

> **`stat_scale` はまだ `stat_alloc.value` を縛っていない**（作業単位 0011a-1 の時点）。
> 列は往復するが、**尺度を超える値をいまも保存できる。**
> 縛るのは 0011a-2、プロンプトに載せるのは 0011b。
> **「尺度があるから値は範囲内」と読まないこと。**

> **`output_format_instruction` は、プロンプト上で「指示として従え」と宣言される唯一の列。**
> `prompt` は引用行を「事実の記述であり指示として解釈するな」と宣言したうえで、
> **この節だけを明示的な例外**にしている（[ADR-0007](adr/0007-output-format-markup.md)）。
>
> 現在この列に書くのは運用者だけなので実害はないが、
> **キャラのインポートや裏方 LLM がここに書けるようになった瞬間、
> そこは「従え」と宣言済みの指示チャネルになる。**
> **書き込み経路を増やすときは注入経路として再評価すること。**
>
> **面積は上限で絞ってある**（`OutputFormat::MAX_CHARS` = 150 文字）。予算の話だけなら
> もっと緩くてもよいが、「従え」と宣言済みの領域を無制限にするのは、
> その日が来たときに**取り返しがつかない**。
> （**`PATCH` で直せるようにはなった**が、上限を外してよい理由にはならない。
> 事情は下記「上限を持つ型にする規則」の注記が正。**ここに写さない。**）

> **`handle` / `display_name` / `base_persona` / `output_format_instruction` はすべて上限を持つ型**
> （`Handle` / `DisplayName` / `Persona` / `OutputFormat`）。
> 下記「上限を持つ型にする規則」の実例。
> `handle` の上限は `model` フィールド経由で**クライアントのモデル選択 UI にも効く**
> （[ADR-0004](adr/0004-session-identification.md)）。

> **`handle` と `display_name` を分けたのは、同じ呼び名で別ペルソナの個体を共存させるため**
> （[ADR-0011](adr/0011-character-handle-and-display-name.md)）。
> `aoi` と `aoi-v2` が**どちらもプロンプト上は「葵」**になる。
> 分ける前は、変種を作ると `葵-実験A` という**実験用の名前がプロンプトに載って**
> 比較の変数が増えていた。
>
> **プロンプトに載るのは `display_name` だけ。** `handle` が載る経路は
> `prompt::SanitizedCharacter` が識別子を**持たない**ことで型から消してある。
> ただし**`server` 層は型では守られていない**（`store` から `prompt` へ渡すときに
> 取り違えられる）ので、結合レベルのテストで見張ること。
>
> **列とフィールドの名前が `name` だったのは 0004b-3 まで。**
> 「名前」がどちらを指すのか読むたびに判断が要ったので、概念に合わせて改名した。

### `stat_alloc` — 性格ステータス配分

| 列 | 用途 |
|---|---|
| `character_id` | |
| `axis` | 軸名。**固定6軸にしない。設定可能にする** |
| `value` | 配分値 |

軸を可変にするのは、「どの軸が応答傾向に効くか」自体が検証対象だから。
enum やスキーマで軸を固定すると、実験のたびにマイグレーションが必要になる。

> **`axis` にも上限がある**（`StatAxis::MAX_CHARS` = 20 文字）。下記の規則の実例。
> 軸名は削れない枠に**件数分**載り、しかも**件数の方には上限が無い**ので、
> 1軸が長いほど載せられる軸が減る。
>
> **`value` にはまだ上限が無い。** 桁数はプロンプトに数文字しか効かないため急がないが、
> 未決事項として残っている（マイルストーン5の実測後に決める）。

### `session` — 会話セッション

| 列 | 用途 |
|---|---|
| `id` | **`AUTOINCREMENT`。** `model` に `aoi@42` の形で DB の外へ出る |
| `character_id` | |
| `label` | 人間向けの識別名 |
| `created_at` / `updated_at` | |

> **`session.id` だけは DB の外へ出る。** 利用者のクライアント設定に書かれた `aoi@42` と、
> 応答の `model` に返す `aoi@<session-id>` の2経路があり、
> **外に出た参照は DB 側で id が再利用されても更新されない。**
> 再利用されると `aoi@42` が別のセッションを指し、ADR-0004 が最も避けたい
> 「気づきにくい記憶の混線」になる。だから `AUTOINCREMENT`
> （[ADR-0010](adr/0010-session-id-identity.md)。UUID は却下）。
>
> `AUTOINCREMENT` は `ALTER TABLE` では足せず**テーブル再構築が要る**。
> `migrations/0003_*.sql` がそれで、**外部キーを切れない**事情から
> `session` / `message` / `summary` / `generated_image` の4つを作り直している
> （`PRAGMA foreign_keys` はトランザクション内では無視される。詳細は当該 SQL の冒頭）。

### `message` — メッセージ

| 列 | 用途 |

>

> `message_id_is_never_reused_after_deleting_the_highest_row` と
> `session_and_message_ids_do_not_rewind_across_reconnects`。
> **スキーマ文字列に `AUTOINCREMENT` があることを見るテストにしないこと。**
> 宣言はあるが効いていない状態を検出できない。実際に最大 id の行を消して採番を見る。

### `character_attribute` / `character_fact` — 設定由来

どちらもキャラクター設定の一部として**人が書く**もので、`memory` とは**別テーブルにする。**
**設定どうしも2つに分ける**（[ADR-0009](adr/0009-character-attributes-and-facts.md)）。

> **`character_attribute` は実装済み**（2026-08-20 / 作業単位 12a）。
> **`character_fact` は作らないことに決めた**（2026-08-22 /
> [ADR-0009](adr/0009-character-attributes-and-facts.md) 末尾に根拠と**再検討の引き金**）。
> 測った欠陥（一人称の揺れ）は属性で塞がり、**`base_persona` はまだ9割空いている。**
> **設計（2テーブルに分ける理由）はそのまま生きている。作らないのは「まだ要らない」から。**

#### `character_attribute` — 不変属性（キー付き）

ジェンダー・年齢・種族のように「記憶ではないが変わりようのない」要素。

| 列 | 用途 |
|---|---|
| `character_id` | |
| `subject` | `user` / `character`（`memory` と同じ区別） |
| `key` | 属性名（`種族` / `年齢`）。**上限を持つ型**（`StatAxis` と同じ形） |
| `value` | 属性値（`猫獣人`）。**上限を持つ型** |

- 主キーは `(character_id, subject, key)`。置き換えは**丸ごと**（`stat_alloc` と同じ意味論）
- **件数にも上限がある**（8件）。プロンプトの削れない枠に載るため。
  **上限とその出どころは [ADR-0009](adr/0009-character-attributes-and-facts.md) の
  「上限の数字と、その出どころ」節が正。ここに写さない。**
- **空の `value` は保存できない**（`AttributeValue::parse` が通さない）。
  **「性格値 0 の軸」とは扱いが違う**——あちらは 0 が正当な保存値で、落とすのは `prompt` の責務。
  こちらは**そもそも書けない。**
- **壊れた行は置き換え1手で直る。** `stat_alloc` が3手かかるのは、突き合わせに
  `character.stat_scale` を読むから（[ADR-0015](adr/0015-stat-scale-per-character.md) の ⚠）。
  **属性の置き換えは親の列を一切読まない。**
- **画像側（フェーズ3）はこのテーブルを辞書引きしてタグ化する。**
  `value` を `ValidTag` へ直接変換しない（[ADR-0006](adr/0006-slot-based-tag-compilation.md)）
- **この表は `attribute_revision` の投影である**（2026-09-09 / 作業単位 A-3a）。
  行の意味も主キーも変えていないが、**書き手が1つに絞られた。** 下の節を読むこと。

#### `attribute_revision` — 属性の変更の履歴（[ADR-0028](adr/0028-attributes-that-change.md) §決定5）

| 列 | 用途 |
|---|---|
| `id` | 主キー（`AUTOINCREMENT`）。**同着の並びの第2キー**でもある |
| `character_id` | **持ち主。** 誰の属性の話か |
| `subject` | `user` / `character`。**その属性自身の主語**（§決定4。誰にも答えさせない） |
| `key` | どのキーが変わったか |
| `before` | 変更前の値。**`NULL` は「無かった」**（＝追加） |
| `after` | 変更後の値。**`NULL` は「消えた」**（＝削除） |
| `created_at` | |

**`character_attribute` は、この表の「いま」の投影である。**
[ADR-0009](adr/0009-character-attributes-and-facts.md) の「履歴に価値が無い」を
[ADR-0028](adr/0028-attributes-that-change.md) が覆した。理由は**書き手が人だけではなくなるから** ——
属性は削れない枠に毎ターン載るので、**静かに変わると気付く手段が無い**
（変容が本文に出ない決定と同じ形 / [ADR-0024](adr/0024-stat-drift.md) §9。あちらには票の表がある）。

> **⚠ 提案を出すサブ LLM はまだ無い**（[ADR-0028](adr/0028-attributes-that-change.md) は
> 決定3〜7 の「形」だけを採用した）。**いま書き手は人（`PUT .../attributes`）だけである。**

#### 追記のみ。書き込みの経路は1つ

**この表を UPDATE / DELETE する文は無い**（`memory` / `stat_drift_vote` と同じ立場）。
`Store::replace_character_attributes` が、1つのトランザクションで
**現在の集合を読む → 差分を履歴へ追記 → 投影を差し替える**を行う。

> **⚠ 走査が守っているのは「投影へ書く SQL の綴りが、ちょうど2つ、あのファイルにだけある」まで。**
> **「1つの関数に閉じている」ではない**（2026-09-09 に訂正）——
> **既存の定数を使い回す2つ目の `pub async fn` を同じファイルに足しても全緑**だった
> （レビューが 2046、是正の回に測り直して **2049 全緑・exit 0**）
> （走査は SQL の文面を見るので、**誰がそれを実行するか**は見ていない）。
> **原子性のほうにはもっと権威が無い**（履歴の追記を `commit()` の後ろへ出しても **2049 全緑**）。
> **殺す見張り番は作れていない。** 詳しくは `src/store/attribute.rs` の
> `Store::replace_character_attributes` の ⚠ 節。

見張り番は `src/store/attribute.rs` の走査2本（`src/**` と `migrations/**` を見る）:

| 見張り番 | 何を見るか |
|---|---|
| `no_statement_outside_the_one_writer_touches_the_projection` | 投影へ**書く位置**にある言及が、あの1ファイル以外に無い |
| `no_statement_updates_or_deletes_a_revision` | 履歴の言及が**許可された形**（追記・読み出し・DDL）だけである |

> **2つは形が違う。** 投影の名前は散文にも出るので、**書く位置に絞って**見る
> （すべての言及を許可リストに掛けると、コメントを1行書くたびに赤くなる）。
> 履歴の名前は散文に綴らない約束にしてあるので、**すべての言及**を許可リストに掛けられる。
>
> **⚠ 走査は「文字列リテラルに書かれた SQL」ではなく生ソースを見る。**
> `format!` で表名と動詞を別々に継ぎ足す形は素通りする（記憶の走査と同じ穴）。
> **`tests/` 配下も見ない**（統合テストは本番バイナリにリンクされない）。

#### 差分ゼロなら1行も書かない

同じ集合を2回 `PUT` しても履歴は増えない（並べ替えだけでも増えない）。
**変わっていない行が混ざると、変わった行がその中に埋もれる。**

#### **壊れた行の修復は履歴に残らない**（守れていないこと）

`key` / `before` / `after` の CHECK は `character_attribute` の**写し**（長さ・NUL・空白・型）。
そのため**上限を超えた値をそのまま `before` に書くと履歴の INSERT が落ち**、
落ちれば置き換えごとロールバックして**唯一の修復経路が閉じる。**

そこで**記録できない変更は記録せず、`warn` を残して修復を通す。**
「壊れた行を直した」という事実は、ログにしか残らない。

> **⚠ `before` を `NULL` で書いて残す案は採らない。** それは「追加」の意味なので、
> **記録が嘘をつく**（読み手には「無かったものが増えた」に見える）。
> **修復した件数を `PUT` の応答に載せる案は D-12 の宿題**（2026-09-09 / A-3a のレビュー）——
> 応答の形が変わると**画面の欄の突き合わせに触れる**ので、画面を作る作業単位で一緒に決める。

#### 1行壊れたときに何が止まるか

| | |
|---|---|
| **止まるもの** | **履歴の一覧だけ**（`GET .../attributes/revisions` が 500） |
| **止まらないもの** | 属性そのものの読み・**置き換え**・本文の応答・記憶・変容 |

**黙って飛ばさない。** 「静かに変わったことに気付く」ための表なのだから、
**その表から静かに1行消えるのが最も悪い壊れ方**である。
直す導線は `sqlite3` だけ——**履歴に更新も削除も無い。**

#### 索引

`attribute_revision_recent_idx (character_id, created_at)`。
主キーは `id` なので、これが無いと「新しい順に N 件」が全表走査になる
（履歴は消えないので行数は編集回数に比例して増える）。**キーは列に含めない**
——読むのは「新しい順の並び」であって、キーごとの履歴ではない。

#### `character_fact` — 設定由来の事実（散文）

「幼い頃に故郷を離れている」のような、**文でしか書けない**設定。

| 列（予定） | 用途 |
|---|---|
| `id` | 1件ずつ削除・更新するため |
| `character_id` | |
| `subject` | `user` / `character`（`memory` と同じ区別） |
| `content` | 本文 |
| `category` | 分類 |

件数上限ではなく**予算の枠として扱い、溢れたら削る**（記憶と同じ）。

#### なぜ `memory` と分けるのか

**ライフサイクルが正反対だから。**

| | `character_fact`（設定） | `memory`（観測） |
|---|---|---|
| 誰が書くか | 人（管理 API） | 抽出サブLLM |
| 編集・削除 | **自由にできる必要がある** | **してはならない**（不変条件2） |
| 履歴の価値 | 無い（著述であって観測ではない） | **これが存在理由**（「以前はXだったが今はY」） |

同じテーブルに置いて `locked` 等のフラグで区別すると、
**`memory` の「DELETE / UPDATE の API を作らない」という防御に例外ができる。**
例外を持つ防御は、例外の範囲を毎回確かめる必要が出て弱くなる。
SQL 走査テストの許可リストも緩めることになる。

**分けておけば `memory` の防御は例外なしのまま保てる。**
`character_appearance`（フェーズ3の外見定義）と同じ扱いになる。

> **`prompt` は `character_fact` と `memory` を同じ「# 記憶」節に載せる。**
> モデルから見れば区別の必要は無い。分けるのは**書き込み側の都合**である。
>
> **`character_attribute` はこの節に載せない。** 属性は削れない枠、記憶は溢れたら削る枠で、
> 同じ節に置くと予算の扱いが節の中で分岐する（[ADR-0009](adr/0009-character-attributes-and-facts.md)）。
>
> **混ぜるなら節の説明文を直すこと。** 現在の「過去の会話から抽出した事実の記録です。」は
> 人が書いた設定に対しては偽であり、放置すると「区別の必要は無い」という前提が崩れる。

> **`MemoryContent` / `MemoryCategory` と同じ上限を課すこと**（「上限を持つ型にする規則」）。
> 記憶の枠は想起が選ぶ（[ADR-0023](adr/0023-three-layer-recall.md)）が、長大な設定は1件で枠を食い、同じ形でプロンプトを圧迫する。
> **見張り番 `every_field_at_its_limit_still_fits_the_default_budget` を
> 新しいテーブルにも広げること。** 広げないと上限の意味が無くなる。

### `character_agreement` / `agreement_transition` — 取り決め（約束・決まり）（[ADR-0051](adr/0051-promises-and-rules.md) §決定1・4）

**表は2枚**（`migrations/0018_agreement.sql` / 作業単位 A-12a）。形は属性の 0009 / 0013 と同じで、
**履歴が正、取り決めの表の状態は「いま」の投影**（[ADR-0028](adr/0028-attributes-that-change.md) §決定5）。
記憶とも属性とも別の表（ADR-0051 §決定1 —— 属性はキーと値の形で、状態も守る側も持てない）。

| 表 | 1行は | 列 |
|---|---|---|
| `character_agreement` | 取り決め1件 | `id` / `character_id` / `content`（**要旨の平叙文**。`AgreementContent` / 上限 60）/ `kind`（`promise` 約束 / `rule` 決まり）/ `keeper`（**守る側**: `user` / `character` / `both`）/ `state`（いまの状態）/ `source_session_id`（**生まれた会話**。手で書いたものは `NULL`、提案は候補が生まれた会話）/ `created_at` |
| `agreement_transition` | 状態の変化1回 | `id` / `agreement_id` / `before`（**`NULL` は「書かれた」**）/ `after` / `created_at` |

* **状態**は `proposed`（提案中）/ `active`（有効）/ `rejected`（却下）/ `fulfilled`（果たした）/ `broken`（破った）/ `withdrawn`（取り消した）。
  **本文に載るのは `active` だけ**（毎回、「# 約束・決まり」の節として守る側ごとの小見出しの下に / §決定4）。
  **置き場所は削れない枠ではなく、その次の「優先の枠」**（ADR-0051 §決定4 の追記）—— 次の節。
* **提案中と却下は作業単位 A-12c-1 で書かれるようになった**（モデルの提案・δ3 / ADR-0051 §軽い形の模索の結果と、実装する形）。
  CHECK は 0018 が綴りだけ先に入れていた（後から変えられないため）。**読み手（`domain::AgreementState`）を先に広げてから書き手を足した**
  （逆にすると、`proposed` の行を書いた瞬間にそのキャラクターの一覧の口が 500 になる）。
  **提案中は本文に載らず、有効な件数の上限にも数えない。** 採ると有効になって数える。
  **提案の持ち越し（1往復前の候補）は DB に持たない**（プロセスの中 / `server::agreement_proposal`。失えば拾いが減るだけ）ので、表は増えていない。
* **`keeper` を落とさない**（`memory.subject` と同じ理由 —— 「呼び捨てにしない」を誰が守るのかが混線する）。`Subject` と別の型（「両方」がある）。
* **`source_session_id` の参照アクションは無い**（既定の NO ACTION）。いまは会話を1つだけ消す経路が無く、
  キャラクターを消すときは同じ文のカスケードで取り決めも会話も消える。**会話を1つ消す経路を足す日に、ここをどうするかを決めること**（黙って `NULL` にしない —— 手で書いたものと区別できなくなる）。

#### 行は消さない。書き換えるのは投影の状態の列（と、採るときの提案中の行の中身）だけ

> 採る口（作業単位 A-12c-1）だけは、**提案中の1行**の中身・種類・守る側を、利用者が直した値で書き換える
> （ADR-0051 §決定2「直してから採る」）。**モデルが提案した元の綴りは残らない**（直したかどうかも履歴に出ない）。
> 有効・終わった取り決めの中身は、どの文でも書き換わらない（採る文は `AND state = ?` に提案中を束ねる）。

* **書く**（`Store::add_agreement`）: `BEGIN IMMEDIATE` の中で**有効な件数を数え → 上限なら断り → 投影に1行 → 履歴に「無 → 有効」の1行。**
* **終わらせる**（`Store::end_agreement`）: 同じく**いまの状態を読み → 有効でなければ断り → 投影の状態を書き換え → 履歴に「有効 → 終わり」の1行。**
  **中身を読まない**ので、中身が壊れた行も終わらせられる（本文を止めている行を本文から外す道）。
* **提案を書く**（`Store::record_agreement_proposals` / 作業単位 A-12c-1）: `BEGIN IMMEDIATE` の中で**候補が生まれた会話が今もこのキャラクターのものかを確かめ**
  （[ADR-0049](adr/0049-deleting-characters-and-conversations.md) §決定3）→ 提案ごとに**綴りがまったく同じ提案中・有効があれば足さず**、無ければ投影に提案中の1行 → 履歴に「無 → 提案中」の1行。
  **依頼はトランザクションの外**（CLAUDE.md 絶対制約）—— 検出と確かめが返り切ってから呼ぶ。
  似ているもの（dedup2）を落とすのはここではなく `parse::agreement_proposal` の後段で、却下の行もその相手にする。
* **採る**（`Store::adopt_agreement`）: **いまの状態を読み → 提案中でなければ断り → 有効な件数を数え → 上限なら断り → 中身・種類・守る側（直したものだけ）と状態を書き換え → 履歴に「提案中 → 有効」の1行。**
* **捨てる**（`Store::reject_agreement`）: **いまの状態を読み → 提案中でなければ断り → 投影の状態を書き換え → 履歴に「提案中 → 却下」の1行。**
* **DELETE は無い。** 消えるのはキャラクターを完全に消したときのカスケードだけ（[ADR-0049](adr/0049-deleting-characters-and-conversations.md)）。
* 見張り番は `src/store/agreement.rs` の走査2本（`src/**` と `migrations/**`）:

| 見張り番 | 何を見るか |
|---|---|
| `the_projection_is_written_only_here_and_never_deleted` | 取り決めの表へ**書く位置**の言及が、あの1ファイルの INSERT 1つと UPDATE 2つ（状態だけを書き換える文と、提案中の1行を採る文）だけ（DELETE / DROP / REPLACE がどこにも無い） |
| `no_statement_updates_or_deletes_a_transition` | 履歴の言及が**許可された形**（追記・読み出し・DDL）だけ |

> **⚠ 守れていないのは属性の履歴と同じところ** —— 走査が見るのは SQL の綴りで、
> **投影と履歴が同じトランザクションで動くこと**ではない。そこを見ているのは振る舞いのテスト
> （`tests/store_agreement.rs` の「履歴に残る」「上限なら何も保存されない」）。

#### 件数の上限（有効なものだけを数える）

**有効な取り決めは `domain::MAX_ACTIVE_AGREEMENTS`（16）件まで**（叩き台 / ADR-0051 §決定4）。
上限に達していたら書く口は断る（`StoreError::AgreementLimitReached` → 409 `agreement_limit_reached`）。
**黙って古いものを落とさない** —— 画面が古いものを終わらせるよう促す。終わったもの・提案中・却下は数えない。
**提案は上限に達していても書ける**（提案中は数えない）。採る口が同じ上限で断る（作業単位 A-12c-1）。

#### 本文の予算 —— 削れない枠の次の「優先の枠」（ADR-0051 §決定4 の追記）

上限いっぱい（16 件 × 60 字）を削れない枠に入れると、既定の予算（8192）では
削れない枠だけで取り分を超えた（6644 → 10883 > 7168 の実測 / 作業単位 A-12a）。**既定の予算は上げない**（ADR-0036）。そこで:

* **取る順は「削れない枠 → 最新の1往復（残りに入るなら） → 取り決め → 残りを記憶と履歴で半々」**（`prompt::budget::Frames`）。
  最新の1往復を取り決めより先に確保するのは、取り決めが残りを取りすぎて**履歴が 0 件**になるのを防ぐため
  （既定の予算・長いペルソナ・取り決め2件で残りが約 40 になる筋書き / 見張り番 `the_newest_exchange_is_kept_before_the_agreements_take_the_rest`）。
* **入りきらないときだけ、古い側から落とす。** 見出し・小見出しは実際に載る守る側の分だけ数える。
* **落とした件数は `warn` の1行に出し**（`dropped` / `kept`）、**一覧の口の `last_turn` にも出す**
  （直近のターンの `included` / `dropped`。**DB には持たない** —— 起動し直すと `null`）。画面はそれを読んで「載っていない取り決めがある」と言う。
* 見張り番は `prompt` の `agreements_at_their_limit_never_exhaust_the_default_budget_and_the_drop_is_reported`（既定の予算）と
  `agreements_at_their_limit_all_fit_a_sufficient_budget`（16384）。**`every_field_at_its_limit_still_fits_the_default_budget` は削れない枠の見張り番のままで、取り決めは入らない。**

#### 1行壊れたときに何が止まるか

| 壊れた行 | 止まるもの | 止まらないもの |
|---|---|---|
| **有効な行** | **本文の組み立て**（`Store::active_agreements` が丸ごと失敗 → chat が 500）と一覧（`GET .../agreements`） | 終わらせる口（中身を読まない）・履歴の総数 |
| **終わった行・提案中・却下の行** | 一覧と履歴の一覧と、**提案の確かめ**（「# 提案済み」を作るのに一覧と同じ読みを使う —— 読めなければ、その往復の確かめを飛ばして `warn`。検出は止まらない） | **本文**（本文は有効な行しか読まない）。壊れた提案中の行は、**直さずに採ると断られる**（採る口は書き換えた後の行を検証し、読めなければ何も書かない —— 壊れた行を有効にして本文を止めない）。捨てる口は中身を読まないので捨てられるが、**一覧は止まったまま**（どの状態の行でも、壊れていれば一覧は止まる） |

**黙って飛ばさない**（黙って空として続けると、キャラクターが理由なく約束を忘れて応答する —— 属性と同じ判断）。
有効な行が壊れて本文が止まったら、その行を終わらせれば本文は戻る（id は `sqlite3` で読む。**一覧の口は壊れた行を指し示さない** —— 守れていないこと）。

### `stat_drift_vote` — 性格ステータスの変容の票（[ADR-0026](adr/0026-drift-by-accumulation.md)）

| 列 | 用途 |
|---|---|
| `id` | 主キー |
| `character_id` | **持ち主。** 誰の性格についての票か |
| `session_id` | **どの往復で立ったか。** 票を会話に突き合わせるのに要る |
| `axis` | 軸名。**保存済みの綴り**（許可リストと値 0 の門を通ったものだけ） |
| `delta` | 向き。`up` / `down`（`memory.subject` と同じく**綴りで持つ**） |
| `created_at` | |

**毎ターンの提案をここに1行ずつ残し、適用は票が閾値に達したときだけ行う**
（[ADR-0026](adr/0026-drift-by-accumulation.md) §決定2。閾値そのものは作業単位 16e）。
記録専用モード（`PERSONACORE_STAT_DRIFT=shadow`）は**この表だけを書き、値を動かさない。**

#### 入るのは「門を通った提案」だけ

許可リスト（保存済みの軸との完全一致 / [ADR-0024](adr/0024-stat-drift.md) §1）と、
値 0 の軸の除外（§4）を通ったものだけが入る。**破棄はログのままで、表に入らない。**
唯一の入口は `domain::DriftOutcome::vote`。

> **飽和した提案も入る。** 上端で `+1` を出し続けている状態は、票から見れば
> 「上げようとし続けている」という情報である。記録の時点で落とすと、
> 蓄積はその傾向を二度と見られない。**飽和の判定は適用の時点で行う。**

#### 追記のみ

[ADR-0022](adr/0022-repairing-memories-without-deleting.md) の「消さない」と同じ立場。
票は「なぜこの値になったのか」の記録でもあるので、後から書き換えると意味が消える。
`store` に**更新の API も削除の API も無く**、見張り番は
`src/store/drift.rs` の `no_statement_updates_or_deletes_a_vote`
（`src/**` と `migrations/**` を走査する）。

> **守れる範囲は `memory` の走査と同じ**——**親の削除には従う**
> （`character` / `session` から `ON DELETE CASCADE`）。孤児の行を作らないためで、
> 「追記のみ」が守るのは**アプリからの書き換え**までである。

#### 向きを整数ではなく綴りで持つ理由

* **符号の反転が目で読める。** `1` / `-1` だと、`sqlite3` のダンプを見ても
  取り違えに気付けない。
* **CHECK が書ける**（`delta IN ('up', 'down')`）。
* **綴りの正は `domain::DriftDelta::label` ひとつ**で、写しを作らない
  （`store::drift::delta_to_db` がその関数を呼ぶだけ）。
  ログの集計キーと同じ語なので、**測定でログと票をそのまま突き合わせられる。**

#### 1行壊れたときに何が止まるか

`Store::recent_drift_votes` は**1行でも読めなければ丸ごと `InvalidStoredValue`**
（`recall_memories` / `stat_allocs` と同じ側）。**黙って飛ばさない**のは、
蓄積が数を数えて閾値と比べる仕掛けだからで、**1票減ることは
「変容が1回起きない／余計に起きる」に直結し、しかもどこにも現れない。**

| | |
|---|---|
| **止まるもの** | そのキャラクターの**蓄積の判定だけ**（16e） |
| **止まらないもの** | 本文の応答・記憶の抽出・変容の判定・**票の記録**（追記は既存の行を読まない） |

**止まっても票は溜まり続ける**ので、壊れた行を直せば続きから読める。
直す導線は今のところ `sqlite3` だけ——**票に更新も削除も無い**ので、
アプリ経由で消す手段は用意していない。

#### 索引

`stat_drift_vote_recent_idx (character_id, created_at)`。
**主キーは `id` なので、これが無いと「直近 N 件」の読みが毎ターン全表走査になる。**
票は追記のみで消えないので、行数は会話のターン数に比例して増え続ける。
`character_attribute` が「明示的な索引は足さない」と決めたのは
主キーの自動索引で足りたからで、ここは事情が違う。

**軸は列に含めない。** 蓄積は「直近 N 件の並び」として読む
（[ADR-0026](adr/0026-drift-by-accumulation.md) §決定2 は票を溜めて消費する）ので、
軸を第2列に入れると読みが軸の数だけ分裂する。

> **⚠ 集約の規則は [ADR-0027](adr/0027-drift-from-what-was-not-chosen.md) が置き換えた。**
> **「溜めて消費する」は変わらないが、票の重みが軸の希少度で決まり、
> 選ばれなかった軸も毎ターン減る。** つまり**読むのは「直近 N 件」のままでよい**が、
> **N 件の中の全軸を見る**（選ばれた軸だけではない）。

#### 表が答える問いは「その軸が何回 `0` でなかったか」（作業単位 16e-b）

集約は票の件数を**希少度の重み `1 / 回数`** に使う
（[ADR-0027](adr/0027-drift-from-what-was-not-chosen.md) §決定1）。
**`0` と採点された軸は票にならない**——全軸採点では毎ターン全軸が採点されるので、
`0` まで票にすると**全軸の件数が同じになり、重みが一律に戻る**（§12 の危険3）。

> **⚠ 数えるのは直近 1024 件まで**（`server::drift::DRIFT_WEIGHT_VOTES`）。
> 票は消えないので、全件読むと**読む量が会話の長さに比例して増える。**
> **窓を超えた古い票は数から落ちる**ので、重みは `1/1024` より軽くならない。
> **ADR が当て直したのは窓の無い計算**なので、長い会話では規則が少しずれる。

### `stat_drift_charge` — 性格ステータスの変容の累積（[ADR-0027](adr/0027-drift-from-what-was-not-chosen.md)）

| 列 | 用途 |
|---|---|
| `character_id` | **持ち主**（`axis` と合わせて主キー） |
| `axis` | 軸名。**保存済みの綴り** |
| `charge` | **累積**（`REAL`）。票で増え、薄れで減り、**段を動かすと費用ぶん消える** |
| `updated_at` | 最後に書き戻した時刻 |

**1軸1行の現在値**である。[ADR-0027](adr/0027-drift-from-what-was-not-chosen.md) §決定7 の
「累積が費用に達したら1段動かし、費用ぶんを消費する」の**溜め place**で、
**票の表とは立場が逆**——あちらは追記のみ、こちらは毎ターン上書きされる。

#### なぜ票から計算し直さないのか

**累積は「何が起きたか」ではなく「いま何が溜まっているか」**である。
票の履歴から再現するには**そのキャラクターの初期値**が要るが、`stat_alloc` は
上書きされるので**初期値はどこにも残っていない。**
窓を切って近似すると、[ADR-0026](adr/0026-drift-by-accumulation.md) が
実測のうえで却下した「時間窓」に戻ってしまう。

#### 行が無い軸は累積 `0`

初回のターンは行が1つも無い。**空の行を作らない**——作ると
「一度も走っていないキャラクター」と「累積が 0 に戻ったキャラクター」が
表の上で区別できなくなる。埋めるのは呼び出し側（`server::drift`）。

#### 記録専用モードは**この表にも書かない**

溜めておくと、`PERSONACORE_STAT_DRIFT` を `on` に切り替えた瞬間に
**溜まっていた分がまとめて放出される。** 記録専用モードの存在理由は
「値が動かないので決定性が保たれる」ことなので、
**切り替えた直後だけ荒れる**のはその前提を裏から壊す。
書き込みは `domain::DriftApply`（許可証）を要求する。

#### 1行壊れたときに何が止まるか

`Store::drift_charges` は**1行でも読めなければ丸ごと `InvalidStoredValue`**
（票の表と同じ側）。黙って飛ばすと**その軸の累積だけが 0 に戻る**——
「その軸だけ変容が遅い」としか観測できない。

| | |
|---|---|
| **止まるもの** | そのキャラクターの**値の適用だけ** |
| **止まらないもの** | 本文の応答・記憶の抽出・変容の判定・**票の記録** |

**有限でない値（`inf` / `nan`）は書かない。** 書けてしまうと次の読み出しが必ず失敗し、
**累積には削除の導線が無い**ので、そのキャラクターの変容が永久に止まる。

**表の側にも門がある**（`migrations/0012_stat_drift_charge_finite.sql`）——
`CHECK (charge BETWEEN -1e308 AND 1e308)`。`typeof(charge) = 'real'` **だけでは ±Inf が通る**
（`9e999` は REAL である）ので、`sqlite3` から手で書けてしまう形を表の側で塞いである。
0009 / 0010 が `axis` に3条件を重ねているのと同じ判断で、見張り番は
`tests/store_schema.rs::drift_charge_check_rejects_an_infinite_or_mistyped_value`。

> **⚠ `typeof` が捕まえるのは「変換されずに残る形」だけである。**
> REAL の型アフィニティは**数に見える TEXT を REAL へ直す**ので、
> `'1.5'` を書いても `typeof` は `'real'` になり、読み出しでも落ちない
> （`migrations/0011_stat_drift_charge.sql` のコメントはここを取り違えている。実測 / 16e-b）。
> 弾けるのは**数に見えない TEXT と BLOB** である。

> **⚠ アプリ側の三重の門と役割が違う。**
> `DriftTuning::new` / `Store::save_drift_charges` / `DriftAxisLedger::new` が塞ぐのは
> **アプリからの書き込み**で、表の CHECK が塞ぐのは **`sqlite3` からの手書き**である。

#### 索引は足さない

主キー `(character_id, axis)` の自動索引で、この表への読みは全部まかなえる
（引くのは「そのキャラクターの全行」だけ）。行数は**軸の本数**で頭打ちになるので、
票の表と違って伸び続けない。

### `stat_axis_candidate` ほか — 変容が見いだす軸の候補（[ADR-0046](adr/0046-drift-proposes-new-axes.md) §決定6）

**表は3枚。どれも追記のみ**（`migrations/0015_stat_axis_candidate.sql` / 作業単位 A-9a）。

| 表 | 1行は | 列 |
|---|---|---|
| `stat_axis_candidate` | 候補1件 | `id` / `character_id` / `name`（`StatAxis` と同じ上限 20）/ `source_memory_id`（**出どころの記憶**。複合外部キーで**同じキャラクターの記憶**に縛る）/ `created_at`。`UNIQUE (character_id, name)` |
| `stat_axis_candidate_transition` | 状態の移り変わり1回 | `candidate_id` / `state`（`trial` / `passed` / `failed` / `adopted` / `rejected`）/ `reason`（**不合格のときだけ** `pinned` / `silent` / `too_few_samples`）/ `created_at` |
| `stat_axis_trial_vote` | 試用の票1件 | `candidate_id` / `session_id`（**候補の持ち主の会話に限る** —— 書き手が同じトランザクションで照合する / A-9c）/ `vote`（`up` / `down` / `zero`）/ `created_at` |
| `stat_axis_discovery_attempt` | **候補を尋ねた試み1回**（`0016` / 作業単位 A-9b） | `character_id` / `through_memory_id`（**その回に数え終えた記憶** ＝ 数えた記憶のうち最新。複合外部キーで同じキャラクターの記憶に縛る）/ `outcome`（`proposed` / `duplicate` / `malformed` / `truncated` / `upstream_failed` / `not_recorded`）/ `created_at` |

#### 「前回の試み」は候補の表からは取れない —— だから試みの表がある（A-9b）

候補づくり（ADR-0046 §決定2）は**そのキャラクター自身の記憶（`subject = character`）が前回の試みから `N` 件増えたら**1回尋ねる。
**候補の行が作られるのは採った回だけ**なので、完全一致で捨てた回・崩れた応答の回・上流を呼べなかった回は候補の表に痕跡を残さない。
そこから「前回」を取ると**採るまで毎ターン尋ねる**。だから**上流を呼んだ回は、結末が何であれ試みの表に1行残す**
（採った回は `Store::record_axis_candidate` の `Propose` が候補と同じトランザクションで、採らなかった回は `Store::record_axis_discovery_miss` が書く）。

* **目印は `max(through_memory_id)`**（`Store::axis_discovery_mark`）。後退しない。まだ一度も試みていなければ無い（＝全部数える）。
* 数えるのは**想起の入口（`Store::recall_memories`）が返す記憶のうち、主語が `character` で目印より id が大きいもの**（`domain::memories_since`）。上書きされた記憶は想起に出ないので数えない。
* **候補の出どころ（`source_memory_id`）は、その回に数えた記憶のうち最新**（Issue origin#42 の申し送り2）。目印と同じ値。
* **上流を呼ぶ前に止まった回（枠が無い・記憶が足りない・読めない・依頼が長すぎる）は残さない** —— 尋ねていない。
* `N` は `PERSONACORE_AXIS_DISCOVERY_MEMORIES`（**既定は測っていない値** / 権威は `domain::AxisDiscoveryMemories::DEFAULT`）。
* **走るのは変容の走らせ方が off でないキャラクターだけ**（理由は `server::extract::run` の doc）。**枠の数 `m` = 0 なら DB にも触らない。**
* **使えない名前（却下・不合格）は依頼に新しい順で、予算に入るだけ載る**（A-9c / Issue origin#43 の申し送り1）。
  名前の数には上限が無く、全部を削れない枠に載せていた A-9b の形では、溜まると「依頼が長すぎる」でそのキャラクターの候補づくりが永久に止まった。
  **載せきれない古い名前も二度は採らない** —— 最後の判定は照合（`domain::axis_name_clash` が全候補と完全一致で照らす）。
  予算は**記憶が先**に取る（`prompt::axis_discovery` の doc）。載せた件数と総数はログの `axis_discovery_refused_sent` / `axis_discovery_refused_total`。

#### 試用と判定（A-9c / ADR-0046 §決定3・4）

試用中の候補があるキャラクターでは、**ターンごとに固定の軸とは別の依頼**（`prompt::axis_trial` —— 候補1本と直前の1往復だけ）で候補を採点し、
票を試用の票の表へ追記する（`server::axis_trial`。抽出タスクの中で**変容の後・候補づくりの前**）。**値は動かさず、本文のプロンプトにも載らない。**
**固定の軸の依頼・票・値は1バイトも変わらない**（見張り番 `the_fixed_axes_drift_the_same_with_or_without_a_trial`）。代償は、試用中だけ裏方の呼び出しが1往復に1回増えること。

* **1ターンに採点するのは1つだけで、どれにするかは状態を持たない輪番**（`domain::candidate_to_score`）。並べて1回で採点しない（項目は独立に判定されない）。
  鍵は**そのターンの応答の `message.id`** を混ぜて（splitmix64）試用中の件数で割った余り —— 応答の id は1往復に2ずつ進むので、素の余りでは偶奇が揃って同じ候補を選び続ける。
  **A-9c の最初の版は「最も古い1つ」だった**が、最も古い候補が止まると後ろの候補に票が1件も入らなかった（レビュー指摘1）。
* **数えるのは票が書けた回だけ。** 崩れた応答・打ち切られた応答・上流の失敗・長すぎた依頼は票にせず、`T` に数えない（`0` として数えると沈黙が水増しされる）。
  **代償: 一度も読める答えが返らない候補は試用が終わらず、枠を1つ埋めたまま、試用のターンのおよそ 1/k（k = 試用中の件数）を食い続ける**
  （他の候補は進むが k/(k−1) 倍ほど遅くなり、裏方の呼び出しもそのぶん空費する）。**止まった候補1つで枠も1つなら、そのキャラクターの試用も候補づくりも止まる。**
  打ち切る規則（崩れが続いたら不合格）は置いていない（不合格の理由を増やすには移行が要る）。崩れた回はログの `axis_trial_outcome`（理由）と `axis_trial_quotes`（剥がした引用記号の数）に残る。
* **試用は候補づくりの前**（`server::extract::run`）。このターンに生まれた候補はこのターンには採点されず、このターンの判定で空いた枠はこのターンの候補づくりが使える
  （見張り番 `a_candidate_made_this_turn_is_not_scored_until_the_next_turn` / `a_slot_freed_by_this_turns_verdict_is_used_by_this_turns_discovery`）。
* **票が `T` 件そろったら判定を追記する**（`domain::judge_axis_trial`。すでに `T` 件以上あれば尋ねずに判定する）。上から順に最初に当たった行で決まる:

  | 順 | 判定 | 条件 |
  |---|---|---|
  | 1 | 不合格（`silent`） | `0` の率 ＞ 線 |
  | 2 | 不合格（`too_few_samples`） | 非ゼロの票 ＜ `K` |
  | 3 | 不合格（`pinned`） | 非ゼロのうち上げの割合 ＞ 線 |
  | 4 | 合格（`passed`） | それ以外 |

  **線とちょうど等しい値は合格の側**（ADR-0046 と Issue origin#43 の「超える」。ADR-0030 §決定1 の表は「≥」と書いている —— 違いは `domain::axis_trial` の doc）。
  **割合は非ゼロが `K` 以上のときだけ読む**ので、張り付きを最後に見る。
* `T` / `K` / 線は `PERSONACORE_AXIS_TRIAL_TURNS` / `PERSONACORE_AXIS_TRIAL_MIN_NONZERO` / `PERSONACORE_AXIS_TRIAL_LINE_PERCENT`。
  **既定は測っていない値**（権威は `domain::AxisTrialRule` —— `T` と線は ADR-0030 の手順の値で、候補の分布では測っていない。`K` には根拠が無い）。
  `K` > `T` の組は起動を止め、理由は「組の不整合」として両方のつまみを名指しする（`T` だけを 9 にすると既定の `K` = 10 との組で止まる。値は同じログの行に両方出る）。
* 走るのは**変容の走らせ方が off でないキャラクターだけ**（shadow / on で走る）。**`m` = 0 なら DB にも触らない** —— `m` を 0 に下げると、試用中の候補は票が止まったまま枠に残り、戻すと続きから数える。

#### 状態は追記で進み、いまの状態は導出

**候補の表は状態を持たない。** いまの状態は**移り変わりの、候補ごとの最後の行**で、
読み手は `domain::current_axis_candidate_state` で列ごと検査して導く
（最初が `trial`、隣り合う2つが `AxisCandidateState::can_become` を満たす）。
規則は **試用 → 合格／不合格、合格 → 採用／却下** で、行き先の無い状態からは動かない。

#### 書き込みの経路は1つ

3枚への INSERT は `src/store/axis_candidate.rs` にだけあり、`Store::record_axis_candidate` が
`BEGIN IMMEDIATE` の中で**いまの状態を読んでから**1件を追記する
（空いた枠を数える・遷移を検査する・試用中かを見る）。**`m` = 0 では候補を作れない。**
見張り番は同じファイルの走査2本（`src/**` と `migrations/**`）:

| 見張り番 | 何を見るか |
|---|---|
| `no_statement_updates_or_deletes_an_axis_candidate_row` | 3枚（**＋試みの表 / A-9b**）の言及が**許可された形**（追記・読み出し・DDL）だけ |
| `no_file_but_the_one_writer_appends_to_the_axis_candidate_tables` | 3枚（**＋試みの表**）へ**書く位置**の言及が、あの1ファイルにだけ各1つ |

> **⚠ 守れていないのは `attribute_revision` と同じところ** —— 走査が見るのは SQL の綴りで、
> **「1つの関数に閉じている」ではない**（同じファイルに2つ目の書き手を足しても通る）。
> **採用で `stat_alloc` に値 0 の行を足すのは第2段**（ADR-0046 §決定6）で、この書き手にまだ無い。

#### 試用の票は `stat_drift_vote` と混ぜない

固定の軸の集計・画面・測定の道具を1つも変えないため（ADR-0046 §決定6）。
**`0` も記録する**（試用の判定は `0` の率を数える / §決定4）。変容の票は `0` を記録しない。

#### 1行壊れたときに何が止まるか

## 上限を持つ型にする規則

**プロンプトの「削れない枠」に載る自由文は、必ず上限を持つ型にする。**
`String` / `Option<String>` のまま持たない。

削れない枠（[02-architecture.md](02-architecture.md) のコンテキスト予算）は、
記憶や会話履歴と違って**溢れても削られない**。そこに無制限の文字列が載ると、
そのキャラクターは以後のすべてのチャットが `PromptError::BudgetExhausted` になる。

> **~~しかもフェーズ1には更新 API も削除 API も無いので、アプリ経由では二度と直せない。~~**
> **2026-08-16（0012）で `PATCH` と `DELETE` を作った**
> （[ADR-0016](adr/0016-character-update-and-delete.md)）。
> **上限を持たせる理由は弱まっていない** —— 直せるようになっただけで、
> **入れた瞬間からそのキャラクターは使えない**ままだから。
> **識別子は今も直せない**（不変）。

### なぜ規則にしたか

**同じ構造の穴が3回出た。** `MemoryContent` → `Persona` → `output_format_instruction`。
そのたびに個別のテストを1本足す形だと、**4つ目のフィールドを足す人が
「その最大値は？」を考えずに済んでしまう。** 規則と、規則そのものを見張るテストを置く。

### 現在の上限

いずれも**文字数**（`chars().count()` = Unicode スカラー値の個数）で数える。
バイト数にすると UTF-8 では日本語1文字が3バイトなので、
**日本語だけが英語の 1/3 しか書けなくなる。**

| 値 | 型 | 上限 | 備考 |
|---|---|---|---|
| `character.display_name` | `DisplayName` | 50 | **プロンプトに載る呼び名** |
| `character.base_persona` | `Persona` | 600 | キャラクター定義の全文（作業単位 12b で 1000 → 600） |
| `character.output_format_instruction` | `OutputFormat` | 150 | 「指示として従え」と宣言される唯一の節 |
| `stat_alloc.axis` | `StatAxis` | 20 | 短いラベル。件数分載る |
| `memory.content` | `MemoryContent` | 500 | 事実1件 |
| `memory.category` | `MemoryCategory` | 50 | 短いラベル |
| `character_agreement.content` | `AgreementContent` | 60 | **削れない枠ではなく優先の枠**（入りきらないときだけ古い側から落ち、件数が報告される）。**件数も上限つき**（`MAX_ACTIVE_AGREEMENTS` = 16 / ADR-0051） |

> **`character.name` はこの表に載せない。** 0004a 以降、`name` は
> **プロンプトに載らない**（載るのは `display_name`）ので、削れない枠を食わない。
> 上限は依然として必要だが、それは `model` フィールドと UI のためであって予算のためではない。
> **見張りテストの想定値に `name` を数え直さないこと。**

**件数に上限が無いもの**（軸・記憶・会話履歴・今回の発言）は、この規則の対象外。

* 記憶と会話履歴は**削れる枠**なので、増えても予算内に収まるよう `prompt` が落とす。
* 軸は削れない枠に載るが、**現実的な件数**（参照値6軸の倍 = 12軸）を最悪ケースとして
  見張りテストに置いている。
* 今回の発言は削れない枠に載るものの、長すぎても**その1回が失敗するだけ**で、
  短く送り直せば回復する。保存された設定と違い恒久的な破損にならないので上限を持たせない。

### 見張り番

`src/prompt/mod.rs` の **`every_field_at_its_limit_still_fits_the_default_budget`**。
上の表の値を**すべて上限いっぱい**にし、しかも**すべてアストラル面の文字**
（1文字 = 4バイト = 見積もりの最悪ケース）にしたうえで、

1. 既定の予算（8,192 − 1,024 = 7,168）に収まること、
2. **その状態でも直近の記憶が1件は載る**こと

を確かめる。2 は余白の見張りで、どれかの上限を上げるとまずここが破れる。

> **余白はもうほとんど無い。** 現時点の最悪ケースは削れない枠 6,958 / 取り分 7,168 で、
> **残りは 210**（うち 104 を「直近の記憶1件」が使う）。上限いっぱいのペルソナだけで
> 4,000 を占めるため、**どれか1つでも上限を実質的に上げると入らなくなる**
> （実測: 名前 50 → 100 で余白 10、軸 20 → 23 で余白 66、形式指示 150 → 300 で予算超過）。
> これは意図した状態で、**上限を上げるなら既定のコンテキスト長を上げる判断とセット**になる。

**新しいフィールドを削れない枠に足すときは、このテストに足すこと。**
足せない（＝収まらない）なら、上限か既定のコンテキスト長のどちらかを見直す。

### **上限は後から下げられない**

どの上限も**書き込みの検証**と**読み出しの検証**の両方に使っている。
下げると、保存済みの正当な値が `StoreError::InvalidStoredValue` になって
**そのキャラクターが読めなくなる。**

> **~~一覧から黙って消える~~ → 0012b で「読めない行」として指し示すようにした。**
> `id` と、読めなかった列が一覧に出る（`handle` そのものが読めない行は `handle: null`）。
> **`handle` が読めない行だけは今も API から直せない**（識別子は不変）。
> **それ以外は `PATCH` で直せる。** 復旧手段が DB の直接編集だけ、ではなくなった。

下げるなら既存データを詰めるマイグレーションが要る。**上げる方向は安全**だが、
上の見張りテストを必ず確認すること。

## 不変条件（絶対に守る）

以下は `CLAUDE.md` の「絶対制約」にも転記してある。**レビュアーが最優先で検出する項目。**

### 1. `memory.subject` を省略しない

「猫が好き」がユーザーの発言かキャラの発言かを区別しないと、**一人称が混線する。**
キャラがユーザーの記憶を自分のものとして喋り出す、という形で必ず表面化する。

`subject` は `Option` にせず、`domain::Subject` enum として必須にする。

### 2. `superseded_by` は上書き削除ではなく時系列保持に使う

矛盾する記憶が出てきたとき、**古い行を DELETE / UPDATE で潰さない。**
新しい行を追加し、古い行の `superseded_by` に新しい行の id を入れる。

> **同じ「時系列保持」の立場の表が3つある。** 記憶（この節）／票（`stat_drift_vote`）／
> **属性の履歴（`attribute_revision`）。** 3つとも**追記のみで、アプリからの書き換えが無い。**
> **属性の側の詳しい話は上の `attribute_revision` の節に置いてある**（ここに写さない）。
> **軸の候補の3枚（ADR-0046 / 作業単位 A-9a）も同じ立場**（上の `stat_axis_candidate` の節）。

これはフェーズ2で「以前はXと言っていたが、最近はYと言っている」という形の想起を
可能にするため。**上書きしてしまうとこの情報は永久に失われる。**

**いま `superseded_by` を書くのは、人の訂正だけ**（`POST /admin/characters/{handle}/memories/{memory_id}/corrections` →
`Store::supersede_memory` / [ADR-0022](adr/0022-repairing-memories-without-deleting.md)）。訂正版を新しい行として足し、
古い行の `superseded_by` にその id を入れる。**自動の矛盾解消（フェーズ2）はまだ無い**が、列と、それを潰さない実装は守る。

> **例外: しまったキャラクターを完全に消すと、そのキャラクターの `memory` の行はカスケードで物理的に消える**
> （`DELETE /admin/characters/{handle}` / [ADR-0049](adr/0049-deleting-characters-and-conversations.md)）。**意図どおり。**
> この不変条件は**直すとき**の規則で、想起する主体ごと捨てる操作には、保つべき時系列が残らない（ADR-0049 §「記憶を消さない」制約との線引き）。
> 消せるのは**しまったキャラクター**（または会話が1件も無いキャラクター）だけで、完全に消す前に必ず「しまう」を通る。

> **`store` には `memory` を DELETE する API も、`superseded_by` 以外の列を UPDATE する API も無い。** これが唯一の防御であり、
> `src/store/memory.rs` の SQL 走査テストが **`src/**` 全体**と `migrations/**` を検査して
> **許可された形以外を落とす**（禁止リストではなく許可リスト。禁止語の列挙は
> `UPDATE memory SET locked = 1, content = ?` のような並べ替えで原理的にすり抜ける）。
>
> 現在の許可形は `INSERT INTO memory (` / `FROM memory` /
> `UPDATE memory SET superseded_by`（**`SET` 句にカンマがあれば落とす**）と、
> `migrations` 側の DDL 3種（`CREATE TABLE` / `CREATE INDEX ... ON` / `REFERENCES`）。
> **読みの経路を増やすときは許可形の更新が要る**（`JOIN memory` は現状落ちる）。
> そこがレビュー点になるのは意図どおり。
>
> **`INSERT OR REPLACE` / `REPLACE INTO` も禁止。** SQLite の `REPLACE` は競合行を
> **DELETE してから INSERT する**ため、`DELETE` の文字がソースに現れないまま行が消える。
> 「上書き API を素直に書く」ときの最短経路がこれになる。
>
> **走査の範囲を `src/store/**` に絞らないこと。** `server` に生の SQL を書けば
> 走査の外に出る（[ADR-0008](adr/0008-admin-api.md)）ので、Rust 側は `src/**` 全体を見る。
> 人間向けのコメントで代用しない。
>
> **走査が見るのは「文字列リテラルに書かれた SQL」だけ。** 次は網の外にある:
> `format!` での組み立て（**中身が全部リテラルでも**接尾辞側にテーブル名が現れず素通りする）、
> `DELETE FROM character ... IN (SELECT character_id FROM memory ...)`
> （キャラクター削除に伴う CASCADE。設計としては正当だが**この網は止めない**）。
> 生文字列 `r#"..."#` は**かつての抜け道**で、今は字句として読むので落ちる。
> 逆に、**抽出が現実の構文に追いつけなくなったら**（閉じていない文字列・生文字列・
> ブロックコメント）走査テストが検出して赤にする。
> 走査が静かに無効化されるより、うるさく落ちる方を選んでいる。

> **記憶本文と分類には上限がある**（`MemoryContent` = 500 / `MemoryCategory` = 50）。
> 上記「上限を持つ型にする規則」の**最初の実例**で、記憶に固有の事情がもう一段ある:
> 記憶を消す API が無いため、抽出サブLLM が暴走して会話ログ丸ごとを1件の記憶として吐くと、
> **その行はアプリ経由では二度と消せない。** 想起から外す手段は人の訂正（[ADR-0022](adr/0022-repairing-memories-without-deleting.md)）だけで、
> 訂正されるまでは、想起に選ばれるたびに記憶の枠を食い続ける。
> （かつての全件注入では、そのキャラの以後の全プロンプトに載り続けた。）
>
> 記憶は**削れる枠**なので予算そのものは壊さないが、削られるということは
> **想起が欠ける**ということで、「なんとなく前と違う」としか観測できない形で効く。

> **FK 制約はこの不変条件を守らない。** `superseded_by` の FK が防ぐのは「参照先（後継行）が
> 消えること」であり、守りたい**古い行の側は無防備**。
> `DELETE FROM memory WHERE superseded_by IS NOT NULL` は「もう上書き済みだから消してよい行」を
> 選ぶ最も自然なクエリでありながら、**保持したい行だけを正確に消す。**
> **古い行の保護はアプリ層の責務**であり、DB は止めてくれない。

> **`superseded_by` の循環はスキーマで防げない。** 自己参照（`id` が自分を指す）は
> `CHECK` で潰せるが、`1→2` かつ `2→1` のような循環は防げない。
> フェーズ2で「以前はX」を辿る実装は自然に while ループになるため、
> **辿る側に必ず上限（深さ制限）を持たせること。**

#### 上書きの経路のいまの制約（訂正 `Store::supersede_memory` と、将来足す自動の上書き）

- **新しい行の INSERT と、古い行の `superseded_by` の UPDATE は同一トランザクション。**
  分けると「新しい記憶はあるが古い記憶が有効なまま」という、
  矛盾する記憶が2件とも想起される状態が生まれる。
  `Store::supersede_memory` は `BEGIN IMMEDIATE` の1つのトランザクションでこの2つを行う（ADR-0022 §3）。
- **後継記憶を生成するサブLLM 呼び出しは、そのトランザクションの外で完了させる。**
  CLAUDE.md の絶対制約（トランザクション内で外部通信を `await` しない）。
  いまの訂正は人が本文を書くので LLM を呼ばない。**自動の上書き（フェーズ2）を足すときに効く制約。**
- `store` が `memory` に対して持つ書き換えは **`superseded_by` の UPDATE だけ**で、DELETE する API は無い
  （しまったキャラクターを完全に消すときのカスケードは例外 —— 上の例外の注記）。
  上書きの経路を足すときは、**`superseded_by` 以外の列を書ける API を同時に生やさないこと。**

### 3. `raw_content` を必ず保持する

パース失敗時の調査に不可欠。`dialogue` / `narration` に分解できたかどうかに関わらず、
**生出力を常に保存する。** 「パースに成功したから生は要らない」としない。
プロンプト調整の効果測定も、過去の生出力があって初めてできる。

> **例外: しまったキャラクターを完全に消すと、その会話の `message` の行は `raw_content` ごとカスケードで消える**
> （`session` → `message` の `ON DELETE CASCADE` / [ADR-0049](adr/0049-deleting-characters-and-conversations.md)）。**意図どおり。**
> この不変条件は「残っている会話について」の規則として読む。捨てた会話の調査の材料は残らず、それを受け入れている。

### 4. SQL は必ずプレースホルダ

文字列連結でクエリを組まない。**特に LLM の出力を含む値は例外なくバインドする。**
LLM 出力は「外部からの信頼できない入力」として扱う。

### 5. `generated_image` の `positive_prompt` / `negative_prompt` / `seed` を必ず保持する

**良い結果が出たときに再現・微修正できることが、実験の効率を大きく左右する。**
「プロンプトは組み立て直せる」と考えて省略しない。辞書やテンプレートを更新した後では、
当時のプロンプトはもう再現できない。

ComfyUI が出力する PNG にはワークフロー全体がメタデータとして埋め込まれるが、
**それとは別に DB 側でも持つ**（検索・集計のため）。

## 想起戦略

~~**メモリ件数が数百件を超えるまで、ベクトル検索は実装しない。** 全件注入で足りる~~
（[ADR-0003](adr/0003-full-memory-injection.md)。**置換済み**）

**いまは3層で想起する**（[ADR-0023](adr/0023-three-layer-recall.md)）。ベクトル検索はしていない。

| 層 | 何を | 予算 |
|---|---|---|
| 1（身元） | `character_attribute`。人が書く | **削れない枠**。予算に関係なく必ず載る |
| 2（直近） | 記憶を新しい順に | 記憶の枠を層2と層3で半分ずつ。片方が余ったらもう片方が使う |
| 3（関連） | 記憶を、今回の発言との語の重なり（文字 n-gram と希少度）が高い順に | 同上 |

- **本文の想起の候補は、利用者についての記憶（`subject = user`）だけ**（[ADR-0050](adr/0050-consolidating-memories-into-experience.md) §決め直し 1 / origin#59 A-11a）。
  キャラクター自身についての記憶は、本文に載せると自分の台詞の言い直しが定型として戻る輪になる（ADR-0050 の測定）。
  **行は消さずに残り、抽出の依頼（既知の記憶）と軸の候補の依頼には今までどおり載る。**
  会話をまたいで覚えていてほしい約束・決まりは、属性（層1）に人が書く（ADR-0050 §決め直し 5）。
- `store` の想起の入口（`Store::recall_memories`）は**主語を問わず有効な記憶を全件**返し、
  主語で絞るのも層に分けて選ぶのも `prompt`（`build_prompt` / `src/prompt/recall.rs`）。
- **引かなかった件数は数えて `info` に出す**（ADR-0023 §3 / `report_recall`。主語で外した件数は `excluded_own` として別の欄）。

> 埋め込みを使うなら、埋め込みのモデル（`nomic-embed-text-v1.5` など）を載せた上流が要る。
> どの上流に何を載せるかはまだ決めていない。**今は使わない**（層3を埋め込みへ移すときの注意は ADR-0023 の「層3の絞り込みは、埋め込みへ移すと効き目を失う」）。
