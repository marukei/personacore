### `temperature = 0` でも1回目だけ出力が違う（**比較実験の前提**）

**プロンプトが変わった直後の1回目は、2回目以降と違う出力になる。** 2回目以降は安定する。

2026-08-14 に実測（`ministral-3-14b-instruct-2512`）。personacore 経由でも LM Studio 直叩きでも
**同じ形で再現した**ので、本サービス側の問題ではない。

```
同じ要求を3回:  1回目 ≠ 2回目,  2回目 == 3回目
```

**これに気付かないと、性格値の比較実験が丸ごと無意味になる。**
実際、マイルストーン5の最初の測定では「同じ性格値なのに出力が変わる」という結果になり、
危うく「上流が非決定的だ」と誤診するところだった。

**手順**: 条件ごとに**3回投げ、2回目と3回目の一致を確認して2回目を採用する。**
これで、独立に設定した同一条件が**バイト一致**するようになる（実測）。
一致しない条件が出たら、その測定は捨てること。

### **セッションをまたぐと一致しない**

上の手順で得られるのは**同一セッション内の再現性だけ**である。
**サーバを再起動して同じ条件を測ると、文面が変わる**（実測 2026-08-15）。

```
同一条件（同じキャラ・同じ性格値・同じ発言・temperature=0）
  前回セッション len=380 / 今回セッション len=253 / 一致=False
```

**ただし性質は再現する。** 上の例では両方とも「うおおーっ！」で始まり、
`*"…"*` の形式で、饒舌という同じ特徴を示した。

**したがって:**

- **バイト比較は同一セッション内でのみ意味を持つ**（対照実験はこの範囲で組む）
- **セッションをまたぐ比較は、読んで質的に行う**
- **「前回と違う文面が出た」を変化の証拠にしない**

### ⚠ **LM Studio の中身は llama.cpp で、`:1234` はその前のプロキシ**（2026-08-28 に実測）

`Get-CimInstance Win32_Process -Filter "Name='llama-server.exe'"` の `CommandLine` が全部読める。
**engine は `extensions/backends/llama.cpp-*/llama-server.exe`**、**`--port` と `--api-key` は動的。**

実際の引数（14B のとき）:

```
--jinja --chat-template-file <temp>/chat-template.jinja
--ctx-size 16384 --n-gpu-layers 999999 --n-cpu-moe 0 --main-gpu 0 --split-mode layer
--ctx-checkpoints 32 --batch-size 2048 --ubatch-size 512 --threads 12 --parallel 4
--cache-type-k f16 --cache-type-v f16 --flash-attn on --kv-offload --kv-unified --load-mode mmap+mlock
```

**同じプロセスに、プロキシ経由と engine 直で当てて比べられる**（対照としてこれ以上は無い）。
**9B・VRAM に余裕あり・交互 6 往復・出力は6回とも完全一致:**

| | tok/s |
|---|---|
| プロキシ（`:1234`） | 58.2 〜 59.4 |
| engine 直 | 60.1 〜 62.3 |

**→ 層の取り分は約 4.5%。** TTFT はどちらもミリ秒（プロキシ 3.5〜4.4ms / 直 11.7〜19.0ms で、**プロキシのほうが速い**）。

> **⚠ 「LM Studio を外すと速くなる」は、この機では支持されない。**
> **体感の差の出どころは、たぶん JIT ロード**（下記 7〜10 秒）。**`llama-server` はプロセスが重みを抱える。**
>
> **⚠ そして、比べるときは engine の設定を揃えること。**
> 司令塔が最初に出した「15〜20% 速い」は、**自分の `--parallel 1` を LM Studio の `--parallel 4 …` と、
> しかも 95% VRAM の下で比べた**もので、**両方外したら 4.5% になった。**
>
> **⚠ サンプラも揃えること。** **揃える前は `temperature 0` でも出力が 6 文字目で分岐した。**
> **LM Studio は指定していないサンプラの既定を当てている。**
> `top_k 0` / `top_p 1.0` / `min_p 0` / `repeat_penalty 1.0` / 各 penalty 0 を明示すると、
> **345 文字がバイト単位で一致する。**

### ⚠ **JIT ロード中でもエラーは返らない**（2026-08-28 に実測）

**ロードが終わるまでブロックして 200 を返す。** この機で **7〜10 秒**（14B / ディスクキャッシュが温かい状態）。
**personacore 経由でも、非ストリーミング 8.96s・ストリーミング 8.56s で、どちらも 200。**
**中継が始まる前にロードが吸収される**ので、**`relay::IDLE_BUDGET` は原理的にこれを見ない。**
効いている上限は `llm` 側の `idle_timeout`（既定 180 秒）。

> **⚠ ただし、冷えた起動ではコンテキスト長の照会（上限 5 秒）が間に合わない。**
> **本文の予算が実際の半分（8192 / 実測 16384）で走り、最大 5 分（引き直しの間隔）で自己回復する。**
> **WARN では報告されるが、HTTP からは分からない。**

### ⚠ **上流の既定のサンプラを知りたいなら `/props` ではなく `/slots`**（2026-08-29 に実測 / C-13）

**`llama-server` は2つの窓を持っていて、答えが違う。**

| 窓 | 何を言うか | `repeat_penalty` |
|---|---|---|
| **`/props`** | **engine の起動時の既定** | **1.0** |
| **`/slots`** | **その要求が実際に何を使ったか**（要求を処理した直後に読む） | **1.1** |

**`llama-server` の起動引数にサンプラのフラグは1つも無い。**
**つまりこの `1.1` は、LM Studio のプロキシが本文に入れて送っている。**

**→ 権威は `/slots` だけ。`/props` を「上流の既定」として読むと、間違った答えが返る。**
**⚠ そして明示で送れば差し替えは尊重される**（`repeat_penalty: 1.0` を送るとスロットに `1` が入る）。

**⚠ この2つの窓を使う道具は、毎回プロセスのコマンドラインから繋ぎ先を引き直すこと。**
**`--port` と `--api-key` は、モデルを載せ直すたびに変わる**（実測で PID・port・key が全部入れ替わった）。

**⚠ 観測できる窓があっても、腕の対照にはならない。**
**「サンプラを送らない要求」と「既定と同じ値を明示した要求」は、`/slots` では区別できない**
（プロキシが同じ値を注入するため）。**区別するには、`:1234` の手前で本文を控えるしかない。**
