## 背景

origin#57 の測定（ADR-0050）で分かったこと:

- **約束・決まりは会話をまたいで覚えている価値がある。** 決まりを要旨（決め台詞を含まない平叙・三人称）で持たせた腕は、新しい会話でも決まりを覚えていた（2/2）。持たせない腕は覚えていなかった。
- **ただし、キャラクター自身の記憶をそのまま本文に戻すと、決め台詞も一緒に戻る。** 本文の想起から `subject=character` を外した（origin#59）ので、いまは約束・決まりも本文から落ちている。
- **既に抽出された記憶を、サブ LLM で分類・書き直しさせると悪化した**（機械が書いた行の腕は、定型が主 8/10・決まり 0/2）。抽出は決まりも決め台詞も同じ「〜と定義した」の形で書くので、文の形から境界が引けない。
- v0.1 の間のつなぎ（属性で持つ）は、利用者が「実際に運用するのは非常に難しい」と判断した。属性は 8 件・値 20 字までで、約束・決まりの置き場所として窮屈。

## 利用者に問うたこと（2026-10-21）

| 問 | 答え |
|---|---|
| 誰が書くか | **モデルが提案し、利用者が採る**（自分で書くこともできる） |
| 終わったとき（果たした・破った・取り消した） | **モデルが提案し、利用者が確定する** |
| 本文のどこに載せるか | **有効なものを毎回全部載せる（上限つき）** |

## 決定

### 1. 専用の表に持つ。記憶とも属性とも別

- **約束・決まり**（以下「取り決め」）を、キャラクターごとの新しい表に持つ。1行が1つの取り決め。
- 持つもの:
  - **中身**: 要旨の平叙文。上限を持つ型にする（削れない枠に載るため —— CLAUDE.md §1）。叩き台は 60 字。
  - **種類**: 約束（いつか果たす）／決まり（守り続ける）。
  - **守る側**: 利用者／キャラクター／両方。「誰が誰に」を落とすと一人称が混線する（`memory.subject` を省略しない理由と同じ）。
  - **状態**: 提案中／有効／却下／果たした／破った／取り消した。
  - **出どころ**: 生まれた会話（とメッセージ）。手で書いたものは無し。
- **状態の変化は追記だけの履歴に残す**（ADR-0028 §決定5 と同じ形 —— 履歴は追記、現在の状態は導出か、同じトランザクションで更新する投影）。**行は消さない**。終わった取り決めは履歴に残り、「以前は約束していた」を保つ。キャラクターを完全に消したときだけ、カスケードで消える（ADR-0049）。
- 記憶（`memory`）は変えない。キャラクター自身の記憶は今までどおり本文の想起から外れたまま（ADR-0050）。

### 2. 生まれた取り決めは、モデルが提案し、利用者が採る

> **2026-10-22**: この決定は、別の会話での測り直しを通ってから作る（§「作る前」の測定と決め直し 2）。土台は先に作る。

- **裏方が、本文の応答を返し切った後に**（抽出と同じ —— CLAUDE.md §1）、**直前の1往復を生の台詞のまま**渡し、「この往復で、新しい約束・決まりが生まれたか」を尋ねる。既にある有効な取り決めも渡す（重複を防ぐため）。
- 返ってきた候補は**提案中**として保存し、**本文には載せない**。利用者が画面で**採る（有効にする）・直してから採る・捨てる（却下）** を選ぶ。
- 利用者が画面で自分で書いた取り決めは、提案を経ずに有効になる。
- **既存の記憶は入力にしない。** 測ると、抽出済みの記憶からの分類は悪化した（ADR-0050）。入力は生の台詞だけ。
- 裏方の書き込みは、生んだ会話が今も在り同じキャラクターのものであることに縛る（ADR-0049 決定3）。

### 3. 終わった取り決めも、モデルが提案し、利用者が確定する

> **⚠ 2026-10-22 に置き換わった**（§「作る前」の測定と決め直し 3）: 終わりの提案は作らない。終わらせるのは利用者だけ。下は当初の案として残す。

- 同じ裏方の依頼で、「有効な取り決めのうち、この往復で果たされた・破られた・取り消されたものはあるか」も尋ねる。
- 返ってきた終わりの候補は、**有効のまま**「終わりの提案あり」として画面に出す。利用者が**確定する（果たした／破った／取り消した）・退ける**を選ぶ。確定するまで本文に載り続ける。
- 利用者は提案が無くても画面から終わらせられる。

### 4. 有効な取り決めは、毎回全部、削れない枠に載せる

- 本文のシステムプロンプトに「# 約束・決まり」の節を置き、**有効な取り決めを全部**、守る側ごとに分けて載せる。提案中・終わったものは載せない。
- **件数と長さに上限を置く**（叩き台は 16 件・各 60 字）。上限が無いと、取り決めを足しただけで以後のチャットが `BudgetExhausted` になりうる（CLAUDE.md §1）。見張り番 `every_field_at_its_limit_still_fits_the_default_budget` に、この節を上限いっぱいで足す。
- 上限に達したら、新しい提案を採る前に、古い取り決めを終わらせるよう画面が促す（黙って落とさない）。

> **2026-10-22 追記（A-12a の実装で分かったこと / 司令塔の決定・利用者には事後に報告）**: 叩き台（16 件 × 60 字）を**削れない枠**に足すと、見張り番 `every_field_at_its_limit_still_fits_the_default_budget`（数えられない上流＋既定の予算 8192 での最悪の保証）を満たせない。着手前の削れない枠は最悪で 6644／取り分 7168 で、余りは 524 しかなく、取り決めの節を上限いっぱいで足すと 10883 になる。**上限を下げても解けない**（小見出しだけで 127 を使い、60 字の1件 257 も入るかの境目）。
> 既定の予算を上げる案は採らない（既定は上流の窓が読めないときの落とし所で、上げると小さい窓の上流で溢れる —— ADR-0036）。
> **決定**: 取り決めの節は「削れない枠」ではなく、**削れない枠の次に、記憶と履歴より先に取る「優先の枠」**に置く。残りから取り決めが要るだけ先に取り、その後の残りを記憶と履歴で半々に分ける（origin#56）。**入りきらないときだけ古いものから落とし**、落とした件数をログ（`warn`）と画面に出す（黙って落とさない）。利用者の上流（16384）では上限いっぱいでも全部載る見込みで、「毎回全部載せる」は実際の環境では保たれる。最悪の環境では一部が落ちうるが、`BudgetExhausted` にはならない。B-60（ADR-0052）が入れば、日本語の窓は約5倍になる。
> **利用者が了承した（2026-10-22 朝）。**
> **順序の補足（A-12a のレビュー / 司令塔）**: 優先の枠が残りを取りすぎると、会話の履歴が 0 件になりうる（origin#56 の形が取り決め経由で戻る）。**取る順は「削れない枠 → 最新の1往復（残りに入るなら） → 取り決め → 残りを記憶と履歴で半々」**とする。会話の流れを1往復も見ない応答は、取り決めを1件載せるより悪い。
>
> **提案の走らせ方（利用者の決定 / 2026-10-22 朝）**: 提案の形が線を通ったら、**毎ターンや区切りごとの自動ではなく、画面の「この会話から約束を探す」を押したときだけ**、直近の会話に提案の依頼をかける。探索で最も有望だった形（1段目と2段目をそれぞれ2回引いて揺れを打ち消す）は、8往復あたり依頼4つ・約 76 秒/往復と重く、本文と同じ llama を使うので、自動で走らせると本文が待たされるため。

### 5. 画面

- キャラクターごとの「約束・決まり」の画面: 提案（採る・直す・捨てる）／有効な取り決め（終わりの提案の確定・退ける、手で終わらせる）／履歴。
- 手で書く入口を置く。

### 6. API と互換

- 新しい口を足す（一覧・提案の採否・手で書く・終わらせる・履歴）。**口と欄の追加なので ADR-0047 §② の表では `1.x`**。既存の口の形は変えない。
- **新しい表を足すマイグレーションが入るので、v0.2 で開いた DB は v0.1 の exe では開けない**（これまでの版と同じ一方通行）。利用者は「後方互換を壊してよい」としたが、**この設計では既存の形を壊す必要は無かった**。
- v0.1 の間に属性へ書いた約束・決まりは、自動では移さない（どれが約束なのかを機械で判定できない）。利用者が画面で書き直す。

### A-12c-1 で決めたこと（2026-10-23 / origin#71）

- **裏取り:** 記録済みの δ3 の3通し（弥生1・翼1・翼2）を本番の Rust の読み・票・後段に通すと、検出 254 本・確かめ 154 本の依頼がバイト単位で一致した。候補 109 件・提案 29 件も一致し、不一致は 0（dedup のとき。dedup2 に替えると、翼1 の往復 60 の1件が増える —— 測定が穴として名指ししたもの）。
- **測った版から違えたところ（司令塔が採った）:**
  1. 会話の最後の往復の候補は、次にそのキャラクターと話したときに、印の往復だけを添えて確かめる（本番は会話の最後を知らない。出るのが1往復遅れる）。番号が飛んだ往復も同じ。
  2. 往復の番号は、会話ごとに1から数える。
  3. 「# 提案済み」と dedup の相手は、DB にある提案中・却下・有効の行（手で書いた有効な行も含む。終わったものは除く）。dedup は16件に絞らず、全件と比べる。
  4. 種類は常に「決まり」で保存する。守る側が読めない提案・60字を通らない提案・記号を落とすと空になる中身は書かず、数える。
  5. 失敗したら、その往復の検出か確かめを飛ばし、候補を捨てる。2本目の確かめが失敗しても、1本目で決まった候補は残す。
  6. 依頼に載せる値は `SafeText` を通す。
  7. 検出が `length` で切れた回も、読める行は読む。
  8. 提案中の一覧は、既存の `GET …/agreements` に載せる。新しい口は足さない（採る `…/adoption`・捨てる `…/rejection` は足した）。API の版は 1.3。
- **裏方の鎖での優先:** 提案は抽出の鎖の最後で直列に走る（同時に生きる裏方の依頼は1本。本文の差し引きに収まる）。ただし、**提案の段の最中に次の往復が来たら、提案の段だけを止めて、次の往復の鎖を走らせる。** 止めないと、鎖が長くなった分だけ、次の往復の記憶の抽出（本体の機能）が `skipped=busy` で捨てられる。止めた往復が失うのは、持ち越しの候補とその往復の確かめだけ。抽出・変容・試用・軸の候補の段の最中なら、今までどおり捨てる。
- **受容（遊んでから直す候補）:**
  - dedup2 は否定を区別しない。手で書いた決まりや退けた提案の**反対**（「敬語を使う」に対する「敬語を使わない」）は、重なりとみなされて提案されない。
  - 壊れた行が1つあると一覧が読めず、確かめが毎往復飛ぶ（書き手はすべて上限を通すので、壊れた行ができるのは DB を直接編集したときだけ）。
  - 止めた依頼は、上流が切断に気づくまで生成を続けうる。次の往復の抽出とわずかに重なる（重なりの長さは測っていない）。

> - **ボタンの形が成り立たなかった理由:** 提案の依頼は1本で最大 約 8.6k ＋ 応答 2048 あり、本文の数えた計画が裏方のために空けている分（ADR-0052 §B-60d-1 で決めたこと）を超える。2本同時に投げると、本文と合わせて窓を超え、ADR-0052 M4 の形で本文も裏方も落ちる。

## 危険

- **提案の依頼は本文と同じモデルへの賭け**（ADR-0037）。既存の記憶からの分類は悪化した。生の台詞からの提案はまだ測っていない（§測る問い）。
- 削れない枠が増える。上限いっぱいの取り決めが記憶と履歴の取り分（origin#56 の半々）を削る。上限は見張り番で押さえるが、実際の窮屈さは遊んでから見る。
- 裏方の依頼が1つ増える（1ターンあたりの上流への依頼）。抽出の依頼と1つにまとめるかは作業単位で決める（まとめると、抽出の文面を変えることになる —— ADR-0037）。

## 却下した選択肢

- **モデルが自動で有効にし、利用者は取り消すだけ**: 誤った約束が利用者の確認なしに会話へ載る。
- **利用者だけが書く**: 利用者が「運用は非常に難しい」とした属性と同じ負担になる。手で書く入口は残す。
- **記憶と同じく、想起で選んで載せる**: 話題に関係しない約束は載らず、忘れる。約束は「関係しないときにも守る」ものなので、毎回載せる。
- **既存の記憶から分類して作る**: ADR-0050 の測定で悪化した。
- **属性を広げて約束・決まりも持たせる**: 属性はキーと値の形で、状態（有効・果たした・破った）も守る側も持てない。

## まだ決めていないこと

- 中身の字数・件数の上限の値（叩き台 60 字・16 件）。
- 提案の依頼を抽出と1つにまとめるか、別にするか。
- 期限（「明日まで」など）を持たせるか。
- 本文での節の書き方（守る側ごとの見出し、状態の言い方）。
