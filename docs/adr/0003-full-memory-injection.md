# ADR-0003: メモリはベクトル検索せず全件注入する

- 状態: **置換済み**（[ADR-0023](0023-three-layer-recall.md) による）
- 日付: 2026-08-13（原典の引き渡しドキュメントより）

## 背景

会話記憶をプロンプトへどう載せるか。一般的には「ベクトル検索で関連する記憶だけを引く」が
定石とされるが、本プロジェクトの規模でそれが妥当かを判断する必要があった。

## 決定

**メモリ件数が数百件を超えるまで、ベクトル検索は実装しない。全件をプロンプトに注入する。**

ベクトル検索の導入は「全件注入がコンテキストを圧迫し始めてから」でよい。

## 理由

1. **量的に足りる。** 50件 × 平均30トークン ≒ **1,500トークン程度**。
   メインモデルの実用コンテキストは 8k〜16k なので、全件注入で十分収まる。
2. **検索は漏れるほうが怖い。** 検索を挟むと「必要な記憶が引かれない」リスクが生じる。
   キャラクターの一貫性が壊れる形で表面化し、しかも**原因の特定が難しい**。
   全件注入なら「載っているのに使われなかった」とモデル側に切り分けられる。
3. **早すぎる最適化。** 数百件に達するのがいつかも分かっていない段階で、
   埋め込み生成・インデックス管理・再計算のコストを抱え込む理由がない。

### 却下した選択肢

- **最初からベクトル検索** — 上記2、3のとおり。
- **FIFO で件数を打ち切る**（商用サービスの方式）— 原価制約から来る妥協であり、
  ローカル実行の本プロジェクトが真似する理由がない（[01-overview.md](../01-overview.md)）。

## 結果

### 得られたもの

- 想起の挙動が完全に決定的で、デバッグしやすい
- 埋め込み生成のインフラを持たずに済む

### 諦めたもの / 前提

- **メモリが増えたら破綻する。** これは織り込み済みで、
  「圧迫し始めてから」導入する。そのときのために:
  - **想起処理は一箇所に閉じ込める。** 後で検索に差し替えられるようにする。
  - **ベクトルDBは別途立てない。** SQLite に `sqlite-vec` を足せば同一DB内で完結する
    （[03-data-model.md](../03-data-model.md)）。
  - LM Studio に `text-embedding-nomic-embed-text-v1.5` が導入済みなので、
    埋め込み生成は必要になった時点ですぐ始められる。

### 移行の判断基準

件数そのものではなく**トークン予算**で判断する。`prompt` が予算配分を明示的に管理しているので、
そこで検知する。

> **「履歴が削られたら」ではない。** 会話は無限に伸びるので、
> **履歴が削られること自体は正常な運用**であり、それを信号にすると常に鳴り続ける。
>
> 見るべきは**記憶が予算に占める割合**。具体的には
> **`memory_tokens` がプロンプト取り分の半分を超えたら `warn`** とする。
> 「履歴が0件になった」は既に手遅れの状態であり、信号としては遅すぎる。

> **⚠ この判定は分子と分母の単位が揃っている前提。現在は揃っていない。**
>
> 分子（`memory_tokens`）は `prompt::estimate` の見積もり単位（≒ UTF-8 バイト数）、
> 分母（`prompt_allowance`）は実トークン由来のコンテキスト長。
> **日本語では見積もりが実トークンの 2〜3 倍**になるため、比率だけが膨らむ。
>
> 上記「50件 × 平均30トークン ≒ 1,500トークン」を当てると、
> 実トークンでは取り分の 21% にすぎないのに、見積もり単位では
> 50件 × 30文字 ≈ 4,750 > 3,584（7,168 の半分）で**鳴る。**
> つまり **本 ADR が「十分収まる」と宣言している設計点で信号が常時点灯する。**
> 鳴りっぱなしの信号は無視される信号であり、頻度の抑制では解決しない。
>
> **`server` で実コンテキスト長を見積もり単位へ換算する導線が入るまで、
> この信号は較正されていないものとして扱うこと**
> （[06-roadmap.md](../06-roadmap.md) の `server` 受け入れ条件）。
