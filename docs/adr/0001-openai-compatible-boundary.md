# ADR-0001: 本サービスを OpenAI 互換サーバとして実装する

- 状態: 採用
- 日付: 2026-08-13（原典の引き渡しドキュメントより）

## 背景

ローカルLLMのキャラクター会話基盤を作るにあたり、
「オーケストレーション層をどういうインターフェースで外に出すか」を決める必要があった。

素直に考えると独自 API を切り、それに合わせた FE を書くことになる。
しかしそれでは**コア機能（プロンプト組立・記憶管理）の検証が、FE を書き終えるまで始まらない。**

## 決定

**本サービス自体を OpenAI 互換 API サーバとして実装する。**
上流（LM Studio）と下流（FE）の**両側で同じ規格を話す中間層**にする。

```
FE ──/v1/chat/completions──► personacore ──/v1/chat/completions──► LM Studio
```

提供するエンドポイントは `POST /v1/chat/completions`（ストリーミング必須）と `GET /v1/models`。

## 理由

1. **フェーズ1でフロントエンドを一切書かずにコア機能を検証できる。**
   既存の OpenAI 互換チャットクライアントをそのまま FE として使える。
   これが決定打。最も不確実性が高いのはプロンプト組立の設計であり、
   そこを最短で検証できる形を選ぶ。
2. 推論バックエンドを LM Studio → vLLM 等に差し替えても中間層は無変更で済む。
3. フェーズ2で自作 FE を載せる際も、本サービス側は変更不要。

### 却下した選択肢

- **独自 API + 自作 FE を最初から作る** — 検証開始が FE の完成まで遅れる。
  最も不確実な部分の検証が最後に来るという最悪の順序になる。
- **LM Studio のプラグイン / 拡張として実装する** — LM Studio の内部構造に縛られ、
  推論バックエンドの差し替え自由度を失う。

## 結果

### 得られたもの

- FE を書かずにフェーズ1を完結できる
- 推論バックエンドと FE の両方について、差し替え自由度を確保

### 諦めたもの

- **OpenAI 互換 API の表現力に縛られる。** 特にセッションIDの概念がないため、
  リクエストがどのセッションのものかを同定する手段を別途考える必要があった。
  → `model` フィールドに埋める方式で解決（[ADR-0004](0004-session-identification.md)）。
  代償として、**クライアントから推論モデルを選ぶ手段は無くなる。**
- クライアントが毎回全履歴を送ってくるため、自前の永続化との**二重管理**が発生する。
  自前DBを正とし、クライアント送信分は最新メッセージのみ採用する方針で対処する。
