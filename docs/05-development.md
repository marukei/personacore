# 05. 開発方針

## テスト駆動開発

**実装とテストをセットで提示する。テストのない実装を受け入れない。**

- パーサ、プロンプト組立、トークン予算計算は**純粋関数として切り出し、単体テストを厚く**する。
- 上流（推論サーバ）への通信は**トレイトで抽象化**し、テストではモックを注入する。
- 実際の上流に接続するテストは通常のテストスイートに混ぜない
  （環境依存で壊れ、CI にもならない）。疎通確認は別枠で明示的に走らせる。

### テストが「効いている」とは

存在するだけのテストは価値がない。レビュアーは以下を見る。

- `assert!(result.is_ok())` だけで中身を検証していないか
- **異常系・境界値**があるか — パース失敗、空メモリ、性格値0、トークン予算超過
- モックが本物の振る舞いから乖離していないか
- 実装をなぞっているだけで、仕様を検証していないケース

## セキュアコーディング

個人利用のローカルツールだが、**LLM 出力を扱う以上、入力の信頼境界は厳密に引く。**

| 項目 | 方針 |
|---|---|
| SQL | **必ずプレースホルダ。** 文字列連結でクエリを組まない |
| 外部入力の検証 | **LLM の出力も外部入力**として扱いバリデーションする |
| コマンド実行 | **LLM 出力をシェル・パスに渡さない** |
| エラー出力 | 内部パス・接続文字列・スタックトレースをレスポンスに含めない（ログには出してよい） |
| バインドアドレス | `127.0.0.1` のみ。外部公開しない |
| `Host` / `Origin` / 要求の authority | **全部の経路の手前で検査する**（`src/server/host_guard.rs` / origin#54 B-58）。`Host` が `127.0.0.1:<実際に待ち受けているポート>` / `localhost:<同>` のどちらでもなければ 403（`Origin` も同じ組み合わせ。authority があればそれも見る）。バインドだけでは、ブラウザで開いた外のページから DNS rebinding で届く。**ルータを組み立てる2つ目の入口を作らない**（作るなら同じ検査を積む） |

最も現実的な事故は **LLM が生成した文字列がそのまま SQL やパスに流れること**。
「モデルが変なものを出すはずがない」という前提を置かない。

## マイグレーションを触るときの罠

**`sqlx::migrate!` は「SQL の内容変更」は追跡するが、「ファイルの追加」は追跡しない。**

マクロは各マイグレーションを `include_str!` として展開するため、既存ファイルの
**内容を書き換えた場合は再コンパイルされ、変更が反映される**。
しかし**新しいファイルを追加しても、`.rs` を一切触らなければ再コンパイルされない。**

```
0001 の内容を変更      → 再ビルドされ反映される
0002_xxx.sql を追加    → 再ビルドされず、0002 が存在しないまま
src/**.rs を touch     → ようやく 0002 が認識される
```

### なぜ危険か

新しいマイグレーションを足した直後、**`cargo test` は古いスキーマのまま緑になる。**
新列を使う実装を書いた瞬間に「テストは通るのに実行時に `no such column`」で詰まる。

### 回避 — `build.rs` で解決済み

リポジトリ直下の `build.rs` が `cargo:rerun-if-changed=migrations` を出しており、
**マイグレーションを追加すると lib が再コンパイルされる。** 手作業は不要。

A/B で実測済み: ダミーの `0003_probe.sql` を追加し `.rs` を一切触らずに `cargo test` すると、
`build.rs` **あり**では新テーブルが認識されてテストが失敗し、**なし**では緑のまま黙って無視された。

> **`build.rs` を消すとこの罠が復活する。** 中身は1行だが、消してよいファイルではない。

手作業で回避する場合は `cargo clean -p personacore` か、`src/` 配下の `.rs` を touch する。

> **変異検査でスキーマ制約の実効性を確かめるときも同じ罠を踏んでいた。**
> 「制約を消したのにテストが通った」を「テストが効いていない」と誤判定しないこと。

### ⚠ SQL を1バイトも編集しなくても、同じエラーになる（ADR-0044 / 2026-09-19）

**`sqlx::migrate!` のチェックサムは SQL の「バイト列そのもの」の SHA-384 で、改行の正規化が無い**
（`sqlx-core 0.9.0` の `migrate/migration.rs`: `Sha384::digest(sql)`）。
**つまり改行コードが変わっただけで別の SQL として扱われる。**

このリポジトリは属性ファイル（`.gitattributes`）を持たず `core.autocrlf` が有効だったので、
**同じコミットでも checkout の仕方で `migrations/*.sql` の改行が変わっていた** ——
`worktree add` / `clone`（Windows）は全部 CRLF、Mac / Linux の clone は全部 LF、
ツールが書き直したファイルだけ LF という混在も起きる。

**実測（2026-09-19）**: 別の checkout の exe が作った DB を、もう一方の checkout の exe で開いたら

```
migration 5 was previously applied but has been modified
```

**SQL は1バイトも編集していない。改行だけが違う。**

#### いまはこう塞がっている

| 層 | 何をするか | 見張り番 |
|---|---|---|
| 属性ファイルの `migrations/*.sql text eol=lf` | **これから組む exe** の埋め込みを LF に揃える | `no_migration_file_carries_a_carriage_return` |
| `Store::migrate` の冒頭（`src/store/migration_ledger.rs`） | **既に在る DB** の `_sqlx_migrations.checksum` を、**CRLF 版に一致する行だけ** LF 版へ付け替える | `a_ledger_written_by_a_crlf_checkout_opens` ほか |

**付け替えの条件は「CRLF 版に一致し、LF 版に一致しない」だけ。**
**本当に編集された SQL は今までどおり止まる**（対照は
`a_genuinely_edited_migration_still_stops_the_open`）。
**触るのは sqlx の帳簿の1列だけ**で、利用者のデータには1バイトも触らない。

> **⚠ 属性ファイルのその1行を消すと、次に Windows で checkout した機で
> `no_migration_file_carries_a_carriage_return` が赤になる。**
> **その機で組んだ exe は、LF の帳簿を持つ DB を開けない** ——
> **付け替えは逆向きには働かない**（どちらが正典かを帳簿から決められなくなるため。
> 理由は `src/store/migration_ledger.rs` のモジュール doc）。

> **⚠ 属性を足しても、その時点で作業ツリーに残っている CRLF は自動では直らない**
> （レビュー1周目の実測 —— `main` の作業ツリーは `0001`〜`0004` と `0013` が CRLF のままで、
> そのまま `cargo test` すると CR 走査ほか 4 本が赤になる）。
> **属性を入れた checkout では、1度だけ手で揃える**:
> ~~`git add --renormalize migrations/`（索引の内容は変わらない）→ `git checkout -- migrations/`。~~
> **⚠ それでは書き直されない**（司令塔がマージ直後に実測 / 2026-09-19 —— CR は 181 / 21 / 151 / 62 / 106 のまま）。
> **`git checkout --` は「索引と同じ内容」と見なしたファイルを書かない**ので、CRLF のまま残る。
> **`rm migrations/*.sql` → `git checkout -- migrations/`** で初めて 13 本とも CR=0 になった（索引から書き直させる）。
> **`git diff --stat` が空のまま**（索引は元から LF）**で、`tr -cd '\r' < f | wc -c` が 0 であること**を確かめること。

**適用済みの SQL を編集しないという規約は、いままでどおり要る。**
この段が足したのは「**編集しなくても同じ止まり方をする経路が在った**」という事実だけである。


## PowerShell でファイルを書き換えるときの罠

**`Set-Content -NoNewline` に配列を渡さないこと。全行が改行なしで連結される。**

```powershell
# 壊す（580行のファイルが1行になる）
(Get-Content $p) -replace 'a','b' | Set-Content $p -NoNewline

# 安全
[System.IO.File]::WriteAllLines($p, $lines, (New-Object System.Text.UTF8Encoding $false))
```

2026-08-15 に `docs/06-roadmap.md` をこれで壊した（内容は残るが構造が消える）。
**復元は `git checkout` ではなく `git show HEAD:<path>` の読み出し**で行うこと
（`checkout` は同じディレクトリの他の未コミット作業も巻き込む）。

同系統の罠:

- **変数名は大文字小文字を区別しない。** `$a = ...` が型付き引数 `$A` を潰す
- **`-match` は既定で大文字小文字を区別しない。** `'FAILED'` が `0 failed` に一致する
- **複数箇所を行番号で差し替えるときは後ろから。** 前を先に変えると添字がずれる

## 変異検査のログを、共有の場所に一般名で置かない（2026-08-28 / 作業単位 A-7b）

**`/tmp/m1.log` … `/tmp/m5.log` に変異検査のログを置いたら、
別のエージェントが同時刻に走らせていた変異検査の出力が混ざった。**

**症状**: 1つのログに lib のテスト結果が2回出る／
`test only_the_calibration_variable_is_ever_read test server::extract::tests::… ... ok`
のように**2つの実行の行が1行に融合する**／`test result:` の合計が実際の倍近くになる。
**`Get-CimInstance Win32_Process` で、別のスクラッチパッドで `cargo test --no-fail-fast` が
走っていることを確認した。**

### ⚠ 「別ツリー・別 target だから合否は汚れない」は、条件つきでしか正しくない

| 何で判定するか | 汚れるか |
|---|---|
| **終了コード** | **汚れない** |
| **ログを読んで赤の本数と名前を出す** | **汚れる。** 同名ファイルへ同時に書けば行が交錯する |

**変異検査は後者でしか成立しない**（「何本赤か」「どのテストが赤か」を読む）。
**だから「汚れないが念のため測り直した」ではなく、「読み方の側が汚れていたので測り直した」。**

### ⚠ そして「別ツリーだから安全」は言い過ぎ

**ツリーと `target` が別でも、エフェメラルポートと CPU は共有している。**
`13b` の `WSAENOBUFS`（OS code 10055）は**まさにこれ**で、
**変異と無関係な赤が出る。**「赤くなった」の**理由まで見ること。**

### 指針

- **ログもスクリプトも、自分のディレクトリの下に置く**（`scratchpad\<作業単位>\logs\`）。
  **`scratchpad` や `/tmp` の直下に `m1.log` のような一般名を置かない。**
  規約は道具（スクリプト）について書かれていたが、**ログでも同じ事故が起きる。**
- **測定の頭で、他に `cargo` が走っていないかを見る。**
  `Get-CimInstance Win32_Process -Filter "Name='cargo.exe'"` で `CommandLine` まで出る。

## テーブルを作り直すときの罠（`0003` で全部踏んだ）

SQLite 公式の「テーブル再構築 12 ステップ」は **`PRAGMA foreign_keys = OFF` を前提にしている。
本プロジェクトではその前提が成立しない。** 実測した3点。

| 事実 | 実測 |
|---|---|
| **`PRAGMA foreign_keys` はトランザクション内では無視される** | tx 内で `= OFF` にしても読み直すと **`1` のまま** |
| **`DROP TABLE`（親）は暗黙の `DELETE FROM` を起こす** | FK 有効だと子行が **CASCADE で消える** |
| **親テーブルが無いと、子テーブルへの DML がコンパイルできない** | `no such table: main.<親>`（`SELECT` は通る） |

sqlx はマイグレーションを既定でトランザクションに包む（`sqlx-sqlite/src/migrate.rs` の
`Migrate::apply`）ので、1番目がそのまま効く。`defer_foreign_keys` は tx 内でも効くが、
**これは検査の遅延であって `ON DELETE CASCADE` の抑止ではない。**

### 帰結 — 作り直す範囲は自分では選べない

3番目のため、**親を落としてから子を落とすことも、子を落としてから親を落とすこともできない。**
`session` / `message` だけを作り直すつもりが、`summary` / `generated_image` まで巻き込む
**4テーブルの再構築**になった（[ADR-0010](adr/0010-session-id-identity.md)）。

**依存関係で繋がったテーブル群は、まとめて作り直すことになる。** 見積もりのときに数えること。

### `-- no-transaction` に逃げないこと

sqlx は `-- no-transaction` を付ければトランザクション無しで流せるが、**採ってはいけない。**

`execute_migration` は「SQL 実行」→「`_sqlx_migrations` へ INSERT」の**2文**である。したがって

- 2文の間で落ちると **スキーマだけ移行済みで記録が無い DB** が残る
- そもそも SQL 自体が原子でないので、`DROP TABLE` の途中で落ちると
  **テーブルが消えたままの DB** が残る

どちらも `Store::connect` が恒久的に落ちる形で、**エラーメッセージから原因に到達できない。**
FK を有効なまま子→親の順で作り直す方が、丸ごとロールバックされるぶん安全。

> SQLite では **DDL もトランザクショナル**なので、`VACUUM` のような暗黙 COMMIT を
> 起こす文を混ぜない限り、再構築全体が原子的になる。

### 再構築したら「落ちていないこと」を挙動で確かめる

**テーブル再構築で最も静かに落ちるのは索引と時刻列。** どちらも正常系のテストは緑のまま通る。

- **索引は名前だけ照合しても意味がない。** 列順や `DESC` が変わっても名前は同じ。
  `pragma_index_xinfo` で**列名と `desc` まで**固定すること
- **復元 INSERT から `created_at` を落としてもエラーにならない。**
  `DEFAULT (strftime(...,'now'))` が効いて**静かに移行時刻へ書き換わる。**
  旧スキーマへ**明示的な値**を入れてから移行し、その値をアサートすること
  （DEFAULT 任せだと移行時刻と区別が付かず、アサートを足しても効かない）

実際に `0003` のレビューで、**この2つだけが変異検査を緑で通り抜けた。**

## 時刻を比較するテストのマージンは 1 秒以上にする

**SQLite の `strftime('now')` と Rust の `Utc::now()` は別の時計を読んでいる。**

| | Windows での実体 | 観測された最小ステップ |
|---|---|---|
| SQLite `'now'` | `GetSystemTimeAsFileTime`（粗い） | **1 ms** |
| chrono `Utc::now()` | `GetSystemTimePreciseAsFileTime` | 0.0001 ms |

実測（4000回）で **SQLite 側が最大 2.73ms 遅れる**。
しかも **2.7ms は上限ではない。** SQLite 側の粒度は Windows のシステムタイマ分解能に従い、
現在 1ms なのは**無関係な別プロセスが分解能を上げているから**である。
誰も上げていない既定状態では **15.6ms 刻み**になる。

> **つまりこのフレークの発生率は、無関係な他アプリの挙動に左右される。**
> 手元で通ったから安全、とは言えない。

### 指針

- **マージンは 1 秒以上。** 20ms 未満は環境依存で必ず再発する
- 「`before <= created_at <= after`」型の assert の目的は
  **「エポックでも2999年でもない」の健全性確認**なので、緩めても検出力はほぼ落ちない
- 上限側にも同じ定数を足す（対称にすると意図が読み手に伝わる）
- 定数はファイルごとに散らさず `tests/common/` に1つ置いて共有する
  （統合テストはバイナリが分かれるので `mod common;` が要る）

## 仮想時計（`tokio::time::pause`）と sqlx は同居できない

**時間に依存するテストを実時間で待たせないための `pause()` / `advance()` が、DB を触る回を殺す。**
`11c-3a` で実測した。

**自動前進は「runtime が待ちに入ったら、控えている一番近いタイマーまで飛ぶ」。**
DB 待ちはその「待ち」なので、**sqlx のプール取得の期限（既定 30 秒）まで一気に飛んで
`Query(PoolTimedOut)` になる。** sqlx-sqlite は `spawn_blocking` を使わないので、
tokio 側の自動前進抑止も効かない。

> **しかもこの期限（30 秒）は `IDLE_BUDGET` と同じ値だった。**
> 見張りたい予算と、踏みたくない期限が一致していると、
> **「飛ばす」と「飛ばしすぎる」の間が無くなる。**

### 症状の見分け方

**発生率は負荷で変わるので、単独で通しても安全とは言えない。** 実測:

| 同時プロセス数 | 失敗率 |
|---|---|
| 1 | 0.8〜3.3% |
| 8 | 22% |
| 16 | 30% |

**変異検査を汚す。** レビュアーが当てた変異の赤が、実際には `PoolTimedOut` だったことがある。
**「赤くなった」の理由まで見ないと、変異の効果と区別できない。**

### 指針

- **自動前進を開けたままにしない。** `yield_now` を回す空回りタスクで runtime を常に忙しくしておき、
  時計は**台本が `advance` したときだけ**動かす。
- **止め番を外す位置に注意する。** `11c-3a` では**中継が終わった直後の数行**
  （最後の `recent_messages` と `close`）だけが無防備で、そこが 3〜30% の発生源だった。
  **DB に触る `await` が1つでも自動前進の下に残っていたら再発する。**
- **自動前進を開ける経路をテストの API に残さない。** 引数で切り替えられる形にすると、
  次に書く人が同じ穴を開ける（`11c-3a` では `Clock` enum ごと削除した）。
- **時計を飛ばす仕掛けが動かなかったとき、テストが「緑のまま何も測らない」形にしないこと。**
  飛ばせたかどうかを前提として `assert` する。

## 実機で測るときの作法

**LM Studio を使った測定で、実際に踏んだ罠だけを書く。**
**どれも「測ったつもりで何も測っていなかった」形をしている。**

### 1. **1回目の応答は捨てる**

`temperature = 0` でも、**プロンプトが変わった直後の1回目だけ他と違う出力を返す。**
2回目以降は安定する。**各条件で3回投げ、2回目を採り、3回目との一致で安定性を見る。**

### 2. **本文を測るときは、記憶が増えないようにする**

抽出が動いていると、**3回投げる間に1回目・2回目から抽出された記憶が `# 記憶` 節に積まれる。**
**プロンプトが違うのだから出力が違って当たり前**で、これを「決定性が崩れた」と読み違えた。

> ~~**`PERSONACORE_SUB_MODEL` に存在しないモデル名を与えれば、抽出は走るが1件も保存しない。**~~
> **⚠ この手口は、いまの LM Studio では成り立たない**（2026-08-28 / C-11 の作業者が発見、司令塔が再現）。
>
> **存在しない綴りを送っても、エラーにならない。200 が返り、載っているモデルが黙って答える。**
> 司令塔の実測（`this-model-does-not-exist-9999` を送った）:
>
> ```
> {"model": "ministral-3-14b-instruct-2512", "choices":[{"message":{"content":"Hello! 😊"}}], …}
> ```
>
> **⚠ 実害は2つ。**
> * **この節が勧める「記憶を増やさずに本文の決定性を測る」手口が使えない**（C-11 では記憶が5件保存された）。
> * **⚠ モデル名を1文字間違えると、測定は静かに既定のモデルを測り続ける。**
>   **`E-3` が校正の器具で塞いだのと同じ形が、上流の側にもある。**
>
> **→ 差し替えたことを確かめる手段を別に持つこと。**
> **C-11 は「そのモデルだけが `loaded` になること」と「warm 応答の `model` 欄」で陽性対照を立てた。**
>
> **代わりに記憶を止めたいなら、抽出そのものを切る設定を使うこと**（`PERSONACORE_*` の一覧は下記）。

### 3. **冷えた実行と温まった実行を比べない**

モデルの**初回ロード**が実働時間に乗る。
実測で **3B の1回目 470 秒 / 2回目 107 秒**——同じ作業で 4.4 倍違った。
**比べるなら、両方とも温まった状態で。**

### 4. **`PERSONACORE_SUB_MODEL` は実験の切り替えスイッチ**

「主語を間違えるのはプロンプトの設計か、モデルの能力か」を、
**コードを1行も変えずに**切り分けられた（[ADR-0021](adr/0021-memory-extraction-format.md) §10）。
**設定にしておくと、後から測れる。**

### 5. **判定は読んで行う**

`grep` で数えると測り方が測定を歪める。実例:
`grep` で JSON から値を切り出して `wc -m` したら、**日本語が `\uXXXX` で書かれていたので
エスケープ列の文字数を数えていた**（237 と出たが実際は 79 文字）。

### 6. **抽出の応答の取り出し方**

`sed -n 's/.*"content":"\(.*\)"},"finish_reason".*/\1/p'`。
**`"refusal"` フィールドは存在しない。** 一度これで全条件が空になり、
**空文字どうしが一致するので「全条件 STABLE=yes」に見えた。**
**採れた文字数を必ず出すこと。**

### 7. **上流は温まるまで 500 を返す**

14B の JIT ロード中に **500（HTML 本文）が数件**返る。
測定の**開始直後の数条件が失われる**ので、捨て回しを先に入れるか、失われた条件を数える。

### 8. **サーバを止めてからビルドする**

起動中の `personacore.exe` を掴んだまま `cargo build` するとリンクが失敗し、
**古いバイナリのまま測定を始めてしまう。** `Finished` を見ても足りない。

## 適用済みマイグレーションの SQL を編集しない

**`sqlx` はマイグレーションのチェックサムを記録している。** 一度適用された SQL を
**コメント1文字でも**書き換えると、その DB は次回接続時に
`migration N was previously applied but has been modified` で**起動不能**になる。

- **未コミット・未適用のうちは直接編集してよい**（`0001` は開発中に何度も書き換えた）
- **適用済みになったら、新しい `000N_*.sql` を足す**
- コメントの誤りを直したいだけでも、この制約は変わらない。
  **説明はコード側（`src/domain/text.rs` 等）に集約しておくと、後から直せる**

## 新しい版で開いた DB を古い exe で開いたとき（B-55 / origin#36）

新しい版が足したマイグレーションが適用済みの DB を、それを知らない古い exe で開くと、
**止まる。止まること自体が正しい**（知らない列を持つ DB を古い exe が書き換えない。
版の検証は適用の前なので、DB には何も書かずに止まる。ただし先に走る付け替えの段
（`migration_ledger.rs`）は、既知の版の CRLF 行しか書かず、新しい版の exe が開いた帳簿には
その行が残らない）。戻すには新しい版の exe を使うか、
写しておいた保存先に戻す。

- `Store::migrate` は sqlx の `VersionMissing` を `StoreError::DatabaseFromNewerVersion` にする。
  `Display` は定数の日本語（「この保存先は新しい版の personacore で開かれています。…」）で、
  版の番号は `source`（`Caused by`）に出る。見張り番は `tests/store_schema.rs` の
  `a_database_opened_by_a_newer_version_stops_with_a_typed_error` と、
  実行ファイルの終了経路を見る `tests/newer_database_cli.rs`。
- **⚠ この言い換えが効くのは、この版より後の exe だけ。** 配布済みの v0.1.4 以前の exe は
  英語の sqlx の文（`migration N was previously applied but is missing in the resolved migrations`）
  のまま止まる。振る舞いは変わらない。

## エラー処理

- エラーは `thiserror` で型付けする。
- **ライブラリ層で `anyhow` を使わない。** `main` 付近のみ許容。
- **本番コードパスに `unwrap()` / `expect()` / `panic!` を置かない。** テストコードでは可。
- `parse` は特に、**いかなる入力でも panic しない**こと。フォールバックへ落ちる。

## ログ

- `tracing` を使う。**`println!` を残さない。**
- **パース成功率を必ず記録する。** プロンプト調整の効果測定に必要。
- エラーログには詳細を出してよい（レスポンスに出さないだけ）。

## ドキュメント

- **適切な長さで分割する。** 長大になる場合は階層構造を持たせる。
- 「決定」は `adr/` に、「現状の説明」は各ドキュメントに書く。**両方に同じことを書かない。**
- **未決事項は未決と明記する。** 決まったふりをして書かない。
- 日本語で統一する。

## 想定される落とし穴

原典から引き継いだもの。実装時に必ず思い出すこと。

1. **ストリーミングの中継** — SSE を受けて SSE を返す二段構成。
   バッファリングで詰まると体感が死ぬ。
2. **サブLLM呼び出しのタイミング** — 本文レスポンスを返した**後**に非同期で走らせる。
   同期実行するとレイテンシが倍増する。
3. **性格値ゼロの扱い** — 「パッション: 0/5」と書くとモデルが「情熱がない」を
   過剰演技して無感情になる。**値が 0 の軸はプロンプトに含めない。**
4. **履歴の二重管理** — クライアントは毎回全履歴を送ってくる。自前DBを正とし、
   クライアント送信分は最新メッセージのみ採用する。セッション同定は `model` フィールド
   （[ADR-0004](adr/0004-session-identification.md)）。
   **`model` は信頼できない入力なので、キャラ名の許可リストと照合してから使う。**

### 属性を実験の切り替えスイッチとして使う（2026-08-22 / 作業単位 13d）

**`character_attribute` は管理 API から入れるので、コードを1行も変えずに実験できる。**
`PERSONACORE_SUB_MODEL` を差し替えて 3B と 14B を比べたのと同じ形
（[personacore の作法](adr/0021-memory-extraction-format.md) §10）。

**13d はこの形で、身元を固定すると捏造が消えることを測った。**

    curl -X PUT "$B/admin/characters/$h/attributes" \
      -H 'Content-Type: application/json; charset=utf-8' \
      -d '{"attributes":[{"subject":"character","key":"勤続","value":"この店で十年"}]}'

**上限は 8件・キー12文字・値20文字。** 変数を増やさないため、
**狙う欠陥に対応する属性だけを入れること**（13d は4件だけにした）。

> **⚠ 属性を足すと抽出プロンプトも太る。** 13d では `skipped=busy` が2回出て、
> **抽出が15回ではなく13回**になった。**件数を比べるときに効く。率で見ること。**

### 選別を測るなら、先に圧力をかける（2026-08-22 / 作業単位 15b）

**3層の想起を入れて、既定の予算のまま32ターン回した。**
**`omitted` は全ターン 0 だった** —— 146件すべてがプロンプトに載っていた。

> **層に分けたことは、載る中身を1件も変えていない。**
> **つまり全件注入でも同じ結果になる。**
> **機構が壊れないことしか測れていなかった。**

**そこで `PERSONACORE_CONTEXT_TOKENS=6144` で予算だけを絞った**（**コードは1行も変えない**）。
最終ターンで **148件中40件だけ**が載る状態になり、**そこで初めて選別が実際に選ぶ。**

**この形で測って初めて「層3が29ターン前の記憶を引き戻した」と言えた。**

> **一般化すると** —— **「選ぶ仕掛け」は、選ばざるを得ない状態で測ること。**
> **余裕がある状態で測ると、選ばなかった仕掛けと区別が付かない。**
> テストで繰り返し出た「**その分岐が効く状態にフィクスチャが入っているか**」と同じ問いを、
> **実機の測定にも当てること。**

> **⚠ 「N件で破綻する」の N を取り違えないこと。**
> `memory_tokens > 取り分/2` の**警告の閾値**（約90件）と、
> **枠が本当に尽きる点**（約180件）は別物である。**前者では何も落ちない。**

### 「出るか」と「意味があるか」は別の問い

**`16e` の腕E で踏んだ。** 測る問いを「**`0` は実際に出るか**」と立て、**出た**（20.1%）。
**だが役に立たなかった** —— **`0` の置き場所が会話と無関係**で、
**「なし」が正解のターンの `0` 率が全体と一致した。**

> **「出た／出ない」で答えられる問いは、たいてい問いが足りていない。**
> **「正しい場所に出たか」まで含めて立てること。**

**分布を見ると独立に判別できることがある。** 腕E の `0` は**1ターンあたりちょうど 1.00 個**で、
**0個:16 / 1個:40 / 2個:16 / 3個以上:0**。
**内容に応じて独立に出るなら二項分布**（`n=5, p=0.2`）**で 3個以上が約4回あるはず**だが、**1回も無い。**
**判断ではなく割り当てだった。**

> **数え上げの合計だけでなく、1回あたりの分布を見ること。**
> **合計は同じでも、「毎回1個」と「たまに3個」はまったく違う機構である。**
