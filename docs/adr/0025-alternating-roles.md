# ADR-0025: プロンプトの役割の並びは、組み立ての出口で保証する

- 状態: **採用**
- 日付: 2026-08-23
- 関連: [ADR-0013](0013-context-budget-layers.md)（履歴は最初に削る枠）、
  [ADR-0001](0001-openai-compatible-boundary.md)（上流は OpenAI 互換）

## 背景 —— **本番で 502 が出た**

作業単位 16b の実機測定中に、**そのキャラクターとの会話が突然 502 になり、
セッションを切り直すまで回復しなくなった。** 変容とは無関係だった。

上流（LM Studio / Ministral）が返したのはこれである:

> `Jinja Exception: After the optional system message, conversation roles must alternate user and assistant roles`

**原因は `prompt::build_prompt` が組む `messages` の並びで、確定している。**

`history` は `[user, assistant, user, assistant, …]` の平坦な列で、
予算配分（`budget::plan` → `take_newest`）は**件数で前から落とす。**
`history_start` が**奇数**になると、**`system` の直後が `assistant` になる。**

### 実測（レビュアーが決定的に再現。2026-08-23）

**1. 網羅的な掃引:** 完全に交互な履歴20件・記憶0件で `context_tokens` を 1100〜2399 まで1ずつ振ると、

```
odd_seen=467  broken=467
first= context=1509 history_start=19 included=1 roles=[System, Assistant, User]
```

**`history_start` が奇数になった 467 通りすべてで壊れた。例外はゼロ。**

**2. 失敗時点の再現:** 測定に使った DB をそのまま使い、履歴 40 件・予算 16384/1024 で
記憶の件数だけを振ると:

| 記憶 | `history_start` | `messages[1]` |
|---|---|---|
| 80 | 10 | `User` |
| 82 | 10 | `User` |
| **84** | **11** | **`Assistant`** ← 失敗時点 |
| 86 | 12 | `User` |

そして **502 の直前3回はすべて `recalled_recent=84`** だった。

**3. 自力では抜け出せない。** 記憶が1件増えれば偶数側へ動くが、
**失敗した往復では抽出が走らないので記憶は増えない。**
「一度壊れたら、そのセッションでは壊れたまま」が実測どおり起きた。

**4. 観測していたテストは1本も無い。** 役割の並びを見る唯一のテスト
（`messages_are_system_then_history_then_the_user_message`）は **`history_start = 0`** で回っており、
**この状態に一度も入らない。** 履歴のトリミングを見るテストは**件数しか見ていない。**

### 第2の経路 —— **見張り番が、壊れた並びを自分で作って許容していた**

`build_prompt` は**空白だけの履歴を1件だけ落とす**（`filter_map(history_turn)`）。
交互列から1件抜ければ `user, user` が隣接し、**同じ上流エラーになる。**

**そして既存テスト `blank_history_entries_are_skipped` が、まさにその形を緑にしていた** ——
`[Assistant(空白), User(本文)]` → `messages = [System, User, User]`。

> **CLAUDE.md の「フィクスチャがその分岐が効く状態に一度も入らない」の、さらに一歩先。**
> **入っていたのに、壊れた出力を期待値として書いてあった。**

## 決定

**`build_prompt` は、役割の並びを出口で保証する。**

### 1. 不変条件

**`messages` は次を必ず満たす:**

1. 先頭は `system` 1件
2. **その次は必ず `user`**
3. 以後 `user` / `assistant` が厳密に交互
4. **末尾は `user`**（今回の発言）

### 2. 履歴を削る単位を**往復**にする

`history_start` を**偶数へ切り上げる**（＝1件多く、古い側から落とす）。

**切り下げない。** 切り下げると1件多く載り、**予算を超える。**
削る枠を増やす方向は常に安全である（[ADR-0013](0013-context-budget-layers.md) の「履歴は最初に削る枠」）。
> **2026-10-21 追記（origin#56 B-59）**: 「履歴は最初に削る枠」はもう成り立たない。削れない枠を引いた残りを**記憶と履歴で半々に分け**、片方が余らせた分はもう片方が使う（`src/prompt/budget.rs` の `Frames`）。記憶が先に全部取ると履歴が0件になり、会話を見ずに記憶の定型を組み直す応答になったため。**往復に揃えるときに古い側から1件多く落とす（切り下げない）規則は変わらない** —— 履歴の取り分の中でも同じく安全側に倒す。なお、この ADR は「履歴は最初に削る枠」を ADR-0013 のものとして引いているが、ADR-0013 の本文にその記述は無い。

### 3. 空白だけの履歴は、**往復ごと**落とす

**片方だけ落とさない。** 落とすなら相方も一緒に落とす。

**`blank_history_entries_are_skipped` の期待値を変える**（司令塔の採否済み）。
**あの期待値は「壊れた並びを上流へ送る」ことを固定していた。**

### 4. 見張り番は**掃引**で置く

**1点のテストでは足りない**ことが実測で分かっている
（`history_start = 0` の1本しか無かった）。

**予算を範囲で振り、得られた `messages` が §1 の不変条件を満たすことを全通り確かめる。**
レビュアーの探りがそのまま見張り番になる形にする。

> **⚠ 掃引の対照を忘れないこと。** 「不変条件を破る入力を1つも見つけられなかった」と
> **「そもそも壊れる状態に入っていない」は別物**である（CLAUDE.md「対照が自己成就する」）。
> **奇数の `history_start` に実際に入った回数**を数え、**0 なら掃引の失敗として赤にする。**

## 理由

### 却下した選択肢

- **上流へ送る直前（`llm` 層）で検査する** —— **その位置では直せない。**
  検査して弾いても 502 が 500 になるだけで、会話は止まったままである。
  **組み立ての側が正しい列を作るのが本筋。**

- **`HISTORY_LIMIT` を偶数に保つだけ** —— **効かない。** 今回の `HISTORY_LIMIT` は
  **既に偶数（50）**で、失敗時点の履歴は 40 件、**読み取り側の切り詰めは一度も起きていない。**
  壊したのは**予算配分の側**である。

- **履歴を「往復の型」に作り直す**（`Vec<Turn { user, assistant }>` にして、
  予算の費用も往復単位で持つ） —— **構造的にはこちらが正しい。**
  役割の並びが**型で表現できなくなる**ので、掃引の見張り番すら要らなくなる。
  **いま採らないのは、`budget::plan` の費用配分（記憶と履歴の按分）を丸ごと書き換えるため**で、
  **本番が 502 で止まっている状況で持ち込む変更としては大きすぎる。**
  > **引き金:** 履歴の扱いに**3つ目の規則**が要ったとき（今は「古い順に落とす」と
  > 「往復で落とす」の2つ）。あるいは要約（`summary` テーブル）を履歴へ挿し込むとき。
  > **そのときは §4 の掃引が回帰試験として効く。**

- **空白の履歴をそのまま載せる**（落とさない） —— 並びは保たれるが、
  **空の `content` を上流へ送ることになる。** 空の本文が別のテンプレートを壊す形は
  **実測で別に出ている**（`m12/server_aborted_empty_bodies.log`）ので、**踏み込まない。**

## 結果

### できるようになること

- **履歴がどれだけ削られても、上流が受け取る列は常に正しい。**
- **壊れる状態に入ったことを、掃引が数として示す。**

### 諦めたもの

- **役割の並びは、いまも「型」ではなく「見張り番」が守っている。**
  `ValidTag`（[ADR-0006](0006-slot-based-tag-compilation.md)）と同じ強さだと読まないこと。
  **型で表現できなくする道は上に書いた（却下ではなく延期）。**

### この一件から残すもの

**502 は「上流が悪い」ように見えた。** 実際は**こちらが不正な列を送っていた。**
**上流のエラー文面が原因を名指ししていた**（`roles must alternate`）ので追えたが、
**名指ししないエラーだったら、モデルの気まぐれとして片付けていた可能性が高い。**
