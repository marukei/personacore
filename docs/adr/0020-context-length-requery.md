> **2026-10-22 追記:** §背景の「エラーにならない。切り捨てられるのはプロンプトの先頭」は **LM Studio の壊れ方**である。**llama は、小さい窓に読み込み直されたときに窓を超えたプロンプトを 400 で断る**（エラーとして見える）。窓に入るが「プロンプト ＋ 応答の上限」が窓を超える回は、応答が黙って短くなる。引き直しが要ることは変わらない（窓を取り違えたまま組めば、断られるか短くなる）。[ADR-0052](0052-count-with-the-upstream-tokenizer.md) §測った結果 M5。

## 背景

**稼働中に上流が小さいコンテキストでモデルを再ロードしても、こちらは気づけない。**

[ADR-0013](0013-context-budget-layers.md) の訂正が結論を出している:

| 変化 | 検出できるか |
|---|---|
| チャットテンプレートが重いモデルへ変更 | できる（上界が破れる） |
| トークナイザの性質が変わった | できる（同上） |
| **稼働中に小さいコンテキストで再ロード** | **できない** |

**`usage.prompt_tokens` からは原理的に取れない。** 上流が切り捨てた結果の値は、
こちらの過大な見積もりと区別が付かない。

**このとき何が起きるか。** こちらは 16,384 のつもりでプロンプトを組み、上流は 4,096 で切り捨てる。
**エラーにならない。** 切り捨てられるのは**プロンプトの先頭**——つまり
**ペルソナと性格ステータスと記憶**である。**キャラクターが静かに別人になる。**

## 決定

### 1. **定期的に引き直す。事象を待たない**

**事象で引くことはできない。** ADR-0013 の訂正が示したとおり、
**この失敗は構造上どの観測点にも現れない。**
「疑わしい事象を見たら引き直す」は、**その事象が起きない失敗には効かない。**

> **却下ではなく、順序の問題。** 上界破れ・`finish_reason` の異常・上流エラーの連続は
> **別の失敗を捕まえる**ので、後から足す価値はある。
> **ただし、それを足しても本件は塞がらない。** 先に定期の引き直しを置く。

### 2. **間隔は 5 分の定数。設定にはしない**

- 引くのは `/api/v0/models` の**メタデータ1回**で、推論を起こさない。
  ローカルの往復なので費用は無視できる。
- **5 分**は「ずれたまま気づかない窓」の上限である。
  再ロードは利用者が LM Studio を触った瞬間に起こるので、**分の単位で足りる。**
- **設定可能にしない。** 起動時に決めるものを増やすと、
  **本番の入口を通るテストを足さない限り配線が観測対象から外れる**（CLAUDE.md の実例）。
  [ADR-0019](0019-relay-idle-watchdog.md) と同じ判断。

### 3. **本文の応答に待ちを足さない**

**引き直しを応答の経路に置かない。** 毎リクエスト引くのは ADR-0013 が既に却下している
（往復が倍になる）が、**「間隔を空けて、たまに引く」形でも、引く回のリクエストだけが遅くなる。**
**その1回が遅い理由は、ログを見ないと誰にも分からない。**

**機構の形は実装側の判断でよい**（背景タスク / 応答を返し切った後に引く / その他）。
**条件は3つ:**

- **応答の経路に待ちを足さない。**
- **間隔ごとに高々1回**（往復を倍にしない）。
- **サーバが止まるときに残らない。**

### 4. **明示設定があるときは引き直さない**

`PERSONACORE_CONTEXT_TOKENS` は**照会値より優先される**（ADR-0013 の層）。
**優先されている以上、引き直しても予算は変わらない。** 引く意味が無いので引かない。

> **これは最適化ではなく、意味の問題。** 引いて `warn` を出すと、
> **「変わった」と言いながら予算は変えない**という読み手を惑わす記録になる。

> **⚠ 2026-11-03 に追記した**（下の「追記 —— 明示設定の面も、観測のためだけに照会する」）。
> **予算は今も引き直さないが、上流が生きているか・鍵が通るかは照会する。**

### 5. **値が変わったら `warn`。失敗したら現在値を保つ**

- **変わったら `warn`。** 黙って予算だけ変えると、
  「昨日と同じ発言が今日は `BudgetExhausted` になる」理由が追えない。
- **引き直しに失敗したら、いまの値を保つ。**
  **既定値へ落とさない。** 落とすと、上流が一瞬詰まっただけで予算が黙って縮む。
  起動時の `resolve_budget` が既定へ落ちるのは「他に手がかりが無い」からで、
  **すでに手がかりを持っている状況とは違う。**
- **新しい値は次のプロンプト組立から効く。** 組立中のものには遡らない。

## 却下した選択肢

- **毎リクエスト照会する** — ADR-0013 が却下済み（往復が倍）。
- **疑わしい事象だけで引く** — 上記1。**本件が起きても事象が発生しない。**
- **`usage` から推定する** — ADR-0013 の訂正が原理的に不可能と結論している。
- **間隔を設定可能にする** — 上記2。
- **引き直しに失敗したら既定へ落とす** — 上記5。**上流の一瞬の不調で予算が縮む。**

## 結果

### 得られるもの

- **静かに別人になる経路が、5 分以内に `warn` として現れる。**
- **費用はメタデータの往復1回 / 5 分。** 推論を起こさない。

### 諦めたもの / 前提

- **最大 5 分は気づけない。** その間のプロンプトは切り捨てられうる。
  **切り捨てられた回を後から特定する手段は無い**（上流が黙って切るため）。
- **`warn` を読む人が要る。** 自動で何かを直すわけではない。
- ~~**明示設定を置いている運用では、この仕掛けは一切動かない**（上記4）。~~
  ~~**それは意図した振る舞い**だが、「動いていない」と「壊れている」の区別は~~

## 追記 —— **サブモデルの窓も、同じ仕掛けで引く**（2026-08-27 / 作業単位 B-7）

**抽出と変容の依頼は、本文とは別のモデル（`PERSONACORE_SUB_MODEL`）へ出る。**
**その窓も同じ `/api/v0/models` から引き、同じ間隔で引き直す。**
**背景タスクは1本のまま**で、間隔ごとに本文用 → サブ用の順に引く
（**2026-11-03 から同時に引く** —— 末尾の追記）。

### ⚠ 上記の §4（明示設定があるときは引き直さない）は、**サブ側には適用しない**

**理由**: §4 の根拠は「**明示設定が優先されるので、引いても値は変わらない**」である。
**抽出の上限には、そもそも明示設定が存在しない。**
適用すると、**`PERSONACORE_CONTEXT_TOKENS` を置いただけで、
設定していない値（抽出の上限）まで落とし所に固定される。**

**その結果、上の「諦めたもの」の1行が事実でなくなった** ——
**明示設定を置いていても、背景タスクは立つ**（サブ側のために）。
**本文側を引き直さないことは、`requeries_main_budget=false` の欄が押さえている。**

> **⚠ 副次的に、明示設定が持っていた「起動時の照会がゼロ」という性質も消えた。**
> **上流が黙っている環境では、起動時に最大 5 秒（`DEFAULT_CONTEXT_TIMEOUT`）待つ。**
> **本文用とサブ用は `tokio::join!` で同時に投げているので、待ちは倍にならない。**

### 起動時の1行に、**それぞれの照会先が引くモデルの綴り**を載せている

**引き直しの照会先を取り違えても、5分待たないと観測できない**からである。
**実測: サブ側の照会先を本文用のクライアントに向ける変異は、`clippy` を含めて 1554 全緑を通った**
（`_` で受けて捨てる1手が要るが、それだけ）。

**起動時に決まっている事実を、5分待って確かめる必要はない。**
見張り番は `the_two_requery_targets_name_their_own_models_on_the_real_bind` で、
**`sub_model=` を含む行を拾い、その同じ行の中で**両方向の否定まで見る。

## 追記 —— **明示設定の面も、観測のためだけに照会する**（2026-11-03 / 作業単位 B-66 / Issue origin#94）

**コンテキスト長を書いた面（`PERSONACORE_CONTEXT_TOKENS` か、上流プロファイルの面の `context_tokens`）にも、
上流が生きているか・鍵が通るかを照会する。** 利用者と決めた。

### なぜ

§4 のとおり、書いた面へは一度も照会しなかったので、**上流が後から起きても止まっても、`GET /admin/upstream` の
観測は起動時の「答えなし」のまま変わらなかった**（v0.3.0 と偽の上流で実測 / Issue origin#94 のコメント1）。
**利用者の普段の構成（コンテキスト長を書いた繋ぐ面）では、画面から上流が生きているか・鍵が通るかが分からない。**
鍵を断る上流でも `unauthorized` が立たず、初めての知らせが会話の失敗になっていた。

### §4 とは衝突しない

§4 の根拠は「**引いても予算は変わらないのに『変わった』と warn する記録が読み手を惑わす**」である。
**この照会は予算に触れず、「変わりました」の `warn` も出さない。** 書くのは観測の欄（名乗った名前・答え方・
申告された窓・断られたか・いつどう確かめたか）だけである。**§4 の「予算を引き直さない」はそのまま。**

### 決めたこと

| 時機 | 書いた面 | 書いていない面 |
|---|---|---|
| 起動時 | **背景タスクの最初の1回**（`App::bind` の中で待たない —— 上流が黙っていても起動は遅くならない） | 今までどおり `App::bind` の中（予算を決めるため） |
| 5分ごと | **観測だけ**（同じ背景タスク・同じ間隔 `REQUERY_INTERVAL`） | 今までどおり予算まで引き直す |
| 上流モデルの画面の「いま確かめる」（`POST /admin/upstream/check`） | **観測だけ** | 5分ごとと同じ（予算まで引き直す） |

- **新しい定数・設定のつまみは足していない**（間隔は §2 の5分のまま / ADR-0036）。
- **照会の回は1度に1つ。** 両方の面の回が走っているときに「いま確かめる」が来たら、**2本目を並べずにその回を待って返る**
  （409 にしない —— 5分ごとの回と重なっただけで失敗を見せないため。`context::CheckGate` の doc）。
  **乗ってよいのは、待っている間にその回が最後まで走ったときだけ**（レビュー是正）—— 持ち主の要求が切断されて回が
  落ちたら、待っていた側は自分で照会する。起動の直後の片面の回にも乗らない。
- **観測に「いつ・どう確かめたか」を足した**（`checked_at` / `check_result`）。画面は「まだ確かめていない」
  「繋がらない」「一覧に答えない」「断られた」「鍵を送っていない」「答えた」を言い分け、**繋ぐ面で照会したが繋がらない
  （応答が1つも来ない）ときだけ異常の帯**にする（起こす面の振る舞いは変えない）。時刻は読み手の時間帯の `HH:MM:SS` で出す
  （経過は出さない —— 画面は普段は読み直さないので、経過は読んだときのまま止まる）。
- **届いたが一覧が読めない（`no_model_list`）は帯にしない**（レビュー是正）。**モデル一覧は上流に「任意」の能力**
  （[ADR-0038](0038-what-personacore-requires-of-an-upstream.md) §決定1）なので、一覧の口を持たない上流にコンテキスト長を
  書いて繋ぐと、会話は通るのに照会は毎回失敗する。帯にすると出続ける（D-12b-2 の2周目が避けた形）。
- **書いた面への照会では、「どちらの綴りでも読めませんでした」を警告にしない**（`debug` / レビュー是正 /
  `LmStudioClient::models_for_observation`）。その面にはこれまで照会しなかったので、この `warn` は出ていなかった ——
  観測のためだけの照会で、5分ごとに新しい警告を鳴らさない。書いていない面は今までどおり `warn`。
- **自分で起こす面は、起動時の照会をしない**のは今までどおり（載るのを待つ番人が聞く）。5分ごと・「いま確かめる」では聞く。

**`resolve_budget` / `resolve_sub_context` の明示の枝（起動時に照会しない）は変えていない** —— 起動時の照会を
背景へ移しただけで、`App::bind` が返る時点では書いた面へ1度も聞いていない。見張り番は
`tests/server_upstream_check.rs`（`bind` が返った時点の照会が 0 回・走り出した後に聞かれる・予算が動かない・
「いま確かめる」で両方の面が変わる・2本目を並べない）と、`server::context` の単体テスト
`checking_an_explicit_face_never_says_the_length_changed`（書いた値と違う窓を申告させても「変わりました」が出ない）。

### 変わったこと（上の節との関係）

- §4 の「明示設定があるときは引き直さない」は**予算の話として**残る。「明示なら照会そのものをしない」は撤回した。
- 「追記 —— サブモデルの窓も…」の「間隔ごとに本文用 → サブ用の順に引く」は、**同時に引く**へ変わった
  （「いま確かめる」と同じ口を通すので、黙った上流での待ちを2倍にしない）。間隔あたりの往復はモデルごとに1回のまま。
